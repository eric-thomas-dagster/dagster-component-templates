# RPAHealthCheckComponent

Emits a Dagster `@asset_check` for an asset produced by an RPA / scheduler
integration. Verifies three things without making any external calls — it
just reads the metadata already emitted by the upstream integration:

1. **Freshness** — the asset materialized within the last `max_age_hours`
2. **Status** — the `status` metadata field is one of the accepted
   terminal-success values (UiPath `Successful`, Automation Anywhere
   `COMPLETED`, Blue Prism `Completed`, Power Automate `Succeeded`,
   Control-M / RunMyJobs `Ended OK`, …)
3. **Output (optional)** — the `output_payload.output_arguments` (or
   `.trigger_input` / `.stdout` / `.output`) field is non-empty when
   `require_non_empty_output: true`

## Why

RPA bots fail *silently* more often than people admit: schedules drift, a
release_key gets orphaned, the bot ends "Successful" but returns an empty
payload, or the scheduler queue backs up so the last run is 3 days old. A
downstream asset that just consumes the RPA asset has no idea any of this
happened.

This check turns three implicit assumptions ("it ran recently, it ended in
a terminal-success state, and it produced output") into an explicit gate
that shows up red in the Dagster UI and — with `severity: ERROR` —
blocks downstream materialization.

## Fields

### Required

| Field | Type | Description |
|---|---|---|
| `target_asset` | `str` | Slash-separated asset key to check (e.g. 'uipath_invoice_extract' or 'rpa/uipath/invoices'). |

### Other

| Field | Type | Default | Description |
|---|---|---|---|
| `check_name` | `str` | `"rpa_health"` | Asset check name shown in the UI. |
| `max_age_hours` | `float` | `24.0` | Fail if the latest materialization is older than this many hours. |
| `expected_statuses` | `List[str]` | `["success", "Successful", "COMPLETED", "Completed", "Succeeded", "Ended OK"]` | Terminal-success values across RPA + scheduler vendors. Check passes if the asset's status metadata is in this list. |
| `require_non_empty_output` | `bool` | `False` | Also fail if output_payload.output_arguments (or output_payload.trigger_input) is empty. |
| `severity` | `str` | `"WARN"` | 'WARN' (flag only) or 'ERROR' (blocks downstream materialization). |

## Declaring multiple checks in one YAML

Each RPA asset gets its own `RPAHealthCheckComponent` block. Split with
`---` (standard YAML multi-doc) so a single `defs.yaml` can gate an entire
RPA fleet:

```yaml
# UiPath — invoice extraction bot must have run within the last 6h and
# returned non-empty output arguments.
type: dagster_community_components.RPAHealthCheckComponent
attributes:
  target_asset: uipath_invoice_extract
  check_name: uipath_invoice_health
  max_age_hours: 6.0
  require_non_empty_output: true
  severity: ERROR

---

# Automation Anywhere — nightly reconciliation bot.
type: dagster_community_components.RPAHealthCheckComponent
attributes:
  target_asset: aa_nightly_recon
  check_name: aa_recon_health
  max_age_hours: 26.0
  severity: WARN

---

# Blue Prism — CRM sync process.
type: dagster_community_components.RPAHealthCheckComponent
attributes:
  target_asset: blueprism_crm_sync
  check_name: blueprism_crm_sync_health
  max_age_hours: 24.0
  severity: WARN

---

# Power Automate — SharePoint file mover.
type: dagster_community_components.RPAHealthCheckComponent
attributes:
  target_asset: power_automate_sharepoint_move
  check_name: sharepoint_move_health
  max_age_hours: 12.0

---

# Control-M — end-of-day batch anchor asset ("Ended OK" is terminal
# success on both Control-M and RunMyJobs).
type: dagster_community_components.RPAHealthCheckComponent
attributes:
  target_asset: controlm/eod/final_close
  check_name: eod_close_health
  max_age_hours: 25.0
  severity: ERROR
```

## Terminal-success vocabulary

The default `expected_statuses` list is calibrated against every RPA and
scheduler vendor DCC currently integrates with, so the same check works
across the whole fleet without a per-vendor override:

| Vendor                            | Terminal-success `status`          |
|-----------------------------------|------------------------------------|
| UiPath Orchestrator               | `Successful`                       |
| Automation Anywhere               | `COMPLETED`                        |
| Blue Prism                        | `Completed`                        |
| Microsoft Power Automate          | `Succeeded`                        |
| Control-M                         | `Ended OK`                         |
| Redwood RunMyJobs                 | `Ended OK` (via Control-M mapping) |
| Stonebranch UAC                   | `SUCCESS`                          |
| IWS (IBM Workload Scheduler)      | `SUCC`                             |
| ActiveBatch                       | `Succeeded`                        |

Override `expected_statuses` in YAML if your integration emits a
non-standard status label — the default is a superset, not a hard-coded
whitelist.

## How it works

The check body reads the latest materialization event via
`context.instance.get_latest_materialization_event(asset_key)` and
inspects the `metadata` dict already written by the upstream integration's
`context.add_output_metadata({...})` call — specifically the `status`
scalar and the `output_payload` JSON blob (see
`uipath_orchestrator_integration/component.py` for the shape).

No REST calls, no vendor SDK, no polling. The check is free to run and
can be scheduled or evaluated on demand from the Dagster UI.
