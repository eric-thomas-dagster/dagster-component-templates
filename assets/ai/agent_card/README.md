# Agent Card

Declares one hosted agent — reached over MCP or plain HTTP, never an in-process Python class — and advertises what it's good for, so `AgenticPipelineComponent`'s `delegate` op can discover it and dynamically route work to it instead of requiring a hardcoded, inline-YAML agent list.

## What this does

Field names track the real [A2A protocol's `AgentCard` schema](https://docs.cloud.google.com/gemini/data-agents/reference/rest/Shared.Types/AgentCard) where there's a direct analog (`name`, `description`, `skills`, `version`, `default_input_modes`/`default_output_modes`), so wiring this to a literal `.well-known/agent.json` later is a rename, not a redesign. `invocation` is this component's own extension — real A2A agents all speak one wire protocol and don't need a transport choice; this bridges two (MCP and plain HTTP).

This component is **declare-only** — a bare `AssetSpec`, no compute function, no sensor (same convention as `external_bigquery_table` and the other `external_*` components). It exists so:

1. The agent shows up as a node in the Dagster asset graph (lineage, Asset Catalog), tagged `kind=agent`.
2. A `delegate` step in the same project discovers it automatically — same sibling-scan mechanism `EnhancedDataQualityChecks` uses to auto-inherit a checked asset's `partitions_def` — by reading `metadata["agent_card"]` off this spec. No wiring required beyond having both components in the same defs folder.
3. Many of these specs' `agent_card` metadata can be aggregated into a flat JSON manifest (same shape, array of cards) for cross-project discovery — a `delegate` step's `registry.manifest_url`/`manifest_path` reads that manifest the same way `CatalogAgentComponent` reads the component-schema `manifest.json`.

## `capabilities` — recommended starter vocabulary

`capabilities` is a freeform list (like `tags`, not an enforced enum) describing WHAT KIND of action this agent can perform — the lever `delegate`'s `required_capabilities` pre-filters on, cheaply, before any LLM reasons over prose. It's our own convention, not part of A2A or MCP. A starter vocabulary, so teams converge on the same words instead of inventing synonyms:

| Capability | Meaning |
|---|---|
| `critique` | Reviews/scores something someone else produced (pairs with `critique_loop`-style use) |
| `supervise` | Makes a routing/approval decision over other work |
| `triage` | Classifies incoming items by urgency/category and decides next step |
| `translate` | Converts between languages or formats |
| `summarize` | Condenses longer content |
| `classify` | Assigns a label from a fixed or open set |
| `lookup` | Retrieves a fact/record given an identifier |
| `extract` | Pulls structured fields out of unstructured text |
| `generate` | Produces new content from a prompt |
| `code_review` | Reviews source code changes |

Not exhaustive — add whatever your fleet actually needs. The point is picking from a shared list, not enforcing one.

## Example YAML — MCP-hosted agent

```yaml
type: dagster_community_components.AgentCardComponent
attributes:
  agent_id: refund_lookup_agent
  name: "Refund Lookup Agent"
  description: "Looks up refund status and policy exceptions for e-commerce orders."
  skills:
    - id: lookup_refund_status
      name: "Lookup refund status"
      description: "Given an order id, returns refund status and any policy exceptions."
      tags: [refunds, orders, customer-support]
  invocation:
    mcp_server:
      name: refunds-mcp
      type: http
      url: https://internal.example.com/mcp
      headers_env: {Authorization: REFUNDS_MCP_TOKEN}
    tool_name: lookup_refund
    tool_args_template: {order_context: "{prompt}"}
```

## Example YAML — plain-HTTP-hosted agent

```yaml
type: dagster_community_components.AgentCardComponent
attributes:
  agent_id: sentiment_agent
  name: "Sentiment Agent"
  description: "Scores the sentiment of free-text customer feedback."
  skills:
    - id: score_sentiment
      name: "Score sentiment"
      description: "Returns a sentiment label and confidence for input text."
      tags: [sentiment, nlp, customer-feedback]
  invocation:
    http:
      url: https://internal.example.com/agents/sentiment
      auth_bearer_env_var: SENTIMENT_AGENT_TOKEN
      response_text_path: "$.result.label"
```

## Use it with `delegate`

```yaml
# 1. Declare the agents (as many of these as you have hosted agents)
type: dagster_community_components.AgentCardComponent
attributes:
  agent_id: refund_lookup_agent
  ...

---

# 2. A pipeline step dynamically picks among whatever AgentCardComponent
#    instances live in this same defs folder (or an external manifest)
type: dagster_community_components.AgenticPipelineComponent
attributes:
  asset_name_prefix: support_bot
  source: {kind: literal, text: "Customer asks: where's my refund for order #4821?"}
  steps:
    - id: handled
      op: delegate
      task: "Answer the customer's question about their order."
      picker: {model: gpt-4o-mini, api_key_env_var: OPENAI_API_KEY}
  outputs:
    assets: [handled]
```
