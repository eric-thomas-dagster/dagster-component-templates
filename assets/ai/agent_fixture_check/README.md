# `AgentFixtureCheckComponent`

Grade an agent's structured outcome against owner-written fixtures -- an asset check (not a
separate asset) attached to the agent's own outcome asset. Generalized from (not hardcoded to) an
internal engineering-agents reference implementation's `defs/grades.py`, which grades one specific
"improvement advisor" outcome asset against one fixtures file; this component grades **any** agent
whose outcome asset returns a dict shaped like:

```python
{
    "filed": [{"title": "...", "body": "..."}, ...],       # real actions taken
    "would_file": [{"title": "...", "body": "..."}, ...],  # practice-mode "would file" records
    "text": "...",                                          # a fallback: the agent's own final note
}
```

A human grade (a Slack 👍/👎, a manual review) is a separate signal this check doesn't attempt to
replace -- it only checks whether the agent found enough of what the fixtures expect.

## Fixture file shape

```json
{
  "fixtures": [
    {"id": "flaky_retry", "any": [["flaky", "retry"]]},
    {"id": "missing_field", "any": [["missing", "field"], ["required", "column"]]}
  ]
}
```

A finding matches a fixture when it contains **every word of at least one** of its `any` groups
(case-insensitive substring match) -- `missing_field` above matches text containing both "missing"
and "field", OR text containing both "required" and "column". The text pool is `{title} {body}` for
every entry under `findings_keys` (default `["filed", "would_file"]`); if that pool is empty, the
outcome's `fallback_text_key` field (default `"text"`) is used instead -- so a practice-mode run
that matched nothing structured, or a tool-less agent whose only record is its own prose summary,
still gets graded against *something*.

`fixtures_file` resolves relative to this component's own `defs.yaml` directory when not absolute.

## Fields mode: grading structured extraction output

The matcher above only grades free text -- it can't tell whether a document-extraction agent got
`invoice_total: 1042.50` right, because there's no "contains these words" check for a number. Set
`match_mode: fields` to grade a flat `{field_name: value}` dict instead:

```yaml
type: dagster_community_components.AgentFixtureCheckComponent
attributes:
  asset_key: invoice_extractor_outcome
  fixtures_file: eval/invoice_fixtures.json
  match_mode: fields
  fields_key: fields
  fuzzy_field_threshold: 0.7
  numeric_tolerance: 0.01
  min_recall: 0.8
  severity: WARN
```

```python
# invoice_extractor_outcome's shape in fields mode
{"fields": {"vendor_name": "Acme Corp", "invoice_total": 1042.50, "invoice_date": "2026-01-15"}}
```

The fixtures file is shaped differently in this mode -- one entry per graded field:

```json
{
  "fixtures": [
    {"id": "vendor_name", "field": "vendor_name", "expected": "Acme Corporation"},
    {"id": "invoice_total", "field": "invoice_total", "expected": 1042.50}
  ]
}
```

Each fixture's `field` is looked up in the outcome's `fields_key` dict (default `"fields"`) and
compared against `expected` with a type-appropriate fuzzy match:

- **Numbers** (and numeric strings like `"1,042.50"`) are compared by near-equality: `math.isclose`
  with `numeric_tolerance` as the relative tolerance (default `0.01`, i.e. within 1%) -- `1042.50`
  matches an expected `1042.51`, but not `950.00`.
- **Everything else** is compared as text: a token-sort ratio (word order ignored, case-insensitive)
  over Python's stdlib `difflib.SequenceMatcher` -- no new third-party dependency, since neither
  `rapidfuzz` nor `python-Levenshtein` is already a dependency anywhere in this repo (the same
  approach is already used by [`fuzzy_match`](../../transforms/fuzzy_match) and
  [`text_similarity`](../text_similarity)). `"Acme Corp"` scores `0.72` against `"Acme Corporation"`,
  above the `fuzzy_field_threshold` default of `0.7`; a genuinely different value scores far lower.
  Note this is a generic string similarity, not type-aware -- two different *dates* that happen to
  share most characters (same year, nearby digits) can score higher than you'd expect, so pick a
  higher `fuzzy_field_threshold` (or compare dates numerically, e.g. as a day-count) if that matters
  for your fixtures.

Recall/precision are computed per *field* instead of per finding-text, into the same metadata shape
as text mode: `recall` = matched fixtures / total fixtures, `precision` = matched fields / extracted
fields that had a fixture to grade against (fields the agent extracted but weren't seeded aren't
penalized). `min_recall`/`severity`/`check_name` all work exactly as in text mode.

`match_mode` defaults to `"text"` -- existing components are completely unaffected unless you
explicitly opt into `fields`.

## Why an asset check, not an asset

Matches how Dagster already models expectations about data -- the reference's own user direction
was explicit: "asset checks for expectations... stay close to how Dagster works today," not a new
service or a bespoke grading pipeline. `AssetCheckSeverity.WARN` (the default) lets a below-threshold
run show up clearly in the Dagster UI without failing the run; set `severity: ERROR` to make a
downstream dependent's run wait on this check (with `blocking` semantics wired up by whatever
job/sensor materializes the outcome asset).
