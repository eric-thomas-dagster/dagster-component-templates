# `AgentMemoryStoreComponent`

Form long-term agent memory from a DataFrame of conversation turns using **Mem0** (`pip install mem0ai`), grouped per user (and optionally per agent/session).

No component in this registry did this before — [`conversation_memory`](../conversation_memory) is a sliding-window chat-turn JSON file: it appends/trims raw messages, with no extraction, consolidation, semantic search, or per-user scoping. "Agent memory" as an architectural pattern — distinct from RAG, which retrieves from a fixed corpus — is a genuinely different thing: an LLM extracts durable facts from a conversation and consolidates them into a vector store for later semantic recall, updating what's already known about a user rather than keeping a raw transcript.

## How it works

Each materialization groups the upstream DataFrame by `user_id_column` (and `agent_id_column`/`run_id_column`, if set), builds a `[{"role":..., "content":...}]` message list per group from `role_column`/`content_column`, and calls Mem0's real `add()` once per group. The asset itself materializes no value (its effect is the memory write) — metadata reports `groups_written`/`memories_written`.

## Scope (deliberately limited)

This component wraps `add()` (write) and an optional `search()` smoke check — **`get_all()`/`update()`/`delete()` are not implemented**, because their exact signatures for Mem0's self-hosted `Memory` class weren't confirmed against primary docs at the time this was written (only the cloud REST API's shapes for those are documented). This repo's convention is to not guess API shapes; if you need those operations, verify them against your installed `mem0ai` version first.

`agent_id`/`run_id`/`metadata`/`infer` on `add()` are confirmed on Mem0's cloud API reference and referenced in the OSS README, but aren't spelled out on the self-hosted `Memory` class's own docs page. They're only sent when the corresponding column is actually configured (`agent_id_column`/`run_id_column`/`metadata_column`) — if your installed `mem0ai` version doesn't accept one, you'll get a clear `TypeError` rather than a silently-wrong default.

## Demo mode

`demo_mode: true` (the default) never calls Mem0, an LLM, or an embedder. The component's internal `_DemoMemoryClient` persists to a local JSON file (`demo_store_path`, default `./{asset_name}_agent_memory_demo.json`) and returns real-shaped `add()`/`search()` responses — `infer=true` extracts the last user message as the "memory" (a simple stand-in for real fact extraction), `infer=false` stores the raw message list verbatim, matching Mem0's own documented `infer` semantics.

Set `demo_mode: false` for a real Mem0 stack. If `vector_store`/`llm`/`embedder` are all left unset, Mem0's own self-hosted default applies: on-disk Qdrant + OpenAI (`gpt-5-mini` for extraction, `text-embedding-3-small` for embeddings) — requires `OPENAI_API_KEY`. Set any of the three to use a different stack, e.g.:

```yaml
vector_store:
  provider: qdrant
  config: {host: localhost, port: 6333}
llm:
  provider: openai
  config: {model: gpt-5-mini}
```

## Validation notes

Verified directly against Mem0's own docs (`docs.mem0.ai`), not inferred from a blog: the self-hosted quickstart confirms `Memory()`'s zero-config defaults and the `add(messages, user_id=...)` / `search(query, filters={"user_id": ...})` shapes (note: `search` takes a `filters` dict, not a `user_id` keyword argument — an easy mistake, since the cloud API's examples read differently). The configuration docs confirm `Memory.from_config({"vector_store": {...}, "llm": {...}, "embedder": {...}})`. `add()`'s full parameter list beyond `messages`/`user_id` (i.e. `agent_id`/`run_id`/`metadata`/`infer`) is confirmed on Mem0's cloud API reference but not pinned down for the self-hosted class specifically — see "Scope" above for how this component handles that gap.

## Relationship to a receipt-store / agent-memory platform play

This repo separately has `resources/context_receipt_store` — a SQLite-backed, schema-versioned (`receipt-spec.v1.json`) audit trail of retrieval/output/evidence/outcome events. It's retrieval-provenance-shaped (what was fetched, from where, scored how, did it get cited or work out) — deliberately never storing raw query/output text, only ids/hashes/scores. Agent memory (this component) is semantic-fact-shaped (what should be remembered about this user) — complementary, not overlapping.

A plausible future direction: log each memory write as its own receipt event (e.g. a `memory_write` type referencing the triggering `receipt_id`), giving memory formation the same lineage/outcome-feedback loop retrieval already has via `context_receipt_store`. **This is not implemented here** — extending that store's schema is a deliberate version decision for whoever owns it, not something this component does unilaterally.

## Example

```yaml
type: dagster_community_components.AgentMemoryStoreComponent
attributes:
  asset_name: customer_agent_memory
  upstream_asset_key: support_chat_turns
  user_id_column: customer_id
  role_column: role
  content_column: content
  validate_search: true
  validate_search_query: "What does this customer care about?"
  group_name: agent_memory
  kinds: [mem0, memory, llm]
  demo_mode: true
```

## Composes with

- [`conversation_memory`](../conversation_memory) — the simpler sliding-window chat-history sibling, for when you just need recent-turn recall, not consolidated long-term facts.
- Any chat/agent pipeline producing a per-turn DataFrame (`role`/`content`/`user_id` columns) — e.g. a `litellm_agent` or `langgraph_agent` run logged to a table.

## What doesn't work in v1

- **`get_all()`/`update()`/`delete()`** — deliberately not implemented; see "Scope" above.
- **Reading memories back into a pipeline as an asset** — this component only writes. Querying Mem0 at serve time (an agent recalling memories mid-conversation) is an online operation best done by the agent runtime itself, not a batch Dagster asset; `validate_search` is a QA smoke check only, not a retrieval API.
- **Receipt-store integration** — a documented future idea, not built. See "Relationship to a receipt-store" above.
