# Anthropic Batch Results

Fetches and parses the results of a completed Anthropic Message Batch. Runs after `anthropic_batch_status_sensor` confirms `processing_status == "ended"` (the `batch_id` arrives dynamically via that sensor's `RunRequest.run_config`), or against a statically configured `batch_id` for manual runs and backfills.

Last of three components that make up the Anthropic Message Batches pipeline — see `anthropic_batch_submit`'s README for the full picture.

```yaml
type: dagster_component_templates.AnthropicBatchResultsComponent
attributes:
  asset_name: support_ticket_batch_results
  api_key_env_var: ANTHROPIC_API_KEY
  # output_schema: my_project.schemas:TicketClassification
```

## Wiring: `asset_name` must match the sensor's `results_asset_key`

The underlying op's name is derived from `asset_name` via `AssetKey.to_python_identifier()`. The paired `anthropic_batch_status_sensor`'s `results_asset_key` field must be set to this exact same `asset_name` value, so that sensor's `RunRequest.run_config` addresses the correct op — see that component's README for the full explanation of why this indirection exists (a real bug this repo already hit once with a literal `"config"` op-name shortcut).

`batch_id` arrives at runtime as op config (`config.batch_id`, populated by the sensor's `RunRequest`) and takes priority over the component's static `batch_id` field, which exists purely for manual/backfill runs.

## Guard: refuses to run before the batch has ended

Even though this asset is designed to be triggered only once the status sensor confirms completion, it independently calls `client.messages.batches.retrieve(batch_id)` and raises a clear error if `processing_status != "ended"` — defending against someone materializing it manually (or via a stale backfill) before the batch is actually done.

## Per-row result handling

Each entry from `client.messages.batches.results(batch_id)` (the SDK's streaming-JSONL helper — never manually fetched via `results_url`) becomes one output row:

| `result_type` | `raw_output` | `error` |
|---|---|---|
| `succeeded` | Joined text of all `text` content blocks in `result.message.content` (non-text blocks like `tool_use` are ignored) | `None` |
| `errored` | `None` | `f"{error.type}: {error.message}"` |
| `canceled` | `None` | `"request canceled"` |
| `expired` | `None` | `"request expired"` |

## Optional typed parsing via `output_schema`

Set `output_schema` to a dotted path `module.path:ClassName` pointing at a Pydantic model (same dotted-path-import convention as `smart_retry`'s `kind: python` handling). For every `succeeded` row, `raw_output` is parsed as JSON and validated against that model (`Model.model_validate_json(raw_output)`); the model's fields become additional output columns.

**A bad answer never fails the task.** If parsing or validation fails for any reason (malformed JSON, a missing required field, a type mismatch), the row is marked `invalid_output=True`, `raw_output` is kept as-is, and the typed columns are left null for that row — the whole asset still succeeds. `invalid_output_count` is surfaced in output metadata so a spike in malformed model responses is visible without digging into individual rows.

## Output metadata

| Key | Meaning |
|---|---|
| `row_count` | Total rows (= total requests in the batch). |
| `succeeded_count` | Rows with `result_type == "succeeded"`. |
| `errored_count` | Rows with `result_type == "errored"`. |
| `invalid_output_count` | Rows where `output_schema` parsing/validation failed (0 if `output_schema` is unset). |
