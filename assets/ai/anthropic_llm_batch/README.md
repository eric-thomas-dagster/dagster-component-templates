# AnthropicLlmBatchComponent

Submit a DataFrame's prompts as an async **Anthropic Message Batch** —
roughly half the price of the synchronous `messages.create` endpoint, in
exchange for turnaround that's usually under an hour but can take up to
24h. This is a real integration with the batch endpoint itself, not a
synchronous call in a thread pool.

One component, three things happen automatically. Earlier iterations of
this split submit / sensor / results into three separate components that
had to be manually cross-wired (`watch_asset_key`, `results_asset_key`,
`job_name`) across three YAML blocks. A single `build_defs()` can return
assets *and* sensors together, so this component derives all of that wiring
internally from one `asset_name` — configure it once and the sensor "just
appears," already pointed at the right asset.

## Two modes

**`wait_for_completion: false`** (default) — the real deferred mode. Emits:
- `{asset_name}__submit` — builds the batch requests, submits them, returns
  a small manifest (`batch_id` / `processing_status` / `request_count`).
- `{asset_name}` — the actual output. Stays dormant until triggered.
- `{asset_name}__batch_status_sensor` — polls the *live* `processing_status`
  (never trusts stale cached metadata) and materializes `{asset_name}`
  directly via `RunRequest(asset_selection=...)` once the batch reaches
  `"ended"`. No worker sits blocked waiting, and there's no
  `job_name`/companion job to define — the sensor targets the results
  asset by key.

**`wait_for_completion: true`** — a single asset named `asset_name` that
submits, polls synchronously to `"ended"`, and returns the fully parsed
results DataFrame directly. No sensor is created in this mode. Useful for
small batches, tests, or backfills where you want everything back in one
materialization.

## Idempotency (retries don't pay twice)

Anthropic's batch-creation API has **no metadata field** (unlike OpenAI's),
so retry-reattach relies entirely on Dagster's own asset materialization
metadata. A deterministic `prompts_hash` (sha256 over the sorted
`(custom_id, prompt)` pairs) is stamped into the submit asset's metadata
and read back on every run:

- Same hash as last time → **reattach** to the existing live batch
  (`messages.batches.retrieve`), never resubmit.
- Different hash → the prior batch is stale: best-effort **cancel** it
  (itself async on Anthropic's side — this fires the cancel and moves on,
  it doesn't block waiting for cancellation to finish), then submit fresh.

## custom_id validation

Anthropic requires every request's `custom_id` to match
`^[a-zA-Z0-9_-]{1,64}$`. If `id_column` produces a value outside that
pattern, the asset raises a clear error naming the offending value rather
than silently mangling it — fix the column's values, or unset `id_column`
to fall back to the row's positional index.

## Typed output

Set `output_schema` to a dotted path (`module.path:ClassName`) to a Pydantic
model. Each row's `raw_output` is parsed as JSON and validated against it;
on success the model's fields are merged in as extra columns. On **any**
failure (bad JSON, validation error) the row is marked `invalid_output=True`
with `raw_output` preserved as-is — it never fails the whole asset. Results
also carry a `result_type` column (`succeeded` / `errored` / `canceled` /
`expired`) since Anthropic reports per-request outcomes separately from the
batch's own `processing_status`.

## Example

```yaml
type: dagster_component_templates.AnthropicLlmBatchComponent
attributes:
  asset_name: support_reply_results
  upstream_asset_key: support_tickets
  prompt_column: body
  id_column: ticket_id
  model: claude-haiku-4-5-20251001
  system_prompt: "Draft a helpful, concise reply to this support ticket."
  wait_for_completion: false
```

Requires `ANTHROPIC_API_KEY` (or whatever `api_key_env_var` names) in the
environment.

## Related

- **`openai_llm_batch`** — the OpenAI Batch API equivalent. Kept as a
  separate component rather than unified behind a `provider:` field,
  matching this repo's one-component-per-vendor convention; the two APIs
  differ enough underneath (direct JSON vs. file upload, a single `status`
  enum vs. a separate per-request `result.type`) that unifying wouldn't
  actually remove much code. litellm itself only wraps Anthropic's
  `retrieve_batch` — it has no `create_batch`/`cancel_batch` support for
  Anthropic at all, so this component talks to the `anthropic` SDK
  directly rather than through litellm.
