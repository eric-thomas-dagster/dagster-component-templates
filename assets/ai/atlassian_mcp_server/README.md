# AtlassianMcpServer

A local **stdio MCP server** that proxies to Atlassian's own hosted MCP server
(`https://mcp.atlassian.com/v2/mcp` — Jira, Confluence, Jira Service Management), authenticated
with a static **personal API token** or **service-account key** — no OAuth.

## Scope cut: token auth only, not OAuth 2.1

Atlassian MCP's primary auth mechanism is OAuth 2.1 (interactive browser consent). Atlassian also
documents a token-based path explicitly recommended for **"backend services or CI/CD
pipelines"** (their own words), which grants the **same** tool access as an interactive session —
not a reduced subset — but **must be explicitly enabled by your org admin first** (off by
default; see
[Atlassian's own setup docs](https://support.atlassian.com/atlassian-ai-gateway/docs/configure-authentication-via-api-token/)).

This component supports only the two token modes below, not OAuth — a deliberate scope cut.
Unlike Notion's hosted MCP server (OAuth via RFC 8414 dynamic client registration, no
pre-registered app needed), Atlassian's OAuth 2.1 flow requires a pre-registered OAuth app with no
dynamic registration and no confirmed MCP-specific consent scope string. If your org hasn't
enabled token-based MCP auth, this component cannot be used yet — use the OAuth sign-in flow in an
interactive MCP client instead.

## `auth_mode: personal_api_token` (default)

Acts as the token's owner. Confirmed header shape: `Authorization: Basic
base64(email:api_token)`.

```yaml
type: dagster_community_components.AtlassianMcpServerComponent
attributes:
  resource_key: atlassian_mcp
  auth_mode: personal_api_token
  atlassian_email_env_var: ATLASSIAN_EMAIL
  atlassian_api_token_env_var: ATLASSIAN_API_TOKEN
```

Create the personal API token at
[id.atlassian.com/manage-profile/security/api-tokens](https://id.atlassian.com/manage-profile/security/api-tokens).

## `auth_mode: service_account`

Acts as a service account, not a specific person. Confirmed header shape: `Authorization: Bearer
<key>`.

```yaml
type: dagster_community_components.AtlassianMcpServerComponent
attributes:
  resource_key: atlassian_mcp
  auth_mode: service_account
  atlassian_service_account_key_env_var: ATLASSIAN_SERVICE_ACCOUNT_KEY
```

Then, in any MCP-aware component (anthropic_agent / openai_agent / litellm_agent / gemini_agent /
agentic_pipeline) instead of an inline `server:` spec:

```yaml
server_resource_key: atlassian_mcp
```

## Generic tool passthrough, not one tool per Jira/Confluence operation

Atlassian MCP's own tool surface depends on which apps and scopes were granted to the credential
in use. This proxy exposes two generic tools rather than guessing a fixed catalog:

- `list_remote_tools` — lists the Atlassian MCP tools currently available (name + description).
- `call_remote_tool(tool_name, arguments)` — calls one by name with a JSON-object of arguments.

## `allow`

Restrict which Atlassian MCP tools are callable, independent of what your granted scopes expose:

```yaml
allow:
  - jira_search
```

## Per-server usage guidance (`instructions`)

Set `instructions` here, once, instead of pasting the same guidance into every agent that uses
this server via `server_resource_key`. The litellm/openai/anthropic/gemini agent components read
it off the resolved resource and append it to their system prompt under a heading with this
resource's `resource_key` name.
