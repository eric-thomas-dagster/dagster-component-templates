# Audio Diarized Transcriber

Transcribe audio AND label who's speaking when. Every other transcription component in this catalog (`audio_transcriber`, `litellm_audio_transcription`, `speech_to_text_asset`) returns one flat transcript string per file — fine for single-speaker audio, useless for a call, meeting, or podcast where you need to know WHO said WHAT WHEN. This component returns a list of `{speaker, start_seconds, end_seconds, text}` segments (`speaker_1`, `speaker_2`, ...) instead.

## Why this exists

Nothing in the catalog combined transcription with speaker attribution. `speech_to_text_asset` actually had a `enable_speaker_diarization` field already — but its response-parsing code never read the per-word speaker labels back out of the API response, so the feature silently did nothing (fixed separately, see that component's README). This component is the real, dedicated version: per-segment output shaped for downstream use (one row per file, with a list column you can explode), not a bolt-on flag on a whole-file-transcript component.

## Usage

```yaml
type: dagster_component_templates.AudioDiarizedTranscriberComponent
attributes:
  asset_name: call_transcripts
  upstream_asset_key: call_audio_files
  audio_path_column: audio_path
  diarization_backend: google_cloud_speech
  credentials_path: /path/to/service-account.json
  min_speaker_count: 2
  max_speaker_count: 4
```

Pairs with `video_audio_extract_asset` for video (video → audio track → this component), or `synthetic_audio_generator` for a quick test fixture (sine tones won't produce meaningful diarization/transcription content, but exercise the full pipeline mechanics).

Output: `segments` (list of `{speaker, start_seconds, end_seconds, text}` dicts, ordered by `start_seconds`) and `segments_transcript` (all segments' text joined in order, for callers who just want the words). Explode `segments` with `array_exploder` if you want one row per speaker turn instead of one row per file.

## Backends: local vs. cloud

There's no single right answer for "local library vs. cloud API" here, so this component supports both via `diarization_backend`:

### `google_cloud_speech` (default)

Cloud Speech-to-Text v2's native `SpeakerDiarizationConfig` — one API call per file does ASR and diarization together. No heavy local install, per-request cost, needs a GCP service account (`credentials` dict, `credentials_path`, or `GOOGLE_APPLICATION_CREDENTIALS`). This is the backend exercised end-to-end in this repo's test suite.

Required SA role: `roles/speech.client` + Cloud Speech API enabled (same as `speech_to_text_asset`).

### `pyannote` (local, opt-in)

Local `pyannote.audio` for diarization (who spoke when) + local Whisper for transcription (what they said) — pyannote itself does **not** transcribe, so this always runs two passes: pyannote segments the audio into speaker turns, then each turn is cut out via `ffmpeg` and transcribed independently with `openai-whisper`.

```yaml
diarization_backend: pyannote
hf_token_env_var: HF_TOKEN
whisper_model_size: base
```

**Before using this backend:** `pyannote/speaker-diarization-3.1` (the default pipeline) is a **gated model on HuggingFace** — you need your own HuggingFace account, an access token (`hf_token_env_var`), and to accept the model's terms on huggingface.co with that account *before* it will download. There's no way around this from inside the component; if the token is missing or lacks access, you get a clear error before any model-loading is attempted, not a confusing downstream failure.

Also requires `ffmpeg` in PATH, `pip install pyannote.audio` (pulls in `torch`/`torchaudio`), and `pip install openai-whisper`.

`max_segments_per_file` (default 200) caps how many speaker turns get transcribed per file — a misdetected/noisy file can otherwise produce thousands of tiny turns and burn enormous Whisper runtime. `min_segment_seconds` (default 0.3) drops sub-threshold micro-turns that pyannote frequently emits at speaker-change boundaries, which are too short to transcribe meaningfully anyway.

## Choosing a backend

| | `google_cloud_speech` | `pyannote` |
|---|---|---|
| Setup | GCP service account | HF token + terms acceptance + `torch` install |
| Cost | Per-request cloud billing | Free after setup (local compute) |
| Speed | Network round-trip per file | Local inference (CPU: slow; GPU: fast) |
| Data leaves your infra | Yes | No |
| Validated in this repo | Yes (real audio, mocked network call) | Orchestration only — see Validation below |

## Validation

`validation.level: code`.

**`google_cloud_speech` backend** — verified end-to-end against a REAL generated WAV file (not mocked content), with only the Speech v2 network call mocked: confirmed the real audio file's bytes are actually read off disk and sent in the request (not a short-circuited stub), a realistic multi-speaker `WordInfo` response (built from the real `google-cloud-speech` proto-plus types, not hand-rolled) correctly groups into `speaker_1`/`speaker_2` segments with the right start/end timings and text, `segments_transcript` concatenates segment text in the right order, and output metadata (`diarized_rows`/`total_segments`/`backend`) is correct.

**`pyannote` backend** — orchestration-tested only, not model-tested: neither `pyannote.audio` nor `openai-whisper` are installed in this repo's test environment (heavy ML dependencies), and pyannote's real pretrained pipeline can't be downloaded here at all (gated HuggingFace model, needs a real user token + terms acceptance). What IS verified: the real `ImportError` when `pyannote.audio` is genuinely absent; a clear, specific `ValueError` when the HF token env var is unset, raised *before* any model loading is attempted; and — using minimal stand-ins for the diarization pipeline and Whisper model that match pyannote's real `Annotation.itertracks(yield_label=True)` API shape — that the surrounding orchestration is correct against a REAL generated audio file and REAL `ffmpeg` subprocess calls: speaker-label remapping to `speaker_1`/`speaker_2`, `min_segment_seconds` filtering of micro-turns, and `max_segments_per_file` truncation all behave as documented.

Has NOT been run against a real Google Cloud Speech API call or a real pyannote model download. Live-test whichever backend you plan to use before trusting it in production, and flip `validation.level` to `live` once confirmed.
