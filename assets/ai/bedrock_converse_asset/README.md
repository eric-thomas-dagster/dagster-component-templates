# `BedrockConverseAssetComponent`

Call AWS Bedrock's **Converse API** directly (`boto3.client("bedrock-runtime").converse(...)`, not a litellm passthrough) once per row of an upstream DataFrame, and attach the result as new column(s).

No component in this registry called Bedrock's Converse API directly before this one — Bedrock only ever appeared as a `bedrock/<model>` model-string option inside litellm-based components (`rag_pipeline`, `agentic_pipeline`, `litellm_agent`, `embeddings_generator`, `litellm_inference_asset`). litellm's passthrough works for most models, but a native integration is simpler to reason about, supports Bedrock's raw-bytes image protocol natively, and matches this registry's existing direct-SDK AI components (`anthropic_llm`, `anthropic_llm_batch`, `gemini_llm`) rather than its litellm-based ones.

`upstream_asset_key`/`input_column`/`input_type` match [`structured_document_extractor`](../structured_document_extractor)'s and [`image_llm_extractor`](../image_llm_extractor)'s own field conventions, so swapping between a litellm-based extractor and this native-Bedrock one is a small config change, not a rewrite.

## Text vs. image input

| `input_type` | `input_column` holds | What gets sent |
|---|---|---|
| `text` (default) | Raw text | `prompt_template` with `{input}` substituted for the row's text, as a `{"text": ...}` content block. |
| `image` | A path to an image file | The file's **raw bytes** (not base64) as an `{"image": {...}}` content block, plus `prompt_template` as a literal instruction. |

Bedrock Converse's image content block takes raw bytes — verified directly against AWS's own `ImageSource` API reference ("If you use an AWS SDK, you don't need to encode the image bytes in base64."), unlike OpenAI-style vision APIs.

## Structured output

Set `output_schema` (a JSON schema with `properties`) to parse the model's response as JSON, validate it against the schema (`jsonschema.Draft202012Validator`), and add one output column per property — missing or schema-invalid responses fill those columns with `None` rather than raising. Leave `output_schema` unset to store the model's raw text response in `output_column` instead.

Set `min_valid_rate` to emit a `output_schema_valid_rate` asset check on the share of rows that validated — `min_valid_rate_severity: ERROR` blocks downstream consumers; `WARN` (the default) doesn't.

A row-level call failure (a transient AWS error, a malformed response) never aborts the whole asset — that row's output column(s) become `None`, a warning is logged, and the run continues. The total failure count is reported in `failures` metadata.

## Demo mode

`demo_mode: true` (the default) never calls AWS. The component's internal `_DemoBedrockClient` returns a deterministic synthetic response in the exact real response shape (`output.message.content[0].text`, `usage.*`, `metrics.latencyMs`), seeded off each row's own input — not a `demo_seed` field — so repeated demo runs are reproducible. When `output_schema` is set, the demo client fabricates one value per declared property, typed to match the schema (`string`/`number`/`integer`/`boolean`/`enum`).

Set `demo_mode: false` to call a real Bedrock endpoint via the default boto3 credential chain (or `aws_access_key_id`/`aws_secret_access_key`/`aws_session_token` if set explicitly).

## Which model to use

`model_id` defaults to `qwen.qwen3-vl-235b-a22b` — Bedrock's current vision-capable Qwen3 model, verified against AWS's own Bedrock model-card page. For text-only use cases, a text-only Qwen3 variant (e.g. `qwen.qwen3-235b-a22b-v1:0`) or any other Converse-API-compatible Bedrock model ID works equally well.

## Example

```yaml
type: dagster_community_components.BedrockConverseAssetComponent
attributes:
  asset_name: invoice_baseline_extraction
  upstream_asset_key: carrier_invoices
  input_column: file_path
  input_type: image

  aws_region: us-east-2
  model_id: qwen.qwen3-vl-235b-a22b
  prompt_template: >-
    Extract invoice_number, carrier_name, and total_amount from this invoice.
    Return only a JSON object with those three keys.

  output_schema:
    type: object
    properties:
      invoice_number: { type: string }
      carrier_name: { type: string }
      total_amount: { type: number }

  min_valid_rate: 0.9
  group_name: ml
  kinds: [bedrock, aws, llm, vision]
  demo_mode: true
```

## Composes with

- [`structured_document_extractor`](../structured_document_extractor) / [`image_llm_extractor`](../image_llm_extractor) — litellm-based alternatives with the same `upstream_asset_key`/`input_column`/`input_type` field shape, for models not on Bedrock.
- [`ecs_pipes_asset`](../../infrastructure/ecs_pipes_asset) — a self-hosted-model counterpart: run your own fine-tuned Qwen3 (or any model) on ECS via Dagster Pipes, and use this component as a cost/quality baseline against the same input.

## What doesn't work in v1

- **Batch/async Converse calls** — v1 calls Bedrock's synchronous `converse` once per row, sequentially. For very large row counts, consider `batch_size`-style chunking at the upstream asset level, or Bedrock's separate batch inference API (not wrapped by this component).
- **Multi-turn conversations** — each row is a single-turn `messages=[{"role": "user", ...}]` call; no conversation history is carried between rows.
