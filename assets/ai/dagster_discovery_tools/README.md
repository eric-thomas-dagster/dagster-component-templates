# `DagsterDiscoveryToolsComponent`

Read-only "what exists in this deployment" tools for agents, over the **Dagster+ GraphQL API**. No Dagster+
backend or MCP server changes -- this is a plain client, same approach as `ops_tools.py` in an internal
engineering-agents reference sandbox.

## Why this exists

An agent can't ask "what agents / tools / components / schedules / assets exist in this deployment" today --
it has to be told in a prompt, or guess. The Dagster+ MCP server doesn't expose components, agents, or MCP
servers. This component fills that gap with nine read-only tools:

| Tool | What it answers |
|---|---|
| `list_locations` | Code locations: load status/errors, Dagster library versions, schedule/sensor counts |
| `list_assets` | Assets: group_name, freshness policy, automation condition, has_asset_checks, partition stats |
| `list_components(location_name, type?)` | Every UI-created (app-managed) component, with its id/type/YAML |
| `get_component(location_name, id)` | One component's full config |
| `list_agents(location_name?)` | Agent components specifically (parsed from `list_components` by type name) |
| `list_mcp_servers(location_name?)` | MCP-server-shaped components specifically |
| `list_schedules_and_sensors(location_name?)` | Schedules + sensors per repository |
| `list_runs(location_name, limit?, statuses?)` | Recent runs, ALWAYS scoped to one code location |
| `list_alert_policies` | Alert policies configured on the deployment |

Call this first (`list_locations`) -- most other tools need a `location_name`.

## `list_agents` / `list_mcp_servers`: how components get classified

`appManagedComponentsForLocationOrError` returns every UI-created component as `{id, type, yaml}` with no
"is this an agent" field. These two tools classify by substring-matching the component's own `type` string
(`agent`, `advisor`, `reviewer`, `bugfixer` for agents; `mcptools`, `toolscomponent`, `chattools`,
`mcpserver` for MCP servers) -- the same way a person skimming the Components tab would. `list_agents` does
**not** include "last outcome" -- that lives on the agent's own outcome asset's materialization metadata (the
ledger/outcomes pattern), not on the component's static config. Combine with
[`dagster_instance_tools`](../dagster_instance_tools)'s `asset_status` on the agent's outcome asset key for that.

## Honesty about what's verified vs. Dagster+-only

- `workspaceOrError`/`locationEntries`/`RepositoryLocation.dagsterLibraryVersions`/`Repository.{schedules,sensors}`
  and `runsOrError(filter: RunsFilter, ...)` are **real, OSS GraphQL fields** -- confirmed by introspecting the
  installed `dagster_graphql` package's own schema (this repo has no live Dagster+ deployment to test against).
  `RunsFilter.repositoryOrigin` is a Dagster+-only extension (not in the OSS `RunsFilter` input type at all) --
  used here exactly as given by the engineers who validated it against a real deployment.
- Top-level `assetNodes`, `alertPolicies`, and `appManagedComponentsForLocationOrError` are Dagster+-only schema
  extensions this OSS-only environment can't introspect ahead of time. Rather than hard-code a guessed nested
  type name (a wrong inline-fragment type name is a hard GraphQL validation error, not a soft miss), the tools
  that touch them call `auto_selection()`: it introspects the **live** deployment's `__type` for the field's
  return type at call time and builds a field-selection set from whatever is actually there -- real unions get
  real `... on <PossibleType>` fragments discovered live, not guessed. This costs one extra introspection
  round-trip per distinct type the first time it's touched (cached on the client for the process lifetime).

If your deployment's schema doesn't match what these tools expect (e.g. `appManagedComponentsForLocationOrError`'s
success type uses a list field name other than the first list-of-objects field found), the error will be a clear
GraphQL error or an empty result, not a silent wrong answer -- open an issue with what you see.

## Auth + deployment URL

Same mechanism [`insights_custom_metrics_sync`](../insights_custom_metrics_sync) already uses:

- `deployment_url: auto` (default) derives `https://<org>[.<region>].dagster.cloud/<deployment>` from
  `DAGSTER_CLOUD_DEPLOYMENT_NAME` + the instance's Dagster+ organization -- only resolvable where a real
  `DagsterInstance` is available (the plain resource path). **Not resolvable** for
  `mcp_server_resource_key` (that spawns `python -m <this module>` as a separate subprocess with no
  `DagsterInstance` at all) -- set `deployment_url` explicitly whenever you also set `mcp_server_resource_key`.
- `token_env_var` (default `DAGSTER_CLOUD_API_TOKEN`) is sent as the `Dagster-Cloud-Api-Token` header.

## MCP server

Any `mcp_servers`-aware component (`mcp_tool_call`, `mcp_tool_picker`, the agent components, ...) can reference
this toolset via `server_resource_key` once `mcp_server_resource_key` is set:

```yaml
type: dagster_community_components.DagsterDiscoveryToolsComponent
attributes:
  deployment_url: https://acme.dagster.cloud/prod   # required (not auto) when mcp_server_resource_key is set
  mcp_server_resource_key: discovery_tools_mcp
```

Or run it standalone for a local agent / Claude Code: `python -m dagster_community_components.assets.ai.dagster_discovery_tools.component`,
with `DAGSTER_DISCOVERY_TOOLS_DEPLOYMENT_URL` and `DAGSTER_DISCOVERY_TOOLS_TOKEN_ENV_VAR` (and the env var it names)
set in the environment.
