# Document Section Splitter

Splits a long document (e.g. an annual report / 10-K) into its logical sections — cover, MD&A, balance sheet, income statement, notes, auditor's report, etc. — so each section can be routed to the right downstream extraction, then optionally suggests a field schema per section type ("Split→Schema").

## How it works

1. **Extract per-page text.** Each upstream row's PDF (a file path or raw bytes in `column`) is opened with `pdfplumber` and its text is extracted one page at a time.
2. **Classify (one LLM call per document).** All of a document's page texts are sent to the model in a single `litellm` call, asking it to classify every page into one of `section_types`. The reply is a JSON array of `{"page": <1-based int>, "section_type": "<str>"}`.
3. **Merge.** Consecutive pages sharing the same `section_type` are merged into one contiguous section (`page_start`/`page_end`/`section_text`).
4. **Explode.** The asset outputs one row per section — `passthrough_columns` (default: every upstream column except `column`) plus `section_type`, `page_start`, `page_end`, `section_text`.
5. **Suggest a schema (optional, one LLM call per unique section_type).** When `suggest_schema` is true (the default), for each *unique* `section_type` actually produced across the whole run — deduped, not per row, to minimize LLM calls and cost — one additional call asks for up to `max_schema_fields` `{field, description}` entries worth extracting from sections of that type. The result is attached as a JSON string in `suggested_schema_json` to every row of that section_type.

## Honesty notes

- **Classification is model-dependent, not a deterministic parser.** There is no guarantee every page is classified correctly, especially at the boundary between two sections (e.g. the transition from MD&A into the financial statements). Use `classification_model` to pick a stronger model if the default (`gpt-4o-mini`) isn't accurate enough for your documents.
- The model is asked to choose only from `section_types`, but nothing prevents it from returning a value outside that list. Such pages are kept with whatever string the model actually returned rather than silently dropped or coerced into a known type — coercing would misrepresent what the model said.
- A page the model's reply omits carries forward the previous page's `section_type` (or the first entry of `section_types` for page 1) — a documented fallback for a genuinely incomplete reply, not a silent failure. A reply that isn't valid JSON, or isn't a JSON array of `page`/`section_type` objects, raises a clear error instead of producing garbage rows.
- `suggested_schema_json` is a *suggestion*, not a guarantee — it is not validated against the section's actual content shape. A schema-suggestion call that fails (bad/unparseable reply) leaves that section_type's `suggested_schema_json` as `null` rather than fabricating a fallback schema.
- `max_content_chars` truncates the assembled page text (classification call) or section text (schema-suggestion call) sent to the model. A document whose combined page text exceeds this is truncated — later pages may then be classified less reliably. This is a known, documented limitation.

## Default section_types

```
cover, table_of_contents, md_a, balance_sheet, income_statement,
cash_flow_statement, notes, auditor_report, other
```

Override `section_types` with your own fully custom list for a different document domain (legal contracts, SEC filings with different section names, etc.).

## Example

```yaml
type: dagster_community_components.DocumentSectionSplitterComponent
attributes:
  asset_name: annual_report_sections
  upstream_asset_key: annual_report_pdfs
  group_name: ai
  column: file_path
  passthrough_columns:
    - doc_id
  suggest_schema: true
  classification_model: gpt-4o-mini
```
