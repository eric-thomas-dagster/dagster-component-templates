# Document Word Boxes

Extract WORD-LEVEL bounding boxes -- for every word on every page, its exact
text plus position (`x0`, `x1`, `top`, `bottom`) -- from a column of PDF file
paths or PDF bytes, using `pdfplumber`. Useful for review overlays,
field-level QA, redaction previews, and citation interfaces: anything that
needs to point at exactly where a specific word sits on a rendered page.

## Why this exists, and why it's different from `document_layout_analyzer`

`document_layout_analyzer` returns a REGION-level bounding box (table,
figure, header) via a HuggingFace object-detection model, with a real
confidence score because that model genuinely is probabilistic. This
component works at a different granularity entirely: individual words, not
regions, pulled straight from the PDF's own embedded text layer via
`pdfplumber`'s `page.extract_words()` -- no model, no LLM call, no guessing.
The coordinate fields (`x0`, `x1`, `top`, `bottom`) are pdfplumber's own
field names, used here exactly as pdfplumber reports them.

## No real confidence score, and why

A born-digital PDF's text layer is exact, not probabilistic -- there is no
OCR uncertainty to express for a word pdfplumber reads directly out of the
PDF's internal text-positioning data. The `confidence` output column is a
fixed `1.0`, included only for shape parity with field-level extraction
conventions elsewhere in this repo. It is **not** a genuine per-word
probability, and should never be read as one.

## The real limitation: text-layer PDFs only

This only works for born-digital / text-layer PDFs -- the overwhelming
majority of generated reports, invoices, filings, and exports. A
scanned/photographed PDF with no embedded text layer has nothing for
`pdfplumber` to read, so it returns zero words per page. This component
detects that case (zero words extracted across every processed page of a
document) and **skips that document with a logged warning** plus a
`documents_skipped_no_text_layer` metadata counter, rather than silently
returning an empty, unexplained result.

True OCR of scanned/photographed documents (e.g. via `pytesseract`'s
`image_to_data`, which does return genuine per-word confidence scores
because OCR really is probabilistic) is **not built here** -- that's
separate, larger future scope, not something this component fakes or stubs.

## Output shape: one row per word

```yaml
type: dagster_community_components.DocumentWordBoxesComponent
attributes:
  asset_name: pdf_word_boxes
  upstream_asset_key: raw_pdf_files
  column: file_path
  page_range: 1-5
```

Every word (across every processed page) becomes its own output row:

| Column | Meaning |
|---|---|
| *(passthrough columns)* | Every upstream column except `column`, by default -- override with `passthrough_columns` |
| `page_number` | 1-based PDF page number this word was found on |
| `word_index` | 0-based position of this word within its page (in pdfplumber's own extraction order) |
| `text` | The word's exact text, from the PDF's own text layer |
| `x0` / `x1` | Left / right horizontal position (pdfplumber's own field names) |
| `top` / `bottom` | Top / bottom vertical position (pdfplumber's own field names) |
| `confidence` | Always `1.0` -- not a real probability, see above |

## `page_range`

Scopes extraction to specific pages, e.g. `"1,3,5-10"` -- the same
comma/range spec and parsing convention as `pdf_text_extractor`'s `pages`
field. Useful to avoid exploding a 500-page filing into millions of rows
when only a few pages are actually relevant.

## `find_text_bbox` helper function

This component also ships a small, standalone, read-only helper function at
module level: `find_text_bbox(words, needle)`. Given a list of word-box
dicts (the same shape as this component's output rows) and a text snippet,
it finds the contiguous run of consecutive words whose concatenated text
contains `needle` -- a simple, case-insensitive, whitespace-normalized
substring match, **not** fuzzy or embedding-based matching -- and returns a
single combined bounding box spanning those words, or `None` if no match is
found. Because word text is joined with a single space regardless of the
original line layout, a needle that happens to span a line break in the
source PDF is still found correctly. It takes no component/asset
dependencies, so it can be called directly from other code, or copied
verbatim into another component per this repo's self-contained-component
convention.

## Requirements

`pdfplumber` for word extraction from the PDF's embedded text layer.
`tabulate` for the optional preview-metadata markdown rendering.

## Validation

`validation.level: code` -- verified against real PDFs generated via
`reportlab` with known text at known positions (never mocked, and
`pdfplumber` is never mocked), confirming real word text and real
coordinates come back, multi-page word explosion, `page_range` filtering,
the empty-text-layer (scanned-PDF) skip path, passthrough columns,
`find_text_bbox` matching a real multi-word snippet (including one that
spans a line break) and correctly returning `None` for absent text,
partitioning/backfill_policy parity with sibling components, and the
schema-change asset check.
