# `EmailApprovalGateComponent`

Email-native HITL approval gate. Sends the outbound approval-request email via SMTP; polls a shared mailbox via IMAP for replies matching approve/reject keywords from allowlisted approvers; writes the standard JSON approval token on quorum. Composes with [`HumanApprovalGateComponent`](../human_approval_gate) via a shared `approval_dir` — email side handles posting + reply polling + quorum; the existing gate consumes the resulting token unchanged.

## Why IMAP polling (not SES-inbound / webhook)

Interactive email delivery notifications (SES inbound → S3 → Lambda, Postmark/SendGrid inbound parse) require **public HTTPS endpoints** and provider-specific setup — a bad fit for Dagster+ Serverless where containers are ephemeral. IMAP polling works against any mailbox (Gmail, Office 365, Zoho, self-hosted Postfix) with just credentials, and is **completely outbound-plus-poll** — no incoming webhooks.

Trade-off: 30-60s approval-detection latency vs. instant push. Fine for humans.

## Reply detection

For each posted-but-unresolved partition, the sensor scans the IMAP mailbox for messages whose `In-Reply-To` or `References` header matches the outbound `Message-ID`. On match, it classifies the reply as approve / reject by:

1. **Subject tagged**: `[APPROVE ...]` or `[REJECT ...]` at the start (case-insensitive).
2. **Body first line**: `APPROVE` or `REJECT` as the first non-blank, non-quoted line.

Approvers can reply "APPROVE — LGTM" in the body OR use a subject-tagged reply from mobile without opening the thread. Both work.

## Emits

1. **`{asset_name}_posted` asset** (partitioned). Materialization sends the outbound email(s) via SMTP, stores `message_id + subject + sent_at` in a sidecar file. Idempotent on re-materialize (checks sidecar first, doesn't resend).
2. **`{asset_name}_watcher` sensor** (default_status: RUNNING). Polls IMAP every `poll_interval_seconds`, counts approve/reject replies from `approver_allowlist`, writes the JSON approval token when quorum lands.

## Storage backend

Same fsspec-based abstraction as the other approval gates. `approval_dir` accepts local paths OR cloud URIs (`s3://`, `gs://`, `abfs://`). On Dagster+ Serverless, use cloud URIs.

## Common provider recipes

### Gmail (personal or Google Workspace)

- SMTP: `smtp.gmail.com` port 587 (`smtp_use_tls: true`)
- IMAP: `imap.gmail.com` port 993 (`imap_use_ssl: true`)
- Auth: **App Password** required (Account → Security → App passwords). Regular password won't work with 2FA-enabled accounts.
- Same App Password works for both SMTP + IMAP → point `smtp_username_env_var` + `imap_username_env_var` at the same env var, ditto for the password.

### Office 365 / Outlook.com

- SMTP: `smtp-mail.outlook.com` port 587 (TLS)
- IMAP: `outlook.office365.com` port 993 (SSL)
- Basic auth is being deprecated for enterprise tenants. Personal outlook.com accounts still allow App Passwords. Enterprise deployments should route through a service that fronts Microsoft Graph API (out of scope for this component's v1).

### Zoho

- SMTP: `smtp.zoho.com` port 465 (SSL — set `smtp_use_tls: false` since 465 is SSL-from-connect, not STARTTLS)
- IMAP: `imap.zoho.com` port 993

### Self-hosted Postfix + Dovecot

- Standard IMAPS 993 / SMTP 587 STARTTLS. Works out of the box.

## Example

```yaml
type: dagster_community_components.EmailApprovalGateComponent
attributes:
  asset_name: prod_deploy_approval
  upstream_asset_key: candidate_deploy_manifest
  approval_dir: "s3://my-org-approvals/prod-deploys/"

  # SMTP (outbound)
  smtp_server: smtp.gmail.com
  smtp_port: 587
  smtp_use_tls: true
  smtp_username_env_var: SMTP_USER
  smtp_password_env_var: SMTP_PASS
  from_email: dagster-approvals@example.com
  to_emails:
    - alice@example.com
    - bob@example.com
    - carol@example.com

  # IMAP (inbound polling — same account works if it's a shared mailbox)
  imap_server: imap.gmail.com
  imap_port: 993
  imap_use_ssl: true
  imap_username_env_var: SMTP_USER
  imap_password_env_var: SMTP_PASS

  required_approvers: 2
  approver_allowlist: [alice@example.com, bob@example.com, carol@example.com]
  timeout_hours: 24
  on_timeout: escalate
  escalate_email: platform-oncall@example.com

  partition_type: static
  partition_values: "us-east, eu-west, apac"
```

Approvers reply "APPROVE — deploy looks good" (or subject-tag `[APPROVE us-east]`) — the sensor picks it up on next tick and writes the token.

## Composes with

- **`human_approval_gate`** — downstream gate that consumes the JSON approval token this sensor writes. Point both at the same `approval_dir`.
- **`slack_approval_gate` / `teams_approval_gate` / `multi_approver_gate`** — sibling approval mechanisms. Use ONE per partition (they all write to `<safe_partition_key>.json`).

## What doesn't work in v1

- **OAuth 2.0 / modern-auth email providers** — Office 365 tenants that have disabled Basic Auth can't use this component yet. Follow-up: MSAL device-flow auth against Graph API.
- **HTML email replies** — v1 extracts plain-text body only; HTML-only replies get their tags stripped and the body scanned as text. Usually fine; occasionally an HTML-only "Approved!" click on a rich-text reply might not classify.
- **Message threading without `In-Reply-To`** — some old mail clients don't set `In-Reply-To` on replies. The sensor searches both `In-Reply-To` and `References` headers; if neither is set, the reply won't match. Ask approvers to use "Reply" not "New message with subject".
