# Financial Table Extractor

Extract real table structure -- actual rows of actual cell strings -- from a
column of PDF file paths or PDF bytes using `pdfplumber`, entirely locally and
with zero LLM cost by default.

## Why this exists, and why it's different from `document_layout_analyzer`

`document_layout_analyzer` uses a HuggingFace object-detection model
(layoutlmv3 or similar) to return a BOUNDING BOX per detected table region,
plus a confidence score. That tells you roughly where a table sits on the
page. It does **not** tell you what's inside it -- no rows, no columns, no
cell values. Bounding-box detection and table-structure extraction are
genuinely different, and the weaker one (a box) should not be mistaken for
the stronger one (real structure).

This component extracts the stronger thing: `pdfplumber`'s
`page.find_tables()` derives real rows of real cell strings from the PDF's
own line/text geometry -- no model, no LLM call, no guessing. `find_tables()`
(not just `extract_tables()`) is used specifically because it additionally
returns each table's bbox and row/cell geometry alongside `.extract()`'s cell
values, at no extra cost. For financial documents in particular (bank
statements, SEC filings, balance sheets) this is a cheaper, more honest, and
usually more accurate answer than either an LLM or an object-detection model.

## `vertical_strategy` / `horizontal_strategy`

pdfplumber's own documented table-detection knobs, passed straight through --
not hidden or hardcoded -- defaulting to pdfplumber's own defaults
(`"lines"` / `"lines"`):

- `"lines"` / `"lines_strict"` -- detect edges from actual drawn rules on the
  page. Works well for tables with visible borders, which covers most
  financial documents in practice.
- `"text"` -- detect edges from text alignment / whitespace instead, with no
  reliance on drawn lines. Works better for borderless / whitespace-aligned
  tables, but is a fuzzier heuristic and less reliable than `"lines"` -- a
  real, well-known pdfplumber tradeoff, not papered over here.
- `"explicit"` -- pdfplumber's advanced mode where you supply exact
  coordinates yourself; rarely needed since this component has no
  coordinate-list field.

## Output shape: one row per detected table

```yaml
type: dagster_community_components.FinancialTableExtractorComponent
attributes:
  asset_name: extracted_financial_tables
  upstream_asset_key: raw_pdf_files
  column: file_path
  vertical_strategy: lines
  horizontal_strategy: lines
  min_rows: 2
  min_cols: 2
```

Every detected table (after the `min_rows` / `min_cols` filter) becomes its
own output row:

| Column | Meaning |
|---|---|
| *(passthrough columns)* | Every upstream column except `column`, by default -- override with `passthrough_columns` |
| `table_index` | 0-based index of this table within its source document |
| `page_number` | 1-based PDF page number the table was found on |
| `row_count` | Number of rows pdfplumber extracted for this table |
| `col_count` | Max number of columns across the table's rows |
| `table_data` | JSON string: a list of lists of cell strings. A cell that pdfplumber reports as `None` stays `null` in the JSON -- never coerced to `""`, since that would lose the real distinction between a genuinely empty cell and missing data. |
| `header_row_json` | JSON of `table_data`'s first row, for convenience. This is a heuristic guess at a header, not a guarantee the first row actually is one. |
| `table_markdown` | Markdown rendering of the table (via pandas `.to_markdown()`) for the Dagster UI preview and for an LLM to read later without re-parsing JSON. |

## Noise filtering (`min_rows` / `min_cols`)

pdfplumber's table detector is a known source of single-cell / near-empty
false-positive "tables" -- decorative rules, boxed callouts, stray ruled
lines that aren't really tabular data. `min_rows` / `min_cols` (default 2/2)
drop these before they reach the output.

## Optional LLM enrichment (`classify_tables`, off by default)

The default path is fully free, local, and zero-LLM-cost. Set
`classify_tables: true` to additionally label each detected table -- ONE
litellm call per table (not per document):

```yaml
attributes:
  classify_tables: true
  table_labels: [balance_sheet, income_statement, cash_flow_statement, other]
  classification_model: gpt-4o-mini
  api_key_env_var: OPENAI_API_KEY
```

Each row then gets a `table_label` column (null if that table's
classification call failed -- logged as a warning, never guessed). With
`classify_tables: false` (the default), `table_label` is absent entirely and
no litellm call is made.

## Requirements

`pdfplumber` for the default path (table detection + extraction). `tabulate`
for `table_markdown` rendering via pandas `.to_markdown()`. `litellm` is only
needed when `classify_tables=True` -- the default path makes no LLM call at
all.

## Validation

`validation.level: code` -- verified against real PDFs with actual bordered
tables generated via `reportlab`'s `Table`/`TableStyle(GRID)` (not mocked),
confirming real row/column counts and real cell values come back, that
`vertical_strategy="text"` vs `"lines"` behave differently on borderless vs
bordered tables, that `min_rows`/`min_cols` filter out small false positives,
and that `None` cells are preserved as JSON `null` rather than collapsed to
empty strings. `classify_tables` is verified with only `litellm.completion`
mocked (never pdfplumber, never the PDF): `classify_tables=False` makes zero
calls, `classify_tables=True` makes exactly one call per detected table.
