# Knowledge Base Eval

Golden-set retrieval quality as a first-class, checked asset -- against whatever a knowledge
base's search resource returns RIGHT NOW, not a point-in-time snapshot.

Deliberately **not** built on `rag_eval`: that component is tied to `vector_index_snapshot`'s
own on-disk ChromaDB snapshot directories, keyed by a `DynamicPartitionsDefinition` partition
(a real, different design for a real, different use case -- rollback-by-partition). This
component evaluates a LIVE `KnowledgeSearchResource` (from `knowledge_search_server`) or
`HybridKnowledgeSearchResource` (from `hybrid_knowledge_search_server`) resource instead, so it
works with any vector store those components support, and with graph-assisted (hybrid) search,
with no snapshot directory involved at all.

## `search_resource_key`

A plain Dagster resource key, resolved the normal way (`context.resources.<key>`). **There is
no special `<kb>_hybrid_knowledge_search` naming convention anywhere in this repo** (checked
directly) -- whatever key you registered `knowledge_search_server`'s or
`hybrid_knowledge_search_server`'s own `resource_key` under is what you point this at. Both
resources' `.search(query, top_k=k)` return shapes are dispatched automatically:
`{"chunks": [...]}` (KnowledgeSearchResource) or `{"passages": [...], "triples": [...]}`
(HybridKnowledgeSearchResource) -- both list items share `chunk_id`/`text`/`score`/`source`/
`doc_id`.

## Scoring

Each `golden_set` item is `{question, expected_terms?, expected_sources?}` -- both optional
fields may be omitted per question:

- **`score`**: fraction of `expected_terms` found (case-insensitive substring match) anywhere
  in the top-k results' text. A question with no `expected_terms` scores `1.0` (nothing to
  miss, not a failure).
- **`hit` / `rank`**: whether any of `expected_sources` matches a result's `source`, `doc_id`,
  OR `chunk_id` (any one matching counts), and the 1-indexed rank of the first such match.
  Both are `None` (not `False`/`0`) when a question has no `expected_sources` -- "not
  applicable" is tracked separately from "missed".

## Metadata

- `eval_summary` (JSON): `{score, hit_rate, questions, passed, k}` -- `score` is the mean
  per-question score; `hit_rate` is the fraction of hit-applicable questions (those with
  `expected_sources`) that hit; `passed` is the same `score >= min_score` verdict the asset
  check also evaluates.
- `eval_results` (JSON list): `{question, score, hit, rank, matched_terms, missing_terms,
  sources}` per question. `sources` is each top-k result's `source`/`doc_id`/`chunk_id`
  **only** -- passage text never lands in metadata, anywhere, ever.

## The `<asset_name>_quality_check` asset check

Fails when `eval_summary.score` is below `min_score` (enforced even on the very first real
eval -- same precedent `rag_eval`'s own check sets), OR regresses by more than `regression_pct`
(percentage **points** of the 0-1 score -- `regression_pct: 10` means "may not fall more than
0.10 below the prior real eval") against the most recent PRIOR materialization that itself has
`eval_summary` metadata. An ad hoc `{question}` run's materialization has no `eval_summary` at
all, so it's transparently skipped when walking back for "the previous real eval" -- it can
never become a false regression baseline, and the check always passes trivially for the ad hoc
run itself (nothing to evaluate). Only the regression half has nothing to compare against on
the very first real eval, so only that half passes trivially then.

## Run-config override: ad hoc questions

```yaml
# Launchpad / API run config:
ops:
  <asset_name>:
    config:
      question: "What's our refund policy for duplicate charges?"
```

Runs that ONE question through the exact same scoring function (no `expected_terms`/
`expected_sources` -- those only come from `golden_set`) and reports it under
`ad_hoc_question`/`ad_hoc_result` metadata instead of `eval_summary`/`eval_results`. Never
touches `golden_set`, never writes eval history, and (per the asset check's own skip-ad-hoc-runs
behavior above) can never corrupt the regression baseline.

## Dependency

`upstream_asset_key` is declared as a lineage-only `deps` edge (no data passed at runtime) to
the knowledge base's own base asset, so this eval shows up downstream of it in the catalog and
re-evaluates whenever you rebuild the base asset.

## Example

```yaml
type: dagster_community_components.KnowledgeBaseEvalComponent
attributes:
  asset_name: support_kb_eval
  knowledge_base: support_kb
  search_resource_key: hybrid_knowledge_search
  upstream_asset_key: support_kb
  k: 5
  min_score: 0.6
  regression_pct: 10.0
  golden_set:
    - question: "How do I configure a retry policy?"
      expected_terms: ["retry_policy", "max_retries", "backoff"]
      expected_sources: ["docs/retry-policies"]
    - question: "What is a dynamic partition?"
      expected_terms: ["DynamicPartitionsDefinition", "partition_key"]
```
