# KnowledgeGraphSearchServerComponent

Lets an agent search a knowledge graph built by `KnowledgeGraphBuilderComponent`,
via `search_entities`/`get_entity`/`get_neighbors`/`find_path`/`top_entities`
tools returning plain JSON. Same dual-mode shape as `knowledge_search_server`:

1. An importable `KnowledgeGraphSearchResource`, registered under `resource_key`.
2. A self-contained stdio MCP server: `python -m
   dagster_community_components.assets.ai.knowledge_graph_search_server.component`.

`mcp_server_resource_key`, if set, ALSO registers a stdio MCP-server-shaped
resource so any `mcp_servers`-aware component (`mcp_tool_call`,
`mcp_tool_picker`, the agent components, `agentic_pipeline`) can reference
this server via `server_resource_key` instead of hand-writing an inline
command+env entry.

## Backends

- **`provider: networkx`** (default): loads the graph file **once, at
  server start**, into memory. There is no live-reload -- restart the
  server after the builder rewrites the graph file to pick up the change.
- **`provider: neo4j`** / **`provider: falkordb`**: issues a live,
  read-only query per tool call instead (no preload). neo4j queries run
  under `session(default_access_mode="READ")`; FalkorDB's Python client has
  no separate read-only session mode, so this is enforced only by never
  issuing a write clause in the Cypher below. Neither backend is exercised
  against a live server in this repo's own test suite (no account/service
  available here) -- reviewed directly against the `neo4j` driver and
  `falkordb-py`'s documented `select_graph`/`query` API.
- **`provider: sql_tables`**: reads `knowledge_graph_builder`'s own
  `execution_mode='sql'` output tables (`<output_table>_nodes`/`_edges`)
  directly -- same 3 dialects (`sql_dialect`: `snowflake_cortex`,
  `bigquery`, `databricks`). Issues a live, direct vendor-client connection
  per tool call (`snowflake.connector`, `google.cloud.bigquery`,
  `databricks.sql`) using `snowflake_*`/`databricks_*`/`bigquery_project_id`
  fields -- not a registered Dagster resource reference, since this
  resource's methods must also work from the standalone stdio MCP server,
  which has no Dagster execution context. `get_neighbors`/`find_path` use a
  `WITH RECURSIVE` CTE (BigQuery requires the `RECURSIVE` keyword;
  Databricks' recursive CTEs need Runtime 17.1+, GA August 2025 -- an older
  runtime rejects the keyword outright). No alias matching and no
  per-chunk evidence for `get_neighbors`'s distance join (the `sql_tables`
  node/edge schema has neither an `aliases` column nor per-chunk evidence
  arrays -- those are python-mode-only). Every generated statement is
  checked for real syntactic validity with `sqlglot.parse(sql,
  read=<dialect>)`; the recursive-traversal logic itself (direction-
  agnostic join, cycle prevention, depth-bounded BFS, shortest-path
  tie-breaking) is executed for real against DuckDB as a stand-in.

## Tools

| Tool | Returns |
|---|---|
| `search_entities(query, type?)` | Fuzzy name/alias substring search, optionally filtered by type |
| `get_entity(name)` | Exact-name lookup: type, aliases, mention_count, and every in/out relation with its evidence |
| `get_neighbors(name, hops=1, relation?)` | Entities within `hops` (capped at 3) of `name`, optionally filtered by relation |
| `find_path(source, target, max_hops=4)` | Shortest path (capped at 6 hops) between two entities |
| `top_entities(type?)` | Entities ranked by `mention_count`, optionally filtered by type |

Every list-returning tool is capped by `max_results` (default 50).

## Example YAML

Pair with a `knowledge_graph_builder` that wrote to the same `path`/`graph_name`:

```yaml
type: dagster_community_components.KnowledgeGraphSearchServerComponent
attributes:
  resource_key: support_kg_search
  mcp_server_resource_key: support_kg_search_mcp
  provider: networkx
  path: /tmp/support_kg.json
  graph_name: support_kg
  max_results: 50
```

Then an agent component can reference it:

```yaml
type: dagster_community_components.AnthropicAgentComponent
attributes:
  asset_name: support_agent
  mcp_servers:
    - server_resource_key: support_kg_search_mcp
```

### neo4j

```yaml
type: dagster_community_components.KnowledgeGraphSearchServerComponent
attributes:
  provider: neo4j
  uri: bolt://localhost:7687
  username_env_var: NEO4J_USERNAME
  password_env_var: NEO4J_PASSWORD
  graph_name: support_kg
```

### sql_tables

Pair with a `knowledge_graph_builder` whose `execution_mode='sql'` wrote to the
same `output_table`:

```yaml
type: dagster_community_components.KnowledgeGraphSearchServerComponent
attributes:
  provider: sql_tables
  sql_dialect: snowflake_cortex
  output_table: support_kg
  snowflake_account_env_var: SNOWFLAKE_ACCOUNT
  snowflake_user_env_var: SNOWFLAKE_USER
  snowflake_password_env_var: SNOWFLAKE_PASSWORD
  snowflake_database: ANALYTICS
  snowflake_warehouse: COMPUTE_WH
```

## Running the server directly

```
python -m dagster_community_components.assets.ai.knowledge_graph_search_server.component
```

Env: `KNOWLEDGE_GRAPH_SEARCH_PROVIDER` (default `networkx`),
`KNOWLEDGE_GRAPH_SEARCH_PATH` (networkx), `KNOWLEDGE_GRAPH_SEARCH_URI` /
`_USERNAME_ENV_VAR` / `_PASSWORD_ENV_VAR` / `_DATABASE` (neo4j),
`KNOWLEDGE_GRAPH_SEARCH_HOST` / `_PORT` (falkordb),
`KNOWLEDGE_GRAPH_SEARCH_GRAPH_NAME`, `KNOWLEDGE_GRAPH_SEARCH_MAX_RESULTS`
(default 50).
