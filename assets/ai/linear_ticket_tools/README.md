# `LinearTicketToolsComponent`

Team-scoped Linear ticket tools for engineering agents, with a duplicate-check before filing and
an optional practice mode -- the Linear half of "filing tools for GitHub issues and Linear
tickets, scoped to one repo or team, with a duplicate check that ignores generic words and matches
titles only."

| Tool | Answers / does |
|---|---|
| `find_issues(query)` | open tickets the agents already filed whose title matches `query`'s main words (generic project words dropped first) -- a duplicate-check, call before `create_issue` |
| `create_issue(title, body)` | files a ticket in the one configured team |
| `list_agent_issues()` | open agent-filed tickets with their bodies -- for announcing elsewhere (e.g. Slack) |

## Scoped to one team

Every query/mutation is pinned to `team_id` -- a prompt cannot point the tools at another team.

## Duplicate-check uses a description marker, not a label

A personal Linear API key may lack permission to create labels (confirmed: Linear's own docs note
label creation can require elevated access). `find_issues`/`list_agent_issues` identify
agent-filed tickets by a `Filed by an engineering agent.` marker appended to the description
instead -- this works even when the key can't create or read labels at all. When label creation
*does* succeed, the ticket is also labeled `engineering-agent` (nice-to-have, never relied upon).

`find_issues` drops a handful of generic project words (`dagster`, `assets`, `asset`, `project`,
`improve`, `improvements`, `reliability`) before searching, so a query full of common vocabulary
doesn't "match" nearly every prior ticket by coincidence. If every word in a query is generic (or
too short), `find_issues` returns no results without even sending a search -- not an error.

## Auth

`api_key_env_var` (default `LINEAR_API_KEY`) holds a personal API key or OAuth2 access token, sent
**raw** in the `Authorization` header -- Linear does **not** want a `Bearer ` prefix (same
convention already established by `linear_ingestion`/`resources/linear_resource` in this repo).
Linear has no REST surface at all; GraphQL (`https://api.linear.app/graphql`) is the only way in.

## Practice mode (`practice_mode_env_var`)

Same mechanism as `github_pr_tools`' own `practice_mode_env_var`: set it to the NAME of an env var
(not a value templated into this field) your deployment can scope per-environment -- e.g. set it
in a Dagster+ **branch deployment** and leave it unset in the full deployment. When that named env
var holds anything other than `''`/`'0'`/`'false'`/`'no'`/`'off'` (case-insensitive), `create_issue`
returns `{"practice_mode": true, "would_open": "linear_ticket", "title": ..., "url": null}` instead
of actually filing a ticket. The env var is read fresh, by name, inside the tool call -- not
templated into a typed component field at YAML-resolve time (see `github_pr_tools`' own README for
the real bug this design avoids).

## Using from Claude Code (`claude mcp add`)

```bash
export LINEAR_TICKET_TOOLS_TEAM_ID=your-team-id
export LINEAR_API_KEY=lin_api_...
claude mcp add linear-ticket-tools -- python -m dagster_community_components.assets.ai.linear_ticket_tools.component
```

See `main()`'s docstring in `component.py` for the full list of `LINEAR_TICKET_TOOLS_*` env vars
the standalone server reads.

## As a Dagster resource

```yaml
type: dagster_community_components.LinearTicketToolsComponent
attributes:
  team_id: "{{ env.LINEAR_TEAM_ID }}"
  api_key_env_var: LINEAR_API_KEY
```

Then `context.resources.linear_ticket_tools.call("find_issues", {"query": "..."})`.

## Referencing it by key (`mcp_server_resource_key`)

```yaml
type: dagster_community_components.LinearTicketToolsComponent
attributes:
  team_id: "{{ env.LINEAR_TEAM_ID }}"
  api_key_env_var: LINEAR_API_KEY
  mcp_server_resource_key: linear_ticket_tools_mcp
```

Any `mcp_servers`-aware component (the agent components, `mcp_tool_call`, `mcp_tool_picker`, ...)
can then reference this toolset via `server_resource_key: linear_ticket_tools_mcp`.

## Safety

Every call is pinned to the configured `team_id` -- a prompt cannot point the tools at another
team. `create_issue` only ever files a ticket, never updates or deletes one. Failures come back as
`{"error": "..."}`, never an exception.
