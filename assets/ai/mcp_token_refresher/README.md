# McpTokenRefresher

The **one writer** for a `token_store='state'` hosted-MCP OAuth token
([`HostedMcpServerComponent`](../hosted_mcp_server/README.md)'s alternative to a flat `oauth_dir`
folder). Refreshes via the stored refresh token and uploads a new version to Dagster's own
`defs_state_storage` — everything else (the stdio proxy subprocess, any asset reading the
state-backed token) only ever reads the latest version and never refreshes.

## Why a job, not an asset

A token refresh has no durable data product or catalog lineage worth tracking — it's a plain
side-effecting maintenance action, so this component emits a `@dg.job` (one `@dg.op`), the same
shape as this repo's other op/job-based maintenance components, not an asset-reconciliation one.

## Why a separate, single-writer refresher

A hosted-MCP server's refresh token is typically **replaced on every refresh** — a stale copy
held elsewhere dies after first use. `defs_state_storage`'s own `set_latest_version` is
last-writer-wins, so two processes refreshing the same key at the same time would invalidate
each other's result. This component is designed to be the **only** thing that ever refreshes a
given `state_key` — set `cron_schedule` (an inline field here, not the usual "pair with
`CronScheduleComponent`" convention, since that component only targets asset selections, not
plain jobs) to a cadence comfortably inside the access token's own lifetime (commonly ~1–8h). The
emitted schedule defaults to **running** (unlike most schedules in this repo), since an
un-started refresher silently defeats this component's entire purpose:

```yaml
type: dagster_community_components.McpTokenRefresherComponent
attributes:
  job_name: linear_mcp_token_refresh
  state_key: linear
  cron_schedule: "0 */4 * * *"   # every 4 hours
```

## If the token is already expired and the refresher hasn't run

`HostedMcpServerComponent` (and anything else reading this `state_key` directly) never
refreshes — it fails with a clear "the scheduled refresher has not run recently enough" message
instead of silently loading with a stale/expired token. Check this refresher job's own run
history for the `state_key` in question.

## Pruning old versions — not portable, documented honestly

Dagster's `DefsStateStorage` interface has **no generic method to list or delete prior
versions** for a key (confirmed from the abstract base class's own docstring on
`set_latest_version`: *"Stored bytes for prior versions are not cleaned up by this call;
backends that care about orphan cleanup should handle it out-of-band."*). This component cannot
portably prune old versions itself. Configure a lifecycle/retention rule at the storage backend
(e.g. an S3 bucket lifecycle rule under the `__state__/<key>/` prefix) if you need this.

## This blob is a secret

The stored blob grants everything the signed-in person can see on the target MCP server — the
same blast radius as the refresh token itself. Your `defs_state_storage` backend needs the same
access control you'd give any other secret store.

## Local filesystem storage is explicitly unsupported across processes

Dagster's own `UPathDefsStateStorage` raises a clear error if state is read from a different
process than wrote it while using a **local filesystem** `base_path` — confirmed directly in its
source. Use a real remote blob backend (`s3://`, `gs://`, `azure://`, `abfs://`) for
`defs_state_storage` if this refresher and the components reading its `state_key` might ever run
in different processes or machines, which is the normal case in any real deployment (a scheduled
run, the code-server process, and an agent's own run are rarely the exact same process).

## Sign-in is separate

This component never does the initial OAuth sign-in — that's
[`mcp_oauth_login --state-key <key>`](../../../resources/mcp_oauth_login/__main__.py)'s job
(run once, interactively, before this refresher's first scheduled tick).
