# `ModelProviderComponent`

Declare an LLM provider credential once, and get its health back as a real Dagster object:
an observable source asset reporting the models it offers and whether its API key is set,
plus an api-key-presence asset check (always on) and an opt-in live-connectivity asset
check that makes one real models-list API call using the key.

A companion to the agent components ([`openai_agent`](../openai_agent),
[`anthropic_agent`](../anthropic_agent), [`litellm_agent`](../litellm_agent),
[`gemini_agent`](../gemini_agent)): those read their API key fresh from an env var at call
time and never validate it ahead of a real run. This component makes that validation
inspectable in the Dagster catalog instead of discovering a bad key mid-agent-run.

Engineering-agents feedback round 3, item 6: *"a 'model provider' component (key env var +
presence check + optional test-call asset check + models offered)."*

## Why LiteLLM, not a bespoke client per provider

Built on `litellm` (already a dependency of `litellm_agent`) rather than one hand-rolled
HTTP client per provider:

- **Models offered** uses `litellm.get_valid_models(custom_llm_provider=...)` -- LiteLLM's
  own static per-provider model catalog. Passed an explicit provider, it returns the
  catalog unconditionally (no network call, no credential needed), so this is always free
  to compute and never fails.
- **Live connectivity** (`test_call: true`) reuses the exact building blocks LiteLLM's own
  `get_valid_models(check_provider_endpoint=True)` uses internally
  (`ProviderConfigManager.get_provider_model_info` + `provider_config.get_models()`)
  rather than that top-level function itself, which silently swallows every exception down
  to an empty list. Calling the building blocks directly surfaces the real auth/
  connectivity error in the check's failure message.

Not every provider has a live models-list endpoint plumbed into LiteLLM. When
`get_provider_model_info` returns `None`, or `get_models()` raises `NotImplementedError`
(confirmed for several providers, e.g. `azure`, `groq`, `cohere`, `mistral`,
`vertex_ai`-style backends), the live check reports `supported: false` and still **passes**
-- that's a statement about this provider, not something the user did wrong. `bedrock` is
explicitly special-cased the same way: its LiteLLM `get_models()` is a permanent no-op
returning `[]` (confirmed by reading the source -- Bedrock auth is AWS SigV4, not a bearer
key, so there's nothing for this function to check), so an empty result there is never
misreported as "verified."

## Catching a bad key before a real agent run hits it

`test_call`'s live-connectivity check only runs when something materializes this asset (or its
checks). Left unscheduled, a credential that expired weeks ago won't actually be *checked* until
the next agent run happens to need it -- which is exactly the failure mode this component exists
to catch ahead of time. Two pieces make that automatic:

1. **Schedule the check itself**, not the whole asset -- [`cron_schedule`](../../../schedules/cron_schedule)
   has an `asset_check_keys` field for exactly this (no need to re-materialize `asset_name`, which
   does nothing beyond reporting static catalog info anyway):

   ```yaml
   type: dagster_community_components.CronScheduleComponent
   attributes:
     schedule_name: openai_key_health_check
     cron_expression: "0 * * * *"        # hourly
     asset_check_keys: ["openai_provider"]  # this component's asset_name
     default_status: RUNNING
   ```

2. **Alert on the check failing.** Dagster+'s **Asset** alert type targets by asset key,
   selection, or group (not by a specific check name), and fires on both materialization
   failures and asset check failures for whatever it's scoped to. Scope one to this
   component's `group_name` (`model_providers` by default, or your own `group_name`/`asset_tags`)
   so a failed `_live_connectivity` check pages the same way a failed agent run would, without
   waiting for an agent to discover the key is bad.

Combined, a key that expires at 3am gets caught by the next hourly tick, not by whichever
on-call engineer's agent run happens to need it first.

## Example

```yaml
type: dagster_community_components.ModelProviderComponent
attributes:
  asset_name: openai_provider
  provider: openai
  api_key_env_var: OPENAI_API_KEY
  test_call: true
```

Materializing `openai_provider` reports `api_key_present` and `models_offered` as
observation metadata. Its generated checks:

- `openai_provider_api_key_present` -- fails if `OPENAI_API_KEY` is unset. Free, always on.
- `openai_provider_live_connectivity` -- only generated when `test_call: true`. Makes one
  real models-list call to OpenAI using the live key; fails with the provider's own error
  message on a bad/expired key, passes with the live model list on success.
