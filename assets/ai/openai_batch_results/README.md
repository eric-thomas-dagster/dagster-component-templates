# OpenAI Batch Results

> **🔑 API key required.** Set `OPENAI_API_KEY` (or point `api_key_env_var` at an alternate env var).

Fetch and parse a completed OpenAI Batch API run. Final component of the `openai_batch_submit` → `openai_batch_status_sensor` → `openai_batch_results` trio.

## Purpose

Downloads the batch's output file (and, if present, its separate error file), parses each JSONL line, and returns one row per request: `custom_id`, `raw_output` (the assistant's text, or `None` on error), `error` (the error text, or `None` on success).

This asset only runs once `openai_batch_status_sensor` confirms the batch is `completed` — but it also defends against someone materializing it manually too early: if `client.batches.retrieve(batch_id).status != "completed"`, it raises a clear error rather than returning partial/garbage data.

## batch_id: static or dynamic

`batch_id` can be set statically in YAML (for manual runs / backfills), or supplied dynamically via `config.batch_id` on each run — which is exactly how `openai_batch_status_sensor` wires it in, via `run_config={"ops": {<op_name>: {"config": {"batch_id": ...}}}}`. The dynamic value always wins when both are present.

## Typed output via `output_schema`

Set `output_schema` to a dotted path (`module.path:ClassName`, same convention as `assets/infrastructure/smart_retry`'s `kind: python` handling) pointing at a Pydantic model, and each row's `raw_output` is parsed as JSON and validated against it — on success, the model's fields are merged in as extra columns.

**A bad answer never fails the row or the asset.** Any failure — invalid JSON, a validation error, anything — just sets `invalid_output=True` for that row and leaves the typed columns null, with `raw_output` preserved as the raw text. This mirrors the same semantics Airflow's batch-results pattern is known for: a bad model response gets flagged, not thrown away and not allowed to take down the whole run.

```yaml
type: dagster_component_templates.OpenaiBatchResultsComponent
attributes:
  asset_name: support_reply_results
  output_schema: "my_project.schemas:SupportReply"
```

## Output metadata

Every materialization reports `row_count`, `succeeded_count`, `errored_count`, and `invalid_output_count` so you can see batch health at a glance in the Dagster catalog without opening the DataFrame.
