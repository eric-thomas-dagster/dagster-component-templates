# OpenAI Batch Submit

> **🔑 API key required.** Set `OPENAI_API_KEY` (or point `api_key_env_var` at an alternate env var).

Submit a DataFrame of prompts to OpenAI's async **Batch API** (`POST /v1/batches`) — the ~50%-cheaper endpoint for bulk LLM calls, with turnaround up to 24 hours. This is a genuinely different integration from `litellm_batch_completion` / `litellm_embedding_batch` elsewhere in this repo: those make synchronous chat-completion calls in a thread pool and call that "batch" (batch-of-threads); this component submits one real OpenAI Batch job and lets OpenAI process it asynchronously on its own infrastructure.

## Purpose

`OpenaiBatchSubmitComponent` reads an upstream DataFrame of prompts, builds one JSONL line per row (`{"custom_id", "method", "url", "body"}`), uploads it as a `purpose="batch"` file, and creates a batch against `/v1/chat/completions`. It's the first of three paired components:

1. **`openai_batch_submit`** (this one) — submits the batch, returns immediately by default.
2. **`openai_batch_status_sensor`** — polls OpenAI for completion and triggers a job.
3. **`openai_batch_results`** — fetches + parses the completed batch's output.

## Content-addressed idempotency (not run_id)

Every materialization computes `prompts_hash = sha256(sorted [[custom_id, prompt], ...])` over the exact set of prompts being submitted, and stamps it into both the batch's own `metadata={"prompts_hash": ...}` (visible on OpenAI's side) and the asset's Dagster materialization metadata. On every subsequent run, the asset reads back its **own prior materialization** (`context.instance.get_latest_materialization_event(context.asset_key)`):

- **Same hash as last time** → this is a retry or a redundant re-run of identical input. The prior batch is reattached (`batches.retrieve`), never resubmitted — so retries and manual re-materializations are idempotent even though batches cost money and take hours.
- **Different hash** → the upstream prompts changed. The stale batch is best-effort cancelled (wrapped in `try/except`, since it may already be terminal) and a fresh batch is submitted.
- **No prior batch** → fresh submit.

A `run_id`-keyed approach would not give you this: `run_id` changes on every run, including retries of the exact same input, so it can't distinguish "this is the same work, don't resubmit" from "this is new work."

## Two modes

- **`wait_for_completion: false`** (default) — submit-or-reattach, then return immediately with a small manifest DataFrame (`batch_id`, `status`, `request_count`). No worker sits blocked for up to 24 hours. Pair with `openai_batch_status_sensor` + `openai_batch_results` to pick up the result once OpenAI finishes.
- **`wait_for_completion: true`** — poll to a terminal state (`completed` / `failed` / `expired` / `cancelled`), logging each status transition, and — if `completed` — inline-download and parse the output file, returning the full results DataFrame directly. Raises on timeout or on any other terminal status. Useful for small batches, tests, or backfills.

```yaml
type: dagster_component_templates.OpenaiBatchSubmitComponent
attributes:
  asset_name: support_reply_batch
  upstream_asset_key: support_tickets
  prompt_column: body
  id_column: ticket_id
  model: gpt-4o-mini
  system_prompt: "Draft a helpful, concise reply to this support ticket."
  wait_for_completion: false
```
