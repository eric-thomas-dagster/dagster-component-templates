# OpenaiLlmBatchComponent

Submit a DataFrame of prompts to OpenAI's async **Batch API** (`/v1/batches`)
— roughly half the price of the synchronous chat completions endpoint, in
exchange for turnaround that can take up to the full `completion_window`
(currently always 24h). This is a real integration with the batch endpoint
itself, not a synchronous call in a thread pool like `litellm_batch_completion`
elsewhere in this repo.

One component, three things happen automatically. Earlier iterations of
this split submit / sensor / results into three separate components that
had to be manually cross-wired (`watch_asset_key`, `results_asset_key`,
`job_name`) across three YAML blocks. A single `build_defs()` can return
assets *and* sensors together, so this component derives all of that wiring
internally from one `asset_name` — configure it once and the sensor "just
appears," already pointed at the right asset.

## Two modes

**`wait_for_completion: false`** (default) — the real deferred mode. Emits:
- `{asset_name}__submit` — builds the batch, submits it, returns a small
  manifest (`batch_id` / `status` / `request_count`).
- `{asset_name}` — the actual output. Stays dormant until triggered.
- `{asset_name}__batch_status_sensor` — polls the *live* batch status
  (never trusts stale cached metadata) and materializes `{asset_name}`
  directly via `RunRequest(asset_selection=...)` once the batch reaches a
  terminal state. No worker sits blocked waiting, and there's no
  `job_name`/companion job to define — the sensor targets the results
  asset by key.

**`wait_for_completion: true`** — a single asset named `asset_name` that
submits, polls synchronously to a terminal state, and returns the fully
parsed results DataFrame directly. No sensor is created in this mode.
Useful for small batches, tests, or backfills where you want everything
back in one materialization.

## Idempotency (retries don't pay twice)

A deterministic `prompts_hash` (sha256 over the sorted `(custom_id, prompt)`
pairs) is stamped into the submit asset's materialization metadata and read
back on every run:

- Same hash as last time → **reattach** to the existing batch
  (`batches.retrieve`), never resubmit.
- Different hash → the prior batch is stale: best-effort **cancel** it,
  then submit fresh.

This makes retries and redundant manual re-materializations safe — a
`run_id`-keyed scheme would not give you this, since a run_id changes every
time but content does not.

## Typed output

Set `output_schema` to a dotted path (`module.path:ClassName`) to a Pydantic
model. Each row's `raw_output` is parsed as JSON and validated against it;
on success the model's fields are merged in as extra columns. On **any**
failure (bad JSON, validation error) the row is marked `invalid_output=True`
with `raw_output` preserved as-is — it never fails the whole asset.

## Example

```yaml
type: dagster_component_templates.OpenaiLlmBatchComponent
attributes:
  asset_name: support_reply_results
  upstream_asset_key: support_tickets
  prompt_column: body
  id_column: ticket_id
  model: gpt-4o-mini
  system_prompt: "Draft a helpful, concise reply to this support ticket."
  wait_for_completion: false
```

Requires `OPENAI_API_KEY` (or whatever `api_key_env_var` names) in the
environment.

## Related

- **`litellm_batch_completion`** — synchronous per-row LLM calls in a
  thread pool. Use this component instead when the ~50% cost savings of
  the real Batch API matter more than immediate results.
- **`anthropic_llm_batch`** — the Anthropic Message Batches equivalent.
  Kept as a separate component rather than unified behind a `provider:`
  field, matching this repo's one-component-per-vendor convention; the
  two APIs differ enough underneath (file upload vs. direct JSON, a single
  `status` enum vs. a separate per-request `result.type`) that unifying
  wouldn't actually remove much code.
