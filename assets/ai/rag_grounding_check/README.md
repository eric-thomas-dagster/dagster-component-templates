# RAG Grounding Check

Verify RAG-generated answers are actually grounded in their retrieved source chunks — `rag_eval`'s sibling for **generation faithfulness** rather than retrieval quality. `rag_eval` asks "did we fetch the right chunks?"; this component asks "does the model's answer only say what those chunks actually support?"

Pairs naturally with `rag_pipeline`'s `generate` step output — same `query_column`/`answer_column`/`sources_column` shape, so you can point this straight at it.

```yaml
type: dagster_component_templates.RagGroundingCheckComponent
attributes:
  asset_name: support_bot_grounding
  upstream_asset_key: support_bot_answers
  mode: overlap
  min_grounding_score_threshold: 0.5
  regression_pct_threshold: 10.0
  max_fabrication_rate: 0.1
```

The attached asset check fails the run when the mean `grounding_score` drops below `min_grounding_score_threshold`, OR regresses by more than `regression_pct_threshold` percentage points against the immediately-prior materialization, OR the fabrication rate exceeds `max_fabrication_rate` — exactly `rag_eval`'s cross-materialization regression design, applied to generation instead of retrieval.

## Two ways to check groundedness

- **`mode: overlap`** (default): deterministic, free, no API key. Scores each answer by n-gram overlap (`ngram_size`, default trigrams) against its source chunks, plus a **fabricated-number check** — any number in the answer that doesn't appear anywhere in the sources (a concrete, common hallucination pattern: an invented or transposed statistic, e.g. "grew 45%" when the source says "grew 12%"). This matches dbt Labs' own stated philosophy for "grounding tests": deterministic and free, not another paid LLM call per test.
- **`mode: llm_judge`** (opt-in): any litellm-supported model (`llm_model`, default `gpt-4o-mini`) judges whether the answer is fully supported by the sources — costs money per row, but catches paraphrased claims that share no n-grams with their source yet are still ungrounded (or the reverse: claims that share n-grams but assert something the source never actually said).

Both modes always compute the fabricated-number check (it's free either way) and produce a `grounding_score` in `[0, 1]` on the same scale, so the asset check's thresholds mean the same thing regardless of which mode generated them.

## Ingestion

Two ways to get the query/answer/sources rows in, set exactly one:

- **`upstream_asset_key`**: point at `rag_pipeline`'s output, or any asset producing a DataFrame with `answer_column`/`sources_column`.
- **`source: {kind: warehouse_query, resource_key: ..., sql: ...}`**: pull already-generated answers directly via SQL — e.g. a table of logged production Q&A pairs. Works out of the box with `duckdb_resource` and any resource exposing `.get_engine()`/`.get_connection()`.

## Output columns

- `grounding_score` (float, `0.0`–`1.0`): higher is more grounded.
- `grounded` (bool): `grounding_score >= per_row_grounded_threshold`.
- `fabricated_numbers` (list): numbers present in the answer but nowhere in the sources — empty list means none found.
- `judge_reasoning` (`mode='llm_judge'` only): one-sentence explanation from the judge model.

Asset-level metadata: `mean_grounding_score`, `fabrication_rate`, `n_scored` (rows with a non-empty answer that were actually scored).

## Validation

`validation.level: code`.

**Live-verified (nothing mocked)**:
- `mode: overlap` scoring, on both genuinely-grounded and genuinely-ungrounded (fabricated-detail) answers.
- The fabricated-number detector, including a regression test for a real false-positive it originally had (`"Q3"` misread as the number `3` before a word-boundary fix).
- Cross-materialization regression detection (mirrors `rag_eval`'s design exactly): a first "good" materialization passes the asset check, a second "bad" one correctly detects the drop against the first and fails.
- `source: {kind: warehouse_query}` against a real DuckDB database.
- `max_fabrication_rate`, mutual-exclusivity, and invalid-`mode` validation guards.

**Mocked (no free/local backend exists for this)**:
- `mode: llm_judge` — `litellm.completion` is mocked; the prompt construction, JSON parsing, and score-mapping logic (`confidence` if grounded else `1 - confidence`) run for real.
