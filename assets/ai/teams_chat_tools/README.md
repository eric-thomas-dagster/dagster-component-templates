# teams_chat_tools

A chat-triggered agent run (see [`teams_agent_request_sensor`](../../../sensors/teams_agent_request_sensor))
knows almost nothing on its own -- its prompt only ever carries `{tag.<key>}` identifiers (team,
channel, thread, requester), never the actual message text. `get_thread()` is how the agent
actually reads the conversation: it fetches the live Teams thread, fresh, every time it's
called. No database, no caching -- there's nothing here to go stale or leak across runs. Teams
analog of [`slack_chat_tools`](../slack_chat_tools) -- no shared code, but the same design.

## Type

```
dagster_community_components.TeamsChatToolsComponent
```

| Tool | Does |
|---|---|
| `get_thread()` | The last `max_messages` messages in the thread this run is answering (root message + replies, merged and sorted), oldest first, as `{user, text, id, created_at}` rows. **No arguments** -- it always reads THIS run's own team/channel/thread; there is no tool argument the model could use to read a different conversation. |

## Why this always reads the right conversation without the model telling it to

`get_thread` takes no parameters on purpose. The team/channel/thread identifiers come from this
server process's own environment -- `TEAMS_CHAT_TOOLS_TEAM_ID` / `_CHANNEL_ID` / `_THREAD_ID` --
set via a `{tag.<key>}` placeholder (default: `{tag.teams/team_id}` / `{tag.teams/channel_id}` /
`{tag.teams/thread_id}`) resolved by the **calling agent's own** generic tag substitution, right
before it spawns this subprocess. Same trusted, server-side mechanism `dagster_workflow_tools`'
`launch_job` uses for its requester identity -- the model never supplies the team/channel/thread
itself, so it can't be tricked into reading a different conversation.

## Setup

```yaml
type: dagster_community_components.TeamsChatToolsComponent
attributes:
  mcp_server_resource_key: teams_chat_mcp
  oauth_state_dir: /var/dagster/teams_agent_oauth_state  # can share teams_agent_request_sensor's
  max_messages: 20
```

Then, in the agent's own `mcp_servers`:

```yaml
mcp_servers:
  - server_resource_key: teams_chat_mcp
```

`team_id_template`/`channel_id_template`/`thread_id_template` default to
`"{tag.teams/team_id}"` / `"{tag.teams/channel_id}"` / `"{tag.teams/thread_id}"` and are passed
through **verbatim** as this spawned server's env -- this component never resolves the
placeholder itself, the calling agent's substitution does.

## A real design difference from Slack: two calls, not one

Slack's `conversations.replies` returns a thread's root message AND its replies in one call, so
`slack_chat_tools` never needs to special-case "is this message the root." Microsoft Graph's
`.../messages/{id}/replies` returns **only replies** (confirmed against Microsoft's own
`chatmessage-list-replies` reference) -- the root is a separate resource entirely. So this
component makes two Graph calls every time (`GET .../messages/{thread_id}` for the root,
`GET .../messages/{thread_id}/replies` for the rest) and merges them client-side, sorted by
`createdDateTime`.

## Seeing which receipts a past answer came from (`receipts_db_path`)

Set `receipts_db_path` to the SAME SQLite file a [`teams_reply`](../../sinks/teams_reply)
instance (and the agent's `knowledge_search_server`/`hybrid_knowledge_search_server`) are
configured with, and `get_thread()` attaches a `receipt_ids` list to any message in the thread
that was posted by the bot itself (`from.application` present, Teams' analog of Slack's
`bot_id`) -- looked up from the small `context_receipt_message_links` table `teams_reply`
writes after posting (`platform="teams"`), never from parsing the message text. A user message
never gets this field. See `teams_reply`'s own README ("Closing the loop") for the full design.

## What this does NOT do

- Accept a team/channel/thread override from the model -- see above; this is deliberate, not a
  gap.
- Cache or write anything across calls -- every `get_thread()` call hits the real Graph API
  fresh; `receipts_db_path` (when set) is a read-only lookup against a table `teams_reply`
  writes, never written here.
- Post anything -- see [`teams_reply`](../../sinks/teams_reply) for the deterministic reply
  step.
- Rate ANSWERS -- that's `teams_reply`'s `watch_reactions`, not this component.
