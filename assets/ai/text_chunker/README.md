# Text Chunker Asset

Split text into chunks using multiple strategies (fixed tokens, sentences, paragraphs, semantic) for embedding generation, LLM processing, or batch operations.

## Purpose

This component chunks text automatically passed from upstream assets via IO managers. Simply draw connections in the visual editor - no configuration needed for dependencies!

**Compatible with:**
- Document Text Extractor
- Document Summarizer
- Any text-producing asset (string output or dict with 'text' key)

Perfect for:
- Preparing text for embedding generation
- Creating chunks for RAG systems
- Splitting documents for LLM context windows
- Batch processing of large documents

## Quick Start

### 1. Extract Text from Document

```yaml
type: dagster_community_components.DocumentTextExtractorComponent
attributes:
  asset_name: document_text
  # file path is supplied at run time (RunConfig: ops.document_text.config.file_path, e.g. /path/to/document.pdf),
  # or by an upstream asset -- it is not a YAML field
```

### 2. Chunk the Text

```yaml
# No upstream_asset_key needed - set by drawing connections!
type: dagster_community_components.TextChunkerComponent
attributes:
  asset_name: document_chunks
  chunking_strategy: fixed_tokens
  chunk_size: 512
  chunk_overlap: 50
  output_format: list
```

### 3. Draw Connection

In the visual editor: `document_text` → `document_chunks`

That's it! The IO manager automatically passes the text.

## Features

- **Visual Dependencies**: Draw connections, no manual configuration
- **Multiple Strategies**: Fixed characters, tokens, sentences, paragraphs, recursive, semantic
- **Overlap Support**: Configure overlap to maintain context
- **Sentence Preservation**: Avoid breaking sentences mid-chunk
- **Metadata Enrichment**: Add chunk positions, indices, and statistics
- **Flexible Output**: List, DataFrame, or JSON

## Input Requirements

**Accepts text from upstream assets via IO manager:**
- String content (plain text)
- Dict with 'text' key (e.g., `{"text": "content here"}`)
- Any text-producing asset

## Output Format

**Based on `output_format` parameter:**
- `list` - Returns list of text chunks
- `dataframe` - Returns DataFrame with columns: `chunk`, `index`, `start_pos`, `end_pos`, `length`
- `json` - Returns JSON-serialized list of chunk objects with metadata

## Strategies

| Strategy | Best For | Description |
|----------|----------|-------------|
| `fixed_chars` | General use | Fixed character length |
| `fixed_tokens` | LLM context | Approximate token count |
| `sentence` | Semantic units | Full sentences |
| `paragraph` | Document structure | Paragraph boundaries |
| `recursive` | Hierarchical | Multiple separators |
| `semantic` | Context preservation | Structure-aware |

## Vector-Metadata Contract

`stamp_chunk_contract` (default on) stamps a fixed set of fields onto every chunk -- `document_id`,
`source_uri`, `page_start`/`page_end`, `section`, `chunk_index`, `chunk_id`, `content_hash` and
`extractor_version` -- so this chunker and a vector store agree on the shape of a chunk's metadata
without either side guessing column names. Same field names and `content_hash` (sha256) approach as
[`context_engineering_pipeline`'s `stamp_provenance`](../context_engineering_pipeline#receipt-ready-context)
-- see that component's README for the full rationale -- adapted here for a plain chunker that has
no pipeline-step/recipe concept of its own:

- `document_id` / `source_uri` / `page_start` / `page_end` come from `document_id_column` /
  `source_uri_column` / `page_column` when set, and from the input row's own index / `null`
  otherwise -- never fabricated. This component splits plain text with no inherent page concept, so
  `page_start`/`page_end` stay `null` unless an upstream extractor already attached page numbers to
  the input.
- `section` is the last markdown-style header (`#` .. `######`) found in or before each chunk,
  carried forward until the next header -- derived from whatever real structure the source text
  happens to have, for every `chunking_strategy` (not only a dedicated "markdown" one, which this
  component doesn't have), and left `null` for documents with no headers rather than fabricated.
- `chunk_id`/`content_hash` are idempotent: re-running on unchanged content reproduces the same
  values, and editing one document's text only changes that document's own chunks' hashes.
- `extractor_version` defaults to a fingerprint of this component's own chunking configuration
  (`chunking_strategy`/`chunk_size`/`chunk_overlap`/etc) -- set it explicitly (e.g. a git SHA) to
  use something else instead.
- `embedding_model` is deliberately **not** stamped here -- this component runs before embedding, so
  there's no model name yet. See
  [`vector_store_writer`'s own `embedding_model` field](../vector_store_writer#vector-metadata-contract-embedding_model--embedding_model_column),
  which stamps it once embeddings exist and completes the contract end-to-end.

Set `stamp_chunk_contract: false` to turn all of this off and keep exactly the columns this
component produced before. Present whether or not `add_metadata` is set -- that field only
controls this component's own, unrelated preexisting metadata (`char_start`/`char_end`/
`word_count`/`total_chunks`).

## Asset Dependencies & Lineage

This component supports a `deps` field for declaring upstream Dagster asset dependencies:

```yaml
attributes:
  # ... other fields ...
  deps:
    - raw_orders              # simple asset key
    - raw/schema/orders       # asset key with path prefix
```

`deps` draws lineage edges in the Dagster asset graph without loading data at runtime. Use it to express that this asset depends on upstream tables or assets produced by other components.

Dependencies can also be wired externally via `map_resolved_asset_specs()` in `definitions.py` — the same approach used by [Dagster Designer](https://github.com/eric-thomas-dagster/dagster_designer).

## Partitioning

When `partition_type` is set, each run chunks only the upstream rows in its partition: `partition_date_column` selects the rows whose date falls in a time partition's window (a backfill run covers its whole range) and `partition_static_column` selects the rows for a static/dynamic partition key. Unpartitioned runs chunk every row.
