# Video Scene Summarizer

A "table of contents" for video: detect scene changes via ffmpeg, extract one representative frame per scene, and summarize each with a vision-LLM call — one row per scene (timestamp, frame, summary), instead of a fixed-cadence frame dump.

## Why this exists

Nothing in the catalog combined scene detection with vision-LLM understanding: `video_frame_extract_asset` pulls frames on a fixed schedule (every N seconds/frames, or a fixed count) with no idea which frames are actually *interesting* — a 10-minute video of mostly-static footage produces the same frame density as one full of cuts. `audio_transcriber`/`speech_to_text_asset` only handle the audio track. This component uses ffmpeg's real scene-change detection (content-aware boundaries, not a fixed cadence) and adds an LLM description of each detected scene.

## Usage

```yaml
type: dagster_component_templates.VideoSceneSummarizerComponent
attributes:
  asset_name: scene_summaries
  upstream_asset_key: source_videos
  video_path_column: file_path
  scene_threshold: 0.4
  model: gpt-4o
  api_key_env_var: OPENAI_API_KEY
```

Pairs with `synthetic_video_generator` for testing (generates real MP4s with ffmpeg, no fixtures needed), or `file_lister` for real video files.

## How scene detection works

Runs ffmpeg's `select='gt(scene,THRESHOLD)'` filter, which scores each frame by how much it differs from the previous one and only emits frames crossing the threshold — real content-aware scene boundaries, not a fixed interval. `scene_threshold` (0-1) controls sensitivity: lower catches more/subtler cuts (slow pans, dissolves), higher only catches hard cuts. Each emitted frame's timestamp is recovered from ffmpeg's `showinfo` filter output — there's no other way to know which source timestamp a given output frame came from.

**No scenes detected:** a short or genuinely static clip may have nothing cross the threshold. Rather than silently producing zero rows for that video, the component falls back to extracting and summarizing just the first frame — every real video gets at least one row.

**A video that fails to open at all** (corrupt file, no video stream) is counted in `video_errors` output metadata and logged, not silently skipped with no trace.

## Requirements

`ffmpeg` must be in `PATH` (`brew install ffmpeg` / `apt install ffmpeg`) — not a pip package, so it isn't in `requirements.txt`. `litellm` is a hard dependency; use any vision-capable model (`gpt-4o`, `claude-3-5-sonnet-20241022`, `gemini-1.5-pro`, etc.) with a matching `api_key_env_var`.

## Validation

`validation.level: code` — verified end-to-end against REAL ffmpeg-generated videos (not just mocked content, litellm's `completion` call mocked to avoid real API spend): a real 3-scene video (red→blue→green hard cuts) correctly detects 2 scene boundaries at the right timestamps, extracts real (non-empty) frame files, and each scene gets a (mocked) LLM summary; a genuinely static video correctly falls back to a single first-frame row instead of producing zero rows; a corrupt/unreadable video is counted as a real error in `video_errors` output metadata instead of failing the whole run or being silently skipped. Two real ffmpeg compatibility bugs were caught and fixed by this real-file testing (not visible against mocks): `-vsync vfr` was removed in ffmpeg 9.x (now `-fps_mode vfr`), and ffmpeg exits nonzero — not zero — when the scene filter matches no frames at all (handled explicitly rather than treated as a hard failure). Has NOT been run against a real LLM API call yet — live-test that before trusting it in production, and flip `validation.level` to `live` once confirmed.
