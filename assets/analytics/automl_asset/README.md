# AutoML Asset

Real AutoML for tabular data: give it a DataFrame and a target column, and it searches ACROSS model families (LightGBM, XGBoost, random forest, extra trees, linear models, ...) via [FLAML](https://microsoft.github.io/FLAML/) and picks the winner. Almost no config required.

## Why this exists, and why it's not `ml_pipeline`

`ml_pipeline`'s `grid_search`/`random_search`/`bayesian_search` ops tune hyperparameters for a `model_type`/`sklearn_class` **you already specify** — that's the same thing `GridSearchCV`/`RandomizedSearchCV` already do, just YAML-wrapped. Neither those ops nor plain scikit-learn search *across* algorithm families for you. This component is the actual missing piece: it doesn't need to be told which algorithm to use.

Use `ml_pipeline` when you know exactly what you want and need a reproducible, auditable, step-by-step YAML pipeline. Use this component when you want "find me something good, fast" with minimal configuration — and feed the two together if you like: `ml_pipeline` for preprocessing (scaling, imputation, custom encoding), this component for the model search itself.

## The caching design — this does NOT always run a full search

A full AutoML search is expensive (many model fits across a time budget) and wasteful to repeat on every materialize when the underlying data hasn't meaningfully changed. So:

1. **First materialize** (or whenever the cache is missing/stale/forced): runs a full FLAML search up to `time_budget_seconds`, across `estimator_list` (or FLAML's full built-in set if unset). The winning recipe — which estimator, which hyperparameters — is written to `state_path`.
2. **Every materialize after that**: reads the cached recipe back and does a single cheap refit against it, instead of searching again. Confirmed live: **~0.02–0.07s for the cached refit vs. ~6–8s for the original full search** (roughly 100x cheaper), producing the same estimator and equivalent accuracy.

Force a fresh search with `refresh_search: true` (one-off — e.g. after a known data/schema change), or let it happen automatically on a schedule with `max_state_age_hours` (e.g. `168` to re-tune at most once a week; every run in between is a cheap refit).

```yaml
type: dagster_component_templates.AutoMLAssetComponent
attributes:
  asset_name: wine_quality_automl
  upstream_asset_key: wine_features
  target_column: quality
  task_type: classification
  state_path: /tmp/automl_state/wine_quality.json   # or s3://..., gs://... via fsspec
  time_budget_seconds: 60
  estimator_list: [lgbm, rf, xgboost, extra_tree]
```

`state_path` is any [fsspec](https://filesystem-spec.readthedocs.io/) path — local disk or cloud storage (`s3://`, `gs://`, `abfss://`) — so the cache survives across ephemeral compute (k8s pods, serverless runs) as long as it points somewhere durable.

## Non-numeric features

Feature columns that aren't numeric are automatically label-encoded — a mechanical necessity for several of FLAML's estimator families (tree-based estimators handle raw categoricals fine, but the encoding has to be uniform across the whole feature set FLAML receives). This is **not** a substitute for real preprocessing: if you need scaling, imputation, or custom encoding, route your data through `ml_pipeline` first and point this component at its output.

## Output

The upstream DataFrame with a `predicted` column added (predictions from the final fitted model, on every row). Output metadata includes:

- `search_mode`: `"full_search"` or `"cached_refit"` — which path this materialize took.
- `best_estimator` / `best_config`: the winning FLAML estimator name and its hyperparameters.
- `search_time_seconds`: how long the search/refit actually took.
- `holdout_accuracy`/`holdout_precision`/`holdout_recall`/`holdout_f1` (classification) or `holdout_mae`/`holdout_mse`/`holdout_rmse`/`holdout_r2` (regression) — computed against a genuine held-out split (`test_size`) that's never used for the search itself, so these numbers are honest, not the search's own internal CV score.

## Requirements

Requires `flaml[automl]` — **not** the bare `flaml` package, which does not include AutoML functionality (confirmed live: importing `flaml.automl`/`from flaml import AutoML` raises with a clear warning if you only installed `flaml`).

```
pip install "flaml[automl]"
```

On macOS, `flaml[automl]` pulls in `xgboost`/`lightgbm`, which need the OpenMP runtime. Confirmed live that `flaml.automl` fails to import without it:

```
brew install libomp
```

## Validation

`validation.level: code`. Unlike this session's LLM-based components, there's no paid API to mock here — every test runs the real FLAML search against real, real scikit-learn toy datasets (wine, diabetes), no mocking at all. Verified live: a full search on the wine dataset correctly identifies a winning estimator (`lgbm`) with `holdout_accuracy` computed against a genuine held-out split; a second materialize against the same `state_path` correctly takes the cached-refit path and completes in a small fraction of the full search's time, with an equivalent result; `refresh_search: true` forces a full search even with a valid cache present; a cache older than `max_state_age_hours` is correctly treated as stale and triggers a fresh search; a regression task works end-to-end; a non-numeric feature column is correctly auto-label-encoded rather than causing a crash. Has NOT been run against a cloud `state_path` (s3://, gs://) — the fsspec read/write path is standard and shared with several other components in this repo, but flip `validation.level` to `live` only once that's confirmed too.
