# ElasticsearchAssetComponent

Index data into [Elasticsearch](https://www.elastic.co/elasticsearch) or query an ES index and write results to a relational database table — all as observable Dagster assets.

## Modes

### `index` (default)

Takes the DataFrame from the upstream asset (`upstream_asset_key`) and bulk-indexes its rows as documents into an Elasticsearch index using `elasticsearch.helpers.bulk()`.

```yaml
type: dagster_community_components.ElasticsearchAssetComponent
attributes:
  asset_name: product_search_index
  elasticsearch_url_env_var: ELASTICSEARCH_URL
  index_name: products
  mode: index
  upstream_asset_key: raw/products
  id_field: product_id
  chunk_size: 500
  group_name: search
```

Materialization metadata: `index`, `num_docs`, `chunk_size`, `id_field`.

### `query`

Runs an Elasticsearch DSL query against an index and writes the matching document `_source` fields to a destination database table.

```yaml
type: dagster_community_components.ElasticsearchAssetComponent
attributes:
  asset_name: electronics_search_results
  elasticsearch_url_env_var: ELASTICSEARCH_URL
  index_name: products
  mode: query
  upstream_asset_key: raw/products   # required for lineage only; value is unused in query mode
  query: '{"query": {"term": {"category": "electronics"}}}'
  database_url_env_var: DATABASE_URL
  table_name: electronics_hits
  if_exists: replace
  group_name: search
```

Materialization metadata: `index`, `num_docs`, `destination_table`, `if_exists`.

## Prerequisites

```bash
pip install "elasticsearch>=8.0" pandas sqlalchemy
```

For Elastic Cloud, set `api_key_env_var` in addition to `elasticsearch_url_env_var`.

## Asset Lineage

```yaml
deps:
  - raw/products          # wait for upstream ETL to complete
upstream_asset_key: raw/products   # equivalent single-key shorthand
```

Both `deps` and `upstream_asset_key` are merged into the asset's dependency list.

### Reading from a database instead of an upstream asset

Instead of `upstream_asset_key`, set `source` to run a SQL query and feed its rows straight into this component -- no intermediate asset required. Set exactly one of `upstream_asset_key` or `source` (setting both or neither raises a `ValueError` at load time).

`source` is `{kind: warehouse_query, sql: <query>, resource_key: <registered resource> OR database_url_env_var: <env var>}`. `resource_key` names a Dagster resource exposing `.get_engine()`, `.get_connection()` or `.get_client()` (Postgres, Snowflake, DuckDB, BigQuery, Redshift, ...); `database_url_env_var` names an env var holding a SQLAlchemy URL.

`source` is only valid in `mode: index` (the DataFrame-input mode); `query` mode takes no DataFrame input.

```yaml
type: dagster_community_components.ElasticsearchAssetComponent
attributes:
  asset_name: product_search_index
  mode: index
  elasticsearch_url_env_var: ELASTICSEARCH_URL
  index_name: products
  id_field: id
  source:
    kind: warehouse_query
    database_url_env_var: WAREHOUSE_URL
    sql: "SELECT id, body FROM support.tickets WHERE created_at > current_date - 7"
```

Results stay a DataFrame (this adds no database write-back); compose with a sink component to persist them.

## Partitioning

When `partition_type` is set, each run reads only the upstream rows that fall in its partition (by `partition_date_column` / `partition_static_column`); unpartitioned runs read everything. In query mode the tokens below are substituted into `query`, and `if_exists: replace` is rejected with a partition. Tokens `{partition_key}`, `{partition_date}`, `{partition_start}`, `{partition_end}` (and `{partition_<dimension>}` for multi-partitions) are substituted in `query` on a partitioned run.
