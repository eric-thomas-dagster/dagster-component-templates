# `EcsPipesAssetComponent`

Launch a containerized batch job on AWS ECS (Fargate, EC2, or GPU-backed capacity providers) via **Dagster Pipes**, and materialize the result with the metadata the task reports back. Wraps the real `dagster_aws.pipes.PipesECSClient` — not reimplemented here.

No component in this registry wrapped ECS + Pipes before this one. [`ModalPipesAssetComponent`](../modal_pipes_asset) is the closest existing shape — same partition/backfill-policy/catalog-field conventions — but launches a Modal serverless function via `PipesSubprocessClient`, not an ECS task via `PipesECSClient`. Use this one when your compute needs to run inside your own AWS account (e.g. a GPU-backed ECS capacity provider), not a third-party serverless platform.

## User-code contract

Your task's container must open a Pipes context:

```python
# inference_task/run_batch.py
from dagster_pipes import open_dagster_pipes

with open_dagster_pipes() as pipes:
    pipes.log.info("running inference")
    # ... run the model, validate outputs against a schema ...
    pipes.report_asset_materialization(
        metadata={
            "schema_valid_rate": 0.99,
            "docs_failed": 0,
            "rows_processed": 1842,
        },
    )
```

The Dagster side captures:
- Every `pipes.log.*` call as a run log line (read from CloudWatch via `PipesCloudWatchMessageReader`)
- Every `pipes.report_asset_materialization()` as an `AssetMaterialization` event with metadata
- `extras` configured on the component, readable inside the task via `pipes.extras` / `pipes.get_extra(...)`

## Launch configuration

ECS has three mutually exclusive ways to pick compute for a task — set at most one:

| Field | When to use it |
|---|---|
| `capacity_provider` | Single capacity provider (e.g. a GPU provider) — sugar for a one-entry `capacityProviderStrategy`. |
| `capacity_provider_strategy` | A weighted multi-provider strategy — the full ECS shape, for accounts spreading load across providers. |
| `launch_type` | Plain `FARGATE` or `EC2`, for accounts not using capacity providers at all. |

Everything else ECS's `run_task` API accepts but this component doesn't expose a dedicated field for can go in `run_task_params_overrides`, deep-merged on top of what the component builds.

## Metadata-driven asset checks

`metadata_checks` turns any metadata key the task reports via `pipes.report_asset_materialization(metadata={...})` into a real, configurable `AssetCheckResult` — no Python required:

```yaml
metadata_checks:
  - name: schema_valid_rate
    metadata_key: schema_valid_rate
    comparator: gte      # one of: gte, lte, eq, gt, lt
    threshold: 0.98
    severity: ERROR       # ERROR blocks downstream; WARN does not
```

Only evaluated for a single-partition (or unpartitioned) run — a `single_run` backfill range folds metadata from multiple task launches into one `MaterializeResult` keyed `<partition>/<metadata_key>` and does not emit per-partition checks.

## Demo mode

`demo_mode: true` (the default) does **not** swap `PipesECSClient` for a different transport, and does not abstractly fake ECS API responses. It builds the exact same `PipesECSClient` / `PipesCloudWatchMessageReader` classes used in production, injecting a pair of internal fake boto3 `ecs`/`logs` clients instead of real ones:

- The fake `run_task` call launches `local_script_path` as a real local subprocess, with the container-override environment ECS would have injected.
- The fake `logs` client serves the subprocess's growing stdout as paginated CloudWatch log events (`nextToken`/`nextForwardToken` semantics), so Pipes messages and live logs stream back exactly as they would from a real ECS task.

Only the actual AWS API calls are faked — `PipesECSClient`'s and `PipesCloudWatchMessageReader`'s own request-building, polling, and message-reading code all run unmodified in both modes. Set `demo_mode: false` and configure `cluster`/`task_definition`/network settings for a real account to run against a real ECS cluster.

## Auth

Uses the default boto3 credential chain (IAM role, `~/.aws/credentials`, env vars) by default. Set `aws_access_key_id` + `aws_secret_access_key` (+ optional `aws_session_token`) on the component to override.

## Example

```yaml
type: dagster_community_components.EcsPipesAssetComponent
attributes:
  asset_name: gpu_batch_inference

  task_definition: my-inference-task:3
  container_name: inference
  cluster: my-gpu-cluster
  subnets: [subnet-0123456789abcdef0]
  aws_region: us-east-2
  capacity_provider: gpu-g6e

  log_group: /ecs/my-inference-task
  metadata_checks:
    - {name: schema_valid_rate, metadata_key: schema_valid_rate, comparator: gte, threshold: 0.98, severity: ERROR}

  group_name: ml
  kinds: [ecs, pipes, aws, gpu]
  owners:
    - ml-platform@example.com

  demo_mode: true
  local_script_path: inference_task/run_batch.py
```

## Composes with

- [`ModalPipesAssetComponent`](../modal_pipes_asset) — same Pipes-based observability pattern for Modal serverless functions instead of a self-managed ECS cluster.
- Any downstream asset that reads the metadata this materialization reports.

## What doesn't work in v1

- **Per-partition checks on a `single_run` backfill range** — `metadata_checks` only runs against a single-partition (or unpartitioned) result; a backfill range folds all partitions' metadata into one `MaterializeResult` without per-partition check evaluation.
- **Custom Pipes message readers** — v1 is `PipesCloudWatchMessageReader` only. For an S3-based message channel, subclass this component and override `_build_pipes_client`.
