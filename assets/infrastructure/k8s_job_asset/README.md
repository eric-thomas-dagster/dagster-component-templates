# K8sJobAsset

Wraps `dagster-k8s`'s `execute_k8s_job` to launch a Kubernetes Job on materialization, wait for completion, and surface stdout/stderr in the Dagster run log. Useful for compute that needs to run in-cluster (training jobs, batch jobs, anything containerized) — the Airflow `KubernetesPodOperator` equivalent.

## Fixed: `env_vars` is a dict here, a list of strings to `execute_k8s_job`

`execute_k8s_job`'s real `env_vars` parameter is `List[str]` of `"KEY=value"` entries (parsed via `dagster._core.utils.parse_env_var`), not a dict. An earlier version of this component passed the configured dict straight through, which silently iterated its **keys only** — each treated as a bare variable name to read from the *launcher's* own environment, not the literal value you configured. Fixed: `env_vars` (still a dict in your YAML) is converted to `["KEY=value", ...]` before calling `execute_k8s_job`.

## Image pull / service account / volumes

```yaml
image_pull_policy: IfNotPresent     # useful for local testing with kind
image_pull_secrets:
  - my-registry-secret
service_account_name: ml-jobs-runner
volumes:
  - name: data
    emptyDir: {}
volume_mounts:
  - name: data
    mountPath: /data
```

`volumes`/`volume_mounts` are raw Kubernetes API shapes, passed straight through to `execute_k8s_job` — not simplified, since volume types vary too much (`hostPath`, `configMap`, `secret`, PVC, ...) to flatten into a few fields.

## `timeout_seconds`

Enforced natively by `execute_k8s_job`'s own `timeout=` parameter — not a client-side watchdog.

## `use_pipes` — the Pipes variant, for streamed logs/metadata

`dagster-k8s` also ships `PipesK8sClient`, which streams structured messages (custom
metadata, asset checks, a real materialized value) back through the `dagster-pipes`
protocol live, instead of `execute_k8s_job`'s "capture stdout/stderr, return a fixed
metadata dict after the fact" model. Set `use_pipes: true` to switch:

```yaml
use_pipes: true
pipes_extras:
  region: us-east-1   # read inside the container via context.get_extra("region")
```

**This requires the container's own entrypoint to be Pipes-aware** — a materially
different contract than `execute_k8s_job`'s "run any container, capture its exit code and
output" model:

```python
# inside the container
from dagster_pipes import open_dagster_pipes

with open_dagster_pipes() as context:
    context.log.info("working...")
    context.report_asset_materialization(metadata={"rows": 1234})
```

A plain, Pipes-unaware image works fine with `execute_k8s_job` (`use_pipes: false`, the
default) but will hang waiting for a handshake that never comes under `use_pipes: true`.

`resources`/`volumes`/`volume_mounts`/`service_account_name`/`image_pull_secrets`/
`image_pull_policy` all still work under `use_pipes: true` — `PipesK8sClient` has no
dedicated kwargs for them (unlike `execute_k8s_job`), so this component folds them into
`PipesK8sClient.run()`'s raw `base_pod_spec` for you. `timeout_seconds` maps to
`PipesK8sClient`'s `pod_wait_timeout`.

## Example YAML
```yaml
type: dagster_community_components.K8sJobAssetComponent
attributes:
  asset_name: model_training_job
  image: my-registry/trainer:2.1.0
  command: ["python", "train.py"]
  namespace: ml-jobs
  env_vars:
    EPOCHS: "10"
  cpu_limit: 1000m
  memory_limit: 2Gi
  group_name: k8s
  deps:
    - raw/training_data
```
