# `ModalPipesAssetComponent`

Launch a Modal serverless function via **Dagster Pipes** and materialize the emitted asset(s) with the metadata the function reports back. Sibling of [`ModalAssetComponent`](../modal_asset) — richer observability, at the cost of a small user-code contract.

## Which Modal component to use

| Need | Component |
|---|---|
| Kick off a Modal function; mark asset materialized when it finishes; capture stdout in run logs | [`ModalAssetComponent`](../modal_asset) — trigger-and-track |
| Stream logs + structured metadata + AssetMaterialization events back from inside the Modal function during the run | **`ModalPipesAssetComponent` (this)** |
| Emit MULTIPLE asset materializations from one Modal function | This — Pipes handles multi-output naturally via `ctx.report_asset_materialization()` |

## User-code contract

Your Modal function must open a Pipes context:

```python
# ml/training_app.py
import modal
from dagster_pipes import open_dagster_pipes

# dagster-pipes must be installed in the Modal image.
image = modal.Image.debian_slim().pip_install("dagster-pipes", "torch", "wandb")
app = modal.App("ml-training", image=image)

@app.function(gpu="A10G")
def train(learning_rate: float, epochs: int, partition_key: str = ""):
    with open_dagster_pipes() as ctx:
        ctx.log.info(f"training lr={learning_rate} epochs={epochs}")
        # ... train the model ...
        ctx.report_asset_materialization(
            metadata={
                "accuracy": 0.87,
                "loss": 0.12,
                "gpu_seconds": 234.5,
            },
        )
```

The Dagster side captures:
- Every `ctx.log.*` call as a run log line
- Every `ctx.report_asset_materialization()` as an `AssetMaterialization` event with metadata
- `ctx.get_extras()` bridging (e.g. secrets, config values)

## Auth

Uses whatever credentials the Modal CLI has. Two options:

1. **Ambient** — the Dagster worker has already run `modal setup` (creds in `~/.modal`). Set no env vars.
2. **Per-invocation** — set `modal_token_id_env_var` + `modal_token_secret_env_var` on the component. The subprocess env gets `MODAL_TOKEN_ID` / `MODAL_TOKEN_SECRET` overrides.

## What happens at materialize time

1. Component builds `modal run <app_file>::<function_name> --key=value ...` from `function_args`.
2. Adds `partition_key` to the args + `DAGSTER_PARTITION_KEY` to the env when partitioned.
3. Launches via `dg.PipesSubprocessClient` (built into Dagster core).
4. Modal streams stdout back; Pipes reader captures messages.
5. Returns `MaterializeResult` with reported metadata attached.

## Example

```yaml
type: dagster_community_components.ModalPipesAssetComponent
attributes:
  asset_name: model_training
  app_file: ml/training_app.py
  function_name: train
  function_args:
    learning_rate: 0.001
    epochs: 10

  modal_env: production
  group_name: ml
  kinds: [modal, pipes, ml, training]
  owners:
    - ml-platform@example.com
```

## Composes with

- [`ModalAssetComponent`](../modal_asset) — the trigger-and-track sibling (no Pipes deps, simpler when observability isn't needed).
- Any downstream asset that reads the metadata this materialization reports (via `@asset` inputs on `model_training` + `context.instance.get_latest_materialization_event()`).

## What doesn't work in v1

- **Detach mode** — Pipes needs to observe the subprocess stdout to capture messages. Passing `--detach` in `modal_extra_flags` breaks the Pipes-message channel. Use `ModalAssetComponent` if you need detach.
- **Custom Pipes message readers** — v1 uses the default `PipesTempFileMessageReader`. For very-large log payloads (>1MB), swap to `PipesS3MessageReader` by overriding the `pipes_subprocess_client` resource at the project level.
