# PipesPythonAsset

Run a Python script in a fresh virtualenv or a given external interpreter, through Dagster Pipes — the Airflow `@task.virtualenv` / `@task.external_python` equivalent.

Confirmed real gap before building: this repo's two existing Pipes components (`ecs_pipes_asset`, `modal_pipes_asset`) both use Dagster Pipes clients only against hosted containers (an ECS task, a Modal function) — neither creates a local virtualenv or targets a given local interpreter. No component anywhere in this repo calls `venv.create` or similar.

**The script must call `dagster_pipes.open_dagster_pipes()` itself** and report back via `context.report_asset_materialization(...)` — same convention as `ecs_pipes_asset`/`modal_pipes_asset`. This component launches an *existing* script you wrote; it does not serialize a Python callable's body into another interpreter (Dagster Pipes itself is script-based, not callable-serialization-based).

```python
# scripts/extract_features.py
from dagster_pipes import open_dagster_pipes

with open_dagster_pipes() as pipes:
    model_version = pipes.extras.get("model_version")
    # ... do the work, using whatever's installed in THIS interpreter ...
    pipes.report_asset_materialization(metadata={"rows": 12345})
```

## `mode: "virtualenv"` — Airflow's `@task.virtualenv`

```yaml
mode: virtualenv
requirements:
  - pandas==2.2.2
  - scikit-learn==1.5.0
venv_path: ./.pipes_venvs/feature_extraction   # optional; default: ./.pipes_venvs/{asset_name}
reuse_venv: true                               # default: skip rebuilding if requirements are unchanged
```

Builds a real virtualenv via the standard library's `venv.create()`, installs `dagster-pipes` (always, so the script can actually import it) plus `requirements`. A hash of the requirements list is tracked in the venv (`.requirements_hash`); with `reuse_venv: true` (default), an unchanged requirements list skips rebuilding on the next run — an unpinned or changed list rebuilds.

## `mode: "external_python"` — Airflow's `@task.external_python`

```yaml
mode: external_python
python_executable: /opt/venvs/ml-prod/bin/python
```

Runs the script against an already-existing interpreter directly. No venv is created or managed — you own that interpreter's lifecycle.
