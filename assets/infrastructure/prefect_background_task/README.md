# prefect_background_task

Submit a Prefect background task via `.delay()` and materialize it as a Dagster asset. Requires a task worker already serving the task (`prefect task serve`) — without one, the task run stays scheduled and this blocks until the Dagster run is terminated.

**Story**: same as `prefect_flow_run` (Dagster owns schedule/partition/catalog, Prefect owns the run), but for Prefect's lighter-weight background-task primitive instead of a full deployment. Use this when the unit of work is a single `@task`, not a whole `@flow`.

**The one real difference from `prefect_flow_run`**: `deployment_name` is just a string Prefect resolves — no import needed. A background task has no equivalent by-name trigger API; `.delay()` needs the actual Python function object, so `task_import_path` must be importable from wherever this component builds its defs (installed dependency, or vendored onto the path). This is a real Prefect constraint, not a choice this component made — the official `dagster-prefect` package's `PipesPrefectTaskClient` has the identical requirement.

Works against:
- **Local server**: `prefect server start` → default `api_url` `http://127.0.0.1:4200/api`.
- **Prefect Cloud**: set `api_url` + `api_key_env_var`.

**Requires Prefect 3.0+ — hard requirement, not a soft preference.** Verified directly: Prefect 2's `@task` objects have no `.delay()` method at all — background tasks are a Prefect 3 feature that doesn't exist in 2.x. (The official `dagster-prefect` package requires the same: `prefect<4,>=3.0`, per its own package metadata.)

## Observability without a shared filesystem or blob store

`stream_logs` and `stream_artifacts` work exactly like they do on `prefect_flow_run` — see that component's README for the full explanation of why they exist (short version: `dagster-prefect`'s Pipes message reader defaults to a temp file, which silently drops metadata/logs/checks unless the Dagster step and the Prefect worker share a filesystem; polling Prefect's own `read_logs`/`read_artifacts` APIs sidesteps that with no extra infrastructure). Here they filter by `task_run_id` instead of `flow_run_id`.

## Cancellation is not supported

Unlike `prefect_flow_run`, there's no `forward_termination` field. Prefect's task workers run a task to completion regardless of a cancellation request — confirmed directly in `dagster-prefect`'s own source, which logs a warning and gives up for task-run kind rather than attempting a cancel. This component does the same: if the Dagster run is terminated while waiting, it logs that the task will keep running rather than pretending to stop it.

## Templating

String parameter values support `{partition_key}`, `{run_id}`, `{partition_window_start}` / `{partition_window_end}` (time-window partitions only). Non-string values pass through unchanged.

## Serving the task

Prefect derives a task's identity (`task_key`) from how its defining module was imported. If you serve the task by running its own file directly (`python my_tasks.py` with a `__main__` guard calling `.serve()`), it registers under `__main__` — not the dotted path `task_import_path` uses — so `.delay()`-submitted runs sit at `SCHEDULED` forever; the worker never sees them as the same task. Serve it from a small driver script that imports the task the same way instead:

```python
# serve_tasks.py
from my_project.tasks import summarize
summarize.serve()
```

## Check convention

Identical to `prefect_flow_run.check_names`, including the required translation: a table artifact (`create_table_artifact`) whose KEY, with dashes read as underscores, matches a declared `check_names` entry — e.g. `check_names: [word_count_check]` matches an artifact keyed `word-count-check`. Pass `table=[{"passed": bool, ...}]` (a one-row table — `create_table_artifact` rejects a bare dict). This is a convention this component defines on top of Prefect's artifacts — Prefect itself has no pass/fail check primitive, and its key-naming rule (lowercase/digits/dashes) directly conflicts with Dagster's check-name rule (`^[A-Za-z0-9_]+$`, no dashes), which is why the translation exists at all. An unreported declared check is reported as `passed=False` with an explanatory description, not silently skipped — Dagster requires every declared check to get a result every run, or the whole step fails with a confusing engine error instead.
