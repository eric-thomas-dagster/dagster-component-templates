# RuntimePartitionAsset

An asset whose partition key is chosen **while it runs**, not before — Airflow 3.3's
`PartitionedAtRuntime` (`outlet_events[self].add_partitions(key)`), verified against
Airflow's own official `example_asset_partition` example DAG source before building
anything.

## Why this needs a different shape than every other partitioned asset in this repo

Dagster requires a partitioned step's partition key to be known **before** the run starts
— the execution plan is built knowing which partition is targeted, and the `dagster/partition`
run tag must match an already-registered key. There is no way for a normal partitioned
`@dg.asset` to decide its own key mid-compute.

Confirmed live, not guessed, the real mechanism that works instead: the **executing step is
unpartitioned** (so Dagster imposes no pre-known-key requirement on it), and once it has
decided the key, it:

1. Registers it via `instance.add_dynamic_partitions(...)` if new.
2. Reports the materialization for a **separate, catalog-facing `AssetSpec`** — partitioned
   with that same `DynamicPartitionsDefinition`, with no compute op of its own — via
   `instance.report_runless_asset_event(AssetMaterialization(partition=key))`.

Same "observed, not computed" shape this repo's own `external_assets/` category already uses
for a different reason (watching an external system) — here it's used to get around Dagster's
own partition-key-known-ahead-of-time constraint.

## `key_source` — where the key comes from

```yaml
type: dagster_community_components.RuntimePartitionAssetComponent
attributes:
  asset_key: regional/region_stats
  dynamic_partitions_name: regions_rt
  callable_path: "myproject.ingestion:ingest_region"
  key_source: callable_return
```

- **`callable_return`** (default) — Airflow's "the task computes the key as it runs" case.
  The callable must return a `(key, payload)` 2-tuple.
- **`run_tag`** — Airflow's "triggered externally with a region code" case. The key comes
  from a run tag (`key_run_tag`) set by whoever launches the run; the callable is called
  normally and its return value is the payload.
- **`run_config`** — same calling convention as `run_tag`, but the key comes from an op
  config field (`key_config_field`) instead.

## Two assets, on purpose

This component emits **two** `AssetsDefinition`/`AssetSpec` entries:

- `asset_key` — the catalog-facing asset, dynamically partitioned by `dynamic_partitions_name`.
  Has no compute op; its materialization history is entirely reported, one event per run.
- `executor_asset_key` (defaults to `<asset_key>_runner`) — the real, unpartitioned asset
  that actually runs `callable_path`. This is the one you depend on / schedule / sensor-trigger.

```yaml
attributes:
  asset_key: regional/region_stats
  executor_asset_key: regional/region_stats_runner   # optional, shown here as the default shape
```

## Consumers

Depend on `asset_key` (the dynamically-partitioned one) the same way you'd depend on any
`DynamicPartitionsDefinition`-backed asset. For the Airflow consumer-mapping cases (identity,
an allow-list of keys, or a composite `"part1|part2"` key split with a mapping per segment),
see [`partition_window_sensor`](https://dagster-component-ui.vercel.app/c/partition_window_sensor).

## Concurrency, retries, and timeouts

- `pool` — Dagster's native named concurrency pool, applied to the executing asset.
- `retry_policy_max_retries`/`retry_policy_delay_seconds`/`retry_policy_backoff` — a
  `RetryPolicy` for the executing asset's own step.
- `timeout_seconds` — bounds how long the executing step waits for the callable, via a
  background-thread wrapper. The callable may continue running past the deadline (Python
  threads can't be forcibly killed); this bounds the step's wait, not the call itself.
