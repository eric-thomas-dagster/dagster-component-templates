# `SemanticModelRefreshAssetComponent`

Trigger a **Power BI / Fabric semantic model (dataset) refresh** and wait for it to finish. The
missing piece on the Fabric side of an ADF-style pipeline: ADF's `PBISemanticModelRefresh`
activity has no Dagster-component equivalent before this -- `fabric_workspace` only lists
`SemanticModel` items as external/observable (no trigger-and-wait).

## Verified against Microsoft's own REST API reference

Not guessed -- confirmed against learn.microsoft.com/rest/api/power-bi/datasets/refresh-dataset-in-group
and .../get-refresh-execution-details-in-group:

```
POST https://api.powerbi.com/v1.0/myorg/groups/{workspace_id}/datasets/{dataset_id}/refreshes
GET  https://api.powerbi.com/v1.0/myorg/groups/{workspace_id}/datasets/{dataset_id}/refreshes/{refreshId}
```

The polled `status` field is `"Unknown"` while in progress; terminal values are `"Completed"`,
`"Failed"`, `"Disabled"` (a selective/table-scoped refresh Fabric declined to run) -- all three
from Microsoft's own documented response schema.

## Basic vs. enhanced refresh

An **enhanced refresh** triggers only when a request payload OTHER than `notify_option` is set --
Power BI's own documented rule. Set any of `refresh_type` / `commit_mode` / `max_parallelism` /
`retry_count` / `objects` / `apply_refresh_policy` / `effective_date` / `request_timeout` for an
enhanced refresh (selective table/partition refresh, parallelism control, incremental-refresh
`effectiveDate` override, ...). `notify_option` and the enhanced-refresh fields are **mutually
exclusive on the wire** -- Power BI requires `notifyOption` be excluded from an enhanced-refresh
request body entirely, enforced here at config-validation time, not left to fail at the API.

```yaml
# Enhanced refresh: selective, one partition
attributes:
  asset_key: fabric/sales_semantic_model
  workspace_id: ...
  dataset_id: ...
  refresh_type: Full
  commit_mode: transactional
  objects:
    - table: Customer
      partition: Robert
```

```yaml
# Basic refresh: just a mail notification option
attributes:
  asset_key: fabric/sales_semantic_model
  workspace_id: ...
  dataset_id: ...
  notify_option: MailOnFailure
```

## Auth

Service-principal auth, same env-var pattern as `fabric_pipeline_trigger_job`
(`tenant_id_env_var`/`client_id_env_var`/`client_secret_env_var`, falling back to
`DefaultAzureCredential` when unset) -- but a **different OAuth scope**:
`https://analysis.windows.net/powerbi/api/.default`, not the Fabric API's own
`https://api.fabric.microsoft.com/.default` that `fabric_workspace`/`fabric_pipeline_trigger_job`
use. This scope isn't documented on a single canonical Microsoft Learn page the way the endpoint
paths above are -- it's the scope Microsoft's own sample code and multiple independent community
sources consistently use for service-principal calls to `api.powerbi.com`.

The service principal also needs to be added as a **member or admin of the target workspace**, and
a Power BI admin must enable **"Allow service principals to use Power BI APIs"** in tenant
settings -- outside this component's control; see
[Microsoft's own service-principal setup guide](https://learn.microsoft.com/power-bi/developer/embedded/embed-service-principal).

## `dry_run` / `run_window`

`dry_run: true` logs what would be triggered and skips the real Fabric authentication + REST call
entirely -- no token is acquired. `run_window: 'HH:MM-HH:MM tz [day,...]'` skips cleanly (not
failing) outside a configured time window, same convention as `sap_job_trigger_asset`.
