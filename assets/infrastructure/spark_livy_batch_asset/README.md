# Spark Livy Batch

Submits a Spark batch job to a standalone/YARN cluster via [Apache Livy](https://livy.apache.org/)'s REST API, and polls to completion.

Livy is a REST front door for `spark-submit`: one `POST /batches` creates a batch that runs as a real Spark application on whatever cluster Livy is configured against. This is distinct from [`spark_k8s_operator_asset`](../spark_k8s_operator_asset/README.md) (Kubernetes via the Spark Operator CRD) -- use this one for the classic on-prem/Hadoop-era standalone or YARN deployment.

## Example YAML

```yaml
type: dagster_component_templates.SparkLivyBatchAssetComponent
attributes:
  asset_name: nightly_aggregation_batch
  livy_url: http://livy-server:8998
  file: s3://data-platform/jobs/nightly_aggregation.py
  args: ['--date', '2024-01-01']
  executor_memory: 4g
  num_executors: 10
  group_name: batch
  kinds: [spark, livy]
```

## Failure handling

On a batch ending `dead`/`killed`/`error`, this component fetches the batch's log tail (`GET /batches/{id}/log`) and includes it in the raised exception, so you see the real Spark driver error without a separate log lookup. Set `fail_on_batch_failure: false` to materialize anyway with the state in metadata instead.

Livy's own docs only enumerate a state list for *interactive sessions* (not_started/starting/idle/busy/shutting_down/error/dead/success), not a public batch-state enum -- this component treats `success` as the only success terminal state and anything else that stops changing (`dead`/`killed`/`error`) as a failure, rather than hardcoding an undocumented state list.

## Authentication

Set `request_headers` if your Livy server sits behind an authenticating proxy (e.g. `{"Authorization": "Bearer ..."}`).
