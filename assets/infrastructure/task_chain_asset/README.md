# TaskChainAsset

Run an ordered list of `command`/`sql`/`python` steps as a single Dagster asset — what a job
scheduler like RunMyJobs/AutoSys/Control-M calls one job with multiple sequential steps. Each
step runs in order; the first failing step stops the chain immediately (later steps never run)
and fails the whole asset with the failing step's id/type attached.

## Step types

Each entry in `steps` is a dict with a unique `id`, a `type`, and type-specific fields:

```yaml
steps:
  - id: extract
    type: command
    command: "./scripts/extract.sh {{ partition_key }}"
    success_exit_codes: [0, 2]   # optional -- 2 also counts as success
    skip_on_exit_code: 3         # optional -- 3 skips the REST of the chain without failing
  - id: load
    type: sql
    resource_key: warehouse
    sql: "COPY INTO raw.orders FROM @stage/{{ partition_key }}"
  - id: notify
    type: python
    callable_path: myproject.tasks:notify_done
```

- **`command`**: runs via the shell (same subprocess idiom as `ShellCommandAssetComponent`).
  `success_exit_codes` extends the normal "0 is the only success" rule; `skip_on_exit_code`
  stops the chain cleanly (no failure) when the command exits with that code.
- **`sql`**: runs against exactly one of `resource_key` (a resource providing
  `get_connection()`/a DBAPI connection, same contract as `SqlAssetComponent`) or
  `connection_env` (an env var holding a SQLAlchemy URL, connected directly — no Dagster resource
  needed), unless the chain's own `dry_run` is `true`, which needs neither. Exactly one of `sql`,
  `sql_file`, or `sql_statements` is required. A step's `resource_key` is only declared as a
  required resource when it's actually in play (not `dry_run`) — see `SqlAssetComponent`'s own
  README for why that specific constraint can't be avoided for `resource_key` itself; use
  `connection_env` or this chain's `dry_run` if you need the asset's definitions to load before
  the resource is wired up.
- **`python`**: resolves `callable_path` (`module.path:function_name`) and calls it with no
  arguments — use the step body to read `context`/partition state via closures in your own
  module if needed.

`{{ partition_key }}` in a `command` string or `sql`/`sql_statements` entries is substituted
with the asset's current partition key (or left as literal text if unpartitioned).

## `run_window` — skip cleanly, don't fail, outside a time window

```yaml
run_window: "09:00-17:00 America/New_York mon,tue,wed,thu,fri"
```

Checked once per materialization, before any step runs (not per-step). Outside the window, the
asset **skips cleanly** — no steps execute, the run succeeds, and real downstream dependents
skip too (via `AssetOut(is_required=False)`), rather than failing or blocking the DAG. A
malformed spec fails open (always runs) rather than silently blocking a chain forever. Unset
(default): always runs. This component has no inline `schedule:` block by design — pair it with
a separate `CronScheduleComponent` targeting this asset, and use `run_window` only to narrow
*within* that cadence (e.g. a schedule that fires hourly, but should only actually do work
during a business-hours sub-window).

## `dry_run`

```yaml
dry_run: true
```

Logs every step's fully-resolved "would run" summary (command text / SQL text / callable path)
and skips executing any of them — no subprocess, no SQL, no callable invocation. Output metadata
always includes `dry_run` so materialization history shows which runs were real.

## `timeout_seconds` bounds the whole chain

Unlike `pool`/`retry_policy_*` (applied via Dagster's own asset-level mechanisms),
`timeout_seconds` is enforced by a background-thread wrapper around the **entire** chain (every
step), not any one step — a step may continue running past the deadline (Python threads can't
be forcibly killed), but the Dagster step fails and moves on once the deadline passes.

## Example

```yaml
type: dagster_community_components.TaskChainAssetComponent
attributes:
  asset_key: infra/nightly_batch
  run_window: "22:00-23:59 America/New_York"
  steps:
    - id: extract
      type: command
      command: "./scripts/extract.sh {{ partition_key }}"
    - id: load
      type: sql
      resource_key: warehouse
      sql: "COPY INTO raw.orders FROM @stage/{{ partition_key }}"
    - id: notify
      type: python
      callable_path: myproject.tasks:notify_done
  partition_type: daily
  partition_start: "2024-01-01"
  retry_policy_max_retries: 2
  timeout_seconds: 1800
```

## Requirements

```
dagster
sqlalchemy
```

`sqlalchemy` is only imported when a `sql` step actually uses `connection_env`. A `resource_key`
step instead needs whatever DBAPI driver the referenced resource depends on (not a requirement
of this component itself).
