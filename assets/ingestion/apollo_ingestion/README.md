# Apollo.io Ingestion

Ingest Apollo.io people, organization, and contact search/prospecting data using dlt's generic REST API source.

Uses dlt's generic REST API source (`dlt.sources.rest_api.rest_api_source`).

By default, runs an in-memory DuckDB pipeline and returns a pandas DataFrame. Set `destination` to persist directly to any dlt-supported destination. See `../DESTINATIONS.md`.

> **Verified against docs.apollo.io**, cross-checked against Apollo's own "API Mastery" developer-hub writeup and third-party API breakdowns (Apollo's docs site has reorganized more than once, so this was corroborated across independent sources):
> - **Base URL**: `https://api.apollo.io/api/v1`.
> - **Auth**: `x-api-key: <api_key>` header -- NOT `Authorization: Bearer`. Apollo also supports OAuth 2.0 for partner integrations acting on behalf of a user, but this connector targets the simpler, far more common API-key mode. Keys are created under Settings -> Integrations -> API Keys; only admins (or users with the right permission profile) can create them. A handful of endpoints (e.g. listing workspace users) require a "master key" rather than a regular key -- not relevant to the resources this connector exposes.
> - **`people`** -> `POST /people/search`. Searches Apollo's global prospecting database for people matching filter criteria; response shape is `{"people": [...], "pagination": {...}}`.
> - **`organizations`** -> `POST /organizations/search`. Searches Apollo's global company/organization database; response shape is `{"organizations": [...], "pagination": {...}}`.
> - **`contacts`** -> `POST /contacts/search`. Unlike `people`/`organizations`, this searches records already saved to the calling account's own Apollo CRM-style contact list, not the global prospecting database; response shape is `{"contacts": [...], "pagination": {...}}`.
> - All three are **POST** endpoints that take filter criteria in a JSON request body, not query params -- a meaningful difference from most of this repo's other generic-REST connectors. This connector sends a minimal `{"page": 1, "per_page": <page_size>}` body by default; extend `_build_resources_config` in `component.py` to pass through additional Apollo filter fields (e.g. `person_titles`, `organization_num_employees_ranges`) for server-side filtering.

> **Pagination honesty note:** the exact pagination response/parameter contract beyond the `pagination` object in each response body was not fully confirmed in the material available while building this connector. This connector does not configure a custom dlt paginator (consistent with this repo's other generic-REST connectors), so each run fetches a single page per resource (`per_page` records, default 25) -- extend `_build_resources_config` with a `page_number` paginator if you need to walk beyond the first page.

> **Partition honesty note:** if you set `partition_type`, it controls Dagster's materialization/backfill schedule only. This connector's compute function does not use the partition key to filter the API request, so every partition run re-fetches the same page rather than a bounded window.

## Configuration

| Field | Required | Description |
|---|---|---|
| `asset_name` | required | Name of the asset that will hold the data |
| `api_key` | required | Apollo.io API key, sent as the `x-api-key` header. |
| `resources` | optional | Comma-separated list of resources to extract: people, organizations, contacts. Default: `people,organizations,contacts` |
| `page_size` | optional | Value sent as `per_page` in each search request body. Default: `25` |
