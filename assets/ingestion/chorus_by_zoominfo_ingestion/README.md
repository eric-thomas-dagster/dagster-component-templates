# Chorus by ZoomInfo Ingestion

Ingest Chorus by ZoomInfo call engagement and user data using dlt's generic REST API source.

Uses dlt's generic REST API source (`dlt.sources.rest_api.rest_api_source`).

By default, runs an in-memory DuckDB pipeline and returns a pandas DataFrame. Set `destination` to persist directly to any dlt-supported destination. See `../DESTINATIONS.md`.

> **Naming / rebrand note:** Chorus.ai was acquired by ZoomInfo and is now branded "Chorus by ZoomInfo" within the ZoomInfo product suite. This component is named `chorus_by_zoominfo_ingestion` to reflect that current branding -- older third-party integration guides, blog posts, and some still-live documentation mirrors still refer to it as plain "Chorus" or "Chorus.ai", which can be confusing when cross-referencing against this component. The underlying product, API host (`chorus.ai`), and auth scheme have not changed post-acquisition as of this writing.

> **Verified against api-docs.chorus.ai and cross-referenced against multiple independent third-party integration guides** (the official docs site did not consistently render for direct automated fetching while building this connector, so confidence is stated explicitly per fact below rather than uniformly):
> - **Base URL**: `https://chorus.ai`.
> - **Auth**: `Authorization: <api_token>` -- the **raw token value, with NO `Bearer ` prefix**. This is confirmed via two independent, identically-worded curl examples in separate secondary sources, both quoting the literal form `Authorization:abcdefghijklmnopqrstuvwxyz0123456789` against `https://chorus.ai/v3/engagements`. This is notably **not** `Authorization: Bearer <token>` -- the easy mistake here, since the Chorus OpenAPI spec reportedly declares an `http/bearer` security scheme even though the documented real-world usage omits the "Bearer " prefix. Generate a token under Settings -> API in the Chorus app.
> - **`engagements`** -> `GET /v3/engagements` (**HIGH confidence** -- this is the literal path quoted in both corroborating sources above). Lists conversations (meetings and dialer calls); returned objects reportedly include `engagement_id`, `subject`, `date_time`, `duration`, `participants`, and `processing_state`, filterable by type/date range -- but the exact query-parameter names for that filtering were not confirmed, so this connector issues an unfiltered `GET /v3/engagements` by default.
> - **`users`** -> `GET /v3/users` (**MEDIUM confidence** -- multiple independent sources state the Chorus API supports retrieving user data, but no source quoted this literal path the way `/v3/engagements` was quoted twice; it's inferred by symmetry with the confirmed `/v3/` versioning convention rather than independently verified).
> - **Transcript retrieval is intentionally NOT exposed** as a `resources` option. It's tied to a specific `engagement_id` (a per-record lookup, not a bulk listing) and the exact nested path was not confirmed with enough confidence to ship -- some secondary sources reference an older `/api/v1/calls/{callId}/transcript`-style path that may or may not still apply under `/v3/`. Shipping a guessed path here would violate this repo's "don't guess endpoint paths" convention; this mirrors why ZoomInfo's per-record `enrich` endpoints and Reclaim's calendar-connection endpoints were excluded from their respective sibling connectors.
> - Chorus.ai does **not** expose a public REST API for user *management* (create/update/deactivate) -- the `users` resource here is read-only listing only.

> **Partition honesty note:** if you set `partition_type`, it controls Dagster's materialization/backfill schedule only. This connector's compute function does not use the partition key to filter the API request, so every partition run re-fetches the same full resource set rather than a bounded window.

| `resources` | optional | Comma-separated list of resources to extract: engagements, users. Default: `engagements,users` |
