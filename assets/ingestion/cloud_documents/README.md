# Cloud Documents

Extract document file **content** (real text extraction) from cloud storage / file-sharing providers, for RAG pipelines. One component, dispatched by `provider`, spanning two genuinely different access patterns:

1. **Generic bucket storage** (`s3` / `gcs` / `azure_blob` / `webdav`): walks `source_path` via `fsspec`, the same pattern `document_ingestion` already uses in this repo -- real `.pdf`/`.docx`/`.html` extraction via pdfplumber/python-docx/BeautifulSoup, `.txt`/`.md` read as plain text, `.doc` skipped (no extraction library available). `webdav` rides on fsspec's own built-in knowledge of the `webdav://` protocol (confirmed via `fsspec.get_filesystem_class('webdav')` -> "Install webdav4 to access WebDAV", not an unknown-protocol error), but the `webdav4` package is NOT installed in this repo's environment, so this path is **best-effort / unverified end-to-end** -- install `webdav4` and test against your own server before relying on it in production.

2. **OAuth-protected vendor APIs** (`onedrive` / `sharepoint` / `box` / `dropbox`): mirrors this repo's own `onedrive_ingestion`/`sharepoint_ingestion`/`box_ingestion`/`dropbox_ingestion` components' own verified auth + listing calls (same token endpoints, same field names where they carry over), then adds the one thing those components don't do -- fetch each file's raw bytes and run them through the same extraction dispatch as (1). Each branch lists ROOT CHILDREN ONLY (no recursion into subfolders), matching the scope of its sibling ingestion component.

This component has no multi-table concept -- one flat set of document rows regardless of provider -- so there is no `asset_shape`/multi_asset option here.

By default, runs an in-memory DuckDB pipeline and returns a pandas DataFrame. Set `destination` to persist directly to any dlt-supported destination (snowflake, bigquery, postgres, filesystem, etc.) -- completely separate from the SOURCE cloud location being read from. See `../DESTINATIONS.md`.

## Document source contract

Every row, every provider, carries the same columns so `document_chunker` and other RAG components can treat every source identically:

| Column | Meaning |
|---|---|
| `doc_id` | Stable per-provider identifier (fsspec URI for bucket storage; the vendor's own file ID for onedrive/sharepoint/box; file ID or path for dropbox). |
| `content` | Real extracted text. |
| `title` | Filename, without extension. |
| `url` | Whatever the provider actually gives: the fsspec URI (bucket storage), Graph's `webUrl` (onedrive/sharepoint), a constructed Box web-viewer URL (`https://app.box.com/file/{id}` -- box), or the file's `path_display` (dropbox -- NOT a clickable share link; a real one needs a separate per-file API call, not made here). |
| `source_type` | The literal provider name, e.g. `"s3"`, `"onedrive"`. |
| `updated_at` | The file's last-modified time, from whichever field that provider's own listing response actually has (fsspec `.modified()`; Graph `lastModifiedDateTime`; Box `modified_at`; Dropbox `server_modified`). |
| `content_hash` | sha256 of `content`. |

## Provider-specific fields

| Provider | Required fields |
|---|---|
| `s3` / `gcs` / `azure_blob` | `source_path` (an `s3://`/`gs://`/`az://` URI). Install the matching fsspec backend (`s3fs`/`gcsfs`/`adlfs`); credentials come from that backend's own standard environment variables. |
| `webdav` | `webdav_base_url`, plus `source_path` (relative path, default `/`) and optionally `webdav_username`+`webdav_password_env_var` or `webdav_token_env_var`. Best-effort/unverified -- see above. |
| `onedrive` | `tenant_id`, `client_id`, `client_secret`, `drive_id`. |
| `sharepoint` | `tenant_id`, `client_id`, `client_secret`, `site_hostname`, `site_path`. |
| `box` | `client_id`, `client_secret`, `box_subject_type`, `box_subject_id`, optional `folder_id` (default root). |
| `dropbox` | `client_id`, `client_secret`, `refresh_token`, optional `folder_path`/`recursive`. |

`onedrive` and `sharepoint` share one `tenant_id`/`client_id`/`client_secret` field set (same Microsoft Graph app-only auth); `client_id`/`client_secret` are also shared with `box` and `dropbox` (each a different vendor's OAuth app, but all 4 already use plain, non-`_env_var` fields in their own standalone ingestion components in this repo). Which fields matter is determined entirely by `provider` -- validated at config-resolution time, not just at runtime.

## Example
```yaml
type: dagster_community_components.CloudDocumentsComponent
attributes:
  asset_name: s3_documents
  provider: s3
  source_path: "s3://my-bucket/docs/"
```

Or an OAuth-protected provider:
```yaml
type: dagster_community_components.CloudDocumentsComponent
attributes:
  asset_name: onedrive_documents
  provider: onedrive
  tenant_id: "${AZURE_TENANT_ID}"
  client_id: "${AZURE_CLIENT_ID}"
  client_secret: "${AZURE_CLIENT_SECRET}"
  drive_id: "b!abc123..."
```
