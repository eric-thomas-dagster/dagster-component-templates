# cloud_storage_copy_asset

A generic "Copy activity" stand-in: moves data from one cloud-storage (or local) path to another, or into a warehouse table -- the same shape as Azure Data Factory's Copy activity's most common pairs (file-to-file across blob/ADLS/S3/GCS, and file-to-database), without being tied to one specific cloud or one specific sink.

## Two modes

- **`copy_mode: binary`** (default) -- a raw byte-stream copy, no parsing at all. Matches ADF's default `Binary` dataset type, which is how most real file-to-file Copy activities actually run: preserve the bytes exactly, no schema, works for any file type. Fast and format-agnostic.
- **`copy_mode: dataframe`** -- reads the source into a DataFrame (same read-side format dispatch as [`file_ingestion`](../file_ingestion): pandas/pyarrow resolve `s3://`/`gs://`/`abfss://`/local paths internally; only Avro needs an explicit `fsspec.open()`) and either writes it back out in a (possibly different) file format, or loads it into a warehouse table via `sink_table`. Use this when the sink format differs from the source, or the sink is a database table.

## Wildcard / recursive copies

Set `wildcard` (e.g. `*.csv`) to copy every file under `source_path` (now treated as a directory) matching the pattern to the same relative path under `sink_path` -- the common "copy everything matching *.csv in this folder" same-format file copy, across blob/ADLS/S3/local. Set `recursive: true` to also match files in subdirectories. Requires `copy_mode: binary` and a `sink_path` (not `sink_table` -- a wildcard copy doesn't parse rows, so there's nothing to load into a table).

## Source and sink are both plain fsspec URIs

`source_path` / `sink_path` accept anything fsspec resolves: `s3://`, `gs://`, `abfss://...`, or a local/plain path. `{partition_key}` in either is replaced with the running partition at materialization time (same convention as [`adls_to_database_asset`](../adls_to_database_asset)'s `blob_name`/`table_name` templating).

## Azure credentials

`azure_account_name_env_var` / `azure_account_key_env_var` / `azure_connection_string_env_var` are only consulted when `source_path` or `sink_path` uses an `abfs://`/`abfss://`/`az://` scheme (and only to build `storage_options` for that call -- an S3/GCS path on the other side of the same copy still uses its own ambient credential discovery). Leave them unset and Azure falls back to `adlfs`'s own ambient credential discovery too, same as the non-Azure schemes.

## `sink_table`

Identical sink shape and behavior to [`rest_api_ingestion`](../rest_api_ingestion)'s own `sinks: [{kind: table, ...}]` -- `resource_key`, `table`, `schema`, `if_exists: append|replace`, `mode: upsert_on_match` (partition-rewrite idempotent DELETE-then-INSERT keyed by `match`). Auto-detects a DuckDB connection's `.register()` fast path; falls back to SQLAlchemy `to_sql` for Postgres/Snowflake/BigQuery/MySQL/MSSQL/etc. Requires `copy_mode: dataframe` (a binary copy has no rows to load into a table).

Exactly one of `sink_path` / `sink_table` must be set.
