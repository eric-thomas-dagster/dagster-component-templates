# Confluence Documents

Extract full Confluence page **body text** (not just page metadata) for RAG pipelines, ready to feed into `document_chunker`.

> **Note:** this is a different component from `confluence_ingestion` elsewhere in this repo, which syncs Confluence pages/blog-posts as metadata rows via dlt but does NOT fetch page body content. This component's whole purpose is the opposite: list pages (by space or by ancestor), fetch each page's body (Confluence's `body.storage` or `body.view` representation via the `expand` query param), and strip it to plain text via BeautifulSoup -- the same pattern `document_corpus/component.py`'s `_extract_text` uses for its own `.html` extraction.
>
> Verified against Atlassian's own Confluence Cloud REST API docs: auth is HTTP Basic with `base64(email:api_token)` (https://developer.atlassian.com/cloud/confluence/basic-auth-for-rest-apis/, NOT a bearer token); body fetch is `expand=body.storage` or `expand=body.view` (confirmed from the v1 Content API's OpenAPI spec, https://developer.atlassian.com/cloud/confluence/swagger.v3.json); space listing is `GET /wiki/rest/api/content?spaceKey=...&type=page` paginated via `start`/`limit`; descendant listing is CQL search, `GET /wiki/rest/api/content/search?cql=ancestor={id}` (confirmed with a worked example at https://developer.atlassian.com/cloud/confluence/advanced-searching-using-cql/), cursor-paginated via `_links.next`.

Every row matches the document-source contract shared by every RAG-source ingestion component in this repo: `doc_id`, `content`, `title`, `url`, `source_type` (`"confluence"`), `updated_at`, `content_hash`. Point `document_chunker`'s `source_column` at `content` and `upstream_asset_key` at this asset for a RAG chunking -> embedding pipeline.

This connector is hand-written with a plain `@dlt.resource` generator wrapping the already-fetched rows (same approach as `firecrawl_ingestion`) -- not `rest_api_source`, since listing pages and reading each one's body is a two-step flow, not one paginated resource. Confluence has no multi-table concept here, so there is no `asset_shape`/multi_asset option.

By default, runs an in-memory DuckDB pipeline and returns a pandas DataFrame. Set `destination` to persist directly to any dlt-supported destination. See `../DESTINATIONS.md`.

## Configuration

| Field | Required | Description |
|---|---|---|
| `asset_name` | required | Name of the asset that will hold the data |
| `base_url` | required | Confluence Cloud site URL, e.g. `https://yoursite.atlassian.net`. |
| `email_env_var` | required | Env var holding the Atlassian account email for Basic auth. |
| `api_token_env_var` | required | Env var holding the Confluence Cloud API token. |
| `space_key` | one of | List every page in this space. |
| `ancestor_page_id` | one of | List every descendant of this page (via CQL `ancestor` search). |
| `body_format` | optional (default `storage`) | `storage` (Confluence's own XHTML-like markup) or `view` (server-rendered HTML, often cleaner to extract). |
| `page_size` | optional (default `25`) | Pages fetched per API call. |
| `max_pages` | optional | Stop paginating after this many pages. Unset = fetch all. |

Exactly one of `space_key` / `ancestor_page_id` is required -- enforced at config-resolution time, not just at runtime.

## Re-running without duplicating rows

`write_disposition` (default `"replace"`) controls what a rerun does to the destination table: `"replace"` (default) makes each run fully replace the table -- the right default here, since dlt's own default (`"append"`) has no notion of a previous run's pages becoming stale and keeps adding another full copy of every page on top of the last (a real, previously-shipped bug: `row_count` doubled on every rerun against a persistent destination, including this component's own default duckdb-file destination, which is a real on-disk file, not in-memory). `"merge"` upserts keyed on `doc_id` (the Confluence page_id) instead, so pages from a prior run that this run didn't revisit (e.g. `max_pages` capped this run short) are kept rather than dropped. `"append"` is the old behavior, kept as an explicit opt-in for a deliberate historical log of every run.

As a safety net independent of `write_disposition`, the returned DataFrame is always deduplicated by `doc_id`, keeping the row with the latest `updated_at` -- this catches stale rows regardless of mode (including `"append"`'s intentional destination-level accumulation, which the DataFrame output never shows). Run metadata reports `write_disposition`, `load_id`, `pages_fetched` (pages this run fetched), `rows_returned` (the deduplicated row count), and `duplicate_rows_removed` (how many the safety net dropped -- nonzero with `"append"`).
