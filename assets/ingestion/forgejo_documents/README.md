# ForgejoDocumentsComponent

Extract Forgejo (or Gitea) repo **file content** (README/markdown/text) and **issue/pull-request text bodies**, normalized to the document-source contract shared by every RAG-source component in this repo. Forgejo is a self-hosted, community-run fork of Gitea, and its REST API is route-for-route compatible with Gitea's — this component works unmodified against either. It walks the repo's file tree (`GET git/trees/{ref}?recursive=true`), fetches matching files' content (`GET contents/{path}` — base64-encoded, with a real per-file `last_commit_when` timestamp Forgejo returns inline), and reuses issue text bodies (`GET issues?type=issues`) and pull request text bodies from `GET pulls` — Forgejo's own dedicated endpoint for PRs (a separate endpoint from `issues`, unlike GitHub, which conflates both behind one `/issues` route).

`resources` (`files`, `issues`, `pulls`) is a genuine multi-resource concept — unlike a flat single-page-source component, selecting just `files` skips issue/PR pagination entirely, and vice versa. `asset_shape='multi_asset'` gives each resource its own independently-materializable asset; the default `asset_shape='single'` unions them into one DataFrame tagged by a `_resource` column.

## Use cases

- Feed a RAG pipeline real documentation text (README, `docs/`, markdown/rst files) instead of just repo metadata
- Chunk + embed issue/PR discussions for a support or engineering-knowledge chatbot
- Build a searchable knowledge base over a self-hosted Forgejo/Gitea docs-as-code repository, updated on a schedule
- Combine with `document_chunker` (`source_column: content`) for an end-to-end Forgejo-to-vector-store pipeline
- Persist straight into Snowflake/BigQuery/Postgres/etc. via `destination`, skipping a separate warehouse-load step

## Dependencies

- `dlt>=1.0.0`
- `pandas>=1.5.0`
- `requests>=2.28.0`

## Document-source contract

Every row (regardless of `source_type`) carries these columns:

| Column | Description |
|---|---|
| `doc_id` | File path (for `forgejo_file`) or Forgejo issue/PR numeric id |
| `content` | File text content, or the issue/PR body (markdown) |
| `title` | Filename, or issue/PR title |
| `url` | `html_url` from Forgejo's API |
| `source_type` | `forgejo_file` / `forgejo_issue` / `forgejo_pull_request` |
| `updated_at` | Real per-file `last_commit_when` for files (falls back to fetch time only if absent); the real `updated_at` for issues/PRs |
| `content_hash` | sha256 of `content` |

## Examples

Docs directory only, markdown files:

```yaml
type: dagster_community_components.ForgejoDocumentsComponent
attributes:
  asset_name: platform_docs
  api_base_url: https://git.mycompany.com/api/v1
  access_token_env_var: FORGEJO_TOKEN
  owner: platform-team
  repo: service
  file_extensions: ".md,.mdx"
  path_prefix: docs/
  resources: files
```

Everything, independently materializable, persisted to Snowflake:

```yaml
type: dagster_community_components.ForgejoDocumentsComponent
attributes:
  asset_name: forgejo_kb
  api_base_url: https://codeberg.org/api/v1
  owner: forgejo
  repo: forgejo
  asset_shape: multi_asset
  destination: snowflake
  dataset_name: forgejo_docs
  persist_only: true
```

## Auth

| Mode | When | How |
|---|---|---|
| Personal access token | Private repos, or to avoid aggressive unauthenticated rate limits | Set `access_token_env_var`. Sent as `Authorization: token <token>` — Forgejo's own documented convention (NOT GitHub's `Bearer` scheme, NOT GitLab's `PRIVATE-TOKEN` header) |
| Unauthenticated | Public repos only | Leave `access_token_env_var` unset |

## Notes on what's verified vs. inferred

Verified directly from Forgejo's own live Swagger/OpenAPI spec (`https://codeberg.org/swagger.v1.json`) and its prose API-usage docs: the `Authorization: token <token>` auth convention, the `Link`-header + `page`/`limit` pagination shape, the `issues` endpoint's `type=issues` filter (lets issues and PRs be fetched without any post-hoc splitting), the dedicated `pulls` endpoint (Forgejo's own name for the resource — not `pull_requests`/`merge_requests`), the `ContentsResponse` shape (including the real `last_commit_when` timestamp), and the `GitTreeResponse`/`GitEntry` shape.

Not explicitly confirmed (flagged, not guessed as fact): whether the `git/trees/{sha}` path segment accepts a branch/tag name in practice (the spec's own parameter description says only "sha of the commit"); the exact `GitEntry.type` enum values (`"blob"`/`"tree"`) are inferred from the standard git object model GitHub's/GitLab's equivalent endpoints use identically, not spelled out in Forgejo's own definitions; and whether `contents` omits `content` for an oversized file the way GitHub's Contents API does (handled defensively either way).
