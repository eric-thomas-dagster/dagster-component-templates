# GithubDocumentsComponent

Extract GitHub repo **file content** (README/markdown/text) and **issue/PR text bodies**, normalized to the document-source contract shared by every RAG-source component in this repo. `github_ingestion` (a separate, pre-existing component) syncs repo metadata/issues/PRs as structured dlt rows — it never fetches the actual content of files in the repo tree. This component's whole purpose is the opposite: walk the repo's file tree (`GET git/trees/{ref}?recursive=1`), fetch matching files' content (`GET contents/{path}`), and reuse issue/PR text bodies (`GET issues?state=all`, which GitHub returns from one endpoint, tagged `github_issue` vs `github_pr` via the presence of a `pull_request` key).

`resources` (`files`, `issues`, `prs`) is a genuine multi-resource concept — unlike a flat single-page-source component, selecting just `files` skips issue/PR pagination entirely, and vice versa. `asset_shape='multi_asset'` gives each resource its own independently-materializable asset; the default `asset_shape='single'` unions them into one DataFrame tagged by a `_resource` column.

## Use cases

- Feed a RAG pipeline real documentation text (README, `docs/`, markdown/rst files) instead of just repo metadata
- Chunk + embed issue/PR discussions for a support or engineering-knowledge chatbot
- Build a searchable knowledge base over a docs-as-code repository, updated on a schedule
- Combine with `document_chunker` (`source_column: content`) for an end-to-end GitHub-to-vector-store pipeline
- Persist straight into Snowflake/BigQuery/Postgres/etc. via `destination`, skipping a separate warehouse-load step

## Dependencies

- `dlt>=1.0.0`
- `pandas>=1.5.0`
- `requests>=2.28.0`

## Document-source contract

Every row (regardless of `source_type`) carries these columns:

| Column | Description |
|---|---|
| `doc_id` | File path (for `github_file`) or GitHub issue/PR numeric id |
| `content` | File text content, or the issue/PR body (markdown) |
| `title` | Filename, or issue/PR title |
| `url` | `html_url` from GitHub's API |
| `source_type` | `github_file` / `github_issue` / `github_pr` |
| `updated_at` | Fetch time for files (GitHub's Contents API has no per-file timestamp); the real `updated_at` for issues/PRs |
| `content_hash` | sha256 of `content` |

## Examples

Docs directory only, markdown files:

```yaml
type: dagster_community_components.GithubDocumentsComponent
attributes:
  asset_name: dagster_docs
  owner: dagster-io
  repo: dagster
  ref: master
  file_extensions: ".md,.mdx"
  path_prefix: docs/
  resources: files
```

Everything, independently materializable, persisted to Snowflake:

```yaml
type: dagster_community_components.GithubDocumentsComponent
attributes:
  asset_name: github_kb
  owner: my-org
  repo: my-repo
  access_token_env_var: GITHUB_TOKEN
  asset_shape: multi_asset
  destination: snowflake
  dataset_name: github_docs
  persist_only: true
```

## Auth

| Mode | When | How |
|---|---|---|
| Personal access token / GitHub App token | Private repos, or to avoid aggressive unauthenticated rate limits | Set `access_token_env_var`. Sent as `Authorization: Bearer <token>` |
| Unauthenticated | Public repos only | Leave `access_token_env_var` unset |
