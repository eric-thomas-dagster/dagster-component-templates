# GitlabDocumentsComponent

Extract GitLab repo **file content** (README/markdown/text) and **issue/merge-request text bodies**, normalized to the document-source contract shared by every RAG-source component in this repo. `gitlab_ingestion` (a separate, pre-existing component) syncs project metadata/issues/merge_requests/commits as structured dlt rows — it never fetches the actual content of files in the repo tree. This component's whole purpose is the opposite: walk the repo's file tree (`GET repository/tree?recursive=true`), fetch matching files' raw content (`GET repository/files/:file_path/raw`), and reuse issue/MR text bodies (`GET issues` / `GET merge_requests`).

`resources` (`files`, `issues`, `merge_requests`) is a genuine multi-resource concept — unlike a flat single-page-source component, selecting just `files` skips issue/MR pagination entirely, and vice versa. `asset_shape='multi_asset'` gives each resource its own independently-materializable asset; the default `asset_shape='single'` unions them into one DataFrame tagged by a `_resource` column.

## Use cases

- Feed a RAG pipeline real documentation text (README, `docs/`, markdown/rst files) instead of just repo metadata
- Chunk + embed issue/MR discussions for a support or engineering-knowledge chatbot
- Build a searchable knowledge base over a docs-as-code repository, updated on a schedule
- Combine with `document_chunker` (`source_column: content`) for an end-to-end GitLab-to-vector-store pipeline
- Persist straight into Snowflake/BigQuery/Postgres/etc. via `destination`, skipping a separate warehouse-load step

## Dependencies

- `dlt>=1.0.0`
- `pandas>=1.5.0`
- `requests>=2.28.0`
- `tabulate>=0.9.0`

## Document-source contract

Every row (regardless of `source_type`) carries these columns:

| Column | Description |
|---|---|
| `doc_id` | File path (for `gitlab_file`) or GitLab issue/MR numeric id |
| `content` | File text content, or the issue/MR description (markdown) |
| `title` | Filename, or issue/MR title |
| `url` | `web_url` from GitLab's API for issues/MRs; a best-effort blob-view URL (or the raw API URL) for files — see module docstring |
| `source_type` | `gitlab_file` / `gitlab_issue` / `gitlab_merge_request` |
| `updated_at` | Fetch time for files (the raw-file endpoint has no per-file timestamp); the real `updated_at` for issues/MRs |
| `content_hash` | sha256 of `content` |

## Examples

Docs directory only, markdown files:

```yaml
type: dagster_community_components.GitlabDocumentsComponent
attributes:
  asset_name: platform_docs
  access_token_env_var: GITLAB_TOKEN
  project_id: "my-group/platform"
  file_extensions: ".md,.mdx"
  path_prefix: docs/
  resources: files
```

Everything, independently materializable, persisted to Snowflake:

```yaml
type: dagster_community_components.GitlabDocumentsComponent
attributes:
  asset_name: gitlab_kb
  access_token_env_var: GITLAB_TOKEN
  project_id: "42"
  asset_shape: multi_asset
  destination: snowflake
  dataset_name: gitlab_docs
  persist_only: true
```
