# LogRocket Ingestion

Ingest LogRocket (logrocket.com) session-replay / frontend-monitoring audit log and session data-export records using dlt's generic REST API source.

Uses dlt's generic REST API source (`dlt.sources.rest_api.rest_api_source`).

By default, runs an in-memory DuckDB pipeline and returns a pandas DataFrame. Set `destination` to persist directly to any dlt-supported destination. See `../DESTINATIONS.md`.

> **Verified directly against LogRocket's live docs** (fetched 2026-10-08):
> - **Base URL**: `https://api.logrocket.com/v1`. Confirmed directly on both https://docs.logrocket.com/docs/audit-log-api and https://docs.logrocket.com/docs/data-export.
> - **Auth**: `Authorization: token <api-key>` -- confirmed on both pages above. This is LogRocket's own custom "token" scheme, **not** `Bearer <token>`. API keys are created in the LogRocket dashboard under Settings > API Keys.
> - Both documented list endpoints are scoped per-org AND per-app via required URL path segments: `/orgs/<org_id>/apps/<app_id>/...`. This connector requires `org_id` and `app_id` fields for this reason (same role as chargify_ingestion's `subdomain` field).
> - **`audit_logs`** -> `GET /orgs/<org_id>/apps/<app_id>/audit/logs/`. Exports Settings > Audit Log entries. Cursor-paginated (`limit`, `cursor` query params; response includes `has_next`, `cursor`, and a `logs` array of `{time, created_date, user, action, description}`).
> - **`session_exports`** -> `GET /orgs/<org_id>/apps/<app_id>/data-export/`. Returns a cursor-paginated list of signed URLs to JSON-Lines files containing exported session data (sessions export to these files after ~1 hour of inactivity). Response: `{cursor, sessions: [{url}, ...]}`. Each row is a *pointer* to an export file, not the session's raw event data -- downloading/parsing those files is a separate downstream step. Accepts an optional starting point via `export_start_date` (ISO date, converted internally to the epoch-milliseconds `date` param the real API expects).
> - Deliberately **not** used as pull resources, despite being documented REST surfaces: the **User Identification API** (a PUT/write endpoint for sending traits *into* LogRocket, not pulling data out), the **Galileo Highlights API** / Session Highlights API (an async AI-query job -- `POST .../highlights/` keyed on a specific `userEmail`/`userID` plus `GET .../highlights?id=...` polling -- not a periodically pollable list of records), and **Streaming Data Export** (push-based, not something this component polls).

> **Partition honesty note:** if you set `partition_type`, it controls Dagster's materialization/backfill schedule only. This connector's compute function does not use the partition key to filter the API request, so every partition run re-fetches the same full resource set rather than a bounded window.

## Configuration

| Field | Required | Description |
|---|---|---|
| `asset_name` | required | Name of the asset that will hold the data |
| `org_id` | required | LogRocket organization ID (required path segment for every API call). |
| `app_id` | required | LogRocket application/project ID (required path segment for every API call). |
| `api_key` | required | LogRocket API key, sent as `Authorization: token <api_key>` (LogRocket's custom 'token' auth scheme, NOT Bearer). |
| `resources` | optional | Comma-separated list of resources to extract: audit_logs, session_exports. Default: `audit_logs,session_exports` |
| `export_start_date` | optional | Start date (ISO 'YYYY-MM-DD') for the `session_exports` resource's optional `date` param. If unset, the API's default starting point is used. |

## Example
```yaml
type: dagster_component_templates.LogRocketIngestionComponent
attributes:
  asset_name: logrocket_ingestion
  org_id: "${LOGROCKET_ORG_ID}"
  app_id: "${LOGROCKET_APP_ID}"
  api_key: "${LOGROCKET_API_KEY}"
  resources: "audit_logs,session_exports"
```
