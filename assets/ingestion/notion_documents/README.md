# Notion Documents

Extract full Notion page **body text** (not just page metadata) for RAG pipelines, ready to feed into `document_chunker`.

> **Note:** `notion_ingestion` (a separate, pre-existing component in this repo) syncs Notion database rows/page *metadata* via dlt's verified `notion` source -- it does NOT fetch a page's body content. This component's whole purpose is the opposite: it walks a page's actual block tree (`GET /v1/blocks/{block_id}/children`, recursively for any block with `has_children: true`) and renders it to markdown, so a RAG pipeline has real page text to chunk/embed.

Verified against Notion's own API reference (https://developers.notion.com/reference): `Authorization: Bearer <NOTION_API_KEY>` + a required `Notion-Version` header (current value `2026-03-11`); `GET /v1/blocks/{block_id}/children` (paginated via `start_cursor`/`has_more`/`next_cursor`); `POST /v1/databases/{database_id}/query` (same pagination shape, returns full Page objects); `GET /v1/pages/{page_id}` for single-page metadata. There is no documented "list all descendant pages" endpoint -- page-tree walking recursively follows `child_page` blocks discovered while walking content, the one real confirmed mechanism for that.

Set `database_id` to extract every page in a Notion database, or `root_page_ids` (comma-separated) to walk one or more page trees. Exactly one of the two is required. `include_child_databases` (default `false`) additionally recurses into any `child_database` block found during a page-tree walk.

This connector is hand-written with a plain `@dlt.resource` generator (same approach as `firecrawl_ingestion` -- recursive block-walking isn't a declarative REST-pagination shape dlt's `rest_api_source` fits), so destination flexibility, `hash_columns`, `on_schema_change`, `exclude_columns`, and `max_rows_per_resource` all still work identically to every other ingestion component. There is no multi-table concept here -- one run produces a flat set of page-body rows -- so there is no `asset_shape`/multi_asset option.

By default, runs an in-memory DuckDB pipeline and returns a pandas DataFrame. Set `destination` to persist directly to any dlt-supported destination. See `../DESTINATIONS.md`.

## Configuration

| Field | Required | Description |
|---|---|---|
| `asset_name` | required | Name of the asset that will hold the data |
| `api_key_env_var` | optional (default `NOTION_API_KEY`) | Env var holding your Notion integration token. |
| `database_id` | optional | Notion database ID to query. Required unless `root_page_ids` is set. |
| `root_page_ids` | optional | Comma-separated Notion page IDs to walk as page trees. Required unless `database_id` is set. |
| `include_child_databases` | optional (default `false`) | Page-tree mode only: also recurse into `child_database` blocks found while walking. |
| `rate_limit_delay` | optional (default `0.34`) | Seconds to sleep after each top-level document (page or database row) is processed. |

Exactly one of `database_id` / `root_page_ids` is required -- enforced at config-resolution time, not just at runtime.

## Output shape

One row per extracted Notion page, following the document-source contract shared by every document-source ingestion component in this repo: `doc_id`, `content` (markdown, rendered from the walked blocks), `title`, `url`, `source_type` (`"notion"`), `updated_at` (`last_edited_time`), `content_hash` (sha256 of `content`). Point `document_chunker`'s `upstream_asset_key` at this asset, `source_column` at `content`, and (optionally) `metadata_columns` at `url,title,updated_at`.

## Re-running without duplicating rows

`write_disposition` (default `"replace"`) controls what a rerun does to the destination table: `"replace"` (default) makes each run fully replace the table -- the right default here, since dlt's own default (`"append"`) has no notion of a previous run's pages becoming stale and keeps adding another full copy of every page on top of the last. `"merge"` upserts keyed on `doc_id` (the Notion page id) instead, so pages from a prior run that this run didn't revisit are kept rather than dropped. `"append"` is the old behavior, kept as an explicit opt-in for a deliberate historical log of every extraction.

As a safety net independent of `write_disposition`, the returned DataFrame is always deduplicated by `doc_id`, keeping the row with the latest `updated_at` -- this catches stale rows regardless of mode (including `"append"`'s intentional destination-level accumulation, which the DataFrame output never shows). Run metadata reports `write_disposition`, `load_id`, `pages_extracted` (pages this run fetched), `rows_returned` (the deduplicated row count), and `duplicate_rows_removed` (how many the safety net dropped -- nonzero with `"append"`, or if the same page is reachable from more than one root/database).

## Example
```yaml
type: dagster_community_components.NotionDocumentsComponent
attributes:
  asset_name: notion_documents
  database_id: "a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4"
```

To walk one or more page trees instead of a database:
```yaml
type: dagster_community_components.NotionDocumentsComponent
attributes:
  asset_name: notion_wiki
  root_page_ids: "a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4,b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5"
  include_child_databases: true
```
