# Postman Ingestion

Ingest Postman (getpostman.com / postman.com) API-platform collection, workspace, environment, and monitor metadata using dlt's generic REST API source.

Uses dlt's generic REST API source (`dlt.sources.rest_api.rest_api_source`).

By default, runs an in-memory DuckDB pipeline and returns a pandas DataFrame. Set `destination` to persist directly to any dlt-supported destination. See `../DESTINATIONS.md`.

> **Verified against Postman's current public API reference** (https://learning.postman.com/api-docs/api-reference and https://learning.postman.com/docs/reference/postman-api/authentication):
> - **Base URL**: `https://api.postman.com`. This is the base URL the current docs document explicitly (an EU-resident alternative, `https://api.eu.postman.com`, exists for Enterprise accounts on EU data residency). The older `https://api.getpostman.com` host still responds live (verified: returns the same 401-unauthenticated shape as `api.postman.com` rather than a 404 or redirect, i.e. it's a live auth-gated alias, not dead), but `api.postman.com` is what the current docs reference, so that's what this connector uses.
> - **Auth**: API key sent in the `X-Api-Key` request header (header names are case-insensitive on the wire; some Postman docs render it `X-API-Key`). Generated in Postman account settings > API keys.
> - **`collections`** -> `GET /collections` -- all collections accessible to the caller. **Response is wrapped**: `{"collections": [...], "meta": {...}}` -- NOT a bare array, so `data_selector` is `"collections"`, not `"$"`.
> - **`workspaces`** -> `GET /workspaces` -- all workspaces accessible to the caller. Response wrapped: `{"workspaces": [...], "meta": {...}}` (`data_selector: "workspaces"`).
> - **`environments`** -> `GET /environments` -- all environments accessible to the caller. Response wrapped: `{"environments": [...]}` (`data_selector: "environments"`).
> - **`monitors`** -> `GET /monitors` -- all monitors accessible to the caller. Response wrapped: `{"monitors": [...], "meta": {...}}` (`data_selector: "monitors"`).
>
> All four resources are flat (non-nested, no required path/query params) GET list endpoints -- none require client-supplied params for a basic listing, unlike e.g. Reclaim's `/api/events/v2` which requires a `start`/`end` window.

> **Partition honesty note:** if you set `partition_type`, it controls Dagster's materialization/backfill schedule only. This connector's compute function does not use the partition key to filter the API request, so every partition run re-fetches the same full resource set rather than a bounded window.

## Configuration

| Field | Required | Description |
|---|---|---|
| `asset_name` | required | Name of the asset that will hold the data |
| `api_key` | required | Postman API key, sent as the X-Api-Key header. Generated in Postman account settings under API keys. |
| `resources` | optional | Comma-separated list of resources to extract: collections, workspaces, environments, monitors. Default: `collections,workspaces` |

## Example
```yaml

  asset_name: postman_ingestion
  api_key: "${POSTMAN_API_KEY}"
  resources: "collections,workspaces"
```
