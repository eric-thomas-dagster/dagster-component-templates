# RudderStack Ingestion

Ingest RudderStack warehouse-native CDP Data Catalog tracking-plan, audit-log, and organization usage data using dlt's generic REST API source.

Uses dlt's generic REST API source (`dlt.sources.rest_api.rest_api_source`).

By default, runs an in-memory DuckDB pipeline and returns a pandas DataFrame. Set `destination` to persist directly to any dlt-supported destination. See `../DESTINATIONS.md`.

> **Verified against RudderStack's primary docs** (rudderstack.com/docs/api/, not a third-party profile):
> - RudderStack's core product is an event-collection/routing data plane (sources push events out to destinations/warehouses) -- it has **no bulk "list all customer records" API** the way a traditional CDP vendor does. The real, documented, pull-able *control-plane* APIs are the Data Catalog API, the Audit Logs API, and the Organization Usage API, which is what this connector exposes. This is a genuine shape difference from the other ingestion connectors in this batch (mParticle/Amperity/Tealium/Pardot/Attentive all have actual customer/audience-record APIs); RudderStack's value here is pipeline-governance reporting (which tracking plans/events exist, who changed what, event volume trends), not customer-record warehousing.
> - **Base URL**: `https://api.rudderstack.com` (`https://api.eu.rudderstack.com` for EU-hosted workspaces -- set `region='eu'`).
> - **Auth**: `Authorization: Bearer <SERVICE_ACCESS_TOKEN>` -- a workspace-level Service Access Token created under Workspace Settings -> Access Tokens.
> - **`tracking_plans`** -> `GET /v2/catalog/tracking-plans` -- lists every Tracking Plan in the workspace.
> - **`audit_logs`** -> `GET /v2/audit-logs` -- paginated audit trail of workspace changes. Supports `per_page` (1-100, default 100) and `created_after` (ISO datetime) filters.
> - **`usage`** -> `GET /v2/organizations/usage/event-metrics` -- organization-level event-volume metrics bucketed by `granularity` (day/week/month) starting at `start` (YYYY-MM-DD). Both params are required by the real API; this connector defaults `start` to 7 days ago (UTC) if unset.

> **Partition honesty note:** if you set `partition_type`, it controls Dagster's materialization/backfill schedule only. This connector's compute function does not use the partition key to filter the API request, so every partition run re-fetches the same full resource set rather than a bounded window.

## Configuration

| Field | Required | Description |
|---|---|---|
| `asset_name` | required | Name of the asset that will hold the data |
| `service_access_token` | required | RudderStack workspace-level Service Access Token (Bearer). |
| `region` | optional | 'us' or 'eu'. Default: `us` |
| `resources` | optional | Comma-separated list: tracking_plans, audit_logs, usage. Default: `tracking_plans,audit_logs` |
| `audit_log_created_after` | optional | ISO datetime lower-bound filter for audit_logs. |
| `audit_log_per_page` | optional | Page size for audit_logs (1-100). Default: `100` |
| `usage_granularity` | optional | 'day', 'week', or 'month'. Default: `day` |
| `usage_start_date` | optional | ISO date start for usage metrics. Defaults to 7 days ago (UTC). |

## Example
```yaml
type: dagster_component_templates.RudderStackIngestionComponent
attributes:
  asset_name: rudderstack_ingestion
  service_access_token: "${RUDDERSTACK_SERVICE_ACCESS_TOKEN}"
  resources: "tracking_plans,audit_logs"
```
