# Salesloft People Ingestion

Fetch Salesloft People via `GET /v2/people.json` and materialize the result as a pandas DataFrame.

Uses the `salesloft_resource` component for authentication (see `resources/salesloft_resource`).

## Installation

```bash
pip install requests pandas
```

Also requires a `SalesloftResourceComponent` on the same code location for authentication (see `resources/salesloft_resource`).

## Output Schema

The DataFrame has one row per person, with whatever fields Salesloft's
`/v2/people.json` returns (varies per org/custom-fields configuration —
common ones include `id`, `email_address`, `first_name`, `last_name`,
`title`, `created_at`, `updated_at`). Unlike Outreach, Salesloft's `data`
array is already a flat list of field dicts, not a JSON:API
`attributes`-wrapped shape — no unwrapping is needed.

## Salesloft API notes

- Response envelope: `{"data": [...], "metadata": {"paging": {"per_page", "current_page", "next_page", "total_pages"}, ...}}`.
  This component pages via `metadata.paging.next_page`, incrementing `page`
  until it's null/absent or `limit` is reached (confirmed against
  Salesloft's "Request & Response Format" / "Filtering, Paging, Sorting"
  docs; `per_page` defaults to 25 server-side and is capped at 100 —
  this component defaults to the max, 100).
- Timestamp range filtering uses the bracket-operator convention
  (`updated_at[gte]` / `updated_at[lte]`) documented generally for
  Salesloft list filters (e.g. `industry[_starts_with]=...`); the People
  endpoint's own filter docs don't spell out the timestamp operator by
  name, so this is the documented general convention rather than a
  People-specific confirmation — validate against a live org before
  depending on exact boundary semantics (inclusive vs exclusive).
- Auth is a static Bearer **API key**, not OAuth — simpler than Outreach
  (no token refresh/expiry to manage). Salesloft restricts API-key auth to
  customer accounts; partners must use OAuth2 instead.
