# sql_to_file_asset

Run a SQL query against a registered warehouse/database resource (or a raw connection URL env
var) and write the result set to a file -- local path or an fsspec URI (`s3://`, `gs://`,
`abfss://...`/`abfs://...`/`az://...`). The reverse direction of
[`adls_to_database_asset`](../adls_to_database_asset) / [`cloud_storage_copy_asset`](../cloud_storage_copy_asset)'s
`sink_table`: a Copy activity whose **sink is a file, not a table**.

Nothing here is invented fresh -- three established conventions already in this repo, combined:

- **SQL source dispatch** (`resource_key` -- `.get_engine()`/`.get_connection()`/`.get_client()` --
  OR `database_url_env_var`) is the same shape as `transforms/data_masking`'s own
  `_ingest_warehouse_query` helper.
- **File-sink writing** (fsspec URI + Azure credential env vars) is the same shape as
  `cloud_storage_copy_asset`'s own `_write_dataframe`/`_azure_storage_options`.
- **`run_window` / `pool` / `dry_run` / retry policy / partitioning** are the same shape as
  `sql_asset`'s.

## Example

```yaml
type: dagster_community_components.SqlToFileAssetComponent
attributes:
  asset_key: exports/daily_orders
  resource_key: snowflake_resource
  query: "SELECT * FROM orders WHERE order_date = CURRENT_DATE - 1"
  sink_path: s3://exports-bucket/orders/{partition_key}.parquet
  sink_format: parquet
  partition_type: daily
  partition_start: "2024-01-01"
```

`sink_path` supports `{partition_key}` templating, same convention as every other partitioned
file sink in this repo. `sink_format` is one of `csv` / `jsonl` / `json` / `parquet`.

## Connection: `resource_key` vs `database_url_env_var`

Set exactly one (unless `dry_run` is true, which needs neither):

- `resource_key`: a registered resource exposing `.get_engine()` (SQLAlchemy engine),
  `.get_connection()` (DBAPI connection), or `.get_client()` (vendor client -- BigQuery's
  `.query(sql).to_dataframe()`, Redshift's `.execute_query(sql, fetch_results=True,
  cursor_factory=RealDictCursor)`). Covers `duckdb_resource`, `snowflake_resource`,
  `postgres_resource`, and any other resource already registered project-wide in this shape.
- `database_url_env_var`: env var holding a SQLAlchemy URL, read at run time via a bare
  `create_engine(url)` -- bypasses Dagster's resource system entirely, so this asset's
  definitions always load cleanly even if the resource isn't wired up yet.

## Azure credentials

`azure_account_name_env_var` / `azure_account_key_env_var` / `azure_connection_string_env_var`
are only consulted when `sink_path` uses an `abfs://`/`abfss://`/`az://` scheme. Leave them unset
and Azure falls back to `adlfs`'s own ambient credential discovery, same as S3/GCS already do via
their own SDKs' default credential chains.

## `run_window` / `pool` / `dry_run`

Same conventions as `sql_asset`/`task_chain_asset`: `run_window` skips cleanly outside a
configured time window (e.g. don't run a heavy export during business hours), `pool` caps
concurrent exports via Dagster's named concurrency pools, and `dry_run` logs the query and
resolved `sink_path` without opening a connection or writing anything. To share one `run_window`
value across several assets instead of repeating the same literal string in each component
instance, see `task_chain_asset`'s README ("Sharing one `run_window` across several assets") for a
`template_vars_module` example.

## Requirements

```
dagster
pandas>=1.5.0
pydantic
sqlalchemy
```

Plus whichever `sink_path` scheme you actually use: `s3fs` (`s3://`), `gcsfs` (`gs://`), `adlfs`
(`abfs://`/`abfss://`/`az://`). `sink_format: parquet` additionally needs `pyarrow`.
