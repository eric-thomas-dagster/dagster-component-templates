# Tealium Ingestion

Ingest Tealium AudienceStream visitor-profile data (for a known list of identifiers) using dlt's generic REST API source.

Uses dlt's generic REST API source (`dlt.sources.rest_api.rest_api_source`).

By default, runs an in-memory DuckDB pipeline and returns a pandas DataFrame. Set `destination` to persist directly to any dlt-supported destination. See `../DESTINATIONS.md`.

> **Verified against Tealium's primary docs** (docs.tealium.com) -- this connector deviates from the rest of this batch in two real, confirmed ways:
>
> **1. Dynamic two-step auth, not a static bearer token.** Tealium's Visitor Profile API v3 requires a LOGIN call before any data call: `POST https://platform.tealiumapis.com/v3/auth/accounts/{account}/profiles/{profile}` with form-encoded `username` (an email) and `key` (the API key, used in place of a password) returns a JSON body of exactly `{"token": "<bearer token, valid 30 minutes>", "host": "<region-specific host, e.g. 'us-east-1-platform.tealiumapis.com'>"}`. The returned `host` -- not a fixed global host -- is the base URL for every subsequent data call, and the token expires in 30 minutes. This connector performs this login call inline inside the asset body (the same pattern already used by `quickbooks_ingestion`'s refresh_token exchange), since the base_url itself isn't known until after authenticating.
>
> **2. Identifier lookup, not a bulk "list all" endpoint.** The real Visitor Profile API v3 (`GET /v3/customer/visitor/accounts/{account}/profiles/{profile}` and its historical counterpart `GET /v3/customer/visitor/historical/accounts/{account}/profiles/{profile}`) looks up ONE visitor profile per call, identified by an `attributeId`/`attributeValue` pair. Tealium's actual bulk-export mechanisms (AudienceStore file drops to S3, AudienceDB direct Postgres access) are infrastructure-level, not REST-callable, so they're out of scope for a dlt rest_api_source connector. This connector instead takes a known list of identifier values (`lookup_values`, comma-separated) under one `lookup_attribute_id`, and fans out ONE dlt resource per value -- the same "one resource per parameterized call" shape already used by `reclaim_ingestion` for its habit-template split in this repo, just driven by a user-supplied list. Set `include_historical=true` to additionally pull each identifier's historical profile alongside its live one.

> **Partition honesty note:** if you set `partition_type`, it controls Dagster's materialization/backfill schedule only. This connector's compute function does not use the partition key to filter the API request, so every partition run re-fetches the same full resource set rather than a bounded window.

## Example
```yaml
type: dagster_component_templates.TealiumIngestionComponent
attributes:
  asset_name: tealium_ingestion
  account: "mycompany"
  profile: "main"
  username: "${TEALIUM_USERNAME}"
  api_key: "${TEALIUM_API_KEY}"
  lookup_attribute_id: "crm_id"
  lookup_values: "cust_1001,cust_1002,cust_1003"
```
