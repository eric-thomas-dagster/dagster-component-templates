# ZoomInfo Ingestion

Ingest ZoomInfo contact and company search data using dlt's generic REST API source.

Uses dlt's generic REST API source (`dlt.sources.rest_api.rest_api_source`).

By default, runs an in-memory DuckDB pipeline and returns a pandas DataFrame. Set `destination` to persist directly to any dlt-supported destination. See `../DESTINATIONS.md`.

> **Access reality, stated plainly:** ZoomInfo's API is real and well-documented (docs.gtm.ai, formerly docs.zoominfo.com -- the docs domain moved under ZoomInfo's "GTM AI" rebrand), but it is genuinely **not self-serve**. There is no public sign-up or free tier to obtain `client_id`/`client_secret` credentials -- API access requires an existing paid ZoomInfo contract, which means a sales process (demos, negotiation, procurement review) before a workspace admin can even generate credentials in the Admin Portal. This component is built faithfully anyway, the same way this repo already ships enterprise-gated connectors elsewhere (e.g. SAP/Workday-style tools) -- it assumes you already have a contract and admin access, and is not a "try it in five minutes" connector.

> **Verified against docs.gtm.ai**, ZoomInfo's current developer platform (docs.zoominfo.com now 301-redirects there post-rebrand):
> - **Base URL**: `https://api.zoominfo.com/gtm`.
> - **Auth**: OAuth 2.0 Client Credentials flow. Token endpoint: `POST https://api.zoominfo.com/gtm/oauth/v1/token`, with the client ID/secret passed via HTTP Basic auth (recommended) and `grant_type=client_credentials` in the body. The response is JSON with `access_token`, `expires_in` (seconds), `token_type` (always `"Bearer"`), and `scope`. This connector fetches a fresh token at the start of every run (tokens are short-lived) and sends it as `Authorization: Bearer <access_token>` on the data calls -- it does not cache/reuse a token across runs.
> - **`contacts_search`** -> `POST /data/v1/contacts/search` (OAuth2 scope `api:data:contact`). Accepts filter criteria in a JSON:API-shaped request body and returns **preview** contact records -- partial profiles meant to help you identify which contacts are worth a follow-up `enrich` call before spending enrichment credits, not full contact detail.
> - **`companies_search`** -> `POST /data/v1/companies/search` (OAuth2 scope `api:data:company`). Same preview-record model as contacts_search, for company/organization records.
> - ZoomInfo's `enrich` endpoints (`/data/v1/contacts/enrich`, presumably a symmetric `/data/v1/companies/enrich`) are **intentionally not exposed** as a `resources` option here: enrich is a "match N known records to their full profile" lookup that requires per-record identifiers (email, person ID, company domain, etc.) supplied by the caller -- it doesn't fit the "pull this whole resource into a table" shape this connector (and its siblings in this repo) are built around.
> - The exact request-body pagination contract for `contacts_search`/`companies_search` (JSON:API `page.number`/`page.size` vs. flat `page`/`per_page` fields) was **not fully confirmed** from the material available while building this connector. This connector sends a minimal `{"page": 1, "per_page": <page_size>}` body by default -- verify the exact shape against docs.gtm.ai for your contract/plan and extend `_build_resources_config` in `component.py` if it differs.

> **Partition honesty note:** if you set `partition_type`, it controls Dagster's materialization/backfill schedule only. This connector's compute function does not use the partition key to filter the API request, so every partition run re-fetches the same page rather than a bounded window.

## Partitioning

When `partition_type` is set, set `partition_date_column` (time partitions) or `partition_static_column` (static/dynamic/multi partitions) and each run returns only the rows in its partition; a backfill run covers its whole range. By default the extract is still fetched in full and loaded to the destination (dlt deduplicates by key), so the partition only scopes what downstream assets receive. To fetch just the partition's slice, set `partition_window_params` to the API's own time-filter parameters, e.g. `{start_param: updated_since, end_param: updated_until, format: iso}`; the window (the whole range for a backfill run) is then written into every resource's request (or only those in `partition_window_resources`). The parameter names are API specific, so take them from the API's docs. `backfill_policy` (`single_run` / `multi_run`) is opt-in; `single_run` needs a partition-range-aware IO manager.
