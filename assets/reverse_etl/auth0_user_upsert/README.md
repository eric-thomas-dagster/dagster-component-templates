# `Auth0UserUpsertComponent`

Reverse-ETL: sync a warehouse table of user records into Auth0 via the Management API's user endpoints.

## Safety

**Read this before pointing this component at a production Auth0 tenant.**

- **The default behavior is non-destructive, with zero special configuration.** With `operation` left unset (or explicitly set to `sync`), every row either (a) creates a new user if no Auth0 user shares its email, or (b) updates profile attributes on the existing user if one does. This mode **cannot** block, suspend, or delete anyone — there is no code path from `operation: sync` to any lifecycle-changing call.

- **Deactivation requires an explicit, separate config field.** A row can never deactivate a user just by having a particular column value. The only way to deactivate anyone is to set `operation: deactivate` on the component itself — a deliberate, reviewable configuration choice for that asset/run, never something inferred from upstream data. `fields_map` is additionally forbidden from ever targeting Auth0's `blocked` field directly (validated at `build_defs` time) — so even a malformed or malicious `fields_map` cannot smuggle a deactivation through the `sync` path.

- **Deactivate mode never creates a user.** If a row's email doesn't match an existing Auth0 user, it is skipped and counted (`rows_skipped_not_found`) — it is never used to create a new user that would then start out blocked. If more than one Auth0 user shares the row's email (Auth0 permits this across connections), the row is skipped and logged as ambiguous (`rows_skipped_ambiguous_email`) rather than guessing which account to act on.

- **There is no delete operation, anywhere, in this component, under any configuration.** Auth0's Management API does expose `DELETE /api/v2/users/{id}` — a true, permanent, unrecoverable hard delete — but neither this component nor `auth0_resource` ever calls it. `operation` only accepts `sync` or `deactivate`; any other value (including something like `"delete"`) is rejected at `build_defs` time with a clear `ValueError`, never silently ignored or guessed at.

- **`operation` is validated at build time, not guessed at runtime.** An unsupported value fails the component's `build_defs()` immediately — before any asset materializes, before any HTTP call is made — rather than silently no-op'ing or falling back to some default behavior.

If you need to permanently remove an Auth0 user, do it by hand in the Auth0 dashboard (or via a separate, explicitly-reviewed script) — not through this pipeline.

## Default (`operation: sync`) behavior, per row

1. Look up the row's email via `GET /api/v2/users-by-email`.
2. **Found exactly one match** → `PATCH /api/v2/users/{id}` with the row's mapped profile attributes only.
3. **Found none** → `POST /api/v2/users` to create a new user under the configured `connection`.
4. **Found more than one** (Auth0 allows the same email across different connections) → skipped and logged, never guessed.

## Explicit (`operation: deactivate`) behavior, per row

1. Look up the row's email the same way.
2. **Found none** → skipped (`rows_skipped_not_found`).
3. **Found more than one** → skipped (`rows_skipped_ambiguous_email`).
4. **Found exactly one** → `PATCH /api/v2/users/{id}` with **only** `{"blocked": true}` (Auth0's documented block mechanism — https://auth0.com/docs/manage-users/user-accounts/block-and-unblock-users). This PATCH never carries any other field.

## `fields_map`

Upstream column → Auth0 user field. Values can be:
- a top-level Auth0 user field (`email`, `name`, `given_name`, `family_name`, `nickname`, `phone_number`, `picture`, ...)
- a dotted path into `user_metadata`/`app_metadata` (e.g. `user_metadata.department`)

Exactly one value **must** be `email` (the match key). The value `blocked` is rejected at build time — see Safety above.

## Prerequisite: `connection`

Required because Auth0's create-user endpoint needs to know which connection to store new credentials under — even though only rows that end up creating a brand-new user actually use it. Use `Username-Password-Authentication` for a database connection, or your enterprise/SSO connection's name for federated users (in which case most profile attributes are typically sourced from the IdP and `password` is not applicable).

## Behavior + gotchas

- **Ambiguous email never guessed** — if a row's email matches more than one Auth0 user (possible across connections), the row is skipped in both `sync` and `deactivate` modes rather than picking one.
- **`blocked` is reserved** — `fields_map` cannot target it; `build_defs()` raises immediately if it does.
- **No delete, ever** — `operation` only accepts `sync`/`deactivate`; `auth0_resource` has no `delete_user` method at all.
- **Email changes via `sync`** — if `fields_map` maps a column to `email` and that row already has a match, the PATCH includes the new email value. Auth0 may reject this for some connection types; treat such errors as a data-hygiene signal, not a component bug.
