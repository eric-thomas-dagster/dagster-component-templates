# `BasecampTodoUpsertComponent`

Reverse-ETL: mirror an upstream DataFrame into Basecamp 3/4 to-dos in a target to-do list, create-or-update.

## Basecamp's unusual API shape (verified against basecamp/bc3-api's own docs)

Basecamp's REST API doesn't look like a typical multi-tenant SaaS API, and this component (via `basecamp_resource`) is built around three specifics confirmed directly against 37signals' own `bc3-api` reference:

1. **Per-account URL, not a single host.** Every request is scoped under `https://3.basecampapi.com/<account_id>/...` — there's no API host shared across accounts the way most SaaS APIs work. The account ID isn't even returned by the OAuth token exchange; it comes from a separate `https://launchpad.37signals.com/authorization.json` call made once, outside this component.
2. **OAuth2 only, no API-key shortcut.** Auth is a standard `Bearer` access token from a 3-legged authorization-code grant (same convention as `basecamp_ingestion`).
3. **The title field is called `content`, not `title`.** `content_column` maps to this.
4. **Updating a to-do requires the FULL field set every time** — `PUT .../todos/{id}.json` clears any field you omit rather than leaving it unchanged, so this component always sends `content` + `description` together.
5. **Completion is a separate sub-resource**, not a field on the main body: `POST .../todos/{id}/completion.json` marks done, `DELETE .../todos/{id}/completion.json` marks not-done.

Basecamp has no native "upsert" endpoint for to-dos, so (same as `github_issue_upsert` / `clickup_task_upsert` / `trello_card_upsert` / `wrike_task_upsert`) this component embeds a key marker (`<!-- dagster-key: <value> -->`) in the to-do's `description` and matches against it on every run — checking both active and completed to-dos, so a row isn't duplicated just because its to-do was already marked done.

## Behavior + gotchas

- **Pagination follows Basecamp's documented `?page=N` increment, not the raw `Link` header.** Basecamp's own docs confirm the `Link` header's next-page URL is literally `?page=N+1` under geared pagination (15/30/50/100 per page); this component increments `page` directly rather than threading raw HTTP response headers through the resource abstraction. An empty page always means "no more," regardless of page size.
- **Both active and completed to-dos are listed and matched** — a to-do that's already marked complete still gets found and updated (not duplicated) on a re-run.
- **No archive/trash support** — removing a row from the upstream DataFrame does not trash or archive the corresponding to-do.
- **`assignee_ids_column` always overwrites** — per Basecamp's "send everything" PUT semantics, an empty/missing value for a row still sends `assignee_ids: []` on update (clearing existing assignees), not "leave unchanged."
