# `BigCommerceProductUpsertComponent`

Reverse-ETL sink: mirror an upstream DataFrame into **BigCommerce Products** via the Catalog API (v3). BigCommerce has no native upsert endpoint, so this sink does search-then-write per row:

1. `GET /catalog/products?sku=<sku>&limit=1` — look up existing product by main SKU.
2. If found → `PUT /catalog/products/{id}` (partial update, unchanged fields preserved).
3. If not found → `POST /catalog/products` (new product).

**SKU is BigCommerce's unique (case-insensitive) key across the WHOLE catalog** — it's the natural merge key for reverse ETL. Unlike variant SKUs, the main product SKU must be unique store-wide.

## Required fields on create

BigCommerce's Create Product endpoint requires at minimum:

- `name` — product name (max 250 characters)
- `type` — `physical` or `digital`
- `weight` — numeric, used for shipping calculations
- `price` — base price

(`categories` is also required if your store has the V2 product experience enabled in the control panel.)

**Every row that results in a CREATE must map these four fields via `fields_map`** — otherwise BigCommerce rejects the POST with a 422. `PUT` updates are partial and do not need them re-sent.

```yaml
fields_map:
  product_sku: sku      # match key
  product_name: name     # required on create
  product_type: type     # required on create ('physical'/'digital')
  list_price: price      # required on create
  weight_lbs: weight     # required on create
```

## Flat body only (no variant nesting)

Unlike Shopify (which nests variant price/sku/inventory under `variants[0]` via a `variant_` prefix convention), this sink writes a **flat** BigCommerce product body straight from `fields_map` — there is no nesting convention here.

BigCommerce variants (size/color combinations, each with their own SKU/price/inventory) are a separate, more complex sub-resource at `/catalog/products/{id}/variants`. This sink covers the common **single-SKU-per-product** case. Multi-variant products need custom Dagster asset code using the resource's methods directly.

## When to use

- Sync a warehouse-side product catalog INTO BigCommerce Products (from a PIM, a dbt mart, or an authoritative source of truth).
- Push computed pricing (dynamic pricing, promo overrides) into BigCommerce product prices as a scheduled job.
- Mirror inventory counts or descriptions computed elsewhere into BigCommerce.

## Prerequisites

1. **Store-level API account with the right scopes** — Settings → API → Store-level API accounts → Create API Account:
   - **Products: read/write** at minimum.
2. **Access Token** — generated when you create the API account (shown once — copy it immediately). Store it in an env var.

## Pairs with

- **`bigcommerce_resource`** — store hash + access token + workhorse HTTP client (required).
- **`bigcommerce_ingestion`** — the READ-side counterpart (dlt-based bulk pull).

## Behavior + gotchas

- **SKU required** — every upstream row must have a value in the column mapped to `sku`; rows with `None` / `NaN` / `""` are skipped and counted in `rows_skipped_no_sku` metadata.
- **Blank vs missing** — `None` / `NaN` values are omitted from the request body (existing BigCommerce value preserved on update). Non-null values overwrite.
- **In-run cache** — if two upstream rows share the same sku, the sink caches the product id created on the first occurrence and PUTs it on the second (no double-post).
- **Response envelope** — every v3 response wraps its payload as `{"data": ..., "meta": {...}}`; the resource unwraps `data` for you.
- **Rate limits** — BigCommerce does NOT send a standard `Retry-After` header on 429 (unlike Shopify) — it sends `X-Rate-Limit-Time-Reset-Ms` (milliseconds). The resource retries honoring that header, up to `max_retries` (default 3).
- **Flat body, single variant** — only the top-level product fields are set. Multi-variant products need custom compute using the resource directly.
- **API version** — set on the resource (default `v3`).
