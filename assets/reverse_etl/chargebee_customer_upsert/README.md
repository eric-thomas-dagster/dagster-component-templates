# `ChargebeeCustomerUpsertComponent`

Reverse-ETL sink: mirror an upstream DataFrame into **Chargebee Customer** records.

## There is no upsert-by-key -- and no PUT/PATCH at all

Chargebee's REST API uses **POST for every mutating operation** — create, update, delete all go through POST. What distinguishes them is the URL path:

- **Create**: `POST /customers` — with an optional merchant-supplied `id` (auto-generated if omitted). If a customer with that `id` already exists, the call **fails** rather than updating it — there's no create-or-update fallback baked into this endpoint.
- **Update**: `POST /customers/{id}` — partial-merge semantics (only fields you send change). 404s if no customer with that id exists.

So a real "upsert" from this component's perspective requires, per row:

1. **Lookup**: `GET /customers?<lookup_field>[is]=<value>` — Chargebee's list endpoint with an operator-suffixed filter (e.g. `email[is]=a@b.com` or `id[is]=cust_123`) — discovers whether a matching customer already exists and, if so, its `id`.
2. **Write**: `POST /customers/{id}` (update) if a match was found, or `POST /customers` (create) if not.

**Two API calls per row, always** — Chargebee offers no atomic upsert-by-key for Customers.

## `lookup_field`

`lookup_field` (default `email`) **must** be a `fields_map` value, since it's used to build the `<field>[is]=` filter on the list call. Set `lookup_field: id` to match on a merchant-supplied id instead (requires an `id` entry in `fields_map` — Chargebee lets you assign your own ids at create time, which this component can then treat as the natural key).

## When to use

- Sync a dbt Customers mart into Chargebee for subscription billing.
- Push warehouse-computed customer attributes (plan tier, segment) into Chargebee custom fields via a mapped field.
- Keep Chargebee Customer records in sync with a CRM or external system of record.

## Example

```yaml
type: dagster_component_templates.ChargebeeCustomerUpsertComponent
attributes:
  asset_name: chargebee_customers_mirror
  upstream_asset_key: dbt_marts_customers
  resource_key: chargebee

  lookup_field: email
  fields_map:
    customer_id: id
    email: email
    first_name: first_name
    last_name: last_name
    company_name: company

  batch_size: 5000
```

## Behavior + gotchas

- **Lookup value required** — rows with `None`/`NaN` in the column mapped to `lookup_field` are skipped and counted in `rows_skipped_no_key`.
- **No bulk batching** — `api_requests` metadata is roughly `2 * rows_upserted` (one list-filter GET + one write POST per successful row).
- **Email is not guaranteed unique in Chargebee** — unlike `id`, Chargebee does not enforce email uniqueness across customers; if multiple customers share an email, the lookup matches the *first* one the list endpoint returns (`limit=1`), which may not be deterministic across runs. Prefer `lookup_field: id` with a merchant-supplied id when you control customer creation.
- **POST-only API** — this component never issues PUT/PATCH; "update" is simply `POST /customers/{id}`.
