# `CloseCrmLeadUpsertComponent`

Reverse-ETL sink: mirror an upstream DataFrame into **Close CRM Leads**. Close has **no native atomic upsert endpoint** (unlike Salesforce's External-ID upsert or HubSpot's batch/upsert) — this sink emulates one via **search-then-write**, using `close_crm_resource`'s `upsert_lead`:

- `POST /api/v1/data/search/` (Close's "Advanced Filtering" API) to look up an existing Lead by `dedupe_field`.
- `PUT /api/v1/lead/{id}/` if a match was found, else `POST /api/v1/lead/` to create.

## ⚠️ Not race-condition-safe

Because there is no atomic create-or-update call, **two concurrent writers upserting the same dedupe value can both miss each other's in-flight create and produce duplicate Leads.** Close's REST API offers no idempotency key, no conditional-write header, and no unique-constraint-on-create behavior to close this search → write window. Mitigate by:

- Never running two overlapping materializations of this asset (or two different pipelines) against the same set of dedupe values at the same time.
- Choosing a dedupe field that's actually unique (an email address, or — safest — a custom field holding your warehouse's primary key) rather than `name`, which Close does not enforce as unique. A non-unique `name` will silently create duplicate Leads even *without* any concurrency, because the search only ever inspects the *first* match it gets back.
- Periodically reconciling duplicates via Close's own Merge Leads feature if they do slip through.

This limitation is fundamental to Close's API, not a corner this component cut — see `close_crm_resource`'s README for the full discussion and the primary-docs citations behind it.

## `fields_map` vocabulary

Unlike Salesforce/HubSpot (arbitrary field-API-name → field-API-name), Close's Lead JSON has a fixed nested shape (`name`, `contacts[].name`, `contacts[].emails[].email`, `contacts[].phones[].phone`, plus flat `custom.cf_xxx` keys). `fields_map` values must be one of:

| Value | Maps to |
|---|---|
| `name` | The Lead's own `name` field. |
| `contact_name` | The primary contact's `name`. |
| `email` | The primary contact's first email (`type: "office"`). |
| `phone` | The primary contact's first phone (`type: "office"`). |
| `custom.cf_xxx` | A Lead custom field — flat top-level key on the Lead body (verified against Close's API docs: custom fields are `"custom.cf_xxx": value` at the top level, *not* nested under a `"custom"` object). |

This sink only models **one contact per Lead** (the common case for a 1:1 lead/contact warehouse mart). If your source data has multiple contacts per Lead, pre-aggregate upstream or open multiple asset instances keyed differently.

## `dedupe_field`

Must be a value present in `fields_map`, and must be one of the fields Close's Advanced Filtering API can search on:

- `email` (**recommended**) — matches via a `has_related` / `contact_email` query.
- `phone` — matches via a `has_related` / `contact_phone` query.
- `name` — matches the Lead's own `name` (not guaranteed unique — see the race-condition note above).
- `custom.cf_xxx` — matches by `custom_field_id`, exact match. **Safest option** when you have a warehouse-side external id to carry over.

`contact_name` is not a valid `dedupe_field` — Close has no search field for a contact's free-text display name.

## Behavior + gotchas

- **Dedupe field required** — every upstream row must have a value in the column mapped to `dedupe_field`; rows with `None` / `NaN` there are skipped and counted in `rows_skipped_no_key`.
- **Blank vs missing** — `None` / `NaN` values are simply omitted from the Lead body built for that row (they never overwrite an existing Close value with a blank).
- **Not atomic, not idempotent** — see the race-condition warning above. Each row costs at minimum 2 HTTP calls (search + create-or-update).
- **Rate limits** — Close enforces a sliding-window limit (per API key and per organization). The resource retries on 429 using Close's `RateLimit` response header, and on 5xx, up to `max_retries` (configured on `close_crm_resource`, default 3).
- **One contact per Lead** — this sink's flat `fields_map` only builds a single `contacts[0]` entry per row. Leads with multiple contacts need either pre-aggregation upstream or a separate sink/asset.
- **Custom fields are an id, not a label** — `custom.cf_xxx` must be the custom field's internal id (visible in Close under Settings → Custom Fields → the field → API docs), not its display label.
