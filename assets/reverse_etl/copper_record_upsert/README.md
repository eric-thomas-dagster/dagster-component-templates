# `CopperRecordUpsertComponent`

Reverse-ETL sink: mirror an upstream DataFrame into **Copper CRM People / Leads / Companies** via **search-then-write**. Copper has **no native atomic upsert endpoint** (unlike Salesforce's External-ID `PATCH`), so this sink emulates one per row:

1. `POST /{object_type}/search` with a filter shaped for `dedupe_field` (e.g. `{"emails": ["a@b.com"]}` for People).
2. If a match comes back, `PUT /{object_type}/{id}`.
3. If not, `POST /{object_type}` to create.

## ⚠️ Not race-condition-safe

**This is an important, non-hideable limitation.** Between the search read (step 1) and the write (step 2/3), another concurrent writer — another Dagster run, a human editing in the Copper UI, a different integration — can create or modify a record matching the same search filter without this method seeing it. The result is a **duplicate record** (Copper will happily create a second Person with the same email), not data corruption, but a duplicate nonetheless.

- Safe for **single-writer, sequential** reverse-ETL jobs (the common case: one nightly/hourly sync asset).
- **Not safe** if multiple processes may upsert the same `object_type` concurrently against overlapping key sets (e.g. two parallel-partitioned runs of this same asset, or a human actively working the same records in the Copper UI during a sync).

If you need stronger guarantees, consider serializing writes (no parallel partition runs for this asset) or doing your own idempotency bookkeeping upstream.

## Why Copper's shapes differ by object type

Verified against `developer.copper.com` — Copper's write-body and search-filter shapes are **not uniform** across object types:

| Object type | Write-body email shape | Search-filter email shape |
|---|---|---|
| **People** | `emails: [{"email": ..., "category": "work"}]` (array) | `{"emails": [value]}` (array) |
| **Leads** | `email: {"email": ..., "category": "work"}` (**singular** object) | `{"emails": value}` (**bare string**, not an array) |
| **Companies** | no emails field at all — only `email_domain` (string) | `{"email_domains": value}` (**plural** key — different from the write-body field name) |

All three object types accept `phone_numbers: [{"number": ..., "category": "work"}]` (array) and a plain top-level `name` string. This component handles all of the above shaping internally based on `object_type` — you just map upstream columns to the logical field names `name` / `email` / `phone` (or any other flat Copper field name, e.g. `email_domain` for Companies, a custom field slug, `details`, etc.) in `fields_map`.

## When to use

- Sync computed data (lead scores, segmentation flags, enrichment) from a warehouse INTO Copper so sales sees it in-context on a Person/Lead/Company record.
- Mirror a golden-record contacts table (dbt marts) into Copper People for a single-writer nightly sync.

## Prerequisites

1. **`dedupe_field` must uniquely identify a record** for your data — typically `email`. It MUST be present in `fields_map`'s values.
2. For **Companies**, map your email-like column to the Copper field name `email_domain` (not the logical `email`) since Companies have no `emails` array.

## Example

```yaml
type: dagster_component_templates.CopperRecordUpsertComponent
attributes:
  asset_name: copper_people_mirror
  upstream_asset_key: dbt_marts_contacts
  resource_key: copper

  object_type: people                  # people / leads / companies
  dedupe_field: email                  # searched via /people/search before writing

  fields_map:
    full_name: name                    # upstream col -> Copper field
    email_address: email               # -> emails: [{email, category: work}]
    phone_number: phone                # -> phone_numbers: [{number, category: work}]

  batch_size: 2000
  group_name: reverse_etl
```

## Example — Companies (note: email_domain, not email)

```yaml
type: dagster_component_templates.CopperRecordUpsertComponent
attributes:

  resource_key: copper
  object_type: companies

    domain: email_domain               # Companies have no emails array
    main_phone: phone
```

## Behavior + gotchas

- **Dedupe key required** — every upstream row must have a value in the column mapped to `dedupe_field`; rows with `None` / `NaN` there are skipped and counted in `rows_skipped_no_key`.
- **Blank vs missing** — `None` / `NaN` values are omitted from the request body entirely (not sent as empty strings), so an existing Copper value is only overwritten if the upstream has an actual value.
- **One HTTP round-trip pair per row** — this is search-then-write, not a bulk/composite endpoint; there is no Copper equivalent of Salesforce's `/composite/sobjects`. Expect roughly 2x the request count of an atomic-upsert sink (one search + one create-or-update per row).
- **Rate limits** — Copper enforces 180 requests/minute overall (rolling window) plus a 3 requests/second cap on Bulk endpoints; both return 429. The resource retries with exponential backoff (honoring `Retry-After`) up to `max_retries` (default 3).
- **Leads vs People email shape** — if you reuse a `fields_map` across object types, remember Leads use a singular `email: {...}` object while People use a plural `emails: [...]` array. This component handles the translation; you only ever write the logical `email` field name regardless of `object_type`.
