# `DocuSignEnvelopeSendComponent`

## ⚠️ This component SENDS REAL SIGNATURE REQUESTS — read before you materialize

Every row that resolves a recipient email + name creates a brand-new DocuSign envelope and, with the default `status: sent`, immediately emails that recipient a signature request — the moment this asset materializes. This is **not** a record upsert like `salesforce_record_upsert` — there's no match key, no create-or-update semantics, and no de-duplication across runs. Re-materializing against the same upstream rows sends duplicate envelopes.

**Before pointing this at a real warehouse table:**
- Test against your own test email addresses first — e.g. `source: {kind: inline, rows: [{signer_email: "you@corp.com", signer_name: "Test"}]}`.
- Consider setting `docusign_resource`'s `use_demo_env: true` to point at DocuSign's sandbox environment while testing.
- Set `status: created` instead of `sent` if you want envelopes to land as drafts in the sender's DocuSign account for manual review before anything is emailed.

## Not a record upsert

Unlike `salesforce_record_upsert` (canonical dual-source upsert pattern in this repo), there's no external-ID match key here — DocuSign envelopes aren't addressable/updatable the way SObject records are. Every materialization that resolves a recipient creates a new envelope. If you need idempotency (e.g. "don't re-send to a contract already sent today"), filter the upstream query/asset to exclude already-sent rows before they reach this component.

## New resource: `docusign_resource`

No DocuSign *write* resource existed in this repo before — only the read-only `docusign_ingestion` asset component. This component pairs with a new `docusign_resource` (`resources/docusign_resource/`), built following this repo's `outreach_resource` pattern: a `ConfigurableResource` wrapping the HTTP calls + a `Component` wrapper that registers it. It reuses the **same JWT Grant OAuth2 flow** `docusign_ingestion` already uses for reads (same auth fields: `integration_key`, `user_id`, `private_key`), so one Integration Key configuration covers both ingestion and activation.

## Template roles and prefilled tabs

`role_name` must match a recipient role already defined on the DocuSign template (`Setup → Templates → ... → Recipients`, e.g. `"Signer1"`). Each row's `recipient_email_column` / `recipient_name_column` are assigned to that role. Optionally, `tabs_map` prefills the template's text tabs from other row columns:

```yaml
tabs_map:
  contract_value: ContractValue   # upstream column -> template tabLabel
  effective_date: EffectiveDate
```

`email_subject_template` supports `{column_name}` substitution the same way, e.g. `"Please sign your {contract_type} agreement"`.

## Per-row failure isolation

One envelope creation failing (invalid template role, DocuSign API error, etc.) is caught and counted — it does **not** abort the run or the remaining rows. Metadata reports `envelopes_sent` / `envelopes_failed` / `rows_skipped_no_recipient` (blank/null email or name), `first_envelope_ids` (a sample of created envelope IDs), and a `first_errors` sample when failures occur.

## When to use

- Send a signature-request envelope for every contract/order a warehouse query marks "ready for signature".
- Trigger an e-signature workflow from a dbt mart (e.g. new-hire paperwork, vendor agreements) without a human manually uploading each one in the DocuSign UI.

## Pairs with

- **`docusign_resource`** — JWT Grant OAuth2 auth via `requests` + `pyjwt` + `cryptography` (required, new resource built for this component).

## Partitioning

When `partition_type` is set, a run sends only the rows in its partition: `partition_date_column` selects the rows whose date falls in a time partition's window (a backfill run covers its whole range) and `partition_static_column` selects the rows for a static/dynamic partition key. Unpartitioned runs send every row.
