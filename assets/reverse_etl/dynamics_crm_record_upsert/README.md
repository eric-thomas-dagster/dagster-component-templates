# `DynamicsCrmRecordUpsertComponent`

Reverse-ETL sink: mirror an upstream DataFrame into a **Microsoft Dynamics 365 (Dataverse)** entity set using Dataverse's **native alternate-key upsert**. Atomic create-or-update in a single request — no search-then-write, no eventual consistency window, no idempotency-key gymnastics.

For each upstream row:
- `PATCH {org_url}/api/data/{api_version}/{entity_set}({alternate_key_field}='{value}')`

With `prefer_representation: true` (default), Dataverse returns:
- **201 Created** if no row matched the alternate key → new row inserted, body includes the row's real GUID.
- **200 OK** if a row matched → row updated in place, body includes the GUID.

Without `prefer_representation`, Dataverse always returns **204 No Content** for *both* outcomes — they're genuinely indistinguishable from the status code alone, and the `OData-EntityId` response header echoes back the alternate-key reference you sent, not the row's real GUID. Keep the default on unless the extra server-side retrieve measurably matters for your load size.

## Entity set names

Dataverse entity **set** names are the plural, lowercase logical name of the table — `accounts`, `contacts`, `leads`, `opportunities`, or a custom table's plural logical name (e.g. `new_customthings`). This is NOT the singular, display-cased name shown in the maker portal UI ("Account", "Contact"). Get it wrong and every request 404s.

## Why one PATCH per row (no composite/bulk mode)

Unlike Salesforce (`/composite/sobjects`, Bulk 2.0), Dataverse has no single-call bulk/composite upsert endpoint. An OData `$batch` endpoint does exist (`POST {org_url}/api/data/{api_version}/$batch`, `multipart/mixed` request bodies, optionally grouped into atomic "changesets" of up to 1,000 operations), but using it means hand-building and parsing raw MIME multipart request/response bodies from scratch. That's real complexity for a win that's about HTTP round-trip count, not server-side parallelism the way Salesforce's Bulk 2.0 is. This component issues **one PATCH per row** via `dynamics_crm_resource.upsert_by_key()`. `$batch` is a documented, not-yet-implemented future optimization — not a fake "composite mode" bolted on for parity with the Salesforce sink.

## When to use

- Sync computed data (lead scores, segmentation flags, health scores) from a warehouse INTO Dynamics 365 so sales/CS teams see them in-context.
- Mirror a golden-record customer table (dbt marts, Reverse-ETL best-practice) into Dynamics Accounts/Contacts with atomic alternate-key match.
- Push status changes into Dynamics as a nightly job.

## Prerequisite: Alternate Key on the table

The `alternate_key_field` you pass MUST be a pre-defined **Alternate Key** on the Dataverse table:
1. Power Apps maker portal → the table → **Keys** → *New key*.
2. Pick the field(s) that make up the key, save, and wait for key creation to finish (Dataverse indexes it asynchronously — large tables can take a while).
3. Pass the field's **logical name** (not its display label) as `alternate_key_field`.

Without a matching Alternate Key, the upsert PATCH 404s.

> This component exposes a single-field alternate key per sink instance. Composite (multi-column) alternate keys are supported by the underlying resource (`dynamics_crm_resource.upsert_by_key()` accepts parallel lists of key names/values) but not by this component's config surface — use custom asset code against the resource directly if you need a composite key.

## Example

```yaml
type: dagster_component_templates.DynamicsCrmRecordUpsertComponent
attributes:
  asset_name: dynamics_crm_accounts_mirror
  upstream_asset_key: dbt_marts_accounts
  resource_key: dynamics_crm

  entity_set_name: accounts                     # plural, lowercase logical name
  alternate_key_field: cr_external_account_id    # must be an Alternate Key in Dataverse
  fields_map:
    account_id: cr_external_account_id           # upstream col → Dataverse field
    name: name
    industry: industrycode
    annual_revenue: revenue

  batch_size: 5000
  prefer_representation: true   # 201/200 disambiguates created/updated + returns GUID
```

## Behavior + gotchas

- **Alternate key required** — every upstream row must have a value in the column mapped to `alternate_key_field`; rows with `None` / `NaN` there are skipped and counted in the `rows_skipped_no_key` metadata.
- **Alternate key value excluded from the body** — the key value is sent only in the URL, never duplicated into the request body; Dataverse ignores alternate-key values in the body on update and would reject (or redundantly re-apply) them on create.
- **Blank vs missing** — `None` / `NaN` values are omitted from the request body so the existing Dataverse value is preserved. Empty strings `""` are sent verbatim.
- **`rows_unknown_action`** — only ever nonzero when `prefer_representation: false`; Dataverse's bare `204 No Content` response can't tell you whether a given row was created or updated.
- **Rate limits** — Dataverse enforces per-user/per-app API request limits (varies by license/SKU). The resource retries on 429 / 5xx with exponential backoff up to `max_retries` on `dynamics_crm_resource` (default 3), and refreshes the OAuth token on 401.
- **Custom tables** — pass the table's plural logical name (often prefixed, e.g. `new_customthings` or `cr123_customthings` depending on the solution publisher prefix).
- **Fields not writable** — some Dataverse fields (the primary GUID column, `createdon`, calculated/rollup columns, certain system columns) aren't writable. Including them in `fields_map` causes Dataverse to reject the row with an error, surfaced per-row in `first_errors`.
