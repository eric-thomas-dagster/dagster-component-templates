# `GoogleAdsCustomerMatchUpsertComponent`

Reverse-ETL / audience activation: mirror an upstream DataFrame into an existing **Google Ads Customer Match** user list via the native `OfflineUserDataJobService` — the same API Google Ads' own audience upload UI uses under the hood.

For each run:
1. `create_offline_user_data_job` — opens a new job against the target user list.
2. `add_offline_user_data_job_operations` — uploads hashed identifiers in chunks of up to 10,000 operations per request.
3. `run_offline_user_data_job` — submits the job for processing.

Customer Match jobs are **asynchronous on Google's side** (processing can take hours). This component reports the job resource name and submitted/skipped row counts — not per-row success/failure. Check **Google Ads UI → Tools & Settings → Audience Manager → your list → Job History** for detailed processing status (same convention as this repo's Salesforce Bulk 2.0 component).

## Privacy: identifiers are hashed before they leave your infrastructure

Google never sees plaintext PII. Supported identifier types — map an upstream column to one via `fields_map`:

| Type | Normalization before SHA-256 |
|---|---|
| `email` | trim, lowercase |
| `phone` | strip everything but digits and a leading `+` (must include country code, e.g. `+14155552671` — a bare `14155552671` gets a `+` added automatically, since Google's hash will otherwise never match) |

A row can supply more than one identifier across different columns (e.g. both email and phone) — Google matches on *any* identifier present, so supplying more improves match rate. A row with a blank value in one mapped column still contributes its other identifier(s); only a row with *zero* valid identifiers is skipped.

## `add` vs `remove`

- **`add`** (default) — activation: add matching users to the list for targeting.
- **`remove`** — suppression: remove matching users, e.g. exclude customers who already converted or churned from further retargeting.

## When to use

- Sync a dbt mart of high-LTV customers into a Customer Match list for lookalike/targeting campaigns.
- Suppress churned or already-converted customers from retargeting (`operation: remove`).
- Push a warehouse-computed segment (e.g. "cart abandoners in the last 7 days") into an existing remarketing audience.

## Prerequisite: the user list must already exist

This component only **uploads members** — it does not create user lists. Create the Customer Match list once via Google Ads UI (Audience Manager → Segments → + → Customer list) or the Google Ads API, then pass its resource name (`customers/{customer_id}/userLists/{list_id}`) as `user_list_resource_name`.

## Pairs with

- **`google_ads_resource`** — OAuth2 connection + `GoogleAdsClient` (required).
- **`google_ads_ingestion`** — the READ-side counterpart (campaign/performance data pull).

Together they cover both directions of Google Ads data movement.

attributes:
  asset_name: google_ads_churned_customers_audience

  user_list_resource_name: "customers/1234567890/userLists/987654321"

## Behavior + gotchas

- **No job created when every row is skipped** — if no row has a valid identifier, the component returns early without calling `create_offline_user_data_job` at all (not even an empty job).
- **Async processing** — `run_offline_user_data_job` submits the job; it does not block for completion. There is no per-row success/failure available synchronously — check Audience Manager → Job History.
- **Phone must include country code** — Google's hash only matches E.164-formatted numbers. A phone value with no leading `+` gets one added automatically (assuming the remaining digits already include a country code), but a number missing its country code entirely will hash to something Google's own normalization will never match — garbage in, silent non-match out, not an error.
- **Chunking** — `add_offline_user_data_job_operations` is called once per 10,000 operations, automatically, regardless of `batch_size`.
- **Rate/quota limits** — Google Ads API enforces per-developer-token and per-account quotas on job operations; very large or very frequent uploads may need to be spread across multiple runs.

## Partitioning

When `partition_type` is set, a run sends only the rows in its partition: `partition_date_column` selects the rows whose date falls in a time partition's window (a backfill run covers its whole range) and `partition_static_column` selects the rows for a static/dynamic partition key. Unpartitioned runs send every row.
