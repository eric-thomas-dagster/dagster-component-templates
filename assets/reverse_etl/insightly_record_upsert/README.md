# `InsightlyRecordUpsertComponent`

Reverse-ETL sink: mirror an upstream DataFrame into **Insightly CRM** Contacts / Leads / Organisations using an **emulated upsert** — search-then-write. **Insightly has no native upsert endpoint** (unlike Salesforce's External-ID `PATCH` or HubSpot's `/batch/upsert`).

For each upstream row:
- `GET /{object_type}/Search?field_name={X}&field_value={Y}` — look for an existing record by `dedupe_field`.
- **Match found** → `PUT /{object_type}/{id}` — update in place.
- **No match** → `POST /{object_type}` — create a new record.

## ⚠️ Not atomic — race condition

The search and the create-or-update are **two separate HTTP calls**, not one atomic server-side operation the way Salesforce/HubSpot's native upsert endpoints are. If two upserts for the same `dedupe_field` value run **concurrently**, both can see "no match" and both `POST`, producing a **duplicate Insightly record**.

- **Safe**: a sequential or single-writer nightly/hourly reverse-ETL run (the normal case for this sink).
- **Not safe**: multiple writers racing on the same dedupe key at the same time (e.g. two overlapping backfills).

This mirrors `pipedrive_person_upsert`'s same search-then-write shape (Pipedrive has the same limitation).

## Object shapes — CONTACTINFOS (Contacts only)

Insightly Contacts store email/phone inside a nested `CONTACTINFOS` array rather than flat fields:

```json
{
  "CONTACT_ID": 123,
  "FIRST_NAME": "Jane",
  "CONTACTINFOS": [
    {"TYPE": "EMAIL", "LABEL": "Work", "DETAIL": "jane@example.com"}
  ]
}
```

`fields_map` special-cases this: values `"email"` / `"phone"` get nested into `CONTACTINFOS` automatically **only when `object_type: Contacts`**. Everything else in `fields_map` (including `"email"`/`"phone"` strings when `object_type` is `Leads` or `Organisations`, which expose flat `EMAIL`/`PHONE` fields directly) maps straight to a flat top-level Insightly field name.

```yaml
fields_map:
  work_email: email          # Contacts -> nested into CONTACTINFOS
  work_phone: phone          # Contacts -> nested into CONTACTINFOS
  first_name: FIRST_NAME     # flat field, unchanged
```

## When to use

- Sync computed customer data (lead score, health score, lifecycle stage) from a warehouse INTO Insightly so sales reps see it in-context on a Contact/Lead.
- Mirror a golden-record customer or organization table (dbt marts) into Insightly Contacts/Organisations.

## Prerequisite: pick a `dedupe_field` that's actually unique

Insightly's generic Search endpoint matches on "any standard or custom field" per its own docs, but it is **not guaranteed unique** the way an External-ID field is in Salesforce. If two Contacts share the same email, the first match returned by Search wins — know your data before relying on this for dedup.

## Example

```yaml
type: dagster_component_templates.InsightlyRecordUpsertComponent
attributes:
  asset_name: insightly_contacts_mirror
  upstream_asset_key: dbt_marts_customers
  resource_key: insightly

  object_type: Contacts
  dedupe_field: email
  fields_map:
    work_email: email          # -> CONTACTINFOS (Contacts only)
    work_phone: phone           # -> CONTACTINFOS (Contacts only)
    first_name: FIRST_NAME
    last_name: LAST_NAME

  batch_size: 5000
  group_name: reverse_etl
```

## Example — Leads (flat fields, no CONTACTINFOS)

type: dagster_component_templates.InsightlyRecordUpsertComponent

    contact_email: EMAIL

## Behavior + gotchas

- **Dedupe field required** — every upstream row must have a value in the column mapped to `dedupe_field`; rows with `None` / `NaN` / empty string there are skipped and counted in `rows_skipped_no_key`.
- **Not atomic** — see the race-condition callout above. Insightly's API genuinely has no server-side dedupe-by-field upsert.
- **Rate limits** — Insightly enforces 10 requests/second plus a daily quota that varies by plan (1,000/day Gratis up to 60,000+/day Professional/Enterprise). Every row costs 2 HTTP calls (search + write); `insightly_resource` retries on 429 with exponential backoff and logs `X-RateLimit-Limit`/`X-RateLimit-Remaining`.
- **CONTACTINFOS nesting is Contacts-only** — setting `fields_map` values to `"email"`/`"phone"` for `object_type: Leads` or `Organisations` does NOT nest them; those object types expose flat fields, so map directly to the flat field name instead (see the Leads example above).
- **No batching** — every row is one search HTTP call + one create/update HTTP call. There's no Insightly equivalent of Salesforce's composite/Bulk 2.0 or HubSpot's `/batch/upsert`; `batch_size` is purely a safety cap on total rows per run, not a batching mechanism.
