# `LinearIssueUpsertComponent`

Reverse-ETL: mirror an upstream DataFrame into Linear issues, create-or-update.

## Linear's find-or-create mechanism: client-generated `id`

Linear has no `upsert` mutation, and unlike Jira/GitHub this component does **not** need a label/body-marker hack to get idempotent writes. Linear's own `IssueCreateInput.id` field is documented directly in its public GraphQL schema:

> "The identifier in UUID v4 format. If none is provided, the backend will generate one."

That means a client is allowed to mint its own UUID for an issue before it exists. This component exploits that directly: it derives a **uuid5** from `(team_id, key_column value)` using a fixed namespace, so the same upstream key always maps to the same Linear issue id, on every run, with no server-side search required.

Each run:
1. Computes the deterministic id for every upstream row.
2. Issues **one bulk** `issues(filter: { id: { in: [...] } })` query (chunked at 200 ids/request) to find out which of those ids already exist — Linear's `IDComparator` supports `in`, confirmed against the schema.
3. Existing ids → `issueUpdate(id, input)`.
4. New ids → `issueCreate(input: { id, teamId, title, ... })`.

This is more scalable than a text-search or label-marker approach: no per-row "search by title" guesswork, and no risk of a human editing the title/body breaking the match (the id lives outside any visible field).

## Pairs with

- **`linear_resource`** — GraphQL connection (personal API key or OAuth2 token, sent raw in the `Authorization` header — required).

## Optional field resolution (cached per run)

- **`label_names_column`** / **`default_labels`** — label *names* are resolved to label IDs via one `team.labels` query, cached for the whole run (not re-queried per row). An unknown label name is skipped with a warning, not a hard failure.
- **`state_name_column`** — workflow state *names* (e.g. `'Done'`, `'In Progress'`) are resolved via one `team.states` query, same caching.
- **`assignee_email_column`** — resolved via one workspace-wide `users` query (first 250 users), same caching. Very large workspaces (>250 users) may miss a match — see Behavior + gotchas.

  description_column: description

  label_names_column: labels
  default_labels: [auto-synced]

  group_name: linear

## Behavior + gotchas

- **`team_id` must be stable** — the derived id is `uuid5(team_id + key)`. Changing `team_id` (e.g. pointing the same component at a different team) changes every derived id, which will look like "every row is new" rather than "every row moved."
- **Label/state caches are per-run, not persisted** — if labels or workflow states change mid-run (unlikely), the cache won't pick it up until the next materialization.
- **>250 labels/states/users** — the one-time lookup queries fetch the first page (250) only; a label, state, or user outside that page silently won't resolve (logged as a warning per row, not a hard failure). Most teams/workspaces stay well under this.
- **No delete/archive support** — unlike `github_issue_upsert`'s `close_missing`, this component only creates and updates; removing a row from the upstream DataFrame does not close or archive the corresponding Linear issue.
