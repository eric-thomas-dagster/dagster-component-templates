# `MarketoLeadUpsertComponent`

Reverse-ETL sink: mirror an upstream DataFrame into **Marketo Leads** using Marketo's native **createOrUpdate** action. Atomic create-or-update per record in a single request — no search-then-write.

For each batch (up to 300 records):
- `POST /rest/v1/leads.json` with body `{"action": "createOrUpdate", "lookupField": <lookup_field>, "input": [...]}`

Marketo returns one result entry per input record, in order, each with a `status` of `created`, `updated`, or `skipped` (with `reasons` explaining why, e.g. `{"code": "1004", "message": "Lead not found"}` when `lookupField` isn't `email`/`id` and no match exists).

## Chunking

Marketo caps the `input` array at **300 records per request** — this is a hard API limit, not a tunable. This component chunks automatically regardless of `batch_size` (which is a separate, higher safety cap on total rows processed per run).

## When to use

- Sync a dbt Contacts/Leads mart into Marketo for nurture campaigns.
- Push a warehouse-computed lead score or segmentation flag into a custom Marketo field.
- Mirror CRM-sourced contact data into Marketo so marketing automation sees it in-context.

## `lookup_field`

Defaults to `email` (Marketo's most common lookup key). Can also be `id` (Marketo's internal Lead ID) or a custom field marked for lookup in your Marketo instance. **Must** appear as a value in `fields_map` — the component validates this at component-build time and raises `ValueError` otherwise.

## Pairs with

- **`marketo_resource`** — OAuth2 client-credentials auth + workhorse HTTP (required). This component uses the resource's `.post()` method (added alongside this component — the resource already had `.get()` for read-side use cases).

## Example

```yaml
attributes:
  asset_name: marketo_leads_mirror
  upstream_asset_key: dbt_marts_contacts
  resource_key: marketo

  lookup_field: email
  fields_map:
    email: email
    first_name: firstName
    last_name: lastName
    company: company
    lead_score: leadScore__c   # custom field, passes through as-is

  batch_size: 50000
```

## Behavior + gotchas

- **Lookup value required** — every upstream row must have a non-null value in the column mapped to `lookup_field`; rows missing it are skipped and counted in `rows_skipped_no_key`.
- **`skipped` status from Marketo itself** — distinct from `rows_skipped_no_key` (which never reach the API at all). Marketo can still return `status: "skipped"` for a record it received (e.g. `lookupField` resolves to multiple leads, or validation fails on a field) — these are counted in `rows_skipped` and surfaced via `reasons` in `first_errors`.
- **Blank vs missing** — `None` / `NaN` values are omitted from the request body per-record so existing Marketo field values are preserved. Empty strings `""` are sent verbatim.
- **No native "external ID" concept** — unlike Salesforce, Marketo's createOrUpdate matches on any field you designate, most commonly `email`; there's no separate "must be flagged External ID in the schema" step.
- **Custom fields** — pass through as their Marketo API name (e.g. fields ending in `__c` for some instances, though Marketo custom field naming varies by org — check Admin → Field Management for exact API names).

## Partitioning

When `partition_type` is set, a run sends only the rows in its partition: `partition_date_column` selects the rows whose date falls in a time partition's window (a backfill run covers its whole range) and `partition_static_column` selects the rows for a static/dynamic partition key. Unpartitioned runs send every row.
