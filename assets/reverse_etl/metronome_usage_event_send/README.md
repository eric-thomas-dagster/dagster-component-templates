# `MetronomeUsageEventSendComponent`

Reverse-ETL usage-based billing activation: send a [Metronome](https://metronome.com) usage event via `POST /ingest` for each row of an upstream DataFrame. Materializing this asset sends **real usage events that affect real customer invoices**.

## Idempotency — read this before you materialize

Metronome's `/ingest` endpoint deduplicates on `transaction_id`: once an event with a given `transaction_id` is accepted, Metronome ignores subsequent events carrying the same `transaction_id` for the next 34 days. **This is the mechanism that makes retries safe.**

- Set `transaction_id_column` to a stable, unique-per-event column from your source system (e.g. a request ID, a log line ID) whenever one exists. This makes both HTTP retries *and* reruns over unchanged upstream data safe no-ops on Metronome's side.
- If `transaction_id_column` is unset, this component falls back to a deterministic hash of `(customer_id, event_type, timestamp, row_position)` — stable across retries *within the same run*, but less robust across reruns than a real source-system ID (e.g. if upstream row order or window shifts).

## Request shape (verified against docs.metronome.com, 2026-10)

- `POST {base_url}/ingest` with a **bare JSON array** body (not `{"events": [...]}`), 1-100 events per request.
- Each event: `{"transaction_id": "...", "customer_id": "...", "event_type": "...", "timestamp": "2026-03-09T12:00:00Z", "properties": {...}}`.
- `customer_id` accepts **either** a Metronome customer UUID **or** an ingest alias (an internal identifier mapped to a customer at creation time) — same field, no separate alias field.
- `timestamp` must be RFC 3339 with a 4-digit year.

## Retry semantics (verified — getting this wrong risks duplicate billing)

Per Metronome's own docs:
- **Network error or 5xx** → always retry until a 200. `transaction_id`'s dedup window makes this safe.
- **429** → you've hit a rate limit; back off with exponentially increasing delay and retry.
- **Any other 4xx** → do NOT retry automatically; it's a malformed request and retrying the same bytes won't fix it.

This component implements the above with a **bounded** retry budget (`max_retries`, default 5, exponential backoff via `initial_backoff_seconds` / `backoff_multiplier`) rather than retrying forever, and raises a `dg.Failure` loudly when that budget is exhausted on a given batch — unlike this repo's `twilio_sms_send` sibling (which isolates per-row failures like a single bad phone number and keeps going), a Metronome batch that's still failing after several retries usually signals a systemic problem (bad auth, network partition), and silently dropping billing events would be worse than failing the run.

## Batching

Metronome hard-caps `/ingest` at 100 events per request — `batch_size` is validated to `1 <= batch_size <= 100`. `max_rows_per_run` is a separate, optional blast-radius safety cap on total rows per materialization (independent of HTTP chunk size).

## When to use

- Send usage-based billing events (API calls, compute-seconds, seats, etc.) from a warehouse mart into Metronome for invoicing.
- Any "one billable event per row" reverse-ETL case where the destination is Metronome rather than a CRM/marketing tool.

## Prerequisite: a MetronomeResourceComponent

Requires a `metronome_resource` registered via `MetronomeResourceComponent` (static Bearer API key auth — see `resources/metronome_resource`).

## Pairs with

- **`metronome_resource`** — static Bearer API key auth (required).
- **`metronome_invoices_ingestion`** — pull-side sibling for finance reporting on the invoices these events produce.
