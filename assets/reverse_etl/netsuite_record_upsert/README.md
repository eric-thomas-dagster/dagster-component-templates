# `NetSuiteRecordUpsertComponent`

Reverse-ETL sink: mirror an upstream DataFrame into **NetSuite Customer** records via SuiteTalk REST (`record/v1/customer`).

## No native upsert -- this is a lookup-then-write, not one call

Unlike Salesforce's native External-Id `PATCH .../sobjects/{Object}/{ExtIdField}/{Value}` (atomic create-or-update in one request), **NetSuite's REST record API has no equivalent single-call upsert endpoint**. For every row, this component does:

1. `GET /customer?q=<lookup_field> IS "<value>"` — search for an existing match.
2. If found → `PATCH /customer/{internalId}` with the row's fields (NetSuite PATCH is already merge/partial-update semantics — no SyncToken-style version number needed, unlike QuickBooks).
3. If not found → `POST /customer` with the row's fields (NetSuite assigns the internal id; include `externalId` in the body when `lookup_field: externalId` so the record is findable by the same key next run).

So the YAML author gets one upsert step per row — but under the hood it's **one GET + one POST-or-PATCH per row, with no bulk/composite batching** in `record/v1`. For high-volume loads (tens of thousands of rows), consider NetSuite's SuiteScript Map/Reduce or CSV Import instead — this component is built for typical daily/hourly sync volumes, not bulk migration.

## Auth: OAuth 1.0a (Token-Based Authentication) -- confirm this, it's a common trap

NetSuite's REST API is **not** OAuth2, despite being a modern REST surface — it still uses OAuth 1.0a TBA (consumer key/secret + token id/secret, HMAC-SHA256 request signing), the same scheme SOAP-era SuiteTalk used. See `netsuite_resource`'s README for full setup.

## When to use

- Sync a dbt Customers mart into NetSuite so finance/ops see warehouse-computed data (credit scores, segmentation) in-context.
- Mirror externally-sourced customer master data into NetSuite as the system of record for billing/ERP.
- Nightly reconciliation job pushing updates from a CRM/warehouse into NetSuite Customer records.

## `lookup_field`

Defaults to `externalId` — NetSuite's dedicated field for external-system matching (works like Salesforce's External Id, but requires this component's GET-then-write pattern rather than being usable in a single PATCH URL segment the way Salesforce's is). Can also be `entityid` or a custom field. **Must** appear as a value in `fields_map`.

## Pairs with

- **`netsuite_resource`** — OAuth 1.0a (TBA) auth + workhorse HTTP (required).
- **`netsuite_ingestion`** — the READ-side counterpart (dlt-based bulk pull); unrelated implementation (dlt source, no write capability) per this repo's no-shared-logic rule.

  asset_name: netsuite_customers_mirror

  resource_key: netsuite

  lookup_field: externalId

    phone: phone

  batch_size: 5000

## Behavior + gotchas

- **Lookup value required** — rows with `None`/`NaN` in the column mapped to `lookup_field` are skipped and counted in `rows_skipped_no_key`.
- **No atomicity across the GET+write pair** — a race is possible if two processes upsert the same `lookup_field` value concurrently (both GET, see no match, both POST → two Customer records created). Not a concern for typical single-scheduler nightly syncs.
- **No bulk batching** — `api_requests` metadata will be roughly `2 * rows_upserted` (one GET + one write per successful row); plan batch_size accordingly for rate limits.
- **PATCH is already sparse** — unlike QuickBooks, NetSuite's PATCH merges only the fields you send; there's no `SyncToken`/optimistic-concurrency version number to track.
- **Role permissions** — the TBA Access Token's Role needs View + Create + Edit permission on Customer records, or writes fail with a 403.

## Partitioning

When `partition_type` is set, a run sends only the rows in its partition: `partition_date_column` selects the rows whose date falls in a time partition's window (a backfill run covers its whole range) and `partition_static_column` selects the rows for a static/dynamic partition key. Unpartitioned runs send every row.
