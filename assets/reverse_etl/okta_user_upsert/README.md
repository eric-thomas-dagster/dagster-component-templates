# `OktaUserUpsertComponent`

Reverse-ETL: sync a warehouse table of user records into Okta via the Users API.

## Safety

**Read this before pointing this component at a production Okta org.**

- **The default behavior is non-destructive, with zero special configuration.** With `operation` left unset (or explicitly set to `sync`), every row either (a) creates a new user if no Okta user shares its login, or (b) merge-updates profile attributes on the existing user if one does (a partial `POST`, never a destructive `PUT` replace). This mode **cannot** deactivate or delete anyone — there is no code path from `operation: sync` to any lifecycle-changing call, and Okta's profile schema has no field that even represents lifecycle status, so there is nothing for a row to accidentally trigger.

- **Deactivation requires an explicit, separate config field.** A row can never deactivate a user just by having a particular column value. The only way to deactivate anyone is to set `operation: deactivate` on the component itself — a deliberate, reviewable configuration choice for that asset/run, never something inferred from upstream data. `fields_map` is additionally forbidden from targeting a `status` attribute (validated at `build_defs` time), as defense in depth even though Okta's own API has no such profile field.

- **Deactivate mode never creates a user.** If a row's login doesn't match an existing Okta user, it is skipped and counted (`rows_skipped_not_found`) — it is never used to create a new user. If the matched user is already `DEPROVISIONED` (already deactivated), the row is skipped as a no-op (`rows_skipped_already_deactivated`) rather than calling an endpoint Okta would reject anyway.

- **There is no delete operation, anywhere, in this component, under any configuration.** Okta's Users API does expose `DELETE /api/v1/users/{id}` — but only on a user already in the `DEPROVISIONED` status, and it is a genuine, unrecoverable hard delete that Okta's own documentation recommends against for audit/compliance reasons. Neither this component nor `okta_resource` ever calls it. `operation` only accepts `sync` or `deactivate`; any other value (including something like `"delete"`) is rejected at `build_defs` time with a clear `ValueError`, never silently ignored or guessed at.

- **`operation` is validated at build time, not guessed at runtime.** An unsupported value fails the component's `build_defs()` immediately — before any asset materializes, before any HTTP call is made.

If you need to permanently remove an Okta user, do it by hand in the Okta admin console (or via a separate, explicitly-reviewed script) — this pipeline deliberately cannot do it, and even Okta's own docs steer you away from it in favor of leaving deactivated users in place for audit/compliance.

## Default (`operation: sync`) behavior, per row

1. Look up the row's login via `GET /api/v1/users/{login}` (Okta's Get User endpoint accepts id, login, or email directly as the path segment).
2. **Found** → `POST /api/v1/users/{id}` — a profile **merge**, not a replace; only the row's mapped attributes change, everything else already on the user is untouched.
3. **Not found** → `POST /api/v1/users` to create a new user (`activate` query param controlled by `activate_on_create`, default `true` — Okta's own documented default).

## Explicit (`operation: deactivate`) behavior, per row

1. Look up the row's login the same way.
2. **Not found** → skipped (`rows_skipped_not_found`).
3. **Already `DEPROVISIONED`** → skipped (`rows_skipped_already_deactivated`).
4. **Found, not yet deactivated** → `POST /api/v1/users/{id}/lifecycle/deactivate` — Okta's distinct lifecycle endpoint, structurally separate from `update_user`/`create_user`, not a profile-field flip.

## `fields_map`

Upstream column → Okta profile attribute (flat names, since Okta's profile object is not nested like Auth0's): `login`, `email`, `firstName`, `lastName`, `mobilePhone`, `secondEmail`, `displayName`, or a custom schema attribute your org has defined.

Exactly one value **must** be `login` (the match key — and required by Okta to create a user at all). The value `status` is rejected at build time — see Safety above.

## Behavior + gotchas

- **Merge, never replace** — `update_user` always calls Okta's `POST` (merge) path, never `PUT` (strict replace that deletes unspecified attributes).
- **`status` is reserved** — `fields_map` cannot target it; `build_defs()` raises immediately if it does (even though Okta's profile schema has no such field anyway — defense in depth).
- **No delete, ever** — `operation` only accepts `sync`/`deactivate`; `okta_resource` has no `delete_user` method at all.
- **Already-deactivated users are a no-op, not an error** — Okta's lifecycle/deactivate endpoint can only be called on a non-`DEPROVISIONED` user; this component checks status first and skips cleanly instead of letting Okta reject the call.
