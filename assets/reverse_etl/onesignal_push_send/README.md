# `OneSignalPushSendComponent`

## ⚠️ This component SENDS REAL PUSH NOTIFICATIONS — read before you materialize

Unlike the ad-audience reverse-ETL components in this repo (Meta/Google/TikTok/LinkedIn custom-audience upserts), there is **no "upload for later matching" indirection** here. Materializing this asset immediately sends a real push notification, via OneSignal's live REST API, to every subscription id resolved from `recipient_column` — the moment the run executes.

**Before pointing this at a real warehouse segment:**
- Test against a small list of your own test-device subscription ids first — e.g. `source: {kind: inline, rows: [{onesignal_subscription_id: "..."}]}` with 1-2 rows, or a low `batch_size` against a dev upstream asset.
- Double-check `recipient_column` actually holds the column you think it does — a typo here means real pushes go to the wrong devices.
- This component adds **no rate-limiting or throttling** beyond `batch_size` (a blast-radius cap, not a throughput control) — if you need pacing, that's your responsibility to configure/orchestrate.

Reverse-ETL message activation: send a personalized push notification to each row of an upstream DataFrame via `POST https://api.onesignal.com/notifications`, `Authorization: Key <REST_API_KEY>`.

## Targeting field: Subscription ID, not the deprecated Player ID

`recipient_column` should hold a OneSignal **Subscription ID** (device-level id), sent via `include_subscription_ids`. This is the current API's targeting field — it replaced the deprecated `include_player_ids` (legacy `onesignal.com/api/v1/notifications` host) as part of OneSignal's shift from a device-centric to a user-centric data model (External ID / Alias based targeting for user-level sends). If you only have legacy Player IDs on hand, they are numerically the same value as the current Subscription ID — only the field name changed.

## Personalization

`message_template` (body/"contents") and `heading_template` (title/"headings", optional) both support simple `{column_name}` substitution from any other column in the same row:

```yaml
heading_template: "You left something behind!"
message_template: "{first_name}, your cart has {item_count} item(s) waiting."
```

A column referenced in a template but missing from the row renders as an empty string rather than failing that row. Omit `heading_template` for a body-only notification.

## Per-row failure isolation

One recipient's send failing (unsubscribed device, invalid id, etc.) is caught and counted — it does **not** abort the run or the remaining rows. Metadata reports `messages_sent` / `messages_failed` / `rows_skipped_no_recipient` (blank/null recipient values), plus a `first_errors` sample when failures occur.

## When to use

- Send a cart-abandonment or re-engagement push to a warehouse-computed segment.
- Trigger a transactional-style push (order update, appointment reminder) from a dbt mart / Dagster asset.
- Any "send a message to each row" reverse-ETL case where the destination is OneSignal push rather than an ad platform's audience list.

## Pairs with

- **`onesignal_resource`** — App ID + REST API key auth (required).
