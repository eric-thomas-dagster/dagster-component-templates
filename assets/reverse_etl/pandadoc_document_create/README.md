# `PandaDocDocumentCreateComponent`

## ⚠️ This component CREATES AND SENDS REAL DOCUMENTS — read before you materialize

Every row that resolves a recipient email creates a brand-new PandaDoc document from a template and, with the default `auto_send: true`, immediately emails that recipient a signature request — the moment this asset materializes. This is **not** a record upsert like `salesforce_record_upsert` — there's no match key, no create-or-update semantics, and no de-duplication across runs. Re-materializing against the same upstream rows creates duplicate documents.

**Before pointing this at a real warehouse table:**
- Test against your own test email addresses first — e.g. `source: {kind: inline, rows: [{signer_email: "you@corp.com", signer_first_name: "Test"}]}`.
- Set `auto_send: false` if you want documents created but left for manual review/send in the PandaDoc UI rather than emailed automatically.

## Not a record upsert

Unlike `salesforce_record_upsert` (canonical dual-source upsert pattern in this repo), there's no external-ID match key — PandaDoc documents aren't addressable/updatable the way SObject records are. Every materialization that resolves a recipient creates a new document. If you need idempotency (e.g. "don't re-send a contract already sent today"), filter the upstream query/asset to exclude already-sent rows before they reach this component.

## New resource: `pandadoc_resource`

No PandaDoc *write* resource existed in this repo before — only the read-only `pandadoc_ingestion` asset component. This component pairs with a new `pandadoc_resource` (`resources/pandadoc_resource/`), built following this repo's `outreach_resource` pattern: a `ConfigurableResource` wrapping the HTTP calls + a `Component` wrapper that registers it. It reuses the **same static API Key auth** `pandadoc_ingestion` already uses for reads.

## Document lifecycle: create -> poll -> send

PandaDoc builds a document from its template **asynchronously** — a freshly created document isn't immediately sendable. With `auto_send: true` (the default), this component:
1. `POST /documents` to create the document from `template_uuid` (+ `recipients`, optional `tokens`).
2. Polls `GET /documents/{id}` every `poll_interval_seconds` until the document reaches PandaDoc's sendable `document.draft` status (or `poll_timeout_seconds` elapses, or PandaDoc reports an error status — either fails that row, not the whole run).
3. `POST /documents/{id}/send` to email the recipient.

Set `auto_send: false` to only perform step 1 — useful if you want a human to review/send from the PandaDoc UI instead.

## Template roles and prefilled tokens

`recipient_role` must match a recipient role defined on the PandaDoc template, if the template uses named roles. Optionally, `tokens_map` prefills the template's tokens from other row columns:

```yaml
tokens_map:
  contract_value: contract.value   # upstream column -> PandaDoc template token name
  effective_date: contract.effective_date
```

`name_template` supports `{column_name}` substitution the same way, e.g. `"{contract_type} Agreement - {customer_name}"`.

## Per-row failure isolation

One document failing (invalid template token, PandaDoc processing error, poll timeout, API error, etc.) is caught and counted — it does **not** abort the run or the remaining rows. Metadata reports `documents_created` / `documents_failed` / `rows_skipped_no_recipient` (blank/null email), `first_document_ids` (a sample of created document IDs), and a `first_errors` sample when failures occur.

## When to use

- Send a signature-request document for every contract/order a warehouse query marks "ready for signature".
- Trigger an e-signature workflow from a dbt mart (e.g. vendor agreements, order forms) without a human manually creating each one in the PandaDoc UI.

## Pairs with

- **`pandadoc_resource`** — static API Key auth via `requests` (required, new resource built for this component).
