# `PinterestAudienceUpsertComponent`

Reverse-ETL / audience activation: mirror an upstream DataFrame into an existing **Pinterest Customer List** — the object a `CUSTOMER_LIST`-type Pinterest Audience points to — via the update-customer-list endpoint:

```
PATCH /ad_accounts/:ad_account_id/customer_lists/:customer_list_id
```

confirmed against Pinterest's own OpenAPI description ([`pinterest/api-description`](https://github.com/pinterest/api-description), `v5/openapi.yaml`): `operation_type` accepts exactly `ADD` / `REMOVE`, and the request body carries `records_v2` — an array of per-row objects supporting multiple identifier fields per row (`email`, `hashed_phone_number`, `maid`, ...). This component uses `records_v2` rather than the older comma-separated `records` string, since `fields_map` can mix identifier types the same way Google Ads/Meta/X do (one row, multiple identifiers) — unlike TikTok's one-file-per-identifier-type upload.

This component only **uploads members into an existing Customer List** — it does not create the list or convert it into an Audience; both are one-time setup steps.

## Privacy: identifiers are hashed before they leave your infrastructure

Although Pinterest's API technically accepts cleartext email addresses (its schema literally says *"Emails must be lowercase and can be plain text or hashed"*), this component always SHA-256 hashes before sending, consistent with every other ad-platform audience-activation component in this repo. Supported identifier types — map an upstream column to one via `fields_map`:

| Type | Normalization before SHA-256 |
|---|---|
| `email` | trim whitespace, lowercase — Pinterest's own customer-list schema explicitly requires lowercase emails |
| `phone` | **digits only** (country code + area code + number) — `+`, spaces, dashes, parentheses, letters, and leading zeros all removed. Confirmed against Pinterest's own conversions/enhanced-match documentation, which is explicit that phone numbers are *"only digits with country code, area code, and number... with any symbols, letters, spaces and leading zeros removed."* |

**This is a real divergence from the other ad platforms in this repo**: Google Ads, TikTok, and X all want E.164 **with** a leading `+` before hashing. Pinterest wants **digits only, no `+`** — the same convention Meta uses. Don't reuse a hash computed for one of those platforms here; it won't match.

## `add` vs `remove`

- **`add`** (default) → Pinterest `operation_type: ADD` — activation: add matching records to the customer list.
- **`remove`** → Pinterest `operation_type: REMOVE` — suppression: remove matching records, e.g. exclude customers who already converted.

## Asynchronous matching, surfaced status

Pinterest scans the submitted records for existing Pinterest accounts; this component surfaces the resulting `status` (`PROCESSING` / `READY` / `TOO_SMALL` / `UPLOADING`) directly in its materialization metadata, along with `num_uploaded_user_records` / `num_removed_user_records` / `num_batches` from the API response. A customer list needs **at least 100 matched Pinterest accounts** to be usable for targeting — fewer than that reports `TOO_SMALL`. Full matching to produce a targetable audience can take up to **48-72 hours** on Pinterest's side, per Pinterest's own developer docs.

## When to use

- Sync a dbt mart of high-LTV customers into a Customer List Audience for lookalike/targeting campaigns.
- Suppress churned or already-converted customers from retargeting (`operation: remove`).
- Push a warehouse-computed segment into an existing remarketing audience.

## Prerequisite: the customer list (and audience) must already exist

Create the Customer List once via Pinterest Ads Manager (Ads → Audiences → Create audience → Customer list) or the Ads API's `customer_lists` create endpoint, convert it into a `CUSTOMER_LIST`-type Audience (`audiences` create endpoint), then pass the customer list's ID as `customer_list_id`.

## Pairs with

- **`pinterest_ads_resource`** — OAuth2 bearer token + ad account ID (required).
- **`pinterest_ads_ingestion`** — the READ-side counterpart (campaign/performance data pull).

Together they cover both directions of Pinterest Ads data movement.

## Behavior + gotchas

- **One `records_v2` row per upstream row, not per identifier type** — if `fields_map` maps columns to both `email` and `phone`, a single row produces one object like `{"email": "<hash>", "hashed_phone_number": "<hash>"}`. `rows_submitted` counts rows, not identifiers.
- **No call made when every row is empty** — if no row has a valid identifier, the update endpoint is never called.
- **Phone hashing differs from Google Ads/TikTok/X** — Pinterest wants digits-only (no leading `+`); those three want E.164 with a leading `+`. Don't reuse one platform's hash for another.
- **`status` reflects match progress, not upload success** — a successful materialization with `status: TOO_SMALL` means the upload succeeded but fewer than 100 Pinterest accounts have matched so far; it is not an error from this component's perspective.
- **Asynchronous matching** — full audience readiness can take 48-72 hours on Pinterest's side. This component reports upload API success (`status`/counts), not final match results.
- **Minimum 100 matched accounts for targeting** — Pinterest's own documented floor; lists below that show `TOO_SMALL` and can't be used in campaigns regardless of how many rows were submitted.
