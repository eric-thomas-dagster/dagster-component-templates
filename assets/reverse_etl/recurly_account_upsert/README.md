# `RecurlyAccountUpsertComponent`

Reverse-ETL sink: mirror an upstream DataFrame into **Recurly Account** records.

## `PUT` only updates -- it never creates

Unlike QuickBooks or Xero, Recurly does **not** overload a single endpoint for both create and update. `PUT /accounts/{account_id}` **only updates** — if no account with that id/code exists, it returns a `404 Not Found` rather than creating one. Creation is a completely separate call: `POST /accounts`.

Recurly lets you reference an account by its `code` (a merchant-assigned unique identifier) anywhere an `account_id` path parameter is expected, via the `code-` prefix convention — e.g. `GET /accounts/code-acme-inc`, `PUT /accounts/code-acme-inc`.

So a real "upsert" from this component's perspective requires, per row:

1. **Lookup**: `GET /accounts/code-<value>` — using the lookup value as the account code. A 404 means no match; this component's `recurly_resource` returns `None` on 404 (instead of raising) specifically so this check is a plain `is None`.
2. **Write**:
   - If found: `PUT /accounts/code-<value>` — update (partial-merge semantics).
   - If not found: `POST /accounts` — create, with `code` set from the row.

**Two API calls per row, always** — there is no way to make `PUT` "create if missing" and no way to know in advance whether an account exists without asking.

## `lookup_field`

`lookup_field` (default `code`) **must** be a `fields_map` value — its value is substituted directly into the `code-<value>` path segment for both the existence check and the write, so it should be a stable, URL-safe identifier (Recurly's own account-code format restricts it to `[a-z 0-9 @ - _ .]`, not starting with `.` or `-`, max 50 chars — this component doesn't re-validate that format, so bad values will surface as a 4xx from Recurly, recorded per-row in `rows_errored`).

## When to use

- Sync a dbt Customers mart into Recurly for subscription billing.
- Push warehouse-computed customer attributes (plan tier, CLV segment) into Recurly account fields.
- Keep Recurly Account records in sync with a CRM or external system of record.

## Pairs with

- **`recurly_resource`** — HTTP Basic auth (private API key, blank password) + workhorse HTTP (required).
- **`recurly_ingestion`** — the READ-side counterpart (dlt REST-source pull); unrelated implementation per this repo's no-shared-logic rule.

## Behavior + gotchas

- **Lookup value required** — rows with `None`/`NaN` in the column mapped to `lookup_field` are skipped and counted in `rows_skipped_no_key`.
- **No bulk batching** — `api_requests` metadata is roughly `2 * rows_upserted` (one existence-check GET + one write per successful row).
- **Code format is not pre-validated** — Recurly restricts account codes to `[a-z 0-9 @ - _ .]` (no leading `.`/`-`, 50 chars max); this component passes your value through as-is, so malformed codes surface as a write error per-row rather than failing fast upstream.
- **404-as-None convention** — this component depends on `recurly_resource`'s `request()` returning `None` on 404 (not raising); any other non-2xx status still raises and is recorded as a row error.

## Partitioning

When `partition_type` is set, a run sends only the rows in its partition: `partition_date_column` selects the rows whose date falls in a time partition's window (a backfill run covers its whole range) and `partition_static_column` selects the rows for a static/dynamic partition key. Unpartitioned runs send every row.
