# `SigmaInputTableUpsertComponent`

Reverse-ETL writeback: write an upstream DataFrame's rows into an existing **Sigma Input Table**, via a pre-published **webhook-triggered Action Sequence**.

## Why a webhook, not a direct "write rows" endpoint

Verified against Sigma's own REST API reference (not guessed) — **Sigma's public REST API has no endpoint that writes rows directly into an Input Table.** The full category list of the API reference (Account types, Agents, Connections, Data models, Datasets (deprecated), Files, Members, Query, Reports, Teams, Templates, Webhooks, Workbooks, ...) contains no "Input Tables" category at all. `POST /v2/files` ("Create a file") only creates *empty* workspaces/folders/workbooks/reports — it does not accept CSV content or back an Input Table.

The real, documented write path is Sigma's **Webhook trigger (Beta)** feature for workbook Action Sequences:

- [Run action sequences automatically (Beta)](https://help.sigmacomputing.com/docs/configure-action-sequences-to-run-automatically)
- [Post data to a webhook endpoint](https://help.sigmacomputing.com/reference/send-to-webhook)
- [Retrieve webhook message schema](https://help.sigmacomputing.com/reference/get-webhook-schema)

A human builds this **once**, in the Sigma UI:
1. Open the target workbook → Automation → Action Sequences.
2. Add an **Insert row(s)** (or **Update row(s)**) action targeting the Input Table, with its column values sourced from **Action variables**.
3. Add a **Webhook trigger** to the sequence, defining one array-type parameter (e.g. `rows`) that the Insert/Update action consumes as its multi-value row source, plus any scalar parameters you want.
4. Publish the workbook. Sigma gives you a `workbookId` + `sequenceId` for the webhook URL.

This component is the **caller side only** — it POSTs the upstream DataFrame's rows to that already-configured webhook. It does **not** create the workbook, Input Table, or Action Sequence.

## Request shape

```
POST {base_url}/v2/webhooks/{workbookId}/{sequenceId}
Authorization: Bearer <token>      (same OAuth2 client_credentials token as every other Sigma call)
Content-Type: application/json

{
  "<rows_parameter_name>": [ {col: val, ...}, ... ],
  ...static_parameters
}
```

"The JSON keys in the webhook request body must match the parameter names you define" (Sigma's own docs) — `rows_parameter_name` **must exactly match** the array parameter name you configured on the webhook trigger.

## Async, fire-and-forget — read this before you rely on it

The webhook responds **HTTP 202** with `{"traceId": "..."}` — the Action Sequence runs **asynchronously** after acceptance. This component:
- ✅ Confirms Sigma **accepted** each chunk (and surfaces every `traceId` in metadata for later audit/support correlation).
- ❌ Cannot confirm the Input Table rows were **actually written** — Sigma's webhook API gives no synchronous write-confirmation.

If you need write-confirmation, verify downstream (e.g. re-run `sigma_workbook_ingestion` and check the Input Table's row count / contents, or check the workbook's row-history panel in the Sigma UI).

## Row cap: 2,000 per action

Sigma documents a hard cap of **2,000 rows per Insert row(s) action** when fed from a single multi-value source. `rows_per_request` defaults to (and is capped at) 2,000; this component chunks the upstream DataFrame into that many webhook calls as needed.

## Schema pre-flight (recommended, on by default)

`validate_schema_before_write: true` (default) calls `GET /v2/webhooks/{workbookId}/{sequenceId}/schema` — which returns `{"variables": {...}}`, keyed by the webhook's declared parameter names — and fails the run with a clear error if `rows_parameter_name` (or any `static_parameters` key) isn't declared. This catches a stale/misconfigured `rows_parameter_name` *before* sending data, rather than silently accepting a 202 for a payload the sequence doesn't actually understand.

## Example

```yaml
type: dagster_component_templates.SigmaInputTableUpsertComponent
attributes:
  asset_name: sigma_forecast_inputs_write
  upstream_asset_key: dbt_marts_forecast_inputs
  resource_key: sigma_resource

  workbook_id: "abc123-workbook-id"
  sequence_id: "def456-sequence-id"
  rows_parameter_name: rows
  fields_map:
    region: Region
    forecast_month: ForecastMonth
    forecast_value: ForecastValue
  write_mode: insert
```

## Behavior + gotchas

- **No API call when every row is empty** — if every row maps to an entirely-null record, the component returns early without calling the webhook at all.
- **`write_mode` doesn't change behavior** — it's a documentation/metadata label. The actual Insert-vs-Update behavior is whatever action the Sigma-side Action Sequence runs; this component sends an identical request shape either way.
- **Async acceptance, not write-confirmation** — see "Async, fire-and-forget" above. A successful materialization means Sigma accepted the data, not that it landed in the Input Table.
- **Beta feature** — Sigma's Webhook triggers and the "Insert row(s) (Beta)" / "Update row(s)" actions are documented as Beta as of this writing; expect the schema/behavior to evolve.
- **HMAC auth not implemented** — Sigma's docs mention an HMAC-signature alternative to Bearer-token auth for webhook triggers; this component only implements the default Bearer-token path (the same `sigma_resource` token used everywhere else).
