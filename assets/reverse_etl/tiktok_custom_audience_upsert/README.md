# `TikTokCustomAudienceUpsertComponent`

Reverse-ETL / audience activation: mirror an upstream DataFrame into an existing **TikTok Custom Audience** via TikTok's two-stage file-based flow:

1. `POST /dmp/custom_audience/file/upload/` — upload one file **per identifier type** present in `fields_map`. TikTok's file format is one ID type per file (a header row names it, e.g. `Email_SHA256` / `Phone_SHA256`) — unlike Google Ads/Meta, which take a single multi-identifier payload per row.
2. `POST /dmp/custom_audience/update/` — append or remove members on the existing `custom_audience_id`, referencing all uploaded file paths in one call (`action: APPEND | REMOVE`).

This component only **uploads members** — it does not create audiences.

## Privacy: identifiers are hashed before they leave your infrastructure

TikTok never sees plaintext PII. Supported identifier types — map an upstream column to one via `fields_map`:

| Type | Normalization before SHA-256 |
|---|---|
| `email` | trim, lowercase |
| `phone` | **E.164 with a leading `+`** (confirmed against TikTok's own customer-file help docs) — same convention as Google Ads, *not* Meta's digits-only one. Include the country code, e.g. `+14155552671` |

TikTok recommends at least 1,000 entries per uploaded file for matching to work reliably. This component logs a warning (not an error) when a file falls short — TikTok's own enforcement may vary, so it uploads anyway rather than blocking a legitimate small run.

## `add` vs `remove`

- **`add`** (default) → TikTok `action: APPEND` — activation: add matching users to the audience.
- **`remove`** → TikTok `action: REMOVE` — suppression: remove matching users, e.g. exclude customers who already converted.

## When to use

- Sync a dbt mart of high-LTV customers into a Custom Audience for lookalike/targeting campaigns.
- Suppress churned or already-converted customers from retargeting (`operation: remove`).
- Push a warehouse-computed segment into an existing remarketing audience.

## Prerequisite: the audience must already exist

Create the Custom Audience once via TikTok Ads Manager (Assets → Audiences → Create Audience → Customer File) or the Marketing API, then pass its ID as `custom_audience_id`.

## Pairs with

- **`tiktok_ads_resource`** — access token + advertiser ID (required).
- **`tiktok_ads_ingestion`** — the READ-side counterpart (campaign/performance data pull).

Together they cover both directions of TikTok Ads data movement.

## Behavior + gotchas

- **One file per identifier type, not one combined file** — if `fields_map` maps columns to both `email` and `phone`, two separate files get uploaded (one `Email_SHA256`, one `Phone_SHA256`), both referenced in a single `update` call. `rows_submitted` counts identifiers, not rows — a row contributing both an email and a phone counts twice.
- **No calls made when every row is empty** — if no row has a valid identifier, neither the upload nor the update endpoint is called.
- **Small-file warning, not a hard failure** — TikTok recommends 1,000+ entries per file; this component warns below that but still uploads, since exact enforcement may vary and a legitimate small incremental sync shouldn't be blocked.
- **Asynchronous matching** — TikTok can take 24–48 hours to process an uploaded file against its user base. This component reports upload/update API success, not match results.
- **Phone hashing differs from Meta** — TikTok (like Google Ads) wants E.164 with a leading `+`; Meta wants digits-only. Don't reuse one platform's hash for another.

## Partitioning

When `partition_type` is set, a run sends only the rows in its partition: `partition_date_column` selects the rows whose date falls in a time partition's window (a backfill run covers its whole range) and `partition_static_column` selects the rows for a static/dynamic partition key. Unpartitioned runs send every row.
