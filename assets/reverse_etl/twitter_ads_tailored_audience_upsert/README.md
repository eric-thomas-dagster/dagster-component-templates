# `TwitterAdsTailoredAudienceUpsertComponent`

Reverse-ETL / audience activation: mirror an upstream DataFrame into an existing **X (Twitter) Ads Tailored Audience** via the single users endpoint:

```
POST /accounts/:account_id/custom_audiences/:custom_audience_id/users
```

The request body is a JSON array of operation objects. Each contains an `operation_type` (`Update` to add, `Delete` to remove) and a `params.users` array — one object per upstream row, each row contributing one or more identifier-type keys (`email`, `phone_number`), each mapped to a **list** of hashed values. Unlike TikTok (one uploaded file per identifier type), a single X user object can carry multiple identifier types at once — the same row-aligned shape Google Ads/Meta use.

This component only **uploads members** — it does not create audiences.

## Privacy: identifiers are hashed before they leave your infrastructure

X never sees plaintext PII. Supported identifier types — map an upstream column to one via `fields_map`:

| Type | Normalization before SHA-256 |
|---|---|
| `email` | trim whitespace, lowercase |
| `phone` | **E.164 with a leading `+`** (whitespace/punctuation stripped, country code required) — confirmed against a worked example in X's own Ads API docs: `+11234567890` hashes to `1fa6b8d986d9b9cd01bf36951815158bbde9f520c0567c835dfe34783d0a4231`, which only reproduces if the `+` is kept before hashing. Same convention as Google Ads and TikTok — *not* Meta's digits-only one |

All hashing is SHA-256, no salt, lowercase hex output — per X's documented rule that "all data... except `partner_user_id` must be hashed using SHA256 and normalized."

## `add` vs `remove`

- **`add`** (default) → X `operation_type: Update` — activation: add matching users to the audience.
- **`remove`** → X `operation_type: Delete` — suppression: remove matching users, e.g. exclude customers who already converted.

## Synchronous call, asynchronous matching

The API call itself is synchronous — it returns `success_count`/`total_count` immediately, and this component surfaces both in its materialization metadata. But X states that **"audience changes are processed in batches that run every 6-8 hours"** on its side — a successful response means X accepted the upload, not that matching against the audience has completed.

## Chunking

X caps each request at **2,500 user operations** and **5,000,000 bytes** per its documented rate-limit/payload rules. This component chunks the built user list into groups of 2,500 automatically, issuing one API call per chunk and summing `success_count`/`total_count` across all of them. `requests_sent` in the output metadata reports how many chunks were sent.

## When to use

- Sync a dbt mart of high-LTV customers into a Tailored Audience for lookalike/targeting campaigns.
- Suppress churned or already-converted customers from retargeting (`operation: remove`).
- Push a warehouse-computed segment into an existing remarketing audience.

## Prerequisite: the audience must already exist

Create the Tailored Audience once via Ads Manager (Tools → Audiences → Create Audience → Create your own) or the Ads API's `custom_audience` endpoint, then pass its ID as `custom_audience_id`.

## Pairs with

- **`twitter_ads_resource`** — OAuth 1.0a credentials + account ID (required).
- **`twitter_ads_ingestion`** — the READ-side counterpart (campaign/performance data pull).

Together they cover both directions of X Ads data movement.

## Behavior + gotchas

- **One user object per row, not per identifier type** — if `fields_map` maps columns to both `email` and `phone`, a single row produces one user object like `{"email": ["<hash>"], "phone_number": ["<hash>"]}`. `rows_submitted` counts rows (user objects), not identifiers — unlike TikTok, where it counts identifiers.
- **No calls made when every row is empty** — if no row has a valid identifier, the users endpoint is never called.
- **Chunked at 2,500 users per request** — X's documented payload limit. A 10,000-row upsert issues 4 requests; `requests_sent` and the summed `success_count`/`total_count` reflect this.
- **Asynchronous matching** — X batches audience changes every 6-8 hours. This component reports upload API success (`success_count`/`total_count`), not match results.
- **Phone hashing differs from Meta** — X (like Google Ads/TikTok) wants E.164 with a leading `+`; Meta wants digits-only. Don't reuse one platform's hash for another.
- **OAuth 1.0a, not OAuth 2.0** — the Ads API still requires consumer key/secret + access token/secret (`twitter_ads_resource`), unlike most of X's newer v2 APIs.
