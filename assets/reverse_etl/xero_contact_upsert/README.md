# `XeroContactUpsertComponent`

Reverse-ETL sink: mirror an upstream DataFrame into **Xero Contact** records.

## There is no single-call upsert -- Name-uniqueness makes this a two-step dance

Xero uses **one endpoint for both create and update** — `POST /api.xro/2.0/Contacts` — but which one happens depends on whether the request body carries a `ContactID`:

- **Create**: body has no `ContactID` → Xero assigns a new one. Xero **enforces uniqueness on Name across active contacts** — a blind create-only POST with a Name that already exists is rejected with a 400 (`"The contact name is already assigned to another contact."`).
- **Update**: body includes the existing contact's `ContactID` → Xero updates that record. Unlike QuickBooks there's no SyncToken-equivalent to manage; fields you omit are left unchanged (partial update is the default, not an opt-in).

So a real "upsert" from this component's perspective requires, per row:

1. **Lookup**: `GET /Contacts?where=<lookup_field>=="<value>"` — Xero's filter-query syntax — discovers whether a match exists and, if so, its `ContactID`.
2. **Write**: `POST /Contacts` — with `ContactID` set (update) if a match was found, or without it (create) if not.

**Two API calls per row, always** — there's no way to skip the lookup, and skipping it on a create-only assumption risks a 400 the moment the same Name recurs.

## `lookup_field`

`lookup_field` (default `Name` — Xero's enforced-unique field for active contacts) **must** be a `fields_map` value, since it's substituted directly into a Xero `where=` filter expression. `ContactNumber` is a common alternative when you maintain your own external id on the contact.

Only **flat** Contact fields are supported in `fields_map` (e.g. `Name`, `EmailAddress`, `ContactNumber`) — Xero's `Phones` and `Addresses` are arrays of sub-objects, not simple nested keys, and are out of scope here.

## When to use

- Sync a dbt Customers mart into Xero for invoicing.
- Push warehouse-computed customer attributes into a Xero Contact's `ContactNumber` (an external-id field).
- Keep Xero Contact records in sync with a CRM or external system of record.

## Example

```yaml
type: dagster_component_templates.XeroContactUpsertComponent
attributes:
  asset_name: xero_contacts_mirror
  upstream_asset_key: dbt_marts_customers
  resource_key: xero

  lookup_field: Name
  fields_map:
    customer_name: Name
    email: EmailAddress
    contact_number: ContactNumber

  batch_size: 5000
```

## Behavior + gotchas

- **Lookup value required** — rows with `None`/`NaN` in the column mapped to `lookup_field` are skipped and counted in `rows_skipped_no_key`.
- **Name-uniqueness 400s surface as row errors** — if two rows in the same batch map to the same `Name` (or a race with a human editing Xero concurrently), the second write can be rejected; it's recorded in `rows_errored`, not retried automatically.
- **No bulk batching** — `api_requests` metadata is roughly `2 * rows_upserted` (one lookup + one write per successful row).
- **`where=` quoting** — double quotes in the lookup value are escaped before being embedded in the Xero filter expression; values containing other filter-syntax-relevant characters should still be sanitized upstream if untrusted.
- **Flat fields only** — Phones/Addresses (Xero array sub-objects) aren't supported by this component's `fields_map`.
