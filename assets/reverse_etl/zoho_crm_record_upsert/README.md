# `ZohoCrmRecordUpsertComponent`

Reverse-ETL sink: mirror an upstream DataFrame into a **Zoho CRM module** using Zoho's **native Upsert Records** API. Atomic create-or-update in a single request — no search-then-write, no eventual consistency window, no idempotency-key gymnastics.

For every chunk of up to 100 rows:
- `POST /crm/{version}/{module_api_name}/upsert` with `{"data": [...], "duplicate_check_fields": [...]}`

Zoho returns, per record:
- `{"code": "SUCCESS", "duplicate_field": "Email", "action": "insert"|"update", "status": "success"|"error", "message": "...", "details": {"id": ..., ...}}`

## When to use

- Sync computed data (lead scores, segmentation flags, enrichment) from a warehouse INTO Zoho CRM so sales teams see them in-context.
- Mirror a golden-record leads/contacts/accounts table (dbt marts, Reverse-ETL best practice) into Zoho with atomic duplicate-check matching.
- Push status changes (lifecycle stage, health score) into Zoho as a nightly job.

## Prerequisite: `duplicate_check_fields`

`duplicate_check_fields` is a list of **Zoho field API names** (not upstream column names) used to detect duplicates — every entry MUST also appear as a value in `fields_map` (mirrors `salesforce_record_upsert`'s `external_id_field` validation, generalized to a list). Rows missing a value for ANY of the upstream columns mapped to a `duplicate_check_fields` entry are skipped and counted in `rows_skipped_no_key`.

Zoho's own system-defined duplicate-check fields per module (used automatically if you omit `duplicate_check_fields` entirely, though this component requires it non-empty): **Email** for Leads and Contacts. For modules without an obvious system-defined field (Accounts, Deals, custom modules), use a field you've marked **unique** (and ideally **mandatory**) in the module's field settings — Setup → Modules and Fields → {Module} → field properties.

Zoho's docs do not publish a hard maximum count for `duplicate_check_fields` (examples show 1-2 fields, e.g. `["Email", "Mobile"]`); this component does not enforce an artificial cap, but keep it small and make sure every field is actually marked unique/mandatory in Zoho — unmatched or non-unique fields make duplicate detection unreliable.

## Pairs with

- **`zoho_crm_resource`** — OAuth2 refresh-token auth + workhorse HTTP client (required).
- **`zoho_crm_ingestion`** — the READ-side counterpart (dlt-based bulk pull, static access token).

Together they cover both directions of Zoho CRM data movement.

## Example

```yaml
type: dagster_component_templates.ZohoCrmRecordUpsertComponent
attributes:
  asset_name: zoho_crm_leads_mirror
  upstream_asset_key: dbt_marts_leads
  resource_key: zoho_crm

  module_api_name: Leads
  duplicate_check_fields: [Email]
  fields_map:
    email: Email
    first_name: First_Name
    last_name: Last_Name
    company: Company
    lead_source: Lead_Source

  batch_size: 5000
```

## Behavior + gotchas

- **Duplicate-check key required** — every upstream row must have a value in EVERY column mapped to a `duplicate_check_fields` entry; rows with `None` / `NaN` in any of them are skipped and counted in the `rows_skipped_no_key` metadata.
- **Blank vs missing** — `None` / `NaN` values are omitted from the request body so the existing Zoho value is preserved. Empty strings `""` are sent verbatim.
- **100-record chunking** — internal, automatic, and independent of `batch_size` (which only caps total upstream rows per run). You never need to set a chunk size yourself.
- **Rate limits** — Zoho enforces per-org API request limits plus a 10-access-token-exchanges-per-10-minutes cap on the underlying resource's OAuth refresh. The resource retries on 429 / 5xx with exponential backoff up to `max_retries` and refreshes the OAuth token on 401.
- **Custom modules** — pass the module's API name (Setup → Modules and Fields shows the API name per custom module).
- **Non-writable fields** — some Zoho fields (formula fields, certain system fields) aren't writable via the API. Including them in `fields_map` causes Zoho to reject those fields per-record (surfaced via `rows_errored` / `first_errors`).

## Partitioning

When `partition_type` is set, a run sends only the rows in its partition: `partition_date_column` selects the rows whose date falls in a time partition's window (a backfill run covers its whole range) and `partition_static_column` selects the rows for a static/dynamic partition key. Unpartitioned runs send every row.
