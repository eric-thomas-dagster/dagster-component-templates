# `ZuoraAccountUpsertComponent`

Reverse-ETL sink: mirror an upstream DataFrame into **Zuora Account** records via Zuora's generic Object CRUD API.

## No upsert, no filter-by-field GET -- ZOQL does the lookup

Zuora's Object CRUD endpoints are strictly single-purpose: `POST /v1/object/account` always creates, `PUT /v1/object/account/{id}` always updates (404s if the id doesn't exist). Neither call can create-or-update, and there's no filter-by-field GET on this API — only GET-by-id, which is no help when all you have is a business key like `AccountNumber`.

Discovering whether an account already exists by `AccountNumber` (or any field) requires Zuora's query language, **ZOQL**, via the separate Action Query endpoint: `POST /v1/action/query` with a body like `{"queryString": "select Id from Account where AccountNumber = 'A00000123'"}`.

So a real "upsert" from this component's perspective requires, per row:

1. **Query**: `POST /v1/action/query` — ZOQL `select Id from Account where <lookup_field> = '<value>'` — discovers whether a match exists and, if so, its Zuora `Id`.
2. **Write**:
   - If found: `PUT /v1/object/account/{id}` — update (partial-merge semantics).
   - If not found: `POST /v1/object/account` — create.

**Two API calls per row, always.**

## Create has mandatory fields Zuora enforces, not this component

Zuora's Object CRUD `POST /v1/object/account` requires `Name`, `Currency`, `BillCycleDay`, and `Status` (`Draft`/`Active`/`Canceled`) at minimum. This component does **not** inject defaults for these — if your `fields_map` omits any of them (or the upstream row has a null in that column), the create call fails with a 400 from Zuora, recorded as a row error. Make sure `fields_map` covers all four for rows that might need creating.

## `lookup_field`

`lookup_field` (default `AccountNumber`, unique per Zuora tenant) **must** be a `fields_map` value, since it's substituted into the ZOQL `where` clause.

## Auth: OAuth2 client-credentials, not session-based

Zuora deprecated session-based (`Z-Session`) auth for all tenants on 2024-08-01. This component's resource (`zuora_resource`) uses OAuth2 client-credentials exclusively — see that resource's README if you're migrating from an older session-auth integration.

## When to use

- Sync a dbt Customers/Accounts mart into Zuora for subscription billing.
- Push warehouse-computed account attributes into Zuora custom fields.
- Keep Zuora Account records in sync with a CRM or external system of record.

## Pairs with

- **`zuora_resource`** — OAuth2 client-credentials auth + workhorse HTTP (required).
- **`zuora_ingestion`** — the READ-side counterpart (dlt REST-source pull); unrelated implementation per this repo's no-shared-logic rule.

## Example

```yaml
type: dagster_community_components.ZuoraAccountUpsertComponent
attributes:
  asset_name: zuora_accounts_mirror
  upstream_asset_key: dbt_marts_customers
  resource_key: zuora

  lookup_field: AccountNumber
  fields_map:
    customer_id: AccountNumber
    account_name: Name
    currency: Currency
    bill_cycle_day: BillCycleDay
    status: Status

  batch_size: 5000
```

## Behavior + gotchas

- **Lookup value required** — rows with `None`/`NaN` in the column mapped to `lookup_field` are skipped and counted in `rows_skipped_no_key`.
- **No bulk batching** — `api_requests` metadata is roughly `2 * rows_upserted` (one ZOQL query + one write per successful row).
- **Create-field gaps surface as row errors, not fast validation failures** — if `fields_map` is missing `Name`/`Currency`/`BillCycleDay`/`Status` and a row actually needs creating, you won't find out until Zuora 400s that row at write time.
- **ZOQL quoting** — single quotes in the lookup value are escaped before being embedded in the ZOQL `where` clause; values containing other ZOQL-syntax-relevant characters should still be sanitized upstream if untrusted.
- **`AccountNumber` immutability** — Zuora only allows changing `AccountNumber` on accounts with no (or only draft) subscriptions; attempting to change it on an active account's update fails and is recorded as a row error.

## Partitioning

When `partition_type` is set, a run sends only the rows in its partition: `partition_date_column` selects the rows whose date falls in a time partition's window (a backfill run covers its whole range) and `partition_static_column` selects the rows for a static/dynamic partition key. Unpartitioned runs send every row.
