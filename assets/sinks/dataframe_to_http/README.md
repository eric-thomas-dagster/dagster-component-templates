# Dataframe → HTTP sink

Write rows from a pandas DataFrame to any HTTP/REST endpoint via POST / PUT. The generic
destination for APIs that don't have a dedicated component in this registry — a StreamSets
HTTP Client destination, a webhook, an internal service, a vendor REST ingest endpoint, etc.

## Batch shapes

| `batch_mode` | HTTP | Body | Use when |
|---|---|---|---|
| `per_record` (default) | one request per row | that row as a JSON object | the endpoint expects one entity per call; URL can template row values |
| `batch_array` | one request per `batch_size` rows | a JSON array of row objects | the endpoint accepts a bulk list in a single call |
| `ndjson` | one request per `batch_size` rows | newline-delimited JSON (`Content-Type: application/x-ndjson`) | the endpoint is a streaming/NDJSON ingest API |

`per_record` mode's `url` may template row values via `{column_name}`, e.g.
`https://api.example.com/customers/{customer_id}`. `batch_array`/`ndjson` send to `url`
literally — one request carries many rows, so there's no single row to template from.

## Auth

`none` | `basic` | `bearer` | `oauth2_client_credentials`. The OAuth2 mode fetches an access
token once per process and caches it in-process until shortly before expiry (same pattern as
this repo's other OAuth2 client_credentials resources, e.g. `zocdoc_resource`).

## Retry

Exponential backoff (`retry_backoff_seconds * 2**attempt`, honoring a `Retry-After` response
header when present) on connection/timeout errors and on any status in `retry_on_status_codes`
(default `[429, 500, 502, 503, 504]`), up to `max_retries` per request. This is separate from
the asset-level Dagster `RetryPolicy` (`retry_policy_max_retries`), which retries the whole
run step on failure rather than a single HTTP call.

## Writing the response back into the record

Set `write_response_to_record: true` to append `http_response_status` /
`http_response_body` / `http_response_json` (and `http_response_value`, if
`response_json_path` is set) onto each row, and materialize the enriched DataFrame as this
asset's own output instead of a plain sink with no output value. Useful when a downstream step
needs the endpoint's generated ID or confirmation payload. In `batch_array`/`ndjson` modes,
every row in a chunk gets that chunk's single response recorded — requests aren't per-row, so
the response can't be attributed more granularly than its batch.

## Failure handling

The component logs each failure (status + response body, or the exception) and aborts after
`fail_after_n_failures` (default 10) failed requests/chunks. After the run, it raises a
`RuntimeError` if any requests failed — the asset materialization fails so Dagster's retry /
alerting can kick in. A sample of failures is attached to the asset metadata
(`failures_sample`).

## Partitioning

When `partition_type` is set, each run processes only the upstream rows in its partition:
`partition_date_column` selects the rows whose date falls in a time partition's window (a
backfill run covers its whole range), and `partition_static_column` (with
`partition_static_dim` for multi-partitions) selects the rows for a static/dynamic partition
key. Unpartitioned runs process every row.
