# DataFrame → Kafka

Send each row of an upstream DataFrame to a Kafka topic as a JSON message.
Destination-side counterpart to `kafka_monitor` (sensor) and
`kafka_to_database_asset`, which only consume from Kafka — use this when a
pipeline needs to publish, not just read (e.g. a migrated StreamSets Kafka
Producer destination, or seeding a topic with synthetic/replay events).

## Composes with

- `synthetic_data_generator` upstream → seed a topic with N test events
- `kafka_monitor` (sensor) + `kafka_to_database_asset` downstream → a full publish → consume → land-in-DB loop, all within the registry
- `kafka_resource` → share one configured client across this sink and the consumer-side components via `resource_key`

## Behavior

- Each row → one Kafka message, value = `json.dumps(row, default=str).encode("utf-8")`
- `key_column` (optional): pins same-key rows to one partition, preserving per-key ordering
- `batch_size` controls how often `producer.flush()` is called during the send loop — it does not cap total rows sent, and a final `flush()` always runs after the loop regardless of batch_size
- Three ways to connect: `bootstrap_servers` (inline), `bootstrap_servers_env_var` (env var), or `resource_key` (use an already-registered `KafkaResourceComponent`'s `get_producer()` — shares auth/config with `kafka_monitor`/`kafka_to_database_asset` if they also use `resource_key`)
- Uses `kafka-python` (the same library as `kafka_resource`, `kafka_monitor`, and `external_kafka_asset`) — not `confluent_kafka` (used only by `kafka_to_database_asset`, the one component on a different client)

## Pattern: this is one of many DataFrame-to-queue components

This component is dedicated to Kafka because each message-queue SDK has
distinct auth + config (bootstrap servers, topic, partition key semantics).
The same shape exists for other queues:

- `redis_writer` (already in registry) → Redis hashes / streams
- `dataframe_to_eventhub` (already in registry) → Azure Event Hubs
- `dataframe_to_pubsub` (planned) → GCP Pub/Sub
- `dataframe_to_kinesis` (planned) → AWS Kinesis

Generic configurations for all-of-the-above don't compose well because
each backend is structurally different — keeping per-backend components
focused beats a single fat component with conditional auth/config.

## Partitioning

When `partition_type` is set, Dagster partitions the asset itself (daily/weekly/monthly/hourly/static/dynamic) the same way every other sink in this registry does — this does not affect per-message Kafka partitioning, which is controlled entirely by `key_column`.
