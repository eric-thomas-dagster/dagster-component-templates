# Gmail Draft Create

Create a Gmail **DRAFT** — templated from an upstream asset's row — via the real Gmail API
(`POST /gmail/v1/users/me/drafts`). This is the write-capable sibling of the read-only
[`gmail_ingestion`](https://github.com/eric-thomas-dagster/dagster-component-templates/tree/main/assets/ingestion/gmail_ingestion)
component, and shares its exact OAuth2 convention: a bearer access token in the
`access_token` field.

```yaml
type: dagster_community_components.GmailDraftCreateComponent
attributes:
  asset_name: nightly_brief_gmail_draft
  access_token: "${GMAIL_ACCESS_TOKEN}"
  upstream_asset_key: nightly_brief

  to_email: me@example.com
  subject_template: "Nightly brief -- {report_date}"
  body_template: |
    {summary_text}

  dry_run: true
```

## This creates a DRAFT only -- it never sends mail

The Gmail API's `drafts.create` endpoint cannot send on a user's behalf; a human still has
to open Gmail and click Send. There is no config flag here that sends instead -- if you
need to actually send mail autonomously, that's a different (and riskier) API surface
(`users.messages.send`), not what this component does.

**Motivating use case:** a nightly automated brief-generation pipeline (an LLM-written
daily summary, an anomaly digest, a sales/ops report) that should land as a reviewable
draft in the user's own Gmail — addressed to their own address — rather than auto-send
unreviewed, LLM-authored content. A human reviews, edits if needed, and clicks Send
themselves.

## Auth

Same convention as `gmail_ingestion`: set `access_token` to a Google OAuth2 access token.
The token needs the `gmail.compose` scope (or the broader `gmail.modify`) to create drafts.
Use `${GMAIL_ACCESS_TOKEN}` to pull it from an env var rather than hardcoding a literal
token in YAML.

## Upstream value shape

`upstream_asset_key` points at the asset whose materialized value supplies the template
fields. Either shape works:

- **dict-shaped** -- a single record, fields used directly.
- **pandas DataFrame** -- one row is selected via `row_index` (default `0`, the first row).

```yaml
upstream_asset_key: nightly_brief
row_index: 0   # pick a different row if the upstream has several candidate drafts per run
```

## Templates

`{column_name}` placeholders fill from the upstream row/record. Missing keys yield empty
string. `to_email`, `subject_template`, `body_template`, and each `cc_emails`/`bcc_emails`
entry are all templated the same way:

```yaml
to_email: me@example.com
subject_template: "Nightly brief -- {report_date}"
body_template: |
  Good morning,

  Here's last night's automated summary:

  {summary_text}

  (This is a draft -- review and send if it looks right.)
```

## How it's built

1. The upstream row/record is resolved into a dict of template fields.
2. `subject_template` / `body_template` / `to_email` / `cc_emails` / `bcc_emails` are
   rendered against it.
3. A real RFC 2822 MIME message (`email.mime.text.MIMEText`, UTF-8 plain text) is built,
   with `To`/`Cc`/`Bcc`/`Subject` headers set.
4. The message is serialized to raw bytes and base64url-encoded, per the Gmail API's
   `raw` field contract.
5. `POST https://gmail.googleapis.com/gmail/v1/users/me/drafts` is called with
   `{"message": {"raw": <encoded>}}` and `Authorization: Bearer <access_token>`.
6. A non-2xx response raises a clear `RuntimeError` with the status code and response body.
7. Returns a `MaterializeResult` with the created draft's `draft_id` and `message_id` in
   metadata, alongside the rendered `to` and `subject`.

## Safety

- `dry_run: true` renders and logs the MIME message without calling the Gmail API or
  creating a draft. Use to verify templates against real upstream data before creating
  real drafts.
- Nothing in this component can send mail -- see "This creates a DRAFT only" above.
