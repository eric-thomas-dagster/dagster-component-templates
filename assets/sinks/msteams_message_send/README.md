# MS Teams Message Send

Post a templated message to a Microsoft Teams channel — one per upstream row (data-driven alert) or one digest message per run. Pairs with [`msteams_resource`](https://github.com/eric-thomas-dagster/dagster-component-templates/tree/main/resources/msteams_resource) for auth.

```yaml
type: dagster_component_templates.MSTeamsMessageSendComponent
attributes:
  asset_name: customer_health_teams_alert
  upstream_asset_key: customers_crossing_health_threshold
  resource_key: msteams
  mode: per_row
  title_template: "Health score alert: {customer_name}"
  message_template: |
    Customer **{customer_name}** just crossed the health-score threshold.
    Score: {health_score}
```

## Scope: business-data-driven alerts, NOT run-status notifications

**This component posts messages driven by WAREHOUSE DATA CONDITIONS** — it evaluates
upstream asset rows (e.g. "which customers just crossed a health-score threshold",
"which orders failed fraud review") and turns each one (or a digest of all of them)
into a human-readable Teams message. It has **no awareness of Dagster run status,
asset materialization success/failure, or freshness violations.**

**It is explicitly NOT a reimplementation of Dagster's own pipeline-health
notifications.** If what you actually want is "tell me when a job fails" /
"tell me when an asset fails to materialize" / "tell me when an asset goes
stale" — do **not** use this component. Instead:

- Pair [`msteams_resource`](https://github.com/eric-thomas-dagster/dagster-component-templates/tree/main/resources/msteams_resource) with a Dagster run-status sensor or hook (`run_failure_sensor`, `make_teams_on_run_failure_sensor`, asset check sensors, etc.) for code-based run-health alerting.
- On Dagster+, use the platform's **built-in alert policies** — they already cover run failures, asset check failures, and freshness violations with zero code.

These two notification paths are deliberately kept separate: "the pipeline broke"
and "the data says something" are different concerns with different owners,
and conflating them makes both harder to tune (alert fatigue on one bleeds
into the other).

## Modes

| Mode | Behavior |
|---|---|
| `per_row` | One Teams message per upstream row. All templates render `{column}` placeholders from the row. |
| `summary` | One message per run. `summary_template` can use `{row_count}` and `{table_md}` (markdown table of up to 50 rows). |

## Templates

`{column_name}` placeholders fill from the row dict. Missing keys yield empty string. Examples:

```yaml
title_template: "Health score alert: {customer_name}"
message_template: |
  Customer **{customer_name}** (plan: {plan}) just crossed the health-score threshold.
  Score: {health_score} (was {previous_health_score})
```

Messages render as a legacy "hero card" (title + text) — the same attachment shape
`dagster-msteams` itself uses for its failure-hook notifications, so it's compatible
with both classic Office 365 Connector webhooks and the newer Workflows-based
incoming webhooks.

## Auth

- **Reuse `msteams_resource`**: set `resource_key: msteams` (or whatever key an `MSTeamsResourceComponent` registered). Preferred when other components in the project already post to Teams — one webhook URL, one place to rotate it.
- **Standalone**: set `webhook_url_env_var` to an env var holding the incoming-webhook URL for the target channel. See [Microsoft's incoming-webhook setup guide](https://learn.microsoft.com/en-us/microsoftteams/platform/webhooks-and-connectors/how-to/add-incoming-webhook).

## Safety

- `dry_run: true` renders + logs every message without posting. Use to verify templates against real data.
- `max_send` caps messages per run — guardrail against runaway upstreams.
- The component never auto-retries — if a post fails, it's logged and counted in `messages_failed`. Add a separate retry sensor if you need that.

## Not a replacement for Dagster+ notifications

See "Scope" above. For *run-level* alerts (job failed, asset materialization failed, freshness violated, etc.) use Dagster+'s built-in alerting, or a run-status sensor/hook paired with `msteams_resource`. This component is for **data-row-driven** outbound Teams messages (one message per record in your upstream, or a digest).
