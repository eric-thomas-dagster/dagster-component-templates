# Slack Message Send

Post a templated message to Slack — one per upstream row (data-driven alert) or one digest message per run. Pairs with [`slack_resource`](https://github.com/eric-thomas-dagster/dagster-component-templates/tree/main/resources/slack_resource) for auth, or [`slack_ingestion`](https://github.com/eric-thomas-dagster/dagster-component-templates/tree/main/assets/ingestion/slack_ingestion) for round-trip pipelines (read from Slack, write business alerts back to Slack).

```yaml
type: dagster_component_templates.SlackMessageSendComponent
attributes:
  asset_name: customer_health_slack_alert
  upstream_asset_key: customers_crossing_health_threshold
  resource_key: slack_resource
  mode: per_row
  channel_template: "#customer-success"
  message_template: |
    :rotating_light: *{customer_name}* just crossed the health-score threshold.
    Score: {health_score}
```

## Scope: business-data-driven alerts, NOT run-status notifications

**This component posts messages driven by WAREHOUSE DATA CONDITIONS** — it evaluates
upstream asset rows (e.g. "which customers just crossed a health-score threshold",
"which orders failed fraud review") and turns each one (or a digest of all of them)
into a human-readable Slack message. It has **no awareness of Dagster run status,
asset materialization success/failure, or freshness violations.**

**It is explicitly NOT a reimplementation of Dagster's own pipeline-health
notifications.** If what you actually want is "tell me when a job fails" /
"tell me when an asset fails to materialize" / "tell me when an asset goes
stale" — do **not** use this component. Instead:

- Pair [`slack_resource`](https://github.com/eric-thomas-dagster/dagster-component-templates/tree/main/resources/slack_resource) with a Dagster run-status sensor or hook (`run_failure_sensor`, `make_slack_on_run_failure_sensor`, asset check sensors, etc.) for code-based run-health alerting.
- On Dagster+, use the platform's **built-in alert policies** — they already cover run failures, asset check failures, and freshness violations with zero code.

These two notification paths are deliberately kept separate: "the pipeline broke"
and "the data says something" are different concerns with different owners,
and conflating them makes both harder to tune (alert fatigue on one bleeds
into the other).

## Modes

| Mode | Behavior |
|---|---|
| `per_row` | One Slack message per upstream row. All templates render `{column}` placeholders from the row. |
| `summary` | One message per run. `summary_template` can use `{row_count}` and `{table_md}` (markdown table of up to 50 rows). |

## Templates

`{column_name}` placeholders fill from the row dict. Missing keys yield empty string. Examples:

```yaml
channel_template: "#customer-success"
message_template: |
  :rotating_light: *{customer_name}* (plan: {plan}) just crossed the health-score threshold.
  Score: {health_score} (was {previous_health_score})
  <https://app.example.com/customers/{customer_id}|View in app>
```

Slack `message_template` supports [mrkdwn](https://api.slack.com/reference/surfaces/formatting) (`*bold*`, `_italic_`, `` `code` ``, `<url|text>` links), not standard Markdown.

### Per-row channel routing

`channel_template` is rendered per row too, so a single asset can fan out alerts to
different channels based on data:

```yaml
channel_template: "{slack_channel}"   # column holding e.g. "#region-us" / "#region-eu"
```

### Threading

```yaml
thread_ts_column: parent_thread_ts
```

If the named column holds a Slack `thread_ts` value, the message is posted as a reply
in that thread instead of a new top-level message. Useful for grouping repeated alerts
about the same entity.

## Auth

- **Reuse `slack_resource`**: set `resource_key: slack_resource` (or whatever key a `SlackResourceComponent` registered). Preferred when other components in the project already post to or read from Slack — one bot token, one place to rotate it.
- **Standalone**: set `token_env_var` to an env var holding a bot token (`xoxb-...`). Requires the `chat:write` scope and the bot invited to the target channel (or a shared IM for a DM).

## Safety

- `dry_run: true` renders + logs every message without posting. Use to verify templates against real data.
- `max_send` caps messages per run — guardrail against runaway upstreams.
- The component never auto-retries — if a post fails for a given channel, the row is logged and counted in `messages_failed`. Add a separate retry sensor if you need that.

## Not a replacement for Dagster+ notifications

See "Scope" above. For *run-level* alerts (job failed, asset materialization failed, freshness violated, etc.) use Dagster+'s built-in alerting, or a run-status sensor/hook paired with `slack_resource`. This component is for **data-row-driven** outbound Slack messages (one message per record in your upstream, or a digest).
