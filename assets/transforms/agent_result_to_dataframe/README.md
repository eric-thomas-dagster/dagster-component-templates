# AgentResultToDataFrameComponent

Turn an agent asset's dict result into a DataFrame so the existing
`dataframe_to_*` sinks (table, csv, parquet, s3, gcs, duckdb, snowflake, ...)
can store it. An agent asset (`anthropic_agent`, `openai_agent`,
`litellm_agent`, `gemini_agent`, `vercel_ai_gateway_agent`,
`snowflake_cortex_agent`, ...) materializes a dict shaped roughly like
`{final_answer, iterations, tool_calls_made, tool_call_details, ...}`. No sink
in this repo accepts that shape directly -- they all read a DataFrame. This
component bridges the two.

## Use Cases

- Log every agent run (prompt, answer, iteration/tool-call counts) to a table
  so history accumulates across partitions.
- Explode `tool_call_details` into one row per tool call for auditing/cost
  analysis.
- Parse a structured JSON answer (an agent prompted to return
  `{category, confidence, ...}`) straight into table columns.
- Works generically on any dict-valued asset, including an
  `agentic_pipeline` step asset (`{text, ...op-specific fields}`), not just
  the 6 dedicated agent components.

## Modes

- **`one_row`** (default): one row per run, built from the result dict's own
  top-level scalar fields. Nested fields (lists/dicts, e.g.
  `tool_call_details`, `transcript`) are dropped unless named explicitly in
  `include_columns`, in which case they're serialized to a JSON string column.
- **`explode`**: one row per entry of a list-valued field (`explode_field`,
  default `tool_call_details`). Each entry's own fields become columns.
- **`extract`**: parses `final_answer` as JSON -- either the whole string, or
  the content of a fenced ```` ```json ```` block -- into columns/rows. For
  agents prompted to return structured output. A single dict becomes one
  row; a list of dicts becomes one row per item. Invalid JSON raises a clear
  error by default; set `on_parse_error: keep_raw` to instead emit one row
  with the raw text under `final_answer_raw` and the failure under
  `parse_error`, rather than failing the whole run.

## Partition-bridge heuristic

Partition this asset the same way as its upstream agent asset (the common
case) and every run sees exactly one result dict -- no special handling
needed. If this asset is left unpartitioned while its upstream is
partitioned (or a `single_run` backfill spans a partition range), Dagster's
IO manager instead hands back a dict keyed by partition key. Since a real
agent-result dict is *also* just a dict, the two are told apart by whether
the top-level dict carries any of the common result-shape keys
(`final_answer`/`text`/`output`/`result`/`answer`/`json`): if none do and
every value is itself a dict, it's treated as a partition bridge and produces
one row group per partition, with `partition_key` set from the bridge's own
keys.

## Example YAML

```yaml
type: dagster_community_components.AgentResultToDataFrameComponent
attributes:
  asset_name: agent_runs_table
  upstream_asset_key: support_ticket_agent
  mode: one_row
  add_run_columns: true
  extra_columns:
    pipeline: support_ticket_agent
  group_name: ai
  partition_type: daily
  partition_start: "2024-01-01"
```

Then store it with any sink, e.g. append-only history in a warehouse table:

```yaml
type: dagster_community_components.DataframeToTableComponent
attributes:
  asset_name: agent_runs_history
  upstream_asset_key: agent_runs_table
  table_name: agent_runs
  if_exists: append
```

| Output | `pd.DataFrame` | One row per run (or per exploded/extracted item) |

## Notes

- `include_columns` / `exclude_columns` apply after mode-specific row
  construction, so they work the same way across all three modes.
- `add_run_columns` (default on) stamps `run_id`, `partition_key`,
  `materialized_at`, and `asset_key` onto every row -- this is what lets a
  `dataframe_to_*` sink with `if_exists: append` build real history instead
  of overwriting on every tick.
- `extra_columns` values may contain the literal substring `{partition_key}`,
  substituted with the row's resolved partition key (empty string when
  unpartitioned).
