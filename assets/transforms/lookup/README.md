# LookupMatch Component

Azure Data Factory's **"Lookup"** data flow transform: for each row in a primary stream, find a matching row in a secondary/lookup stream by key column(s).

This is a different problem than a plain left join (already covered by `dataframe_join`):

1. **Deterministic multiple-match resolution.** When several lookup rows match the same key, ADF's Lookup transform lets you specify sort conditions to deterministically pick exactly ONE match (e.g. "match the most recent `effective_date`", or "match the highest `priority`") -- rather than fanning out into multiple output rows (what a plain join does) or picking arbitrarily. Set `match_sort_by` (+ `match_sort_ascending`) for this.
2. **`isMatch()` output.** Instead of pulling the matched row's columns into the output, ADF's Lookup can add a single boolean column indicating whether a match was found at all -- useful for a later `filter` / conditional-split step, without carrying the matched columns. Set `output_mode: is_match`.

## SQL source for the primary stream

Instead of `upstream_asset_key`, set `source` to pull the primary stream's rows directly via SQL -- no intermediate asset required:

```yaml
source:
  kind: warehouse_query
  resource_key: snowflake_resource   # or database_url_env_var: DATABASE_URL
  sql: "SELECT * FROM orders"
```

Mutually exclusive with `upstream_asset_key` -- set exactly one. The lookup stream is always a Dagster asset (`lookup_asset_key`); there is no SQL-source option for it.

## Backend (`backend: pandas` / `polars`)

Same dual-backend convention as `dataframe_join`, `filter`, `pct_change`, and the other components that follow it: `backend: pandas` (default) uses pandas' `.merge()`; `backend: polars` uses polars' own `.join()` and returns a **polars DataFrame** (not converted back to pandas). The multiple-match dedup step also runs natively in polars (`.sort(...).unique(subset=<key columns>, keep='first')`) instead of pandas' `sort_values().drop_duplicates()`. Mixed input types (an upstream asset handing over the other library's DataFrame) are normalized automatically at the component boundary.

```yaml
backend: polars
```

## Multiple-match resolution (`match_sort_by`)

When several lookup rows share the same key, this component sorts the candidates by `match_sort_by` (+ `match_sort_ascending`) and takes exactly one -- the first after sorting -- so the output has exactly one row per primary row (no fan-out):

```yaml
match_sort_by:
  - effective_date
match_sort_ascending: false   # most recent effective_date wins
```

**Leave `match_sort_by` unset and the pick is first-occurrence / arbitrary** (pandas' own `drop_duplicates(keep='first')` row order) -- not guaranteed deterministic across upstream data that gets reordered between runs. Set `match_sort_by` whenever a *specific* match matters.

## `isMatch()` output (`output_mode: is_match`)

```yaml
output_mode: is_match
output_column: has_price   # defaults to 'is_match'
```

Adds exactly one boolean column (named by `output_column`) and drops every other lookup-side column from the output -- the primary stream's own columns pass through unchanged. Pair with a downstream `filter` component on that column instead of carrying the matched row's data forward.

## YAML Example

```yaml
type: dagster_community_components.LookupMatchComponent
attributes:
  asset_name: orders_with_latest_price
  upstream_asset_key: orders
  lookup_asset_key: price_history
  # NOTE: `on` must be quoted -- YAML 1.1 parses a bare `on` key as boolean True.
  "on":
    - product_id
  match_sort_by:
    - effective_date
  match_sort_ascending: false
  output_mode: columns
  group_name: transforms
```

## Behavior

- Use `on` when the join key column has the same name in both streams; use `left_on` + `right_on` together when they differ.
- No match on a row: `output_mode: columns` leaves the pulled-in columns null/NaN (left-join semantics, row count unchanged); `output_mode: is_match` sets the boolean column to `False`.
- Overlapping non-key column names (in `columns` mode) are disambiguated using `suffixes` (same convention as `dataframe_join`).
- For multi-column, same-direction joins with no multiple-match concerns, prefer `dataframe_join` (`how: left`) -- this component exists specifically for the sort-based single-match and `isMatch()` semantics above.
