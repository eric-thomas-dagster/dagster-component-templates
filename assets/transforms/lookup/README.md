# Lookup Component

Azure Data Factory's **"Lookup"** data flow transform: for each row in a primary stream, find a matching row in a secondary/lookup stream by key column(s). Also covers StreamSets' JDBC/Local Lookup processors' multiple-match and no-match behaviors.

This is a different problem than a plain left join (already covered by `dataframe_join`):

1. **Explicit multiple-match resolution.** When several lookup rows match the same key: `multiple_match: first`/`last` (default `first`) deterministically picks exactly ONE match via sort conditions (e.g. "match the most recent `effective_date`", or "match the highest `priority`") -- set `match_sort_by` (+ `match_sort_ascending`) for this. `multiple_match: all` fans out into one output row per match (StreamSets JDBC Lookup's `SPLIT_INTO_MULTIPLE_RECORDS`, same shape as a plain join). `multiple_match: all_as_list` keeps one output row per primary row and collects every match's added columns into a list per column (StreamSets JDBC Lookup's `ALL_AS_LIST`).
2. **`on_no_match`.** `pass` (default) passes unmatched rows through with null added columns; `error` raises if any row has zero matches (StreamSets JDBC Lookup's fail-on-missing-match policy).
3. **`isMatch()` output.** Instead of pulling the matched row's columns into the output, this component can add a single boolean column indicating whether a match was found at all -- useful for a later `filter` / conditional-split step, without carrying the matched columns. Set `output_mode: is_match`. (To get the attached columns AND a boolean flag at the same time, use `output_mode: columns` with `match_flag_column` instead.)
4. **`columns_to_add` / `rename`.** Restrict which lookup-side columns get attached (default: all non-key columns), and rename them after attaching.

## SQL source for the primary stream

Instead of `upstream_asset_key`, set `source` to pull the primary stream's rows directly via SQL -- no intermediate asset required:

```yaml
source:
  kind: warehouse_query
  resource_key: snowflake_resource   # or database_url_env_var: DATABASE_URL
  sql: "SELECT * FROM orders"
```

Mutually exclusive with `upstream_asset_key` -- set exactly one. The lookup stream is always a Dagster asset (`lookup_asset_key`); there is no SQL-source option for it.

## Backend (`backend: pandas` / `polars`)

Same dual-backend convention as `dataframe_join`, `filter`, `pct_change`, and the other components that follow it: `backend: pandas` (default) uses pandas' `.merge()`; `backend: polars` uses polars' own `.join()` and returns a **polars DataFrame** (not converted back to pandas). The multiple-match dedup step also runs natively in polars (`.sort(...).unique(subset=<key columns>, keep='first')`) instead of pandas' `sort_values().drop_duplicates()`. Mixed input types (an upstream asset handing over the other library's DataFrame) are normalized automatically at the component boundary.

```yaml
backend: polars
```

## Multiple-match resolution (`multiple_match`)

When several lookup rows share the same key, `multiple_match` controls what happens:

```yaml
multiple_match: first   # default. Also: last | all | all_as_list
match_sort_by:
  - effective_date
match_sort_ascending: false   # most recent effective_date wins
```

- `first` / `last`: sorts candidates by `match_sort_by` (+ `match_sort_ascending`) and keeps exactly one -- the output has exactly one row per primary row (no fan-out). **Leave `match_sort_by` unset and the pick is first-occurrence / arbitrary** (row order as given) -- not guaranteed deterministic across upstream data that gets reordered between runs. Set `match_sort_by` whenever a *specific* match matters.
- `all`: every matching lookup row produces its own output row (StreamSets JDBC Lookup's `SPLIT_INTO_MULTIPLE_RECORDS`) -- same fan-out shape as a plain left join.
- `all_as_list`: one output row per primary row; every match's added columns are collected into a list per column (StreamSets JDBC Lookup's `ALL_AS_LIST`).

Ignored when `output_mode: is_match` -- existence doesn't depend on which/how many rows matched.

## Unmatched rows (`on_no_match`)

```yaml
on_no_match: pass   # default. Also: error
```

`pass` leaves added columns null/NaN (or `output_column: false` in `is_match` mode). `error` raises if any primary row has zero matches in the lookup stream.

## Restricting / renaming attached columns (`columns_to_add`, `rename`)

```yaml
columns_to_add: [price]        # default: all non-key lookup columns
rename:
  price: unit_price            # must not rename a join key column
```

Both are `output_mode: columns`-only; set either with `output_mode: is_match` and the component raises (no lookup columns are attached in that mode).

## `isMatch()` output (`output_mode: is_match`, or `match_flag_column`)

```yaml
output_mode: is_match
output_column: has_price   # defaults to 'is_match'
```

Adds exactly one boolean column (named by `output_column`) and drops every other lookup-side column from the output -- the primary stream's own columns pass through unchanged. Pair with a downstream `filter` component on that column instead of carrying the matched row's data forward.

To get the attached lookup columns **and** a boolean match-found flag at the same time, stay in `output_mode: columns` and set `match_flag_column` instead:

```yaml
output_mode: columns
match_flag_column: found
```

## YAML Example

```yaml
type: dagster_community_components.LookupComponent
attributes:
  asset_name: orders_with_latest_price
  upstream_asset_key: orders
  lookup_asset_key: price_history
  # NOTE: `on` must be quoted -- YAML 1.1 parses a bare `on` key as boolean True.
  "on":
    - product_id
  match_sort_by:
    - effective_date
  match_sort_ascending: false
  output_mode: columns
  group_name: transforms
```

## Behavior

- Use `on` when the join key column has the same name in both streams; use `left_on` + `right_on` together when they differ.
- No match on a row: `output_mode: columns` leaves the pulled-in columns null/NaN (left-join semantics, row count unchanged unless `multiple_match: all`); `output_mode: is_match` sets the boolean column to `False`.
- Overlapping non-key column names (in `columns` mode) are disambiguated using `suffixes` (same convention as `dataframe_join`).
- For a plain multi-column fan-out join with no multiple-match resolution needed, prefer `dataframe_join` (`how: left`) -- this component exists specifically for the sort-based single-match, `isMatch()`, and `all`/`all_as_list` semantics above.

## Migrating from the old field names

An earlier, separate flat-layout `LookupComponent` (`transforms/lookup`, since removed and merged into this one) used `upstream_lookup_key` / `sort_conditions` / `match_flag_column`-as-sole-output. Field mapping: `upstream_lookup_key` → `lookup_asset_key`; `sort_conditions: [{column, order}]` → `match_sort_by` (list of columns) + `match_sort_ascending` (bool/list, `order: desc` → `false`); `columns_to_add`, `multiple_match`, `on_no_match`, and `rename` are unchanged in name and behavior.

**Old configs still load and run correctly** -- `upstream_lookup_key` and `sort_conditions` are accepted as deprecated aliases (rewritten onto `lookup_asset_key` / `match_sort_by` / `match_sort_ascending` before validation), so this is not a breaking change in practice. New configs should use the current field names; the old ones have no deprecation deadline but are not documented above and may be removed in a future major version.
