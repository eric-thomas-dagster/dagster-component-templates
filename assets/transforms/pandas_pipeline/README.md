# Pandas Pipeline

Run a multi-step pandas DataFrame chain inside a **single** Dagster asset. The pandas-engine sibling to [`polars_pipeline`](../polars_pipeline/README.md) — same YAML shape, same op menu, same source/sink kinds, same partitioning (including `(bank, batch_day)`-style multi-dimensional partitions via `partition_dimensions`) — for teams that already standardize on pandas, or that want simpler, more linear step-by-step execution to debug.

## Why this exists, and when to use it instead of `polars_pipeline`

| | `polars_pipeline` | This component |
|---|---|---|
| Engine | polars LazyFrame, lazy query-plan fusion across the whole chain | pandas, each op runs eagerly, one at a time |
| Best for | Large data, long op chains, cross-step predicate pushdown | Teams standardized on pandas, simpler step-by-step debugging |
| Format support | csv / json / ndjson / parquet / ipc / avro | csv / json / ndjson / parquet (no ipc/avro — not a natural pandas fit) |
| `op: sql` engine | polars's own SQLContext | DuckDB (reads a pandas DataFrame natively, zero-copy) |
| Partitioning | `partition_dimensions` → `MultiPartitionsDefinition` | Identical — same field names, same behavior |
| `encrypted_file` source/sink | Yes | Yes |

Both components share the exact same YAML shape for everything except engine-internal expression syntax, so someone fluent in one doesn't have to relearn the other — just which ops map to which engine underneath.

## YAML

```yaml
type: dagster_community_components.PandasPipelineComponent
attributes:
  asset_name: top_customers_by_region
  upstream_asset_key: raw_orders
  operations:
    - op: filter
      predicate: "status = 'paid'"
    - op: with_columns
      expressions:
        net_amount: "amount - tax"
    - op: group_by
      group_by: [region, customer_id]
      aggregations:
        total:       {col: net_amount, agg: sum}
        order_count: {col: order_id,   agg: count}
    - op: sort
      by: [region, total]
      descending: true
    - op: head_per_group
      group_by: [region]
      n: 5
  group_name: analytics
```

## Supported operations

Each entry in `operations:` is `{op: <kind>, ...op-specific params}`:

| op | Params | Notes |
|---|---|---|
| `filter` | `predicate: "<sql>"` | SQL predicate via an in-memory DuckDB connection |
| `with_columns` | `expressions: {name: <sql_expr>}` and/or `python_expressions: {name: <python_expr>}` | SQL columns via DuckDB; `python_expressions` runs with `pd` + `df` (the frame so far) bound for anything DuckDB's dialect can't express, e.g. `"df['amount'] * 0.15"` |
| `select` | `columns: [a, b]` | Keep only these columns |
| `drop` | `columns: [a, b]` | Drop these columns |
| `rename` | `mapping: {old: new}` | Rename columns |
| `group_by` | `group_by: [cols]`, `aggregations: {out: {col, agg}}` | Same agg shape as `polars_pipeline` |
| `sort` | `by: [cols]`, `descending: bool`, `na_position: first/last` (default `last`), `na_position_per_column: [first/last, ...]` | Sort. `na_position_per_column` (ADF Sort's per-condition null-handling flag) overrides `na_position` when set — one value per `by` column, sorted one key at a time from last to first with a stable sort to combine them. |
| `head` / `tail` | `n: int` | Take first/last N rows |
| `head_per_group` | `group_by: [cols]`, `n: int` | Top-N per group; sort first if order matters |
| `unique` | `subset: [cols]`, `keep: first/last` | Dedup (`drop_duplicates`) |
| `drop_nulls` | `subset: [cols]` (optional) | Drop rows with null in subset |
| `fill_null` | `value: <any>` | Fill nulls |
| `cast` | `mapping: {col: 'int'/'float'/'string'/'bool'/'datetime'}` | Type cast |
| `join` | `right: {ref: <step_id>}`, `how: inner/left/right/full/cross/semi/anti`, `on_columns`/`left_on`+`right_on` | Join against another step's output (multi-step form only). `semi`/`anti` are implemented as filters (pandas has no native semi/anti join) — they keep only the left side's columns. |
| `union` | `other: {ref: <step_id>}`, `mode: by_name\|by_position` (default `by_name`), `distinct: bool` | Stack another step's rows on top (multi-step form only). `by_name` aligns by column label (pandas' `concat` default), filling missing columns with null; `by_position` renames the other step's columns to match this step's order first. |
| `sql` | `sql: "<query>"` | Escape hatch via an in-memory DuckDB connection — `self` = current frame; prior steps usable by id |
| `pivot` | `index: [cols]`, `pivot_column: col`, `value_columns: [cols]`, `agg_func: sum` (or a `{value_col: agg}` dict), `pivot_values: [v, ...]` (optional), `fill_value` (optional) | ADF's **Pivot** transform, via `pd.pivot_table`. Multiple `value_columns` flatten `(value_col, pivot_value)` MultiIndex columns to `value_col_pivotvalue`. `pivot_values` restricts the output to exactly those pivot-column values — one absent from the data still produces a `fill_value`-filled column (same `pd.Categorical(..., categories=...)` technique as the standalone `cross_tab` component). |
| `lookup` | `right: {ref: <step_id>}`, `on_columns`/`left_on`+`right_on`, `match_sort_by: [cols]` (optional), `match_sort_ascending: bool\|[bool, ...]` (optional, default `true`), `output_mode: columns\|is_match` (default `columns`), `output_column: <name>` (required for `is_match`) | ADF's **Lookup** transform. Default `output_mode: columns` behaves like a left join (NaN for no match). `match_sort_by` sorts the right side and keeps exactly the first match per key *before* merging — guarantees a true 1:1 lookup when multiple right-side rows share a key (e.g. "latest event per customer": `match_sort_by: [event_time]`, `match_sort_ascending: false`). `output_mode: is_match` adds a single boolean `output_column` instead of any right-side columns (same semi-join indicator-merge technique the `join` op's `semi`/`anti` use). |
| `window_calculation` | `function: ntile\|cume_dist`, `order_by: [cols]`, `group_by: [cols]` (optional), `n: int` (required for `ntile`), `output_column: <name>` | Scoped to just these two — rank-equivalents are already covered by the standalone `rank` component and this component's own `sort`/`group_by`. `ntile` buckets rows 1..N as evenly as possible with the FIRST `(row_count mod n)` buckets getting the extra row, matching SQL's `NTILE` convention exactly (computed directly, not via `pd.qcut`, which spreads any remainder across the outer buckets instead — verified by hand: 10 rows / 4 buckets is `[3,3,2,2]`, not qcut's `[3,2,2,3]`). `cume_dist` is `Series.rank(method='max', pct=True)` — verified by hand against `[10, 20, 20, 30] -> [0.25, 0.75, 0.75, 1.0]`. |

Supported `agg` values in `group_by`: `sum / mean / avg / min / max / count / median / std / var / first / last / nunique`. `pivot`'s `agg_func` is looser (any name `pd.pivot_table`'s own `aggfunc` recognizes, plus the same SQL-ish aliases as `cross_tab`: `avg/average/stddev/variance/countdistinct/distinct_count/concat`).

### `pivot` example (closes ADF's **Pivot** gap)

```yaml
- op: pivot
  index: [region]
  pivot_column: quarter
  value_columns: [revenue]
  agg_func: sum
  pivot_values: [Q1, Q2, Q3, Q4]   # declare the full schema; a missing quarter still gets a column
  fill_value: 0
```

### `lookup` example (closes ADF's **Lookup** gap)

```yaml
steps:
  - id: orders
    source: {kind: upstream, upstream_asset_key: raw_orders}
    operations: []
  - id: customer_events
    source: {kind: upstream, upstream_asset_key: raw_events}
    operations: []
  - id: enriched
    source: {kind: ref, ref: orders}
    operations:
      - op: lookup
        right: {ref: customer_events}
        on_columns: [customer_id]
        match_sort_by: [event_time]
        match_sort_ascending: false   # most-recent event wins when a customer has several
```

### `window_calculation` example (closes ADF's **Rank**/**Window** gap — `ntile`/`cume_dist` only)

```yaml
- op: window_calculation
  function: ntile
  order_by: [score]
  group_by: [region]   # optional -- omit for a single global window
  n: 4
  output_column: score_quartile
```

## Source kinds

`source: {kind: ..., ...}` (or per-step `source:` in the multi-step form):

- `{kind: file, path, format?, delimiter?, has_header?, quote_char?, dtype_overrides?}` / `{kind: url, url, format?, delimiter?, has_header?, quote_char?, dtype_overrides?}` — csv/json/ndjson/parquet, format inferred from extension when unset. Cloud URLs (`s3://`, `gs://`, `az://`, `http(s)://`) are pre-fetched via `fsspec` into a temp file first. The three trailing options are CSV-only — see "CSV declared-type reads" below.
- `{kind: upstream_asset, upstream_asset_key}` / top-level `upstream_asset_key:` — read an upstream Dagster asset (accepts a pandas OR polars upstream; polars frames are converted automatically).
- `{kind: ref, ref: <step_id>}` — read another step's output (multi-step form only).
- `{kind: encrypted_file, path, format?, has_header?, quote_char?, dtype_overrides?}` — decrypt a file's raw bytes (AWS Encryption SDK, `key_source`/`raw_key_env_var`/`kms_key_ids`/`key_id`/`encryption_context` fields, same names as [`FieldEncryptionComponent`](../field_encryption/README.md)) then parse into a DataFrame. See that component's README for the encryption mechanism and its StreamSets-ciphertext-interop caveat — it applies here too, at the file level instead of the cell level. Same CSV-only declared-type options as the plain file source.

## CSV declared-type reads (`kind: file`/`url`/`encrypted_file`, format: csv)

```yaml
source:
  kind: file
  path: "incoming/orders.csv"
  has_header: true           # default; set false for a headerless file
  quote_char: "'"            # default pandas' own '"'
  dtype_overrides:
    account_code: object     # pin a column's type -- without this, a zero-padded code
    customer_id: string      # column like "001" silently becomes the integer 1 under
                              # pandas' own schema inference, same failure an Azure Data
                              # Factory Copy activity's declared-type source read avoids
```

`dtype_overrides` values are pandas dtype NAMES as plain strings (`object`/`string`, `Int8`...`Int64`,
`float32`/`float64`, `boolean`, ...) — validated via pandas' own canonical dtype resolver
(`pd.api.types.pandas_dtype`), so any dtype the installed pandas version itself recognizes works, with
no separate name→dtype table in this component to fall out of sync with a pandas release. Only the
columns you list are pinned; every other column is still inferred normally. `has_header`/`quote_char`
are pandas' own `read_csv` kwargs (`header=0`/`header=None`, `quotechar=`), passed through for
completeness.

## Sink kinds

`sinks: [{from: <step_id>, kind: ..., ...}]`:

- `parquet` / `csv` — `path:` (supports `{partition_key}` / `{partition.<name>}` templating).
- `ndjson` — `path:` (same templating), via pandas' native `to_json(orient="records", lines=True)` / `read_json(..., lines=True)`. Additionally takes `mode: overwrite` (default) \| `append` — append reads the existing file, concatenates, and rewrites (single-writer, not concurrent-write-safe). Closes a real gap: until now, writing JSON output needed a second asset even though `kind: encrypted_file` already supported `format: ndjson` for the encrypted path — the plain (unencrypted) file sink just never got the same format.
- `table` — write to any Dagster resource exposing `.get_connection()`/`.get_engine()`. Auto-detects a DuckDB-style connection (`.register()`/`.execute()`/`.unregister()`) for a zero-copy fast path; falls back to `df.to_sql()` for any SQLAlchemy-compatible resource. Supports `if_exists: append/replace` or `mode: upsert_on_match` + `match: [col, ...]` for partition-rewrite idempotency.
- `encrypted_file` — serialize to bytes (csv/json/ndjson/parquet) then encrypt (same AWS Encryption SDK mechanism as the source kind) before writing to `path:`.

## Partitioning

Identical to `polars_pipeline`: `partition_type` (`daily`/`weekly`/`monthly`/`hourly`/`cron`/`static`/`dynamic`) for a single dimension, or `partition_dimensions` (a list of `{name, type, start, values, ...}` dicts) for a `MultiPartitionsDefinition` — e.g. a `(bank, batch_day)` shape for a multi-tenant file-batch pipeline, keeping the partition count at `banks × days` instead of one dynamic partition per file.

## Output

Always returns a pandas DataFrame (there's no `output_type:` field — unlike `polars_pipeline`, which can return either polars or pandas, this component's whole point is staying in the pandas ecosystem).
