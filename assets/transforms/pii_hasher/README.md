# PiiHasherComponent

General-purpose transform: normalize + SHA-256 hash PII identifier columns (email, phone, or any other free-form identifier) in an upstream DataFrame. Pure DataFrame-in / DataFrame-out, like this category's other transforms (`field_mapper`, `data_cleansing`, `type_coercer`) — not tied to any one downstream destination. Feed the output into any reverse-ETL sink, warehouse table, or your own compliance/anonymization pipeline.

This component is self-contained: it does not import from any reverse_etl component or other transform. Its hashing/normalization logic is an independent implementation written in parallel to this repo's ad-platform audience-activation components, which each separately proved the normalization rules below correct per-platform.

## Why normalization differs by platform

Hashing PII correctly requires normalizing it into one canonical string *before* hashing — two systems that hash the same email or phone number differently will never match on the hashed value, even though the identifier is "the same". This repo's own ad-platform reverse_etl components verified (against each platform's own documentation) that the canonical form genuinely differs:

| Platform | Component | Email rule | Phone rule |
|---|---|---|---|
| Google Ads | `assets/reverse_etl/google_ads_customer_match_upsert/component.py` | trim + lowercase | `e164_with_plus` — leading `+`, digits only, country code required |
| Meta | `assets/reverse_etl/meta_custom_audience_upsert/component.py` | trim + lowercase | `digits_only_no_plus` — no `+`, digits only |
| TikTok | `assets/reverse_etl/tiktok_custom_audience_upsert/component.py` | trim + lowercase | `e164_with_plus` |
| X/Twitter | `assets/reverse_etl/twitter_ads_tailored_audience_upsert/component.py` | trim + lowercase | `e164_with_plus` |
| LinkedIn | `assets/reverse_etl/linkedin_matched_audience_upsert/component.py` | lowercase + strip **all** whitespace (broader than a simple trim); no phone identifier supported at all | — |
| Pinterest | `assets/reverse_etl/pinterest_audience_upsert/component.py` | trim + lowercase | `digits_only_no_plus` (Pinterest additionally strips leading zeros per its own docs — a platform-specific nuance beyond what this component's generic `digits_only_no_plus` mode applies) |

This component exposes the two phone conventions (`e164_with_plus` and `digits_only_no_plus`) and the two email conventions (trim+lowercase vs. strip-all-whitespace) as explicit config rather than hardcoding one, so you can match whatever your destination expects — including destinations outside this repo's ad-platform components entirely (a warehouse table, a CDP, a custom API).

## Identifier types

Set per-column via `column_identifiers: {column_name: identifier_type}`:

- **`email`** — trim + lowercase by default. Set `email_strip_all_whitespace: true` for LinkedIn's broader rule (strips internal whitespace too, not just leading/trailing).
- **`phone`** — normalized per `phone_mode`:
  - `e164_with_plus` (default) — strip everything but digits and a leading `+` (Google Ads / TikTok / X convention). Your input should already include the country code.
  - `digits_only_no_plus` — strip the `+` and every non-digit character (Meta / Pinterest convention).
- **`generic`** — trim only, then hash. For any identifier without a platform-specific rule (loyalty IDs, internal customer IDs, SSNs, etc.) — still hashed, just without email/phone-specific case or format normalization.

Null, NaN, and empty/blank-after-normalization values are skipped (hashed column gets `None`/null) rather than hashing an empty string or the literal text `"nan"`.

## Output

For each entry in `column_identifiers`, a new `{column}{hashed_column_suffix}` column (default suffix `_hashed`) is added containing the hex-encoded SHA-256 digest. Columns not listed in `column_identifiers` pass through unchanged.

By default (`drop_original_columns: true`) the original plaintext column is dropped — the entire point of this component is to prevent plaintext PII from flowing downstream. Set `drop_original_columns: false` only for local debugging/testing: **doing so in a production pipeline defeats the purpose of hashing**, since the plaintext PII remains in the output DataFrame and flows to every downstream consumer of this asset.

## SQL source

Instead of `upstream_asset_key`, set `source` to pull rows directly via SQL
-- no intermediate asset required:

```yaml
source:
  kind: warehouse_query
  resource_key: snowflake_resource   # or database_url_env_var: DATABASE_URL
  sql: "SELECT * FROM my_table"
```

Mutually exclusive with `upstream_asset_key` -- set exactly one. Works with
any resource exposing `.get_engine()` (SQLAlchemy), `.get_connection()`
(DBAPI -- Postgres/Snowflake/DuckDB/MySQL/Databricks SQL), or `.get_client()`
(BigQuery, Redshift).

## Example YAML
```yaml
type: dagster_component_templates.PiiHasherComponent
attributes:
  asset_name: hashed_customers
  upstream_asset_key: raw_customers
  column_identifiers:
    email: email
    phone_number: phone
    loyalty_id: generic
  phone_mode: e164_with_plus
  drop_original_columns: true
```
