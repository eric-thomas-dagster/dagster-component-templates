# Polars Pipeline

Run a multi-step polars LazyFrame chain inside a **single** Dagster asset. Polars's query planner fuses filters, eliminates intermediate columns, and parallelizes the whole sequence — but only **within** one lazy chain.

## Why this exists

`summarize(backend=polars)` / `filter(backend=polars)` / etc. each run one operation per Dagster asset. Spread across separate assets, the asset boundary forces materialization at every step — the lazy chain is broken, and there's no fusion or pushdown across steps.

This component takes a **sequence of polars operations** and runs them as one chain. You get polars's full query optimization, at the cost of coarser lineage (one asset for the whole sequence).

| | Per-asset transforms (`backend: polars`) | This component |
|---|---|---|
| Lineage granularity | Per step | Per pipeline |
| Polars query-plan fusion | No (asset boundary breaks chain) | Yes |
| Predicate pushdown across steps | No | Yes (within chain) |
| Streaming engine | No | Optional (`streaming: true`) |
| Cross-asset reuse of intermediate | Yes (any asset can consume) | No |

Rule of thumb: if each step deserves its own catalog entry + lineage, use per-asset. If the steps are tightly coupled and you want throughput, use this.

## YAML

```yaml
type: dagster_community_components.PolarsPipelineComponent
attributes:
  asset_name: top_customers_by_region
  upstream_asset_key: raw_orders
  operations:
    - op: filter
      predicate: "status = 'paid'"
    - op: with_columns
      expressions:
        net_amount: "amount - tax"
    - op: group_by
      group_by: [region, customer_id]
      aggregations:
        total:       {col: net_amount, agg: sum}
        order_count: {col: order_id,   agg: count}
    - op: sort
      by: [region, total]
      descending: [false, true]
    - op: head_per_group
      group_by: [region]
      n: 5
  output_type: polars
  group_name: analytics
```

## Supported operations

Each entry in `operations:` is `{op: <kind>, ...op-specific params}`:

| op | Params | Notes |
|---|---|---|
| `filter` | `predicate: "<sql>"` | SQL predicate via polars's SQLContext |
| `with_columns` | `expressions: {name: <sql_expr>}` | Add/replace columns from SQL expressions |
| `select` | `columns: [a, b]` | Keep only these columns. A name with `/` or `.` (e.g. `a/b`) is a nested struct-field path — extracted and aliased to a flat top-level column (`a__b`). |
| `drop` | `columns: [a, b]` | Drop these columns (top-level only — not nested struct paths) |
| `rename` | `mapping: {old: new}` | Rename columns (top-level only — not nested struct paths; use `select` to extract + alias a nested field to a new name instead) |
| `group_by` | `group_by: [cols]`, `aggregations: {out: {col, agg}}` | Same agg shape as `summarize` |
| `sort` | `by: [cols]`, `descending: bool/list`, `nulls_last: bool/list` (default `false` — nulls first) | Sort. `nulls_last` controls null ordering per-column (list) or overall (bool), passed straight through to polars' own `LazyFrame.sort(nulls_last=...)`. |
| `head` / `tail` | `n: int` | Take first/last N rows |
| `head_per_group` | `group_by: [cols]`, `n: int` | Top-N per group; sort first if order matters |
| `unique` | `subset: [cols]`, `keep: first/last/none` | Dedup |
| `drop_nulls` | `subset: [cols]` (optional) | Drop rows with null in subset |
| `fill_null` | `value: <any>` | Fill nulls |
| `cast` | `mapping: {col: 'Int64'}` | Type cast |
| `join` | `right: {ref: <step_id>}`, `how`, `on_columns`/`left_on`+`right_on`, `suffix` (default `_right`) | Join against another step's output (multi-step form only). `how: semi`/`how: anti` are ADF's **Exists** transform — `semi` keeps left rows WITH a match (no right-side columns in the output), `anti` keeps left rows WITHOUT one. |
| `union` | `other: {ref: <step_id>}`, `mode: by_name\|by_position` (default `by_name`), `distinct: bool` | Stack another step's rows on top (multi-step form only). `by_name` matches columns by name, filling missing ones with null (`dataframe_union`'s own default); `by_position` takes column order from this step and stacks positionally. |
| `sql` | `sql: "<query>"` | Escape hatch via polars' SQLContext (`self` = current chain; prior steps usable by id) |
| `explode` | `column: <name>` (or `columns: [...]`) | Explode a list/array column into one row per element |

| `coalesce` | `columns: [a, b]`, `output_column` | First non-null across the listed columns |
| `route` | `routes: [{name, predicate}]`, `default?` | Fan one step out into several named lanes by predicate (same SQL dialect as `filter`), with an optional catch-all `default` lane. Reference a lane from a later step via `source: {kind: ref, ref: "<step_id>.<lane>"}` or a sink's `from:`. If `default` is set, the bare step id also resolves to that lane. |
| `pivot` | `index: [cols]`, `pivot_column`, `value_columns: [cols]`, `agg_func` (default `sum`), `pivot_values?`, `fill_value?` (default `0`) | ADF's **Pivot** transform — see below. |
| `lookup` | `right: {ref: <step_id>}`, `on_columns`/`left_on`+`right_on`, `match_sort_by?`, `match_sort_ascending?`, `output_mode`, `output_column?` | ADF's **Lookup** transform — see below. |

Supported `agg` values in `group_by`: `sum / mean / avg / min / max / count / median / std / var / first / last / nunique`.

### `pivot` (ADF's Pivot transform)

```yaml
- op: pivot
  index: [region, segment]        # one or more group-by/row-label columns
  pivot_column: quarter            # column whose unique values become new columns
  value_columns: [revenue, cost]   # one or more columns to aggregate
  agg_func: sum                    # sum/mean/avg/min/max/median/first/last/count
  pivot_values: [Q1, Q2, Q3, Q4]    # optional: restrict + declare the exact output
                                    # columns -- a value absent from the data still
                                    # produces a fill_value column instead of being
                                    # silently missing (ADF's declared-schema Pivot)
  fill_value: 0                    # fill null cells after pivoting (default 0)
```

Built on polars' own `DataFrame.pivot` (`on`/`index`/`values`/`aggregate_function` — NOT
pandas `pivot_table`'s `columns`/`index`/`values` names). A single `value_columns` entry
produces bare pivot-value column names (`Q1`, `Q2`, ...); more than one produces
`<value_column>_<pivot_value>` names (`revenue_Q1`, `cost_Q1`, ...) so the columns stay
disambiguated.

### `lookup` (ADF's Lookup transform)

```yaml
- op: lookup
  right: {ref: customer_dim}
  on_columns: [customer_id]         # or left_on: [...] + right_on: [...]
  match_sort_by: [priority]          # optional: resolve multiple right-side matches
  match_sort_ascending: false        # to exactly one row per key before the join
  output_mode: columns               # columns (default, left-join-shaped) | is_match
  output_column: found                # is_match mode only: name of the boolean column
```

Reuses `join`'s own `right: {ref: <step_id>}` shape. `output_mode: columns` behaves like a
left join (null for no match). `output_mode: is_match` instead produces a single boolean
`output_column` — an existence check only, every other right-side column dropped (a
semi-join-shaped result). When `match_sort_by` is set, multiple right-side rows sharing a
key are resolved to exactly one match by sorting the right side (direction via
`match_sort_ascending`) and keeping the first row per key before the join — a true 1:1
lookup regardless of how many right rows share a key.

### `window_calculation` (ADF's Window transform — ntile / cume_dist)

```yaml
- op: window_calculation
  function: ntile                  # or cume_dist
  order_by: [score]
  group_by: [region]               # optional — whole frame if unset
  n: 4                              # required for ntile: number of buckets
  output_column: quartile
```

`ntile` buckets each `group_by` partition (or the whole frame) into `n` roughly-equal
groups ordered by `order_by`, using the standard SQL `NTILE` rule: extra rows go to the
earliest buckets (e.g. 10 rows into 4 buckets → sizes `[3, 3, 2, 2]`). `cume_dist`
computes each row's cumulative distribution — the fraction of rows in its partition with
an `order_by` value less than or equal to its own (standard SQL `CUME_DIST` semantics).
Polars has no built-in `ntile`/`cume_dist` expression, so both are built from
`rank`/`cum_count` + arithmetic. Rank-equivalent window functions are already covered by
the standalone `rank` component and this component's own `sort`/`group_by`, so this op is
scoped to just these two statistical functions.

### `unpivot` (ADF's Unpivot transform)

```yaml
- op: unpivot
  id_columns: [customer_id]
  value_columns: [q1_revenue, q2_revenue, q3_revenue, q4_revenue]
  var_name: quarter
  value_name: revenue
```

Built on polars' own `.unpivot()` (the current polars 2.0 method name — `.melt()` no
longer exists). `on`/`index` map to `value_columns`/`id_columns`.

### `rank` (ADF's Rank transform — full tie-breaking method set)

```yaml
- op: rank
  order_by: [score]
  method: dense
  group_by: [region]   # optional -- omit for a single global rank
  output_column: score_rank
```

Unlike `window_calculation` (scoped to just `ntile`/`cume_dist`), `rank` covers the full
tie-breaking method set: `average`/`min`/`max`/`first`/`dense` (polars' own `Expr.rank()`
vocabulary, `first` aliased to polars' `ordinal`), plus `ntile`/`cume_dist`. A single-column
`order_by` uses polars' native `Expr.rank()` directly; a multi-column `order_by` (ADF: several
sort keys, like a SQL `ORDER BY` with several columns, each with its own `ascending`
direction) is built from `sort()` + `shift()`/`cum_sum()`/`.over()` primitives, since polars'
own `rank()` only ranks by a single expression.

## `inline` and `sql` sources

`source: {kind: inline, rows: [...]}` or `{kind: inline, text: "...", format: csv|ndjson}` embeds rows or raw delimited text directly in the YAML — no external file, for a StreamSets raw-data/dev-origin-style pipeline.

`source: {kind: sql, resource_key?, url_env_var?, query?, table?, incremental?, offset_column?, initial_offset?}` reads from a SQL database via a Dagster resource exposing `.get_engine()`/`.get_connection()` (`resource_key`) or a raw connection URL in an env var (`url_env_var`). Plain mode runs `query:` once. `incremental: true` gives a resumable `WHERE offset_column > <last stored value> ORDER BY offset_column` read against `table:` (or a base `query:`), with the new high-water mark persisted via this asset's own output metadata (`dagster_community_components/last_offset/<step_id>`) — the same mechanism `mongodb_reader`/`elasticsearch_reader` use, no separate state file. `jdbc` is accepted as an alias for `sql`.

## CSV declared-type reads (`kind: file`/`url`, format: csv)

```yaml
source:
  kind: file
  path: "incoming/orders.csv"
  has_header: true           # default; set false for a headerless file
  quote_char: "'"            # default polars' own '"'
  schema_overrides:
    account_code: Utf8       # pin a column's type -- without this, a zero-padded code
    customer_id: Utf8        # column like "001" silently becomes the integer 1 under
                              # polars' own schema inference, same failure an Azure Data
                              # Factory Copy activity's declared-type source read avoids
```

`schema_overrides` values are polars dtype NAMES as plain strings (`Utf8`/`String`, `Int8`...`Int64`,
`Float32`/`Float64`, `Boolean`, `Date`, `Datetime`, ...) — looked up directly as `pl.<Name>` attributes, so
any dtype the installed polars version itself exposes works, with no separate name→dtype table in this
component to fall out of sync with a polars release. Only the columns you list are pinned; every other
column is still inferred normally.

## New sink capabilities

`sinks:` entries of `kind: parquet`/`csv`/`avro`/`ndjson` additionally take:
- `mode: overwrite` (default) \| `append` — append reads the existing file, concatenates, and rewrites (single-writer, not concurrent-write-safe).
- `partition_by: [col, ...]` (kind: parquet only) — writes a Hive-style directory of part-files via polars' native `write_parquet(partition_by=...)`, instead of one file.

`kind: ndjson` (newline-delimited JSON, via polars' native `write_ndjson`) closes a real gap:
until now, writing JSON output needed a second asset (`dataframe_to_json`) even though
`kind: encrypted_file` already supported `format: ndjson` for the encrypted path -- the plain
(unencrypted) file sink just never got the same format.

## Encrypted file I/O

`source: {kind: encrypted_file, ...}` and `sinks: [{from, kind: encrypted_file, ...}]` decrypt/encrypt a whole file's bytes via the real AWS Encryption SDK — the same envelope-encryption mechanism as `FieldEncryptionComponent` (`transforms/field_encryption`), just file-level instead of per-cell. This lets one asset do decrypt → transform → re-encrypt → stage in a single materialization — no separate ops, no hand-rolled Python.

```yaml
steps:
  - id: staged
    source:
      kind: encrypted_file
      path: "incoming/{partition.bank}/{partition.batch_day}.csv.enc"
      format: csv                 # inferred from the name if omitted (.enc/.encrypted stripped first)
      key_source: raw_key         # or 'kms'
      raw_key_env_var: BANK_FILE_KEY
    operations:
      - {op: rename, mapping: {acct: account_id}}
      - {op: cast, mapping: {amount: Float64}}
sinks:
  - from: staged
    kind: encrypted_file
    path: "staged/{partition.bank}.csv.enc"
    format: csv
    key_source: raw_key
    raw_key_env_var: BANK_FILE_KEY
```

| Field | Notes |
|---|---|
| `path` | Local path or cloud URL (via fsspec). Supports `{partition_key}` / `{partition.<name>}` templating. |
| `format` | `csv` \| `parquet` \| `ndjson` \| `json` (sinks: `csv`/`parquet`/`ndjson`/`json` only — no `ipc`/`avro` on write). Inferred from the filename when unset, stripping a trailing `.enc`/`.encrypted` first. |
| `key_source` | `raw_key` (symmetric key from `raw_key_env_var`, base64-encoded 32 bytes) or `kms` (`kms_key_ids`). |
| `key_id` | Logical wrapping-key identifier for `raw_key` mode — must match between the writer and reader. |
| `encryption_context` | Optional AAD. A `path: <resolved path>` entry is always added on top, so ciphertext can't be silently swapped between files or partitions. |

This is a real AWS Encryption SDK integration, not a toy cipher — same provider construction as `FieldEncryptionComponent`, round-trip-tested against the actual library. It is **not** verified to be byte-compatible with any other tool's AWS-ESDK ciphertext (e.g. StreamSets' "Encrypt and Decrypt Fields" stage) — the wire format is a standard envelope, but what gets encrypted (this component writes the serialized file bytes directly, with no per-field wrapping) is this component's own scheme.

## Streaming

Set `streaming: true` to use polars's streaming engine on the final `.collect()`. Works for out-of-core frames (larger than memory). No syntactic change to operations.

Polars 2.0 made the streaming engine the default for `.collect()` regardless of this flag, and that engine doesn't guarantee row order for `group_by`/`join` unless `maintain_order` is set -- a silent reordering, not an error. `group_by` and `join` ops in this component always pass `maintain_order` (confirmed against a real, installed polars 2.0.0), so results stay deterministic either way.

## Output

`output_type: polars` (default) returns a polars DataFrame so downstream polars-aware components can chain. `output_type: pandas` converts at the boundary for pandas-only downstream consumers.
