# Warehouse Join (pushdown)

Join two tables in the warehouse via CTAS. The warehouse engine plans + executes the join; the result lands as a new table. No data through Python.

For N-way joins, chain multiple `warehouse_join` assets — each output_table becomes the next left_table.

## YAML

```yaml
type: dagster_community_components.WarehouseJoinComponent
attributes:
  asset_name: orders_with_customers
  database_url: snowflake://...
  dialect: snowflake
  left_table: raw.orders
  right_table: raw.customers
  output_table: analytics.orders_with_customers
  how: left                    # inner | left | right | outer/full | cross
  on_columns: [customer_id]    # OR use left_on + right_on. NB: not `on:` — YAML 1.1 parses bare `on` as boolean
  select_cols:                 # optional projection — use _l. / _r. to disambiguate
    - _l.order_id
    - _l.amount
    - _l.status
    - _r.customer_name
    - _r.region
  mode: replace
  deps: [raw_orders_in_warehouse, raw_customers_in_warehouse]
```

## Aliases

Left table is aliased as `_l`; right table as `_r`. Use these in `select_cols:` to disambiguate columns with the same name on both sides.

## When names differ

```yaml
left_on:  [customer_id]
right_on: [id]               # right.id maps to left.customer_id
```

## Generated SQL

```sql
CREATE OR REPLACE TABLE analytics.orders_with_customers AS
SELECT _l.order_id, _l.amount, _l.status, _r.customer_name, _r.region
FROM "raw"."orders" AS _l
LEFT JOIN "raw"."customers" AS _r
ON _l."customer_id" = _r."customer_id"
```

## Partitioning

Set `partition_type` (`daily`/`weekly`/`monthly`/`hourly`, or `static`/`dynamic`) and `partition_date_column` (or `partition_static_column`) to run the transform one partition at a time. A partitioned run:

1. reads only its slice of the source (`WHERE <column>` inside the window, or in the partition key(s); a backfill run covers its whole range),
2. builds the result in a scratch table with the same SQL as an unpartitioned run,
3. in one transaction creates the output table if it is missing, deletes that slice of the output and inserts the new rows, then drops the scratch table.

Other partitions' rows in the output are never touched, so re-running a partition is idempotent. The output must keep the partition column (for a summarize, put it in `group_by`); if the transform renames it, set `partition_output_column`. `partition_column_type` is `timestamp` (default) or `date`, and the window is compared in UTC. For `warehouse_join` only the left table is sliced; for `warehouse_union` every input table must carry the column. `multi` partitions are not supported. Unpartitioned runs behave exactly as before.
