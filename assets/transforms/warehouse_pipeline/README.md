# Warehouse Pipeline (YAML → single CTE-CTAS)

Multi-step warehouse-native pipeline compiled to ONE SQL statement using WITH-clauses (CTE chain) and run as a single CTAS. The whole sequence is planned together by the warehouse engine — predicate pushdown across steps, projection pruning, join reordering — and writes the final result to the output table.

Think of it as a YAML-defined view-building or stored-procedure-shape — analogous to `polars_pipeline` for in-Python work, but the optimizer is the warehouse's instead of polars's.

## When to use vs the per-step family

| Use this when | Use the per-step `warehouse_*` family when |
|---|---|
| ONE asset for the whole chain is the right lineage granularity | You want one Dagster asset per transform step |
| Intermediates don't need to be inspectable | You want intermediate tables you can query / debug |
| You want the warehouse optimizer to plan the whole chain together | The intermediates are reused by other assets |

## YAML

```yaml
type: dagster_community_components.WarehousePipelineComponent
attributes:
  asset_name: top_5_categories_by_revenue
  database_url: snowflake://...
  dialect: snowflake
  source:
    upstream_table: raw.orders
  operations:
    - op: filter
      predicate: "status = 'paid'"
    - op: group_by
      group_by: [category]
      aggregations:
        revenue:     {col: amount,   agg: sum}
        order_count: {col: order_id, agg: count}
    - op: top_n
      sort_by: revenue
      n: 5
      ascending: false
  output_table: analytics.top_5_categories_by_revenue
  mode: replace
  deps: [raw_orders_in_warehouse]
```

`agg` values: `sum / mean / avg / min / max / count / nunique / median / stddev / variance`.

## `join` how='semi' / 'anti' (ADF's Exists transform)

```yaml
- op: join
  right: {ref: gold_customers}   # or a table name string
  how: semi                       # or 'anti'
  on_columns: [customer_id]
```

Filters the left side to rows that do (`semi`) / don't (`anti`) have a matching right-side
row — same concept as ADF's Exists transform. Compiles to a portable correlated
`WHERE [NOT] EXISTS (SELECT 1 FROM <right> WHERE ...)` subquery, **not** `SEMI JOIN`/
`ANTI JOIN` keywords (not standard across this component's target dialects). Output is
left-side columns only (`_l.*` by default, or `select_cols` to project explicitly) —
semi/anti never pull right-side columns in.

## `pivot` (ADF's Pivot transform)

```yaml
- op: pivot
  index: [region]                 # row-identity column(s)
  pivot_column: quarter           # whose distinct values become new output columns
  value_columns: [amount]         # column(s) aggregated into each pivoted cell
  agg_func: sum
  pivot_values: [Q1, Q2, Q3, Q4]   # REQUIRED — see below
  fill_value: 0                   # optional — COALESCE()s a missing combination's cell
```

No SQL dialect this component targets has a universal, unbounded `PIVOT` keyword (some —
Snowflake, SQL Server — have one, but it's not portable across every dialect here), so
this compiles to the fully portable conditional-aggregation idiom instead:
`SUM(CASE WHEN quarter = 'Q1' THEN amount END) AS "Q1", ...`, one `CASE WHEN` per
`pivot_values` entry, repeated once per `value_columns` entry (output column names get a
`<value_col>_<pivot_value>` prefix when there's more than one value column, to avoid
collisions).

**`pivot_values` is required**, unlike `pandas_pipeline`/`polars_pipeline`'s own `pivot`
op (which discovers the pivot column's distinct values at runtime, in-process). This
component compiles to SQL *before* execution, so the exact value list must be known
upfront. If you don't know the values ahead of time, run a
`SELECT DISTINCT <pivot_column>` query first and feed the result in, or use the
`pandas_pipeline`/`polars_pipeline` sibling instead.

`pivot_values` entries are rendered as escaped SQL string literals (the same
`'` → `''` doubling convention the sibling `warehouse_*` components already use for their
own IN-list literals) — safe against a pivot value containing a quote or arbitrary text.

## `lookup` (ADF's Lookup transform)

```yaml
- op: lookup
  right: {ref: customers}          # or a table name string
  on_columns: [customer_id]        # or left_on / right_on
  match_sort_by: [updated_at]      # optional — see below
  match_sort_ascending: false      # optional, default false (most-recent-first)
  output_mode: columns             # 'columns' (default) or 'is_match'
  output_column: is_match           # only used when output_mode: is_match
  select_cols: ["_l.id", "_r.name"] # optional — defaults to "_l.*, _r.*"
```

Compiles to a `LEFT JOIN` — every left row is kept, with right-side columns `NULL` when
there's no match. When the right side can have more than one matching row per key,
`match_sort_by` picks exactly **one** deterministically, using the same
`ROW_NUMBER() OVER (PARTITION BY <key> ORDER BY <match_sort_by>)` window-function pattern
`top_n_per_group` already uses — the row ranked `1` wins. `output_mode: is_match` skips
pulling right-side columns in entirely and instead emits a single boolean `output_column`
via `WHERE EXISTS (...)`.

On dialects without a column-exclusion wildcard (same list as `drop`'s limitation above),
the internal row-ranking column (`_lookup_rn`) leaks into a `match_sort_by` lookup's
result when using `_r.*` — same known limitation as `top_n_per_group`'s own fallback. Use
explicit `select_cols` to avoid it on those dialects.

## `window_calculation` (ADF's Rank/Window transforms — `ntile` / `cume_dist` only)

```yaml
- op: window_calculation
  function: ntile          # or 'cume_dist'
  order_by: [score]
  group_by: [region]       # optional — partitions the window independently per group
  n: 4                     # required for function: ntile
  output_column: quartile
```

Scoped narrowly to `NTILE`/`CUME_DIST` — rank-equivalent concepts (ADF's Rank transform)
are already covered by this component's own `top_n`/`top_n_per_group` ops. Both compile
to near-literal standard SQL window functions
(`NTILE(n) OVER (PARTITION BY ... ORDER BY ...)` /
`CUME_DIST() OVER (PARTITION BY ... ORDER BY ...)`), supported identically across every
dialect this component targets (Postgres, DuckDB, Snowflake, BigQuery, SQL Server,
MySQL 8+, Oracle, Redshift, Databricks) — no portability workaround needed.

## `unpivot` (ADF's Unpivot transform)

```yaml
- op: unpivot
  id_columns: [customer_id]          # kept as-is
  value_columns: [q1, q2, q3, q4]    # melted into 2 output columns
  var_column: quarter                # optional, default 'variable'
  value_column: revenue              # optional, default 'value'
  drop_null_values: true             # optional, default false
```

No UNPIVOT keyword this component's target dialects agree on (several — Postgres,
Redshift, MySQL — have none at all), so this compiles to a fully portable `UNION ALL` of
one `SELECT` per `value_columns` entry instead:
`SELECT id_cols, 'q1' AS quarter, q1 AS revenue FROM ... UNION ALL SELECT id_cols, 'q2' AS
quarter, q2 AS revenue FROM ...`. `drop_null_values` adds a `WHERE <col> IS NOT NULL` to
each branch.

## `rank` (ADF's Rank transform — real SQL window functions)

```yaml
- op: rank
  order_by: [score]
  method: dense_rank      # rank | dense_rank | row_number | ntile | cume_dist
  group_by: [region]      # optional — partitions the window independently per group
  ntile_buckets: 4        # required for method: ntile
  output_column: score_rank
```

Unlike `pandas_pipeline`/`polars_pipeline`'s own `rank` op (pandas-style tie-breaking:
`average`/`min`/`max`/`first`/`dense`), this compiles to real SQL window functions —
`RANK()`/`DENSE_RANK()`/`ROW_NUMBER()`/`NTILE(n)`/`CUME_DIST() OVER (PARTITION BY ...
ORDER BY ...)` — standard across every dialect this component targets. Pandas-style
tie-breaking has no portable SQL window-function equivalent, so this op intentionally uses
SQL's own vocabulary instead of forcing a non-portable secondary-aggregation translation;
use the `pandas_pipeline`/`polars_pipeline` sibling for that tie-breaking style instead.
`ntile`/`cume_dist` overlap with `window_calculation` (kept there too, unchanged, to avoid
touching its already-tested behavior) — `rank` is the superset, adding `rank`/`dense_rank`/
`row_number`.

## Generated SQL

For the example above:

```sql
CREATE OR REPLACE TABLE analytics.top_5_categories_by_revenue AS
WITH "_step_1" AS (
    SELECT * FROM "raw"."orders" WHERE status = 'paid'
  ),
  "_step_2" AS (
    SELECT "category", SUM("amount") AS "revenue", COUNT("order_id") AS "order_count"
    FROM "_step_1" GROUP BY "category"
  ),
  "_step_3" AS (
    SELECT * FROM "_step_2" ORDER BY "revenue" DESC LIMIT 5
  )
SELECT * FROM "_step_3"
```

## Sink modes beyond CTAS: `append`, `truncate_insert`, and `merge`

- `append` is a plain, unconditional `INSERT INTO target SELECT ...` (bootstrapping the
  table first if it doesn't exist yet). No truncation, no incremental watermark filter, no
  dedup — every materialization adds the full `SELECT`'s rows on top of whatever is already
  there. Use `incremental` instead if you need a watermark-filtered insert, or `merge` for
  an upsert.
- `truncate_insert` keeps the existing table (schema, grants, indexes) and replaces its
  rows: `TRUNCATE TABLE` (`DELETE FROM` on SQLite, which has no `TRUNCATE` statement) then
  `INSERT`. Unlike `replace` (`CREATE OR REPLACE TABLE`, a real drop + recreate), nothing
  about the table's definition changes.
- `merge` is a true UPDATE-by-key upsert, not the insert-only anti-join dedup
  `incremental`'s own `incremental_merge_key` does. Set `merge_keys: [<column>, ...]`; the
  SQL depends on the destination dialect:
  - `duckdb`, `snowflake`, `bigquery`, `databricks`, `redshift`, `mssql`, `oracle` — a real
    `MERGE INTO ... USING ... ON ... WHEN MATCHED ... WHEN NOT MATCHED ...` (confirmed
    supported per-platform, not assumed -- DuckDB added it in 1.4, Redshift in a 2024
    update).
  - `postgresql`, `sqlite` — `INSERT ... SELECT ... ON CONFLICT (keys) DO UPDATE SET ...`.
  - `mysql` — `INSERT ... SELECT ... ON DUPLICATE KEY UPDATE ...`.

  `ON CONFLICT`/`ON DUPLICATE KEY UPDATE` both require a `UNIQUE` index on the merge keys
  to even parse, which a plain `CREATE TABLE ... AS SELECT` never declares -- this
  component creates one automatically right after the table's first bootstrap, so a second
  run's merge works without extra setup. The `MERGE INTO` dialects need no such index, and
  there's no portable `UPDATE SET *` wildcard to fall back on (confirmed: only Databricks
  supports it; Snowflake explicitly rejects it) -- the merge's column list comes from
  probing the compiled `SELECT`'s real output columns before building the final SQL.

```yaml
sinks:
  - from: s1
    table: mart.customers
    mode: merge
    merge_keys: [customer_id]
```

## Limitations

- `drop`, `top_n_per_group`, and `lookup`'s `match_sort_by` (which use a column-exclusion wildcard internally — `EXCLUDE()` on DuckDB/Snowflake, `EXCEPT()` on BigQuery/Databricks) require one of those four dialects. On others, use explicit `select`/`select_cols` projections instead.
- `rename` is intentionally not supported — use `select` with `AS` aliases instead (e.g. `columns: ['order_id AS id', 'total']`).
- `source:` currently supports only `upstream_table: <name>`. Inline SQL / CTE-from-SQL coming.
- `pivot` requires `pivot_values` upfront (SQL compiles before execution) — see the `pivot` section above for the runtime-discovery alternative.
