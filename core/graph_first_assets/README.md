# Graph-First Assets

Declare a list of real Dagster assets -- key, deps, group_name, kinds, owners, metadata, partitions, automation_condition, freshness -- entirely from `defs.yaml`, with a materialization body that's a genuine no-op.

## Why this exists

For a "graph-first" fidelity mode: when the story is lineage, checks, freshness, and automation, not real data, there's nothing for a real integration component to fetch or write. Rather than hand-writing a `@dg.asset` per node, declare the whole lineage graph from YAML -- one list entry per asset, each carrying whatever `AssetSpec` attributes it needs.

Materializing an entry logs a line and returns a `MaterializeResult`. Downstream components with a real `deps:` on one of these keys see real lineage, real checks can target them, and freshness/automation policies evaluate normally -- there's just nothing behind the curtain.

## Example YAML

```yaml
type: dagster_component_templates.GraphFirstAssetsComponent
attributes:
  assets:
    - key: warehouse/orders
      group_name: warehouse
      kinds: [snowflake]
      description: Raw orders feed (graph-first placeholder)
    - key: warehouse/customers
      group_name: warehouse
      deps: [warehouse/orders]
      metadata:
        owner: data-platform
      automation_condition: eager
      freshness_max_lag_minutes: 60
```

## Per-entry fields

| Key | Effect |
|---|---|
| `key` | Required. Dagster asset key (slash-separated for a multi-segment path). |
| `deps` | Lineage-only upstream asset keys -- no data is passed, no function input required. |
| `group_name` / `description` / `owners` / `tags` / `metadata` | Standard catalog metadata. |
| `kinds` | Asset kinds for the catalog, e.g. `[snowflake]`. |
| `code_version` / `skippable` | Passed straight through to `AssetSpec`. |
| `partition_type` / `partition_start` / `partition_values` / `dynamic_partition_name` | Same shape as the `ExternalXAsset` components: `'daily'\|'weekly'\|'monthly'\|'hourly'\|'static'\|'dynamic'`. |
| `automation_condition` | `'eager'`, `'on_missing'`, or `{kind: on_cron, cron_schedule: '...'}`. Omit to leave automation unset. |
| `freshness_max_lag_minutes` + `freshness_cron` | Builds a real `FreshnessPolicy` when set. |

## What this is not

This isn't a mocking framework for a real integration -- it's for the case where there's genuinely no external system to represent, just a lineage graph to sketch out. If you need a *fake* version of a real source (e.g. a demo without live credentials), pair the real integration component with its own demo-mode seam (`resource_key`, a stubbed client, etc.) instead -- most registry components already have one.

## Requirements

No additional packages required -- this component only creates `@dg.multi_asset`-wrapped no-ops.
