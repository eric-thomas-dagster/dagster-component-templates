# External Asset Catalog

Declares many external (non-executable) assets in the Dagster asset graph from one YAML table — for a neighbouring team's assets that live in a different Dagster code location, so this location's asset graph can show accurate lineage and ownership for them without owning or materializing them.

## What this does

Every other component in `external_assets/` declares exactly **one** external object per instance (one Snowflake table, one Kafka topic, ...). This one is the generic, many-rows-per-instance counterpart: a single component instance is a whole department's or integration's asset catalog. Adding it to your project:
- Makes each listed asset visible as a node in the **Dagster asset graph**
- Lets your own assets declare `deps` on them, drawing lineage edges
- Records owners, kind tags, and arbitrary metadata in the **Asset Catalog**

This component makes no external calls and holds no credentials. It only ever builds plain `AssetSpec` objects from the YAML you give it — it is a **lineage declaration only**.

## Examples

A single declared asset:

```yaml
type: dagster_community_components.ExternalAssetCatalogComponent
attributes:
  assets:
    - key: finance/gl_balances
      owners: ["team:finance-eng"]
      kinds: ["snowflake"]
      description: "General ledger balances, owned by Finance Engineering."
```

A whole department's catalog, with lineage between entries:

```yaml
type: dagster_community_components.ExternalAssetCatalogComponent
attributes:
  assets:
    - key: finance/gl_balances
      owners: ["team:finance-eng"]
      kinds: ["snowflake"]
      tags: {pii: "false"}
      description: "General ledger balances, owned by Finance Engineering."
    - key: marketing/campaign_performance
      deps: ["finance/gl_balances"]
      owners: ["team:marketing-data"]
      kinds: ["dbt", "snowflake"]
      group_name: marketing
    - key: ops/shipments
      owners: ["team:ops"]
      kinds: ["python"]
```

## When to use this vs. a single-system `external_*` component

Every other component in `external_assets/` (`external_snowflake_table`, `external_kafka_asset`, `external_sftp_path`, ...) declares one object and, for some, can also poll that one object for health/data-version via an observation sensor. Use one of those when you want observation for a single system.

Use `ExternalAssetCatalogComponent` when you just need the asset graph to know a set of other teams' assets exist, for ownership and lineage — there is no enumerate/observe behavior here, and none of the fields accept credentials.

## Validation notes

- `owners` is validated by Dagster itself: each entry must be an email address or a `team:`-prefixed name. An invalid owner raises `DagsterInvalidDefinitionError` at component-load time, naming the offending asset key.
- `kinds` on an `AssetSpec` also adds a matching `dagster/kind/<kind>` tag automatically (Dagster's own behavior, not something this component does extra).
- Declared assets are plain `AssetSpec` objects, not `AssetsDefinition`s with a compute function — there is nothing for Dagster to try to materialize.
