# External Flink Job

The Flink analog of [`external_kafka_asset`](../external_kafka_asset/README.md)'s `topics:` list: declare one or several jobs running on a **self-hosted** Flink cluster as external assets, visible for lineage without Dagster materializing them directly.

`jobs:` declares several jobs from one component instance, sharing `jobmanager_url` and (with `create_observation_sensor: true`) **one** polling sensor that polls every tracked job's status over a **single** `GET /jobs/overview` call per tick -- that endpoint already returns every job the cluster knows about in one response, so this is even cheaper than Kafka's per-topic offset lookups, which each need their own call.

## A real Flink gotcha this handles for you

Unlike a Kafka topic name, a Flink job's `jid` is **not stable** -- it's assigned fresh every time the job is (re)submitted (see [`flink_job_run_asset`](../../assets/infrastructure/flink_job_run_asset/README.md)). What *is* stable across resubmissions is the job's **configured name** (set by the job code itself, e.g. `StreamExecutionEnvironment.execute("my-job")`, or a Flink SQL job's default name) -- so this component tracks jobs by `job_name`, matching whatever `GET /jobs/overview` reports, never by `jid`. Make sure your job sets a stable, predictable name; otherwise there's nothing consistent to match on across restarts.

## Example YAML

```yaml
type: dagster_community_components.ExternalFlinkJobComponent
attributes:
  jobmanager_url: http://flink-jobmanager:8081
  jobs:
    - key: streaming/clickstream_enrichment
      job_name: clickstream-enrichment
    - key: streaming/clickstream_aggregation
      job_name: clickstream-aggregation
  create_observation_sensor: true
  sensor_name: flink_jobs_observation_sensor
  check_interval_seconds: 60
  group_name: streaming
```

## Single-job mode

```yaml
type: dagster_community_components.ExternalFlinkJobComponent
attributes:
  jobmanager_url: http://flink-jobmanager:8081
  asset_key: streaming/clickstream_enrichment
  job_name: clickstream-enrichment
  create_observation_sensor: true
```

## What the sensor emits

Each tick: `state`, `jid` (the job's *current* run's id -- expect this to change across restarts even though the asset key doesn't), `start_time`, `duration_ms`. The `dagster/data_version` tag is derived from `(state, start-time)`, so a job cycling RUNNING -> FINISHED -> RUNNING again (a restart) produces a new data version each time, same as a Kafka topic getting new messages.

A tracked job not found in the current `/jobs/overview` response (not yet submitted, or expired from Flink's job store retention) is skipped with a warning log, not an error -- the rest of the tracked jobs in the same tick still get observed.
