# External Kafka Asset

Declares a Kafka topic as an external asset in the Dagster asset graph — making it visible for lineage without materializing it from Dagster.

## What this does

External assets represent data sources managed outside of Dagster. Adding one to your project:
- Makes the Kafka topic visible as a node in the **Dagster asset graph**
- Enables downstream assets to declare `deps` on it, drawing lineage edges
- Records connection metadata in the **Asset Catalog**

This component does not read from or write to Kafka. It is a **lineage declaration only**.

## Example YAML
```yaml
type: dagster_component_templates.ExternalKafkaAsset
attributes:
  asset_key: my_service/asset
  bootstrap_servers: my_bootstrap_servers
  topic: my_topic
  # group_name: None  # optional
  # description: None  # optional
```

## Several topics from one component instance

Use `topics:` instead of the top-level `asset_key`/`topic` fields to declare several Kafka topics
from one `ExternalKafkaAsset` instance, instead of one YAML block per topic:

```yaml
type: dagster_component_templates.ExternalKafkaAsset
attributes:
  bootstrap_servers: BOOTSTRAP_SERVERS
  group_name: kafka_sources
  topics:
    - key: streaming/orders
      topic: orders
    - key: streaming/payments
      topic: payments
      owners: ["team:payments"]
    - key: streaming/shipments
      topic: shipments
      deps: ["streaming/orders"]
  create_observation_sensor: true
  sensor_name: kafka_sources_observer  # required with topics: -- no single topic name to default from
```

All topics share this instance's `bootstrap_servers` and partitioning config. With
`create_observation_sensor: true`, they also share **one** sensor that polls every topic's
offsets over a **single** Kafka connection per tick (or a single resource-backed `.observe()`
loop — see below), instead of one sensor and one connection per topic. A topic whose offset query
fails doesn't block the rest — it's skipped for that tick and reported again next time.

`asset_key`/`topic` and `topics:` are mutually exclusive on one component instance; use several
component instances if different groups of topics need different partitioning.

## Observation sensor

Set `create_observation_sensor: true` to also get the polling sensor that keeps this asset's
health/data-version current — one component, one YAML, no manual `asset_key` wiring:

```yaml
type: dagster_component_templates.ExternalKafkaAsset
attributes:
  asset_key: external/kafka
  bootstrap_servers: BOOTSTRAP_SERVERS
  topic: TOPIC
  create_observation_sensor: true
  check_interval_seconds: 300
```

If the sensor needs to observe an `asset_key` declared by a *different* component (or you want the
asset and sensor on independent lifecycles), pair this component with the standalone
`KafkaObservationSensorComponent` component instead:

```yaml
# 1. Declare the external asset (lineage node)
type: dagster_component_templates.ExternalKafkaAsset
attributes:
  asset_key: external/kafka
  bootstrap_servers: BOOTSTRAP_SERVERS
  topic: TOPIC

---

# 2. Observe it on a schedule
type: dagster_component_templates.KafkaObservationSensorComponent
attributes:
  sensor_name: kafka_asset_observer
  asset_key: external/kafka
  bootstrap_servers: BOOTSTRAP_SERVERS
  topic: TOPIC
```

## Requirements

No additional packages required — this component only creates a `dg.AssetSpec`.
