# External Sql Asset

Declares a Sql resource as an external asset in the Dagster asset graph — making it visible for lineage without materializing it from Dagster.

## What this does

External assets represent data sources managed outside of Dagster. Adding one to your project:
- Makes the Sql resource visible as a node in the **Dagster asset graph**
- Enables downstream assets to declare `deps` on it, drawing lineage edges
- Records connection metadata in the **Asset Catalog**

This component does not read from or write to Sql. It is a **lineage declaration only**.

## Example YAML
```yaml
type: dagster_component_templates.ExternalSqlAsset
attributes:
  asset_key: my_service/asset
  table_name: my_table_name
  connection_string_env_var: CONNECTION_STRING_ENV_VAR
  # group_name: None  # optional
  # description: None  # optional
```

## Observation sensor

Set `create_observation_sensor: true` to also get the polling sensor that keeps this asset's
health/data-version current — one component, one YAML, no manual `asset_key` wiring:

```yaml
type: dagster_component_templates.ExternalSqlAsset
attributes:
  asset_key: external/sql
  table_name: my_table
  connection_string_env_var: CONNECTION_STRING_ENV_VAR
  create_observation_sensor: true
  check_interval_seconds: 300
  watermark_column: updated_at
```

If the sensor needs to observe an `asset_key` declared by a *different* component (or you want the
asset and sensor on independent lifecycles), pair this component with the standalone
`sql_observation_sensor` component instead:

```yaml
# 1. Declare the external asset (lineage node)
type: dagster_component_templates.ExternalSqlAsset
attributes:
  asset_key: external/sql
  table_name: my_table
  connection_string_env_var: CONNECTION_STRING_ENV_VAR

---

# 2. Observe it on a schedule
type: dagster_component_templates.SqlObservationSensorComponent
attributes:
  sensor_name: sql_asset_observer
  asset_key: external/sql
  table_name: my_table
  connection_string_env_var: CONNECTION_STRING_ENV_VAR
  watermark_column: updated_at
```

## Several tables from one component instance

Use `tables:` instead of the top-level `asset_key`/`table_name` fields to declare several tables
from one `ExternalSqlAsset` instance, instead of one YAML block per table:

```yaml
type: dagster_component_templates.ExternalSqlAsset
attributes:
  connection_string_env_var: CONNECTION_STRING_ENV_VAR
  group_name: warehouse_sources
  tables:
    - key: warehouse/orders
      table_name: orders
    - key: warehouse/customers
      table_name: customers
      watermark_column: updated_at
      owners: ["team:data"]
  create_observation_sensor: true
  sensor_name: warehouse_sources_observer  # required with tables: -- no single table name to default from
```

All tables share this instance's `connection_string_env_var`. With `create_observation_sensor:
true`, they also share **one** sensor that queries every table's row count/watermark over a
**single** engine connection per tick, instead of one sensor and one connection per table. A table
whose query fails doesn't block the rest — it's skipped for that tick and reported again next time.

`asset_key`/`table_name` and `tables:` are mutually exclusive on one component instance.

## Requirements

No additional packages required — this component only creates a `dg.AssetSpec`.
