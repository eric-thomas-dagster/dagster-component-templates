# external_temporal_workflow

## Purpose

Declare-only `AssetSpec` for a [Temporal](https://temporal.io/) Workflow (or a Temporal Schedule that fires one). Temporal owns the execution + retry semantics; Dagster's role is catalog presence + lineage — the paired `temporal_workflow_sensor` observes state transitions and emits `AssetObservation`s.

Mirror of `external_argo_workflow` / `external_precisely_job`: no execution, `dagster.observability_type=external` metadata is set, downstream assets can `deps: [...]` against the workflow.

## Example YAML

```yaml
type: dagster_community_components.ExternalTemporalWorkflowAsset
attributes:
  asset_key: temporal/etl/nightly_aggregation
  workflow_type: NightlyAggregationWorkflow
  namespace: default
  task_queue: etl-tq
  temporal_ui_url: http://localhost:8233
  group_name: temporal
```

## Pairs with

- **`temporal_workflow_sensor`** — Case A (Temporal owns the schedule): sensor watches workflow state on the same `asset_key` and emits `AssetObservation` per state transition (`RUNNING` / `COMPLETED` / `FAILED` / …).
- **`temporal_workflow_trigger`** — Case B (Dagster fires the workflow): use instead of this declare-only spec when Dagster owns the trigger. Don't mix both patterns against the same `asset_key`.

## When to use which field

- `workflow_type` — the class name registered on the worker (e.g. `NightlyAggregationWorkflow`). Set this when the same workflow *type* runs many times with different `workflow_id`s (partitioned / templated).
- `workflow_id` — a specific workflow instance. Set only when the asset represents a fixed long-lived workflow (rare — most cases are `workflow_type` + templated ids).
- `schedule_id` — the Temporal Schedule that owns the firing cadence. Set when the workflow is on a Temporal Schedule; the sensor uses this to correlate schedule fires to workflow runs.

All three surface as catalog metadata regardless of which is set.
