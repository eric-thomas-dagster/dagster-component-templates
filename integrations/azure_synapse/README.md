# Azure Synapse Analytics Component

Import Azure Synapse Analytics entities as Dagster assets for comprehensive data warehouse and analytics orchestration.

## Features

- **Pipelines**: Trigger Synapse pipeline runs (unified with ADF)
- **Spark Jobs**: Submit Spark job definitions
- **Notebooks**: Execute Synapse notebooks
- **Observation Sensor**: Track pipeline runs and completion

## `notebooks:` / `spark_jobs:` -- declared items, no live workspace needed

Set `notebooks: [{name, parameters?}, ...]` and/or `spark_jobs: [{name}, ...]` to use an explicit list
instead of discovering notebooks/Spark job definitions from the live Synapse workspace. When set, no
Azure client (nor credential) is constructed for that category at all -- useful for a
converter-generated static definition (e.g. from an ADF/Synapse migration tool) where the deploy
pipeline already knows exactly which items exist. `import_pipelines`/`import_spark_jobs`/`import_notebooks`
still gate whether each category is imported at all; a declared list only changes HOW that category's
items are found. Set `import_pipelines: false` too if you want the project to load with zero live
service calls (pipelines have no declared-list bypass -- discovering them always needs a client).

`SynapseSparkJobDeclaration` has no `args`/`conf`/driver-or-executor-sizing override fields: confirmed
against the real `azure-synapse-artifacts` SDK/REST surface that `begin_execute_spark_job_definition`
takes only the job definition's name -- there's no per-execution parameter override at the API level at
all. A Spark job definition's args/conf/sizing are fixed when the job definition itself is authored in
Synapse Studio.

## `dry_run`

Set `dry_run: true` to log what would be triggered (pipeline run / Spark batch / notebook run, with its
resolved parameters) and skip the real Azure call entirely -- same convention as this registry's SQL,
email, and SAP job-trigger components' own `dry_run` flag.

## Notebook and Spark job execution now check the FINAL run state

Both used to report only the SUBMISSION response's initial (non-terminal) state, and the notebook asset
caught any exception from execution (including real failures) and reported a fake `status: "Skipped"`
success. Both now poll to a real terminal state and raise if it isn't a successful one:

- **Notebooks**: `run_notebook.begin_create_run(...)` submits (its own `.result()` only confirms the
  create-run request was accepted, not completion), then a separate `run_notebook.get_status(run_id)`
  poll checks `result.run_status` until it reaches `success`/`error`/`dead`/`killed`.
- **Spark jobs**: `begin_execute_spark_job_definition(...)` submits, then a separate
  `azure.synapse.spark.SparkClient.spark_batch.get_spark_batch_job(batch_id)` poll checks `state` until
  terminal -- a different package from `azure-synapse-artifacts` (which has no poll-by-batch-id method
  at all), so `azure-synapse-spark` is only required when `import_spark_jobs: true`. `spark_pool_name`
  comes from the submission response; set `default_spark_pool_name` as a fallback if your SDK version's
  response doesn't carry one.

## Configuration

### Basic Example
```yaml
type: dagster_community_components.AzureSynapseComponent
attributes:
  subscription_id: "12345678-1234-1234-1234-123456789012"
  resource_group_name: my-resource-group
  workspace_name: my-synapse-workspace
  tenant_id: "{{ env('AZURE_TENANT_ID') }}"
  client_id: "{{ env('AZURE_CLIENT_ID') }}"
  client_secret: "{{ env('AZURE_CLIENT_SECRET') }}"
  import_pipelines: true
```

### Advanced Example
```yaml
type: dagster_community_components.AzureSynapseComponent
attributes:
  subscription_id: "12345678-1234-1234-1234-123456789012"
  resource_group_name: my-resource-group
  workspace_name: my-synapse-workspace
  tenant_id: "{{ env('AZURE_TENANT_ID') }}"
  client_id: "{{ env('AZURE_CLIENT_ID') }}"
  client_secret: "{{ env('AZURE_CLIENT_SECRET') }}"

  # Import entity types
  import_pipelines: true
  import_spark_jobs: true
  import_notebooks: true

  # Filtering
  filter_by_name_pattern: ^prod_.*
  exclude_name_pattern: test|dev
  filter_by_tags: env,team

  # Sensor configuration
  generate_sensor: true
  poll_interval_seconds: 60

  group_name: synapse_workspace
  description: Synapse Analytics pipeline and Spark orchestration
```

## Entity Types

### Pipelines (Materializable)
- Trigger Synapse pipeline runs (same engine as Azure Data Factory)
- Wait for pipeline completion
- Support for data movement, transformation, and orchestration activities
- Observation sensor tracks automatic runs

### Spark Jobs (Materializable)
- Submit Spark job definitions
- Support for PySpark, Scala, .NET
- Execute batch processing and ML workloads
- Track job submission status

### Notebooks (Materializable)
- Execute Synapse notebooks
- Support for %%pyspark, %%spark, %%csharp, %%sql magic commands
- Typically executed via pipeline notebook activities
- Retrieve notebook metadata

## Authentication

Three authentication options:

1. **DefaultAzureCredential** (recommended): Omit tenant_id, client_id, client_secret
2. **Service Principal**: Provide all three credential parameters
3. **Environment Variables**: Set AZURE_TENANT_ID, AZURE_CLIENT_ID, AZURE_CLIENT_SECRET

## Asset Dependencies & Lineage

Because this component enumerates many assets from one config, dependencies are declared per-asset via `asset_overrides` (keyed by the emitted asset's name). Matches the pattern used by the official [`DatabricksWorkspaceComponent`](https://docs.dagster.io/integrations/libraries/databricks/databricks-workspace-component#managing-dependencies).

```yaml
attributes:
  subscription_id: "..."
  workspace_name: my-synapse
  asset_overrides:
    synapse_pipeline_orders_load:
      depends_on:
        - raw_orders              # simple asset key
        - raw/schema/orders       # slash-delimited → hierarchical AssetKey
    synapse_notebook_scoring:
      depends_on:
        - synapse_pipeline_orders_load
```

The declared deps draw lineage edges in the Dagster asset graph — no data is loaded at runtime. Use them to express that a specific imported Synapse pipeline, Spark job, or notebook depends on upstream tables or assets produced elsewhere in your project. Assets without a matching entry in `asset_overrides` are emitted with no upstream deps (the default).

Dependencies can also be wired externally via `map_resolved_asset_specs()` in `definitions.py` — the same approach used by [Dagster Designer](https://github.com/eric-thomas-dagster/dagster_designer).
