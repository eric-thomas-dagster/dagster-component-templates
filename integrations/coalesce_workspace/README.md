# Coalesce Workspace

Connects to a Coalesce environment, introspects its nodes (SQL transforms) at component-load time, and creates one Dagster asset per node, with upstream dependencies that mirror the Coalesce DAG. Materializing an asset triggers the Coalesce Scheduler API to run the corresponding node and polls until the run reaches a terminal state.

Coalesce's Node-level and column-level test results are surfaced as a real Dagster asset check (`coalesce_node_tests`) per node, not silently dropped — see "Test results as asset checks" below.

Same role and shape as this repo's other `*_workspace` components (`snowflake_workspace`, `mlflow_workspace`, `hvr_hub_workspace`, ...): owns the connection config, discovers objects from the vendor, and builds one asset per discovered object.

## Test results as asset checks

Coalesce's run-status polling (`/scheduler/runStatus`) only reports whether the SQL transform itself succeeded (`completed`/`failed`/`canceled`). Test results — both **Node-level tests** (custom SQL, optionally configured to halt the pipeline on failure) and **Column-level tests** (null/uniqueness checks that always run after the transform) — are a separate signal: a node can finish with `runStatus: completed` while still carrying `hasTestFailures: true` from `GET /api/v1/runs/{runID}/results` (Coalesce's own UI shows this as a "yellow" run, distinct from green/success and red/failure).

This component fetches `/results` for each run and emits a `coalesce_node_tests` `AssetCheckResult` per node (`passed = not hasTestFailures`), alongside the existing `MaterializeResult`:

- `emit_test_checks` (default `true`) — set `false` to skip the `/results` call and check emission entirely.
- `fail_run_on_test_failure` (default `false`) — Coalesce's own per-test "halt pipeline execution on failure" setting (configured in Coalesce, per test) is already the authoritative decision for whether a test failure should stop the pipeline; if a test is configured to halt, the run already comes back `failed`/`canceled` and raises on its own. Set this `true` only if you want Dagster to additionally hard-fail the run whenever *any* test failed, regardless of that per-test Coalesce setting.

## Optional Catalog (Castor) metadata enrichment

Coalesce's Catalog product (`api.castordoc.com`, its own `Token` auth — a separately-licensed product from the Scheduler/v1 REST API used for runs) can enrich each node's asset with:

- `description` — from Catalog's table-level `descriptionMarkdown`
- `owners` — from Catalog's `ownerEntities`
- tags — surfaced as `coalesce/catalog_tags` metadata (Catalog's free-form labels don't map cleanly onto Dagster's structured `tags`, so they're kept as metadata instead)
- `coalesce/column_lineage` metadata — column → `[upstream "table.column"]` map, from Catalog's field-lineage graph

Set `include_catalog_metadata: true` and `catalog_api_token_env_var` to enable. It's off by default and fails soft (logs a warning, leaves the asset spec as-is) if Catalog isn't provisioned for your account or a call errors — this is enrichment, never load-bearing. The lookup runs once, during state refresh (`write_state_to_path`), not on every code-server reload, so the component's "zero network calls on reload" property still holds with this enabled.
