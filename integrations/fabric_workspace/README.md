# Microsoft Fabric Workspace

Imports a Microsoft Fabric workspace's items as Dagster external assets.
Mirrors `azure_synapse` / `azure_data_factory` in shape but uses the
**Fabric REST API** (not Synapse SDKs) since Fabric is a separate product
family with a different API surface.

## What gets imported

| Fabric Item Type | As Dagster | Materialize?  |
|---|---|---|
| Lakehouse | external/observable asset | No (lineage-only) |
| Warehouse | external/observable asset | No (lineage-only) |
| Notebook | trigger asset | Yes — runs the notebook |
| DataPipeline | trigger asset | Yes — runs the pipeline |
| Dataflow | trigger asset | Yes — refreshes the dataflow |
| SemanticModel | external asset | No |
| Report | external asset | No |

## Filtering

```yaml
attributes:
  exclude_name_pattern: "_deprecated$"
  include_names: ["nightly_ingest", "weekly_rollup"]
  filter_by_name_pattern: "^prod_"
  filter_by_description_pattern: "owner:data-eng"
```

`exclude_name_pattern` always vetoes an item, even one explicitly listed in
`include_names`. Otherwise an item is included if it matches **any**
configured inclusion criterion — `include_names` (exact, case-insensitive
allow-list) OR `filter_by_name_pattern` OR `filter_by_description_pattern`
(matched against the item's own `description` field, case-insensitive) —
union/OR semantics, not AND. This is the same `include_names`/
`filter_by_comment_pattern` precedence `snowflake_workspace` already uses,
replicated here for parity rather than reinvented. With none of the three
set, every item passes (unchanged from before). With only
`filter_by_name_pattern` set, an item that doesn't match it is excluded —
the same hard-requirement behavior this field has always had.

All patterns are regexes matched with `re.search` (unanchored — `fuel`
also matches `fuel_old`; anchor with `^…$` for an exact segment match), one
shared pattern across every imported item type (Lakehouse/Warehouse/
Notebook/DataPipeline/Dataflow/SemanticModel/Report) — not configurable
per type.

Filtering runs at **discovery time** (when the cached workspace state is
written), not at Dagster load time — changing any of these fields requires
`dg utils refresh-defs-state` (or waiting for the component's own refresh
cadence) to take effect, the same as any other change to `import_*`/
`filter_by_name_pattern`.

## Multiple instances over one workspace

Two `FabricWorkspaceComponent` instances pointed at the *same* `workspace_id` but different `import_*`/filter settings (e.g. one importing only notebooks matching `part_a`, another only pipelines) hash to the same cached discovery-state key by default — they'd silently share one state file. Set a distinct `key:` per instance to split them:

```yaml
# instance A
attributes:
  workspace: { workspace_id: "{{ env.FABRIC_WORKSPACE_ID }}" }
  key: part_a
  filter_by_name_pattern: "^part_a_"
---
# instance B
attributes:
  workspace: { workspace_id: "{{ env.FABRIC_WORKSPACE_ID }}" }
  key: part_b
  filter_by_name_pattern: "^part_b_"
```

## Auth

Standard `DefaultAzureCredential` chain. Service principal needs to be
added as a **Contributor** on the Fabric workspace. To grant via portal:
Workspace → Manage access → Add SP UPN → Member or Admin.

## API

The component calls:
- `GET /v1/workspaces/{workspace_id}/items` — list items
- `POST /v1/workspaces/{workspace_id}/items/{item_id}/jobs/instances?jobType={Pipeline|RunNotebook|Refresh}` — trigger a run
- `GET <Location>` — poll job status
- `POST <Location>/cancel` — cancel a timed-out or interrupted run
- `GET /v1/workspaces/{workspace_id}/items/{item_id}/jobs/instances` — list job-run history (polling sensor only; see below)

Reference: https://learn.microsoft.com/rest/api/fabric/

## Failure handling

A Failed, Cancelled, Deduped, or timed-out Fabric run raises `dg.Failure` (or
`dg.RetryRequested`, when the failure is retriable — see below) — it no
longer returns the job's state dict as if it were a successful
materialization. `Deduped` (another instance of the same job type was
already running; Fabric skipped this one) fails immediately with a clear
message instead of polling until the timeout. A timeout requests
cancellation of the orphaned Fabric job; a job that already reached its own
terminal state doesn't get a pointless cancel call.

Every `dg.Failure` raised by this component — auth (token acquisition),
trigger-request, and polled-job-status — consistently carries a
`failure_class` metadata value and a matching `[class]` prefix on the
description: `auth` (an insufficient-privileges/authorization errorCode, OR
a 401/403 on the initial trigger request even if Fabric's own errorCode
doesn't match a known keyword), `collision` (`Deduped`), or `other`
(everything else, including a notebook's own code/data bugs). A deliberately
NOT attempted fifth bucket: distinguishing "the Fabric platform itself broke"
from "the notebook's own code or data was bad" would need a verified,
exhaustive Fabric error-code catalog that doesn't exist publicly — rather
than guess, both stay in `other`. The one exception is `exit_value_file` +
`data_failure_exit_values` below, which classifies as `data` with real
confidence because it's an explicit, notebook-signaled condition, not an
inferred one. (The HTTP-status-based `auth` check only applies to the
trigger-request path — the polled job-status path has no HTTP status of its
own, only Fabric's job-level status string.)

Retries: `max_retries` (default `1`) and `retry_backoff_seconds` (default
`30`, doubling per attempt via the run's `retry_number` — i.e. real
exponential backoff in an actual Dagster run) are both configurable per
instance. A failure is treated as retriable from Fabric's own
`failureReason.isRetriable` flag when present; when Fabric omits that flag
(observed for some capacity-paused / throttled failures), a keyword fallback
checks the error code/message for capacity, throttle, rate-limit, and
similar terms — this fallback never overrides an explicit
`isRetriable: false`.

## Parameters

```yaml
type: dagster_community_components.FabricWorkspaceComponent
attributes:
  workspace:
    workspace_id: "{{ env.FABRIC_WORKSPACE_ID }}"
  import_pipelines: true
  default_parameters:
    load_date: "{{ env.LOAD_DATE }}"
  item_parameters:
    my_special_notebook:
      load_date: "2024-01-01"
      backfill: true
```

`default_parameters` applies to every triggered Notebook/DataPipeline/Dataflow;
`item_parameters` (keyed by Fabric display name) merges over it for one
specific item. Both accept a plain `{name: value}` dict.

**The request shape sent to Fabric differs by item type** — this corrects an
earlier claim in this README that it's the same shape everywhere:

- **DataPipeline / Dataflow**: the generic top-level `parameters` list,
  Fabric's documented `Parameter[]` shape (`{name, value, type}`, type
  inferred from the Python value: bool → Boolean, int → Integer,
  float → Number, else → Text).
- **Notebook**: nested under `executionData.parameters` instead, as a dict
  keyed by name (`{"<name>": {"value": ..., "type": ...}}`, with its own
  lowercase type vocabulary: bool → `bool`, int → `int`, float → `float`,
  else → `string`) — a Notebook's `executionData` is its own
  item-type-specific payload, not the generic `Parameter[]` list. Confirmed
  via Microsoft's own `apache-airflow-providers-microsoft-fabric`
  (`MSFabricNotebookJobParameters`) and the official `fab` CLI's job-run
  docs, both of which build exactly this shape for Notebook and only this
  shape — neither ever uses the top-level list for a Notebook trigger.

Not every item/job type accepts parameters at all; Fabric's own API returns
`errorCode: FeatureNotAvailable` for ones that don't, surfaced as a clear
Failure rather than a generic HTTP error.

## Execution data (escape hatch for unsupported job types)

```yaml
attributes:
  execution_data:
    tableName: Table1
  item_execution_data:
    my_special_pipeline:
      optimizeSettings:
        vOrder: true
```

`execution_data`/`item_execution_data` send Fabric's `executionData` field
exactly as given — its own term for "fixed static data, defined by the
specific item job type" (confirmed via the Job Scheduler REST reference's
own example: `executionData` and the top-level `parameters` list can be
sent **together** in the same request). Unlike `default_parameters`/
`item_parameters`, nothing here is converted to any particular shape. For a
Notebook, it's merged alongside the auto-built `executionData.parameters`
(so you can add e.g. `configuration` — environment/default-lakehouse/Spark
pool settings — without losing the parameters this component already
builds from `default_parameters`/`item_parameters`/`load_date_parameter`).

This is the escape hatch for job types whose required config isn't exposed
as a dedicated field yet. Confirmed and documented, but **not yet natively
supported** (no discovery/import, no dedicated fields, and for Spark Job
Definition a different URL path this component doesn't build):

- **Spark Job Definition** (`jobType: sparkjob`, confirmed via its own REST
  reference) needs `executableFile`/`mainClass`/`commandLineArguments`/
  `additionalLibraryUris`/`defaultLakehouseId`/`environmentId` in
  `executionData` — but it's triggered via a **different URL path**
  (`/sparkJobDefinitions/{id}/jobs/sparkjob/instances`, not the generic
  `/items/{id}/jobs/{jobType}/instances` this component uses for every
  other item type), so `execution_data` alone can't make it work yet.
- **DBT Job** and **Copy Job**'s exact `jobType` strings have NOT been
  confirmed against a primary Fabric doc page (only an unverified
  third-party source) — not implemented until verified.
- **Materialized Lake Views refresh** is a Lakehouse sub-operation, not a
  separate item type — not yet wired up either.

An item type this component doesn't recognize (anything outside
`DataPipeline`/`Notebook`/`Dataflow`) now raises a clear `dg.Failure`
instead of silently being triggered as if it were a Data Pipeline, which is
what used to happen.

## Success metadata

A successful trigger returns a real `MaterializeResult` (not the raw Fabric
state dict) with `fabric_item_id`, `fabric_item_type`,
`fabric_job_instance_id`, `fabric_job_status`, and `fabric_job_instance_url`
— enough to jump straight from the Dagster UI to the matching run in the
Fabric portal.

## Load date

```yaml
type: dagster_community_components.FabricWorkspaceComponent
attributes:
  workspace:
    workspace_id: "{{ env.FABRIC_WORKSPACE_ID }}"
  import_pipelines: true
  load_date_parameter: load_date
  load_date_timezone: America/New_York
```

When set, `load_date_parameter` auto-injects today's date (in
`load_date_timezone`, ISO `YYYY-MM-DD`) as that parameter name on every
triggered run, merged with `default_parameters`/`item_parameters` (those take
precedence if they also set the same key). For a one-off backfill, override
the computed date for a specific run with the `fabric/load_date_override` run
tag (e.g. `fabric/load_date_override: "2024-01-01"`) instead of editing the
component config. The resolved value is attached as `fabric/load_date`
metadata on the materialization.

## Concurrency pool and audited skip

Set `pool` to put every triggered Notebook/DataPipeline/Dataflow asset in a
Dagster [concurrency pool](https://docs.dagster.io/guides/operate/managing-concurrency)
— e.g. to cap concurrent runs against a shared, cost-sensitive Fabric
capacity. Use `item_pools` (keyed by Fabric display name, same convention as
`item_parameters`) to give one specific item its own pool instead of sharing
the component-wide one:

```yaml
attributes:
  pool: fabric_jobs
  item_pools:
    expensive_notebook: fabric_jobs_heavy
```

Subclasses that need deeper per-asset customization this field set doesn't
cover can override `_runnable_asset_kwargs(...)` instead of copying all of
`_build_runnable_asset`.

Set the `fabric/skip` run tag to `"true"` to audit-skip the actual Fabric
trigger for a run — useful for a dry-run or a manually-excluded item without
changing component config. The asset still materializes (with
`fabric_skipped: true` metadata) so downstream assets aren't blocked, but no
Fabric API call is made.

## Partitions

```yaml
type: dagster_community_components.FabricWorkspaceComponent
attributes:
  workspace:
    workspace_id: "{{ env.FABRIC_WORKSPACE_ID }}"
  import_pipelines: true
  partition_type: daily
  partition_start: "2024-01-01"
  partition_parameter_name: run_date
```

`partition_type` (`daily` / `weekly` / `monthly` / `hourly` / `static` /
`dynamic` / `cron`) applies the same canonical, widely-shared partitioning
shape used across this repo's other partitioned components to every
runnable asset built by this component instance — including
`partition_cron_schedule`/`partition_cron_fmt` for a custom cadence (e.g.
`'0 0 * * 1-5'` for weekdays only) and `partition_dimensions` for multi-axis
partitioning instead of the flat fields. This enables native multi-date
backfill in the Dagster UI/CLI, not just a single on-demand trigger per item.

When `partition_parameter_name` is also set, the run's own `partition_key` is
injected as that Fabric parameter name on every triggered job (merged with
`default_parameters`/`item_parameters` — those take precedence if they also
set the same key), the same partition-key-to-pipeline-parameter convention
`azure_data_factory` uses, and attached as `fabric/partition_key` metadata.
Without `partition_parameter_name`, the asset is still a real partitioned
asset (for scheduling/backfill purposes), but the Fabric job itself never
learns which partition triggered it.

**If `partition_parameter_name` names the SAME Fabric parameter as
`load_date_parameter`, the partition key wins over "today"** — a backfill of
partition `2026-01-03` sends `load_date=2026-01-03`, not today's date. (The
`fabric/load_date_override` run tag still wins over both.) Without that name
collision, `load_date_parameter` computes "today" exactly as described in
[Load date](#load-date) above, independent of partitioning.

As with any Dagster partitioned asset, an unpartitioned downstream asset
waits on **every** partition before it's considered up to date — standard
Dagster semantics, not specific to this component.

**`partition_end_offset`/`partition_timezone`** thread through to the
underlying Daily/Weekly/Monthly/Hourly/cron partitions definition (real,
documented kwargs on all of them). By default (`end_offset: 0`), a
time-based partition set only ever holds **completed** windows — a daily
set never includes today until tomorrow. For a notebook meant to run
intraday (e.g. every 15 minutes under an eager `AutomationCondition`) and
process *today's* data, set `partition_end_offset: 1` so today's partition
exists and is eligible to materialize; otherwise the asset would keep
re-running yesterday's partition with yesterday's data:

```yaml
attributes:
  partition_type: daily
  partition_start: "2024-01-01"
  partition_end_offset: 1
  partition_timezone: America/New_York
  partition_parameter_name: load_date
```

### Per-item partitioning

Partitioning is set once per component instance by default, which means
every runnable asset it builds shares the same `partitions_def` — not what
you want when only one notebook needs daily backfills and the rest of the
workspace (a static-per-workspace collector, an unpartitioned semantic
model) shouldn't be forced to inherit it, or wait on every partition as a
downstream dependency. Use `item_partitions` (keyed by Fabric display name,
same convention as `item_parameters`/`item_pools`) to override partitioning
for one specific item:

```yaml
attributes:
  # unpartitioned by default
  item_partitions:
    live_notebook:
      partition_type: daily
      partition_start: "2024-01-01"
      partition_parameter_name: load_date
```

An `item_partitions` entry **fully replaces** the component-wide
`partition_type`/`partition_start`/`partition_values`/
`dynamic_partition_name`/`partition_dimensions`/`partition_cron_schedule`/
`partition_cron_fmt`/`partition_end_offset`/`partition_timezone`/
`partition_parameter_name` fields for that one item — including an empty
dict (`{}`) to explicitly un-partition an item even when the component-wide
`partition_type` IS set. Items with no entry fall back to the component-wide
fields. An item entry that doesn't set its own `partition_end_offset`/
`partition_timezone` gets Dagster's own defaults (`0`/`UTC`), not the
component-wide custom values — the replacement is complete, not a merge.

## Observation sensor

Set `polling_sensor: true` to also get a sensor that detects Notebook /
DataPipeline / Dataflow job completions Dagster didn't itself trigger —
another scheduler, or someone running it manually in the Fabric UI — and
emits `AssetObservation` for them, the same `polling_sensor` convention as
`FivetranAccountComponent` / `SnowflakeWorkspaceComponent`:

```yaml
type: dagster_community_components.FabricWorkspaceComponent
attributes:
  workspace:
    workspace_id: "{{ env.FABRIC_WORKSPACE_ID }}"
  import_pipelines: true
  polling_sensor: true
  sensor_check_interval_seconds: 300
```

One shared sensor polls every imported item's job-run history per tick
(one token fetch, reused across items), deduping on each Fabric job
instance's own `id` via the sensor cursor. It observes against each
item's final, `translation:`-resolved asset key, not a re-derived default
— so a `translation:` key override never splits sensor identity from
asset identity.

```yaml
type: dagster_community_components.FabricWorkspaceComponent
attributes:
  workspace:
    workspace_id: "{{ env.FABRIC_WORKSPACE_ID }}"
  import_notebooks: true
  lakehouse_id: "{{ env.FABRIC_LAKEHOUSE_ID }}"
  exit_value_file: "exit_values/{load_date}.txt"
  load_date_parameter: load_date
  data_failure_exit_values: ["no_rows_processed", "schema_drift"]
```

A notebook's own `notebookutils.notebook.exit(...)` return value is
unreachable from the Job Scheduler API directly — "completed, but signalled
bad data" can't be detected from the polled status alone. The workaround:
have the notebook also write its exit value to a file in OneLake
(`notebookutils.fs.put("Files/exit_value.txt", exit_value, overwrite=True)`),
and set `exit_value_file` to that path (relative to `lakehouse_id`'s `Files/`
root; `{load_date}` is substituted with the resolved `load_date_parameter`
value when both are set).

**`lakehouse_id` is required when `exit_value_file` is set, and is
deliberately NOT the notebook's own item id.** A Notebook has no OneLake
storage of its own — `notebookutils.fs` resolves relative paths against the
notebook's attached *default Lakehouse*, confirmed against Microsoft's own
`notebookutils` file-system docs and the OneLake overview's item-type list
(lakehouses/warehouses/eventhouses/KQL databases, not notebooks, are OneLake
data items). Set `lakehouse_id` to that Lakehouse's own item GUID — the
component raises a config error at load time if `exit_value_file` is set
without it.

After the job reports `Completed`, the component reads the file back via
OneLake's ADLS Gen2-compatible API (a separate `storage.azure.com` OAuth
scope from the Fabric API itself) and attaches it as `fabric/exit_value`
metadata. If the value matches one of `data_failure_exit_values`, the
otherwise-`Completed` run is raised as a `dg.Failure` with
`failure_class: data` instead of succeeding silently. A read failure (auth,
404, network) **fails closed** — it raises a real `dg.Failure` rather than
logging a warning and skipping the check — since the entire point of
configuring this field is to catch bad data that would otherwise pass as a
green materialization; silently skipping the check on a transient read
failure would defeat it.

## Known limitations

- **`import_semantic_models: true`'s observable-source-asset keys could clash with `dagster_powerbi`'s own `semantic_model/<name>` assets** if both are enabled against the same workspace. Use one or the other, or set `translation:` to prefix the key.
- **`dg add --auto-install` may not install `azure-identity`** even though it's in `requirements.txt` and the component imports it lazily (same convention as every other heavy/optional dependency in this registry — a fast `dg load`, no hard dependency chain). If you hit an `ImportError` at first materialization rather than at load time, run `uv add azure-identity` (or your project's equivalent) by hand.
- **`fabric_job_instance_url` (success) and the trigger-failure metadata are the Fabric REST API URL**, not a link a person can open — it needs a bearer token, so clicking it in the Dagster UI gets a 401. The fix would be emitting the Fabric **portal**'s own URL for that job run as `MetadataValue.url` instead, but a documented, verified URL format for deep-linking to one specific job run instance in the Fabric portal/Monitoring Hub doesn't exist anywhere checked (the Job Scheduler REST reference, the Monitoring Hub docs, or public community/blog posts) — only a REST API path for retrieving the same job instance's *data* programmatically. Fabricating a portal URL pattern without confirming it live against a real Fabric portal risks shipping a silently broken (or worse, misleadingly wrong) link, so this isn't implemented. If you have a real Fabric tenant, the actual browser URL while viewing a job run in the Monitoring Hub (or the workspace's own Jobs tab) would confirm the pattern — a workspace-level Monitoring Hub link (not per-run) is a safer interim workaround if you already know that URL for your tenant.

## Validation status

This component is **code-validated against the Fabric REST API spec**.
End-to-end validation requires a Fabric capacity (F2 minimum, ~$0.21/hr
pay-as-you-go) AND tenant-level Fabric enablement in Power BI Admin
Portal — which often requires a tenant admin. Ship in your environment
once Fabric is enabled in your tenant.

## Provisioning a Fabric capacity (one-time)

```bash
az provider register --namespace Microsoft.Fabric --wait
az fabric capacity create -g my-rg -n my-fabric -l eastus \
    --sku '{"name":"F2","tier":"Fabric"}' \
    --administration "{\"members\":[\"admin@yourtenant.com\"]}"
```

If the create returns `Unauthorized` ↦ Fabric tenant settings haven't
been enabled. A Power BI tenant admin needs to:
1. Go to admin.powerbi.com → Tenant settings
2. Enable "Fabric capacity admins" group
3. Add yourself or your SP
