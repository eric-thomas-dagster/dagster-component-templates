# `InformaticaPowerCenterWorkspaceComponent`

Wrap **Informatica PowerCenter** (legacy on-prem, distinct from IDMC) behind a Dagster workspace-shape component. Discovers workflows in the PowerCenter repository via `pmrep listobjects` and emits one Dagster asset per workflow. On materialize, invokes `pmcmd startworkflow` and polls `pmcmd getworkflowdetails` until the workflow reaches a terminal state.

Companion of `informatica_workspace` — that one covers cloud IDMC, this one covers on-prem PowerCenter. Same shape (selector + translator + state-backed + polling sensor + freshness check), different execution surface.

## When to use this

- You still run production PowerCenter (or PowerCenter alongside IDMC during migration) and want Dagster to own workflow orchestration.
- You want PowerCenter workflows in the same asset catalog as downstream Snowflake / dbt / Power BI work.
- You're consolidating on Dagster and don't want a separate scheduler process for the legacy PowerCenter tier.

## Full workspace shape (parity with other workspace components)

- **`@public`** class + `StateBackedComponent` caching (discovery cached to disk via `write_state_to_path`; refresh with `dg utils refresh-defs-state`).
- **`translation:` callable** for per-asset customization (rename, tag by folder, add owners).
- **`workflow_selector:`** — filter by folder / include / exclude fnmatch patterns.
- **`workflow_overrides:`** — parameter files + variable overrides + session log paths applied at execute time.
- **`polling_sensor:`** — poll `pmcmd getworkflowdetails` for each workflow's last status.
- **`freshness_lag_threshold_seconds:`** — per-workflow asset check placeholder (real implementation deferred until `pmrep gettaskdetails` history is wired).

## Runtime requirements

- **`pmcmd`** + **`pmrep`** binaries on PATH (or absolute paths set via `workspace.pmcmd_path` / `workspace.pmrep_path`).
- Network access from the Dagster runtime to the PowerCenter domain server (typical: gateway port 6005).
- `$INFA_DOMAINS_FILE` correctly configured on the runtime host so pmcmd can resolve the domain gateway.

## Backing pmcmd / pmrep commands

| Command | Purpose |
|---|---|
| `pmrep connect + listfolders` | Enumerate folders in the repository. |
| `pmrep listobjects -o workflow -f <folder>` | List workflows in each folder. |
| `pmcmd startworkflow -sv <IS> -d <domain> -u <user> -p <password> -f <folder> [-paramfile ...] [-parameter ...] <wf>` | Trigger a workflow run. |
| `pmcmd getworkflowdetails -sv <IS> -d <domain> -u <user> -p <password> -f <folder> <wf>` | Poll for status. |

## Runtime parameters + parameter files

Real PowerCenter workflows take parameters — extract dates, target schemas, connection overrides. `workflow_overrides:` applies them per-workflow via `pmcmd -paramfile` (whole file) or `pmcmd -parameter NAME=VALUE` (inline).

```yaml
workflow_overrides:
  # per-workflow parameter file (Informatica $$Var=value format)
  - match: "REPO_PROD/Sales/wf_load_customers"
    parameter_file: "/etc/infa/params/customers_{partition_key}.par"

  # inline variable overrides (win over paramfile)
  - match: "REPO_PROD/Sales/wf_load_*"
    parameters:
      $$TargetSchema: "raw_sales"
      $$BatchDate:    "{partition_key}"    # substituted at run time
```

The **`{partition_key}`** token in a string value substitutes at run time (via `str.format`) — pair with `PartitionsDefinition` on the asset (via `translation:`) for per-partition PowerCenter runs.

## PowerCenter workflow statuses

Values from `pmcmd getworkflowdetails` "Status:" line:

| Status | Terminal? | Success? |
|---|---|---|
| `Running` | no | — |
| `Suspended` | no | — |
| `Suspending` | no | — |
| `Succeeded` | **yes** | **yes** |
| `Failed` | yes | no |
| `Aborted` | yes | no |
| `Stopped` | yes | no |
| `Terminated` | yes | no |
| `Unknown` | yes | no |

`Succeeded` is the only success state — everything else terminal raises `dg.Failure` when `wait_for_completion: true`.

## Actions

- **`action: noop` (default)** — external asset shape. Every PowerCenter workflow becomes a Dagster asset, but materialize does nothing. Pair with `polling_sensor: true` for observe-only.
- **`action: execute`** — materialize runs the workflow via `pmcmd startworkflow`. With `wait_for_completion: true`, the op blocks until `pmcmd getworkflowdetails` returns a terminal status. On non-success, raises `dg.Failure` with the first error-shaped line from pmcmd output.

## Companion components

- **`informatica_workspace`** — the IDMC (cloud) counterpart. Use both simultaneously if you're mid-migration.
- **`ssis_workspace`** — the Microsoft-stack counterpart.
- **`snowflake_workspace`** / **`dbt_cloud_trigger_job`** — natural downstream steps after PowerCenter lands data.
