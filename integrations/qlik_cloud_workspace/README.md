# QlikCloudWorkspace

N [Qlik Cloud](https://qlik.dev/) apps as Dagster assets from **one component instance**, with **one shared observation sensor** — the workspace-shape sibling to `qlik_cloud_app_reload`.

Closes a real scaling gap found via review feedback on `qlik_cloud_app_reload`: a shop with 30 dashboards needed 30 separate component instances (one YAML block, one polling sensor each). `QlikCloudWorkspaceComponent` takes one `apps:` list instead — `qlik_cloud_app_reload` is still there, unmodified, for the genuinely-one-dashboard case.

Same real Qlik Cloud REST API, verified directly against [qlik.dev's Reloads API reference](https://qlik.dev/apis/rest/reloads/):

- `POST /api/v1/reloads` — trigger (`{appId, partial, resourceType, resourceId}`)
- `GET /api/v1/reloads/{reloadId}` — poll to a terminal status
- `GET /api/v1/reloads?appId=...` — list, used by the shared observation sensor
- Status enum: `QUEUED`, `RELOADING`, `CANCELING` (active) / `SUCCEEDED`, `FAILED`, `CANCELED`, `EXCEEDED_LIMIT` (terminal)

## Transport seam

`QlikCloudTransport` (`trigger_reload` / `get_reload` / `list_reloads` / `poll_to_terminal`) is the one place HTTP calls happen. It's a real, independently importable class — tests exercise it directly against a fake server with no component involved at all, and it's the single swap point for a future demo/stand-in mode, instead of `requests` calls scattered through the component.

## assets_by_app — per-app overrides

Mirrors the official `dagster-databricks` `DatabricksWorkspaceComponent.assets_by_task_key` shape, keyed by Qlik Cloud app id:

```yaml
assets_by_app:
  "60f1b3e2a1b2c3d4e5f6a7b8":
    group_name: finance_bi
    deps: [warehouse/extra_upstream]   # merged with the app's own deps
    tags:
      team: finance                    # merged with the component's own tags
```

`key` / `group_name` / `description` / `kinds` / `owners` replace; `deps` / `metadata` / `tags` merge onto whatever the app entry itself already set.

## Example YAML

```yaml
type: dagster_community_components.QlikCloudWorkspaceComponent

attributes:
  tenant_url_env_var: QLIK_CLOUD_TENANT_URL
  api_key_env_var: QLIK_CLOUD_API_KEY

  # ONE shared sensor across every app below, not one per app.
  polling_sensor: true
  sensor_name: qlik_cloud_workspace_observer

  apps:
    - app_id: "60f1b3e2a1b2c3d4e5f6a7b8"
      asset_key: bi/finance_consolidated_app
      deps: [warehouse/finance_fact]

    - app_id: "71a2c4f3b2c3d4e5f6a7b8c9"
      asset_key: bi/sales_dashboard_app
      deps: [warehouse/sales_fact]
      partial: true
```

## Observing externally-triggered reloads

Set `polling_sensor: true` for **one** sensor (not one per app) that polls `GET /api/v1/reloads?appId=...` for every declared app, for reloads none of them triggered itself — e.g. a reload scheduled directly in Qlik Cloud, or someone reloading from the Qlik hub. Every reload this component triggers is tagged `resourceType: "api", resourceId: "dagster"` on the real API request, which the sensor uses to skip its own triggers and only emit `AssetObservation` for the rest, correctly attributed to the right app's asset key.

## When to use this vs. `qlik_cloud_app_reload`

| | `qlik_cloud_app_reload` | `qlik_cloud_workspace` |
|---|---|---|
| Shape | one app per component instance | N apps per component instance |
| Sensor | one sensor per instance (so one per app) | one shared sensor for every app |
| Per-app customization | every field is top-level | `assets_by_app` overrides, keyed by app_id |
| Best for | a single dashboard | a fleet of dashboards |
