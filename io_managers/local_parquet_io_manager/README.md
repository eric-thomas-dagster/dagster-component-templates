# LocalParquetIOManager

A no-frills IO manager that writes DataFrames as Parquet files in a local directory. Each asset gets its own file; partitioned assets get one file per partition. No database, no cloud — perfect for dev iteration and notebook-style work where you want persistence between runs but not the overhead of a warehouse.

## Backends

`backend: pandas` (default) reads/writes via `pandas.read_parquet`/`DataFrame.to_parquet`. `backend: polars` reads/writes via `polars.read_parquet`/`DataFrame.write_parquet` instead — real polars DataFrames in, real polars DataFrames out.

The polars backend calls `pl.read_parquet`/`DataFrame.write_parquet` directly — eager reads/writes, never `pl.scan_parquet`. That's deliberate: it means this component has no dependency on the `dagster-polars` package at all, so it's unaffected by that package's current Polars 2.0 incompatibility (`PolarsParquetIOManager` crashes on every read under Polars 2.0 — `ArgumentRemovedError: rechunk ... removed in version 2.0` — fixed upstream in [community-integrations#359](https://github.com/dagster-io/community-integrations/pull/359), not yet merged). If you need a `dagster-polars`-backed IO manager specifically (e.g. for its other features), use `polars_io_manager` and pin `polars<2` until that PR lands; otherwise this backend is a drop-in, Polars-2.0-safe alternative for local Parquet storage today.

## Partition ranges (single_run backfills)

For an asset with `BackfillPolicy.single_run()`, one run covers a range of partitions. In that case the asset must return a dict `{partition_key: DataFrame}` whose keys are exactly the range's partition keys; each entry is written to its own per-partition file (same layout as a single-partition run). Loading an upstream range returns `{partition_key: DataFrame}`. Anything else raises a clear `TypeError`/`ValueError`. Single-partition and unpartitioned behaviour is unchanged.

## Example YAML
```yaml
type: dagster_component_templates.LocalParquetIOManagerComponent
attributes:
  resource_key: io_manager
  base_dir: /tmp/dagster_storage
  create_dir: true
```

## What gets written

Each asset materialization produces a `parquet` file at:

```
<base_dir>/<asset_key_part_1>/<asset_key_part_2>/.../<part_n>.parquet
```

For partitioned assets, the partition key is appended:
```
<base_dir>/<asset_key>/<partition_key>.parquet
```

## Why this exists

Dev / no-warehouse / quick-iteration use cases. Pairs well with
`csv_file_ingestion` upstream and any DataFrame-producing transform.

## Requirements

```
pandas
pyarrow
```

`polars` is required only when `backend: polars` is set — it's an optional backend, not a hard dependency.
