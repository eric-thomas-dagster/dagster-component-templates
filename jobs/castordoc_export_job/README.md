# CastordocExportJobComponent

Op-shaped job that **walks the live Dagster asset graph** on each run and
enriches matching **Castor** (CastorDoc / Coalesce Catalog) tables via its
public GraphQL API.

## Architecture notes — read before assuming this mirrors `alation_export_job`

Alation's lineage API lets you create brand-new first-class "dataflow
objects" representing Dagster assets themselves. **Castor's public API
does not support this** — confirmed against Castor's real public docs
(checked 2026-10-08): `upsertLineages` only accepts `parentTableId` /
`childTableId` pointing at `TABLE`/`DASHBOARD` records Castor's own
warehouse/BI connectors already discovered, and the UI-based "Manual
Lineage Importer" is explicitly documented as working "exclusively with
existing assets already known to Catalog" and unable to "register
brand-new external nodes like custom pipeline tools (Dagster, etc.)."

So each run of this job:

1. Walks `context.repository_def.asset_graph`.
2. Resolves each Dagster asset to an existing Castor table by exact,
   case-insensitive name match on the asset key's last path segment, via
   `getTables(scope: {nameContains})`.
3. Pushes descriptions onto matched tables via `updateTableDescriptions`.
4. Optionally (`push_tags`, default on) attaches `dagster` /
   `dagster:group:<group>` / `dagster:kind:<kind>` tags via `attachTags`.
5. Optionally (`push_data_quality`, default off) pushes a best-effort
   "tracked by Dagster" presence record via `upsertDataQualities` — **not**
   a real test result, since the asset-graph walk carries no pass/fail data.
6. Optionally (`push_lineage_edges`, default on) pushes lineage edges via
   `upsertLineages` for asset-graph edges where **both** endpoints already
   resolved to a Castor table. Edges with an unmatched endpoint are skipped
   and counted — Castor has no concept of an external/custom node to attach
   the unmatched side to.
7. Hashes the structural payload; skips the whole push when unchanged from
   the prior run (via `castordoc_export/payload_hash` run tag). Toggle with
   `only_export_on_change`.
8. Tags the run with the payload hash for next-run change detection.

## When to use this vs `lineage_to_castordoc`

| Component | Shape | Use case |
|---|---|---|
| `lineage_graph_extractor` + `lineage_to_castordoc` | **3-asset chain** | Lineage as a first-class Dagster asset. Automation-condition-driven pushes when upstream changes. |
| `CastordocExportJobComponent` (this) | **single op-job** | Scheduled catalog sync; no asset overhead. Usually the better default for "sync my Dagster asset graph to Castor nightly." |

## YAML example

```yaml
type: dagster_component_templates.CastordocExportJobComponent
attributes:
  job_name: sync_dagster_lineage_to_castordoc
  schedule: "0 3 * * *"
  default_status: RUNNING
  catalog_url: https://api.castordoc.com/public/graphql
  api_token_env: CASTORDOC_API_TOKEN
  push_tags: true
  push_data_quality: false
  push_lineage_edges: true
  only_export_on_change: true
  fail_on_catalog_error: true
```

## Required env vars

```bash
CASTORDOC_API_TOKEN=...   # sent as `Authorization: Token <token>` (not Bearer)
```
