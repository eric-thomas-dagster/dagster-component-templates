# `DbtCloudTriggerJobComponent`

Kick off a dbt Cloud job run from a Dagster op-job. The missing "Dagster triggers dbt Cloud" primitive — closes the gap between the observing-only `dbt_cloud_job_sensor` (dbt Cloud → Dagster) and the local-only `dbt_run_job` (dbt Core via subprocess).

Wraps [`DbtCloudResource.run_job_and_poll`](https://docs.dagster.io/api/libraries/dagster-dbt#dagster_dbt.DbtCloudResource) so YAML is enough to build the trigger — no custom op file.

## When to use this

- You want a Dagster sensor / schedule / upstream-event to trigger a **dbt Cloud** run (not dbt Core).
- The `dbt_cloud_job_sensor` component gives you the reverse (observe dbt Cloud completions to trigger downstream Dagster work). This component completes the round-trip.
- Common pairing: `snowflake_workspace polling_sensor: true` fires on Snowpipe load events → a Dagster sensor targets `DbtCloudTriggerJobComponent`'s `job_name` → dbt Cloud job runs → optionally, `dbt_cloud_job_sensor` observes the completion and triggers downstream Dagster mart work.

## Dependencies

Requires a registered `DbtCloudResource` — commonly via the community `dbt_cloud_resource` component (which registers `dagster_dbt.DbtCloudResource` behind YAML).

```yaml
# resources.yaml — register the dbt Cloud resource ONCE per code location
type: dagster_community_components.DbtCloudResourceComponent
attributes:
  resource_key: dbt_cloud_resource
  auth_token_env_var: DBT_CLOUD_API_TOKEN
  account_id: 12345
```

Then reference the resource key from this component:

```yaml
# jobs/dbt_build_hourly.yaml
type: dagster_community_components.DbtCloudTriggerJobComponent
attributes:
  job_name: dbt_build_hourly_job
  dbt_cloud_job_id: 67890
  dbt_cloud_resource_key: dbt_cloud_resource     # matches the resource above
  wait_for_completion: true
  cause: "Triggered by Dagster on Snowpipe load event"
```

## How it wires into a Dagster sensor

The sensor / schedule / upstream event references this component's `job_name`. Example — a filesystem_monitor variant that fires when Snowpipe emits AssetObservations:

```yaml
# sensors/snowpipe_to_dbt_cloud.yaml
type: dagster_community_components.SnowflakeSnowpipeLoadSensorComponent
attributes:
  sensor_name: snowpipe_to_dbt_cloud
  job_name: dbt_build_hourly_job    # ← same string as DbtCloudTriggerJobComponent.job_name above
  pipe_name: FUEL_AND_TRADING_PIPE
  # … (Snowflake auth fields)
```

The chain: Snowpipe load → sensor tick → sensor emits `RunRequest(job_name="dbt_build_hourly_job")` → Dagster launches the op-job → op calls `DbtCloudResource.run_job_and_poll(job_id=67890)` → dbt Cloud runs → op emits per-model `AssetMaterialization` events → downstream Dagster assets automate on those materializations.

## Emitting `AssetMaterialization` events

The `emit_materializations_for` field is the seam that makes the dbt Cloud run visible in Dagster's asset graph. Without it, the run happens but no asset lineage edges into or out of it. Common configuration:

```yaml
emit_materializations_for:
  - mart/daily_summary
  - mart/hourly_pricing
  - mart/site_details
```

Use the **same slash-form asset keys** the corresponding assets are declared with (e.g. via `snowflake_workspace` on the downstream Snowflake mart tables). Once the dbt Cloud run finishes successfully, the op emits one `AssetMaterialization` per key with metadata:

- `dbt_cloud/run_id` — the dbt Cloud run ID
- `dbt_cloud/run_url` — clickable URL back to dbt Cloud's run page
- `dbt_cloud/status` — human-readable run status

Downstream automation conditions (`AutomationCondition.on_upstream_asset_materialized()`) will trip when these materialization events land.

## Per-run overrides

Every field dbt Cloud's REST API accepts as a per-run override is available as an attribute — see the field descriptions above for the mapping. Use these when the same dbt Cloud job needs different behavior per trigger context:

- **`steps_override`** — replace the job's configured steps for this run only. E.g., `["dbt build --select tag:hourly"]` when Dagster wants only the hourly-tagged models built.
- **`schema_override`** — target schema for this run only. Useful when triggering against a branch-deployment schema.
- **`git_branch` / `git_sha`** — run against a specific branch or commit instead of the job's default.

## Fire-and-forget mode

For very-long-running dbt Cloud jobs where you don't want a Dagster op to block:

```yaml
attributes:
  wait_for_completion: false
```

The op returns as soon as dbt Cloud accepts the trigger. Downstream Dagster work should then be gated on `dbt_cloud_job_sensor` (which observes dbt Cloud → triggers when the run completes), NOT on this op's success — this op's success only tells you "the trigger was accepted."
