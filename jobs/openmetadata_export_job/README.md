# OpenMetadataExportJobComponent

Op-shaped job that **walks the live Dagster asset graph** on each run and
pushes lineage + metadata to OpenMetadata's REST API. Idempotent PUTs
(re-running with the same asset graph is a no-op or a clean upsert).

Each run produces:

- **1 DatabaseService** (configurable, default `"dagster"`)
- **1 Database** under the service (configurable, default `"default"`)
- **1 DatabaseSchema per Dagster group** (ungrouped assets collapse into `"default"`)
- **1 Table per Dagster asset** (with description + external URL back to Dagster + tag props linking Dagster metadata)
- **1 lineage edge per asset-graph edge**

## When to use this vs `lineage_to_openmetadata`

Two complementary OpenMetadata paths in the registry:

| Component | Shape | Use case |
|---|---|---|
| `lineage_graph_extractor` + `lineage_to_openmetadata` | **3-asset chain** | Lineage as first-class assets. Snapshot is itself materialized + tracked. `AutomationCondition.eager()` on the sink pushes automatically when upstream changes. Multiple downstream sinks can fan out to different catalogs from the same upstream payload. |
| `openmetadata_export_job` (this) | **single op-job** | One scheduled job; doesn't add lineage as assets to your graph. Simpler when you just want a nightly "sync my Dagster asset graph to OpenMetadata" without asset-graph clutter. |

**Rule of thumb:**
- Pushing to an external catalog is an **operational side-effect**, not a data product. Prefer this op-job shape.
- Only reach for the asset chain when you want the lineage payload itself versioned as a first-class Dagster asset, or you want automation-condition-driven pushes wired into the asset graph.

## YAML example

```yaml
type: dagster_component_templates.OpenMetadataExportJobComponent
attributes:
  job_name: sync_dagster_lineage_to_openmetadata
  schedule: "0 3 * * *"                  # nightly at 3am
  default_status: RUNNING
  catalog_url: https://openmetadata.acme.com
  api_token_env: OPENMETADATA_API_TOKEN
  service_name: dagster
  database_name: default
  only_export_on_change: true
  fail_on_catalog_error: true
```

## Behavior

1. Walks `context.repository_def.asset_graph` to enumerate every asset
   in the current code location.
2. Hashes the structural payload (nodes + edges, no timestamps). If
   `only_export_on_change=true` and the hash matches the previous
   successful run's tag, the push is skipped — OpenMetadata doesn't
   see redundant no-op PUTs on every tick.
3. Builds a plan: 1 service, 1 database, N schemas (one per Dagster
   group), M tables (one per asset), K lineage edges.
4. PUTs each entity to `{catalog_url}/api/v1/...` in order (service →
   database → schemas → tables → lineage). All PUTs are idempotent.
5. On success, tags the Dagster run with the structural hash so the
   next run's change-detection works.

## Limitations

- **Service type is Mysql**. OpenMetadata requires a concrete
  serviceType; Mysql is a stable choice that renders cleanly. The
  displayName is set to "Dagster" so the origin is obvious in the UI.
- **No column-level lineage**. Each asset becomes a Table with columns
  derived from Dagster metadata keys. Column-to-column lineage from
  Dagster's `column_lineage` metadata isn't yet emitted.
- **Sequential PUTs**. Entities go up one at a time; no batching. For
  very large asset graphs (thousands of assets), a future iteration
  could group PUTs.
- **Stops at first PUT error** (when `fail_on_catalog_error=true`) —
  partial catalog state is possible. Idempotent PUTs mean the next run
  fixes any half-pushed state, though.
