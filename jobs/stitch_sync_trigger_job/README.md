# StitchSyncTriggerJobComponent

Trigger a Stitch (Talend/Qlik) replication job via the Stitch Connect API — fire-and-forget or wait for completion.

## Dependencies
- `requests`

## Real API, confirmed

Stitch is Talend's managed ELT product (Talend acquired Stitch in 2018;
Qlik acquired Talend in 2023 — Stitch has operated as a separate
product/brand through both). It is distinct from `talend_cloud_workspace`,
which drives Talend Cloud's own Data Fabric jobs/pipelines, a different
product with a different API.

Confirmed 2026-10 against
[stitchdata.com's Connect API docs](https://www.stitchdata.com/docs/developers/stitch-connect/api)
that the API is still live and documented (not a sunset product, despite two
ownership changes):

- Base URL: `https://api.stitchdata.com`
- Auth: `Authorization: Bearer $STITCH_API_TOKEN` (generated in Stitch account settings; does not expire)
- Trigger: `POST /v4/sources/{source_id}/sync`
- Stop: `DELETE /v4/sources/{source_id}/sync`
- History: `GET /v4/{client_id}/extractions` (rate-limited to 30 requests / 10 minutes)

**Caveat, stated plainly:** Stitch's current public docs describe the
extraction-job resource only at a high level and don't spell out its full
field schema (unlike Airbyte's or Meltano Cloud's job objects). There is no
single "sync run id" returned by the trigger call to poll directly. So
`wait_for_completion` here is **best-effort**: it re-lists
`/v4/{client_id}/extractions` after triggering and matches the most recent
record for `source_id`, checking several plausible field-name variants
(`job_finished_at`/`end_time`/`finished_at` for completion,
`tap_exit_status`/`extractor_exit_status` + `target_exit_status`/
`loader_exit_status` for success/failure) rather than assuming one exact
shape. It defaults to `False` for this reason — verify the real field names
against your own account's response before relying on it in production.
Triggering itself (the documented, simple part) is solid either way.

## What this is
A **Dagster job** (no asset materialized) — the component installs a `dg.job`
plus an optional schedule. Lineage graph stays clean; the work happens
behind the scenes.
