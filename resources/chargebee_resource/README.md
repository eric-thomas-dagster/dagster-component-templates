# Chargebee Resource

Register a `ChargebeeResource` wrapping the **Chargebee API v2** for use by other Dagster components.

## Auth: HTTP Basic, API key as username, blank password

Chargebee has no OAuth2 flow and no token to refresh — every request is HTTP Basic-authenticated with the Chargebee API key as the username and an empty password. This matches the convention already used by this repo's `chargebee_ingestion` component.

## POST is the only mutating verb

Chargebee's REST API uses **POST for every mutating operation** — create, update, and delete all go through POST. There's no PUT/PATCH/DELETE anywhere in the API. What distinguishes "create" from "update" is the URL path: `POST /customers` creates, `POST /customers/{id}` updates (partial-merge — only fields you send are changed). This is a real gotcha for anyone assuming REST-conventional verbs.

## Configuration

```yaml
type: dagster_component_templates.ChargebeeResourceComponent
attributes:
  resource_key: chargebee
  site: mysite
  api_key_env_var: CHARGEBEE_API_KEY
```

## Authentication setup

```bash
export CHARGEBEE_API_KEY="..."
```

Generate an API key from Chargebee's admin console: Settings → Configure Chargebee → API Keys.

## Usage in other components

```yaml
attributes:
  resource_key: chargebee
```

Exposes `request(method, path, json_body=None, params=None)` — `json_body` is form-encoded (not JSON) per Chargebee's convention, and `params` is used for list-filter query strings (e.g. `email[is]=...`). Higher-level upsert logic (lookup-then-create-or-update) lives in consuming components (e.g. `chargebee_customer_upsert`), not in this resource, per this repo's no-shared-logic convention.
