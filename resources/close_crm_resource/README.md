# `CloseCrmResourceComponent`

Self-contained **Close CRM REST API workhorse** (`https://api.close.com/api/v1`). HTTP Basic auth, retries on 429 (sliding-window rate limit) / 5xx. Read + write convenience methods including a **search-then-write emulated upsert**, since Close has no native atomic upsert endpoint — no dependency on any third-party Dagster integration package.

## Why this exists

Consumed by:
- **`close_crm_lead_upsert`** — reverse-ETL sink using the `upsert_lead` convenience method below.
- Custom Dagster asset code that needs raw Close REST access (Leads, Contacts, Activities, Opportunities, etc.).

`close_crm_ingestion` (dlt-backed bulk pull) has its own dlt REST API source configuration and does NOT use this resource.

## Auth

HTTP Basic, API key as **username**, **blank password** (verified against `developer.close.com/api/overview/api-key-authentication`):

```bash
curl https://api.close.com/api/v1/me/ -u <api_key>:
```

Create an API key under Close → *Settings → Developer → API Keys*. Set it as `api_key_env_var`.

## Close has no native upsert — search-then-write, and why that matters

Unlike Salesforce (`PATCH .../{ExtIdField}/{value}`) or HubSpot (`POST .../batch/upsert`), Close's REST API has **no atomic create-or-update endpoint**. `upsert_lead` emulates one:

1. `POST /api/v1/data/search/` (Close's "Advanced Filtering" API) to look up an existing Lead by a dedupe field.
2. `PUT /api/v1/lead/{id}/` if found, else `POST /api/v1/lead/` to create.

**This is NOT race-condition-safe.** Two concurrent writers upserting the same dedupe value (e.g. two overlapping runs of the same pipeline, or two different pipelines writing the same Lead) can both run the search step before either has created the record, both see "not found," and both issue a `POST /lead/` — producing two duplicate Leads for the same person. Close's REST API offers no idempotency key, no conditional-write header (`If-None-Match` or similar), and no unique-constraint-on-create behavior to close this window. Mitigate by:
- Running `close_crm_lead_upsert` as a single serialized asset (no concurrent runs against the same dedupe values).
- Choosing a dedupe field that's actually unique in your data (an email address, or a custom field holding an external id from your warehouse's primary key) — a non-unique `name` field will silently create duplicates even without concurrency, since the search only ever looks at the *first* match.
- Periodically using Close's own **Merge Leads** feature (`POST /lead/merge/` is documented separately) to reconcile any duplicates that slip through.

### Why Advanced Filtering (`/data/search/`) and not the older query-string search

Some older Close client libraries reference a simpler `GET /api/v1/lead/?query=...` free-text syntax (e.g. `email:"foo@bar.com"`). This was checked against Close's **current** API reference (`developer.close.com`) and found nowhere — the documented `List Leads` endpoint only supports `_limit` / `_skip` / `_fields` query params, with no `query` string syntax mentioned. Close's current, documented search mechanism is the Advanced Filtering API (`POST /data/search/`), so `find_lead_by_query` uses that exclusively.

## Dedupe fields supported by `find_lead_by_query` / `upsert_lead`

| `dedupe_field` | Matches against |
|---|---|
| `"email"` | A contact's email — `has_related` / `contact_email` field_condition (text, phrase match). |
| `"phone"` | A contact's phone — `has_related` / `contact_phone` field_condition (text, phrase match). |
| `"name"` | The Lead's own `name` field (text, phrase match). Not guaranteed unique — see race-condition note above. |
| `"custom.cf_xxx"` | A Lead custom field, matched by `custom_field_id` (exact `term` match) — the safest option for an external-id-style dedupe key. |

## Convenience methods

HTTP primitives:
- `get(path, params)` / `post(path, json_body)` / `put(path, json_body)` — raw REST calls, relative to `base_url`.

Search (Advanced Filtering):
- `find_lead_by_query(dedupe_field, value)` — returns the first matching Lead (`{'id', '__object_type'}`) or `None`.

Lead CRUD:
- `create_lead(body)` — `POST /lead/`.
- `update_lead(lead_id, body)` — `PUT /lead/{id}/`.
- **`upsert_lead(dedupe_field, dedupe_value, create_body, update_body=None)`** — search-then-write emulated upsert. Returns `{"action": "created"|"updated", "id": <lead_id>}`, mirroring this repo's `salesforce_resource.upsert_record` return shape.

## Lead body shape

Verified against `developer.close.com/api/resources/leads/create`:

```json
{
  "name": "Bluth Company",
  "contacts": [
    {
      "name": "Gob",
      "emails": [{"email": "gob@example.com", "type": "office"}],
      "phones": [{"phone": "8004445555", "type": "office"}]
    }
  ],
  "custom.cf_FSYEbxYJFsnY9tN1OTAPIF33j7Sw5Lb7Eawll7JzoNh": "Segway"
}
```

Custom fields are **flat top-level keys** of the form `"custom.cf_xxx"` — not nested under a `"custom"` object — on both create and update bodies.

## Rate limits

Verified against `developer.close.com/api/overview/rate-limits`. Close enforces a sliding-window limit per API key *and* per organization (org limit = 3x the per-key limit for the same endpoint group), surfaced via a single combined `RateLimit` response header:

```
RateLimit: limit=100, remaining=50, reset=5
```

Note this supersedes the older, separate `X-Rate-Limit-Limit` / `X-Rate-Limit-Remaining` headers used by some other APIs (and by Close itself historically) — this resource parses the current combined header. On 429, Close guarantees both the `ratelimit` and `retry-after` headers; Close's own docs recommend sleeping for the `reset` seconds from `RateLimit` rather than `retry-after` for a more accurate wait, which is what `max_retries`' backoff does here (falling back to `retry-after`, then plain exponential backoff, if the header is missing).
