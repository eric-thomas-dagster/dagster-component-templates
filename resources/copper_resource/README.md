# `CopperResourceComponent`

Self-contained **Copper CRM REST API workhorse**. Header-based API-key auth, retries on 429 / 5xx, generic `get`/`post`/`put` plus `search()` / `upsert()` convenience methods for downstream sink / read components. No dependency on any third-party Dagster integration package.

## Why this exists

Consumed by:
- **`copper_record_upsert`** — reverse-ETL sink (search-then-write; Copper has no native atomic upsert).
- Custom Dagster asset code that needs Copper People / Leads / Companies CRUD.

`copper_ingestion` (dlt-backed bulk pull) has its own dlt configuration and does NOT use this resource.

## Authentication

Every Copper API request requires **four headers**, all set automatically by this resource (verified against `developer.copper.com/introduction/requests.html`):

| Header | Value |
|---|---|
| `X-PW-AccessToken` | Your Copper API key |
| `X-PW-Application` | `developer_api` (literal constant) |
| `X-PW-UserEmail` | Email address of the API key's owner |
| `Content-Type` | `application/json` |

Missing any of these (most commonly `X-PW-UserEmail`, which is easy to forget since it's not part of the credential itself) returns a 401/403 from Copper.

```bash
export COPPER_API_KEY="xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
```

Find your API key under *Copper Settings → Integrations → API Keys*. The key is scoped to the user whose email you pass as `user_email`.

## Rate limits

Per Copper's own documentation: **180 requests/minute**, evaluated on a rolling window, plus a separate **3 requests/second** cap on Bulk endpoints. Both return **429** on exceed. `max_retries` controls how many times this resource retries a 429/5xx with exponential backoff (honoring a `Retry-After` response header when Copper sends one), logging a warning on every retry so sustained throttling shows up in run logs instead of silently eating wall-clock time.

## Convenience methods

- `get(path, params)` — GET.
- `post(path, json_body)` — POST.
- `put(path, json_body)` — PUT.
- `search(object_type, filter_body)` — `POST /{object_type}/search`. Always returns a **list** (possibly empty) — Copper's search endpoints never return a single bare object.
- `upsert(object_type, search_filter, create_body, update_body=None)` — find-then-create-or-update. Returns `{"action": "created"|"updated", "id": ...}`.

## No native atomic upsert — search-then-write only

Unlike Salesforce's External-ID `PATCH` (atomic create-or-update in one call), **Copper has no equivalent endpoint**. `.upsert()` emulates one:

1. `POST /{object_type}/search` with a filter shaped for the match field (e.g. `{"emails": ["a@b.com"]}` for People).
2. If a match comes back, `PUT /{object_type}/{id}` with the write body.
3. If not, `POST /{object_type}` to create a new record.

**This is NOT race-condition-safe.** Between step 1 and step 2/3, a concurrent writer (another Dagster run, a human editing in the Copper UI, a different integration) can create a record matching the same search filter without this method seeing it — the result is a duplicate record. Safe for single-writer / sequential reverse-ETL jobs; not safe if multiple processes may upsert the same `object_type` concurrently. See `copper_record_upsert`'s README for the sink-level discussion of this limitation.

`search_filter` / `create_body` / `update_body` must already be shaped correctly for the target `object_type` — this method is a dumb find-then-write primitive, not object-type aware. `copper_record_upsert` builds these shapes (People use a plural `emails: [...]` array; Leads use a singular `email: {...}` object; Companies use `email_domain` instead of an emails field at all — three genuinely different shapes verified against Copper's own docs).
