# Databricks Jobs Resource

Register a `DatabricksJobsResource` for use by any op/asset in this code location -- reusable
Airflow-operator-equivalent actions against the real Databricks Jobs API. This component only
registers the resource; it does not materialize anything on its own.

- `run_now_and_wait(job_id=..., ...)` -- trigger an existing job and wait for completion (the
  `DatabricksRunNowOperator` equivalent). Pass `job_name=...` instead of `job_id` to resolve the
  id by name via `jobs.list(name=...)` (raises if zero or more than one job matches). Also
  forwards `jar_params`/`spark_submit_params` alongside the existing `job_parameters`/
  `notebook_params`/`python_params`.
- `submit_run_and_wait(run_json, ...)` -- submit a one-time, ad-hoc run from a JSON body with no
  pre-existing job required (the `DatabricksSubmitRunOperator` equivalent). `run_json` matches
  the Jobs API's "submit a one-time run" request body (e.g. `{"run_name": ..., "tasks": [...],
  "timeout_seconds": ...}`); each `tasks` entry is converted to a `SubmitTask` automatically.
- `repair_run_and_wait(run_id, rerun_tasks=..., ...)` -- re-run only the failed tasks of a prior
  run (or all failed tasks via `rerun_all_failed_tasks=True`), wait for completion.

All three wait for a terminal state and return the same result shape
(`run_id`/`run_page_url`/`life_cycle_state`/`result_state`/`state_message`), raising
`dagster.Failure` on a non-SUCCESS `result_state` unless `fail_on_non_success=False`.

All three also take `poll_interval_seconds` (default `5.0`) controlling how often the
resource polls for completion -- polling is done directly against `jobs.get_run`, not the
SDK's own `wait_get_run_job_terminated_or_skipped` helper, which hard-codes its own cadence
with no way to control it. `submit_run_and_wait` also takes `idempotency_token` (a real
`jobs.submit` parameter, taking precedence over any `idempotency_token` already present in
`run_json`). `repair_run_and_wait` has no `idempotency_token` parameter -- the installed
databricks-sdk's `JobsAPI.repair_run` has no such argument, confirmed directly.

## Usage

Call it from your own asset/op body:

```python
import dagster as dg


@dg.asset
def my_pipeline_step(context: dg.AssetExecutionContext, databricks_jobs_resource) -> dg.MaterializeResult:
    result = databricks_jobs_resource.run_now_and_wait(job_id=123456789)
    return dg.MaterializeResult(metadata={"run_id": result["run_id"]})
```

Wrap it in your own `@dg.asset` only when you want the trigger itself to participate in the
Dagster asset graph (deps, freshness, automation conditions, partitioning, retries). Distinct
from `integrations/databricks_asset_bundle` (submits ad-hoc tasks defined inline from a
`databricks.yml` bundle) and `integrations/databricks_clean_room_notebook_run` (ad-hoc Clean
Rooms notebook submission) -- neither of those calls `run_now` against a pre-existing job.

## Authentication

All secret fields accept an **environment variable name** (not the secret value itself).
Set the corresponding environment variable before running Dagster:

```bash
export DATABRICKS_TOKEN="your-personal-access-token"
```
