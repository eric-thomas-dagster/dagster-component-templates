# `DynamicsCrmResourceComponent`

Self-contained **Microsoft Dynamics 365 (Dataverse) Web API workhorse**. Azure AD OAuth 2.0 `client_credentials` auth, retries on 401 (token refresh) / 429 / 5xx. Read/write convenience methods for downstream components — no dependency on any third-party Dagster integration package.

## Why this exists

Consumed by:
- **`dynamics_crm_record_upsert`** — reverse-ETL sink using Dataverse's native alternate-key upsert.
- Custom Dagster asset code that needs ad-hoc Dataverse Web API reads/writes.

`dynamics_crm_ingestion` (dlt-backed bulk pull) builds its own inline OAuth token and does NOT use this resource.

## Auth: Azure AD OAuth 2.0 `client_credentials` grant

```
POST https://login.microsoftonline.com/{tenant_id}/oauth2/v2.0/token
    grant_type=client_credentials
    client_id=<client_id>
    client_secret=<client_secret>
    scope={org_url}/.default
```

Headless, no browser. The returned bearer token is sent on every subsequent call to `{org_url}/api/data/{api_version}/...`.

### Setup checklist

1. **Azure AD (Entra ID) app registration** — create one, generate a client secret, note the tenant ID / client ID.
2. **Dataverse Application User** — in the Power Platform Admin Center, open the target environment → *Settings → Users + permissions → Application users* → add a new one backed by the app registration's client ID.
3. **Security role** — assign the Application User a security role (e.g. *System Administrator* for testing, or a scoped custom role for production) covering the entities this resource will read/write.

> **Important correction vs. the common assumption:** access here is governed entirely by the **Application User + its security role**, not by an "API permissions" block on the Azure AD app registration. Entra happily issues an access token for the Dataverse resource (`{org_url}/.default`) even with zero API permissions configured on the registration — Dataverse is the one that authorizes (or 403s) each call, based on whether an Application User exists for that client ID and what its security role allows. Don't waste time hunting for a "Dynamics CRM" permission to grant in Entra; the Application User step is the one that actually matters.

## Upsert-by-alternate-key mechanics

Dataverse's native create-or-update:

```
PATCH {org_url}/api/data/{api_version}/{entity_set}({key}='{value}')
```

- `{key}` must be a pre-defined **Alternate Key** on the table (maker portal → table → *Keys*) — not just any column.
- Composite (multi-column) alternate keys are supported: `(key1=val1,key2=val2)`.
- **Without** `Prefer: return=representation`: Dataverse always returns `204 No Content`, for *both* create and update — the two are indistinguishable from the status code, and the `OData-EntityId` response header echoes back the same alternate-key reference you sent, not the row's real GUID.
- **With** `Prefer: return=representation` (this resource's default): `201 Created` (new row) or `200 OK` (existing row updated), with the full row — including its GUID primary-key attribute — in the response body. This is the only reliable way to learn created-vs-updated *and* recover the real GUID in one round trip.

`upsert_by_key()` wraps this and returns `{"action": "created" | "updated" | "unknown", "id": <guid-or-None>}` (mirroring `salesforce_resource.upsert_record()`'s return shape). `"unknown"` only happens if you explicitly pass `prefer_representation=False`.

## No native bulk upsert — `$batch` exists but isn't implemented here

Unlike Salesforce (`/composite/sobjects`, Bulk 2.0), Dataverse has no single-call bulk/composite upsert endpoint. An OData `$batch` endpoint does exist (`POST {org_url}/api/data/{api_version}/$batch`, `multipart/mixed` bodies, optionally grouped into atomic "changesets" of up to 1,000 operations), but using it means hand-building and parsing raw MIME multipart request/response bodies — real complexity for a win that's about HTTP round-trip count, not server-side parallelism the way Salesforce's Bulk 2.0 is. This resource (and `dynamics_crm_record_upsert`) issues one PATCH per row. `$batch` is a documented, not-yet-implemented future optimization, not a fake "composite mode."

```yaml
  resource_key: dynamics_crm

```

## Convenience methods

- `get(path, params)` — GET, relative to `{org_url}/api/data/{api_version}/`.
- `post(path, json_body)` — POST.
- `patch(path, json_body, prefer_representation=True)` — raw PATCH, returns `{'status_code', 'body', 'odata_entity_id'}`.
- `delete(path)` — DELETE.
- **`upsert_by_key(entity_set, key_name_or_names, key_value_or_values, body)`** — native alternate-key upsert. `key_name_or_names` / `key_value_or_values` accept either scalars (simple key) or parallel lists (composite key). Returns `{"action": "created"|"updated"|"unknown", "id": ...}`.

## Pairs with

- **`dynamics_crm_record_upsert`** — reverse-ETL sink using this resource's `upsert_by_key()`.
- **`dynamics_crm_ingestion`** — dlt-based bulk pull (builds its own inline OAuth token, doesn't use this resource).

## What doesn't work here

Interactive OAuth flows (Authorization Code, device code) DO NOT work in Dagster resources — the code-location process has no browser and no user context. `client_credentials` is the only flow this resource supports, which is also Microsoft's own recommendation for unattended service-to-service integrations.
