Register a `HelpScoutResource` for the Help Scout Mailbox API v2 (`https://api.helpscout.net/v2`) for use by other Dagster components.

## Convenience methods

Any component with `required_resource_keys={"help_scout_resource"}` can call these on `context.resources.help_scout_resource`:

| Method | Purpose |
|---|---|
| `create_conversation(mailbox_id, customer_email, subject, body_text, type_="email", status="active", tags=None, customer_first_name=None, customer_last_name=None)` | `POST /conversations` -- creates a conversation AND natively upserts the Customer by email (see below). Returns the new int conversation id, parsed from the `Resource-ID` response header. |
| `update_tags(conversation_id, tags)` | `PUT /conversations/{id}/tags` -- **full replace**, not additive (see below). |
| `add_note(conversation_id, text)` | `POST /conversations/{id}/notes` -- add an internal note thread. |
| `patch_status(conversation_id, status)` | `PATCH /conversations/{id}` using Help Scout's JSON-Patch array body format. |

### Escape hatch

`get_client()` returns an authenticated `requests.Session` pointed at `base_url`.

## Authentication -- OAuth2 `client_credentials` grant (deliberately different from `help_scout_ingestion`)

This resource implements Help Scout's real documented server-to-server auth flow, NOT the static-bearer-token shortcut used by `help_scout_ingestion` elsewhere in this repo. `client_id_env_var`/`client_secret_env_var` accept **environment variable names** (not the secret values themselves):

```bash
export HELPSCOUT_CLIENT_ID="xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
export HELPSCOUT_CLIENT_SECRET="xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
```

Create an OAuth2 app under *Help Scout → My Apps* to get a Client ID/Secret.

On first use, this resource `POST`s to `/v2/oauth2/token` with `grant_type=client_credentials` and caches the returned `access_token` in-memory (keyed by `client_id_env_var`) until shortly before its `expires_in` (~48 hours) elapses. There is **no refresh token** in this grant type -- on expiry, the resource simply re-authenticates with the same client_id/client_secret. This is simpler than `resources/outreach_resource`'s refresh_token-rotation flow (a different OAuth grant entirely), though the caching *shape* is the same idea.

## Conversation create natively upserts the Customer by email

Per Help Scout's own docs: when you `create_conversation(..., customer_email=...)` and that email doesn't match an existing Customer record, Help Scout auto-creates one. There is no separate "customer upsert" call in this resource or in `HelpScoutConversationUpsertComponent` -- this native behavior IS the customer-upsert mechanism.

## Tags are a full replace, not additive

Unlike Lever's `addTags` (additive-only), Help Scout's `PUT /conversations/{id}/tags` replaces the ENTIRE tag list every time. Any existing tag you don't include in the call is removed from the conversation. Always pass the complete desired tag set.

## `PATCH` uses JSON-Patch, not a flat body

`patch_status` sends a JSON-Patch **array** (`[{"op": "replace", "path": "/status", "value": status}]`), not `{"status": status}`. This is Help Scout's real documented PATCH format for conversations.

## Companion components

- **`HelpScoutConversationUpsertComponent`** -- create-or-update DataFrame rows into Help Scout conversations (matched on an optional `conversation_id` column).
- **`HelpScoutIngestionComponent`** -- dlt-based bulk read into a warehouse (the READ-side counterpart; uses the simpler static-token auth).
