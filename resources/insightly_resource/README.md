# `InsightlyResourceComponent`

Self-contained **Insightly CRM REST API v3.1 workhorse**. HTTP Basic auth, pod-based host resolution, retry on 429 (rate limit) / 5xx, plus read/write/search/upsert convenience methods for downstream components — no dependency on any third-party Dagster integration package.

## Auth: HTTP Basic, API key as username, blank password

Insightly identifies the calling user via a per-user **API key** (Settings → API in the Insightly web app), sent as the **username** of an HTTP Basic `Authorization` header with an **empty password**:

```
Authorization: Basic base64("<api_key>:")
```

No OAuth, no token refresh, no expiry — the API key is a long-lived credential. Rotate it manually if compromised (Insightly → regenerate from the same Settings → API page).

## Base URL: pod-specific

Every Insightly account lives on a regional **pod**. Find yours on the Settings → API page, directly under your API key (e.g. `na1`). All calls go to:

```
https://api.{pod}.insightly.com/v3.1
```

Using the wrong pod returns connection/auth failures even with a valid key — pod and key are account-specific together.

## No native upsert

Insightly's v3.1 REST API is plain create-or-update **by numeric internal id**, not a dedupe-by-external-field upsert like Salesforce or HubSpot offer:

```
POST /{ObjectType}            # create
PUT  /{ObjectType}/{id}       # update — id in the URL path
```

The only field-based lookup Insightly documents is the generic search endpoint:

```
GET /{ObjectType}/Search?field_name={field}&field_value={value}
```

which works against "any standard or custom field" per Insightly's own docs (e.g. `field_name=EMAIL_ADDRESS` for Contacts). `.upsert()` below composes search-then-create-or-update out of these three primitives — **it is not atomic**. See the method's docstring and `insightly_record_upsert`'s README for the race-condition caveat.

## Rate limits

- **10 requests/second** max per instance.
- A **daily** quota that varies by plan — 1,000/day (Gratis) up to 60,000+/day (Professional/Enterprise), rolling 24h window.
- Exceeding either returns **HTTP 429**. Responses carry `X-RateLimit-Limit` / `X-RateLimit-Remaining` headers; this resource logs them on a 429 and retries with exponential backoff (capped at 10s) up to `max_retries`.

## Object shapes: CONTACTINFOS

Contacts store email/phone inside a nested array rather than flat fields:

```json
{
  "CONTACT_ID": 123,
  "FIRST_NAME": "Jane",
  "LAST_NAME": "Doe",
  "CONTACTINFOS": [
    {"TYPE": "EMAIL", "LABEL": "Work", "DETAIL": "jane@example.com"},
    {"TYPE": "PHONE", "LABEL": "Work", "DETAIL": "+14155551234"}
  ]
}
```

Leads and Organisations are flatter (Leads expose flat `EMAIL` / `PHONE` fields directly). This resource doesn't special-case object shape — that's `insightly_record_upsert`'s job (it nests `email`/`phone` into `CONTACTINFOS` only when `object_type: Contacts`).

## Convenience methods

- `get(path, params)` — GET relative to the pod base URL.
- `post(path, json_body)` — POST, creates a new record at the collection endpoint (e.g. `Contacts`).
- `put(path, json_body)` — PUT, updates an existing record. `path` must include the numeric id (e.g. `Contacts/123`).
- `search(object_type, field_name, field_value)` — `GET /{object_type}/Search?field_name=X&field_value=Y`.
- `upsert(object_type, search_field_name, search_field_value, body, id_field=None)` — search-then-create-or-update. Returns `{"action": "created"|"updated", "id": ...}`. **Not atomic** — see docstring.

## Pairs with

- **`insightly_record_upsert`** — reverse-ETL sink using this resource's `.upsert()`.
- **`insightly_ingestion`** — dlt-based bulk pull (uses its own inline dlt REST-API-source auth config, doesn't touch this resource).

## What doesn't work here

There's no OAuth flow to misconfigure — Insightly's v3.1 API is HTTP Basic only. The failure modes to watch for are (a) wrong `pod` (account lives on a different regional host), and (b) an API key that belongs to a user without permission on the target object type.
