# MCP Server Resource

Register one MCP server connection once and reference it by name from any MCP-aware
component (`mcp_tool_call`, `mcp_tool_picker`, and the MCP-capable agent components)
instead of repeating the same `name`/`type`/`url`/`command`/`env`/`headers`/`headers_env`
fields inline in every one of them.

## Why

Every MCP-aware component in this repo accepted an inline server spec. That's fine for a
one-off, but a project with several tools/agents hitting the SAME server (e.g. one shared
Dagster+ MCP endpoint) had to redeclare the whole connection on every single one of them --
and a UI wanting to show "which servers does this project use" had nowhere to look except
every consuming component's own config.

```yaml
type: dagster_community_components.MCPServerResourceComponent
attributes:
  resource_key: dagster_plus_mcp
  name: dgp
  type: http
  url: https://mcp.agent.dagster.cloud/mcp/
  headers:
    Dagster-Cloud-Organization: my-org
  headers_env:
    Authorization: DAGSTER_PLUS_BEARER
```

Then, in any MCP-aware component, instead of its own inline `server:` block:

```yaml
server_resource_key: dagster_plus_mcp
```

Exactly one of `server` (inline) or `server_resource_key` (this resource) is required --
both still work, so existing inline configs keep working unchanged.

## Listing its tools (`inspection_asset_name`)

A UI can't offer a tool-name allowlist for `allowed_tools` (on agentic_pipeline's `tool_use_loop`, and on the
litellm/openai/anthropic/gemini/vercel_ai_gateway/snowflake_cortex agent components) without actually running the
server to see what it exposes. Set `inspection_asset_name` to ALSO emit an asset that connects to the configured
server and lists its real tool names + descriptions as metadata:

```yaml
type: dagster_community_components.MCPServerResourceComponent
attributes:
  resource_key: dagster_plus_mcp
  name: dgp
  type: http
  url: https://mcp.agent.dagster.cloud/mcp/
  headers_env:
    Authorization: DAGSTER_PLUS_BEARER
  inspection_asset_name: dagster_plus_mcp_tools
```

Materializing `dagster_plus_mcp_tools` connects to the server (stdio/http/sse) and reports `server_name`,
`tool_count`, `tool_names` (a JSON array of bare names), and `tool_descriptions` (a JSON `{name: description}` map).

**The allowlist prefix is this resource's own `name` field, not `resource_key`.** `allowed_tools` matches against
the NAMESPACED tool name a consumer builds as `f"{name}__{tool.name}"`, where `name` is whatever that `mcp_servers:`
entry's own `name:` is (for `server_resource_key`, that's this resource's `.name`, e.g. `dgp` above -- not the
Dagster resource key `dagster_plus_mcp` it's registered under). So an allowlist for the server above is e.g.
`allowed_tools: ['dgp__list_runs', 'dgp__get_run*']`, built from `tool_names` reported here with `dgp__` prefixed.
