# NetSuite Resource

Register a `NetSuiteResource` wrapping NetSuite's **SuiteTalk REST Web Services** (`record/v1`) API for use by other Dagster components.

## Auth: OAuth 1.0a (Token-Based Authentication) -- NOT OAuth2

This is the single most common point of confusion when integrating with NetSuite's REST API: despite being REST (not SOAP), NetSuite's `record/v1` API still authenticates via **OAuth 1.0a Token-Based Authentication (TBA)** — the same signing scheme used by legacy SuiteTalk SOAP. There is **no bearer token, no client-credentials grant, and nothing to refresh** — the Token ID/Secret pair is long-lived until manually revoked in NetSuite.

Each request is HMAC-SHA256-signed using four credentials:

| Credential | Comes from |
|---|---|
| Consumer Key | NetSuite Integration record (Setup → Integration → Manage Integrations), with Token-Based Authentication enabled |
| Consumer Secret | Same Integration record |
| Token ID | An Access Token created for that Integration, scoped to a specific User + Role |
| Token Secret | Same Access Token |

This resource uses `requests_oauthlib.OAuth1` (not hand-rolled HMAC signing) with `signature_method="HMAC-SHA256"` and the account id as the OAuth `realm`.

## Installation

```bash
pip install requests requests-oauthlib
```

## Configuration

```yaml
type: dagster_component_templates.NetSuiteResourceComponent
attributes:
  resource_key: netsuite
  account_id: "1234567_SB1"       # sandbox account id (prod: no _SBn suffix)
  consumer_key_env_var: NETSUITE_CONSUMER_KEY
  consumer_secret_env_var: NETSUITE_CONSUMER_SECRET
  token_id_env_var: NETSUITE_TOKEN_ID
  token_secret_env_var: NETSUITE_TOKEN_SECRET
```

## Authentication setup

```bash
export NETSUITE_CONSUMER_KEY="..."
export NETSUITE_CONSUMER_SECRET="..."
export NETSUITE_TOKEN_ID="..."
export NETSUITE_TOKEN_SECRET="..."
```

1. **Setup → Integration → Manage Integrations → New** — create an Integration record, enable **Token-Based Authentication**, save. NetSuite shows the Consumer Key/Secret **once** — store them immediately.
2. **Setup → Users/Roles → Access Tokens → New** — create an Access Token for a User + Role scoped to that Integration. NetSuite shows the Token ID/Secret **once** — store them immediately.
3. The Role used must have REST Web Services permission and record-level permissions (e.g. Customer — View/Create/Edit) for whatever records your components read or write.

## Account id -> hostname

NetSuite REST hostnames lowercase the account id and replace `_` with `-`: account id `1234567_SB1` -> `https://1234567-sb1.suitetalk.api.netsuite.com/...`. This resource does that conversion internally — pass `account_id` exactly as shown in NetSuite (e.g. in Setup → Company → Company Information).

## Usage in other components

```yaml
attributes:
  resource_key: netsuite
```

Exposes a single low-level method: `request(method, path, json_body=None, params=None)`. Higher-level upsert logic (lookup-then-write) lives in consuming components (e.g. `netsuite_record_upsert`), not in this resource, per this repo's no-shared-logic convention.
