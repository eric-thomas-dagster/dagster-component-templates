```yaml
type: dagster_component_templates.OutreachResourceComponent

  resource_key: outreach_resource
  client_id_env_var: OUTREACH_CLIENT_ID
  client_secret_env_var: OUTREACH_CLIENT_SECRET

```

## Usage in other components

Once placed on the canvas, other components can reference this resource:

```yaml
attributes:
  resource_name: outreach_resource
```

## Authentication

Outreach uses standard OAuth2. This resource uses the **refresh_token grant**
(a long-running server-side pipeline refreshing an already-issued token),
**not** Outreach's separate "S2S" app-install flow (that one requires an RSA
keypair + a marketplace app install and is meant for multi-tenant apps, not a
single org's internal data pipeline).

You still need to obtain the *first* refresh_token once, out-of-band, via the
standard `authorization_code` grant (e.g. with Outreach's OAuth playground or
a short one-time script that completes the browser redirect flow). After
that, seed it into the env var below — this resource takes it from there.

```bash
export OUTREACH_CLIENT_ID="..."
export OUTREACH_CLIENT_SECRET="..."
export OUTREACH_REFRESH_TOKEN="..."   # from the one-time authorization_code exchange
```

**Rotation gotcha:** Outreach rotates the `refresh_token` on every exchange —
the token returned is not the one you sent, and the old one is invalidated.
This resource caches the newest refresh_token in-memory (per-process) so
repeated runs within one long-lived process keep working without needing the
env var updated. Refresh tokens are valid 14 days, so as long as this
resource refreshes at least that often, the chain never breaks. If the
process is restarted after 14+ days of inactivity, a fresh refresh_token must
be seeded into the env var again via a new `authorization_code` exchange.

Access tokens are cached in-memory and refreshed automatically ~60 seconds
before their ~2 hour expiry.
