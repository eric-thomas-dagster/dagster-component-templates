# PagerDuty Resource

Register a `PagerDutyResource` for use by other Dagster components. Ships
with **~20 convenience methods** covering PagerDuty's REST API v2 (for
incident + service + user + oncall management) AND Events API v2 (for
programmatic alert dispatch) so your assets can call
`context.resources.pd.list_incidents(...)` or `.send_alert(...)` without
touching HTTP.

## Installation

```bash
pip install requests
```

## Configuration

```yaml
type: dagster_community_components.PagerDutyResourceComponent
attributes:
  resource_key: pd
  api_token_env_var: PAGERDUTY_API_TOKEN
  from_email_env_var: PAGERDUTY_FROM_EMAIL
  # events_routing_key_env_var: PAGERDUTY_ROUTING_KEY   # optional (send_alert)
```

## Convenience methods

Any component with `required_resource_keys={"pd"}` can call these on `context.resources.pd`:

### Reads (REST API)

| Method | Purpose |
|---|---|
| `whoami()` | Return the authenticated user (owner of the token). |
| `list_services(query=..., team_ids=..., page_size=100)` | List services. |
| `iter_services(...)` | Auto-paginated variant. |
| `get_service(service_id)` | Retrieve a service. |
| `list_incidents(service_ids=..., statuses=..., incident_key=..., page_size=100)` | List incidents. |
| `iter_incidents(...)` | Auto-paginated variant. |
| `get_incident(incident_id)` | Retrieve a single incident. |
| `list_users(team_ids=..., page_size=100)` | List users. |
| `list_teams(page_size=100)` | List teams. |
| `list_schedules(page_size=100)` | List on-call schedules. |
| `list_escalation_policies(page_size=100)` | List escalation policies. |
| `list_oncalls(schedule_ids=..., since=..., until=...)` | Who's on-call right now (or in a time window). |

### Writes (REST API)

| Method | Purpose |
|---|---|
| `create_incident(service_id, title, details='', incident_key=..., urgency='high', priority_id=..., escalation_policy_id=..., assignee_user_id=...)` | Create an incident. `incident_key` = server-side dedup marker. |
| `update_incident(incident_id, status=..., title=..., urgency=..., priority_id=..., resolution=...)` | Patch an incident. |
| `acknowledge_incident(incident_id)` | Shortcut to `update_incident(status='acknowledged')`. |
| `resolve_incident(incident_id, resolution='')` | Shortcut to `update_incident(status='resolved')`. |
| `add_incident_note(incident_id, content)` | Add a note. |

### Events API v2

| Method | Purpose |
|---|---|
| `send_alert(summary, source, severity='error', dedup_key=..., custom_details=..., component=..., group=..., cls=...)` | Fire an alert via Events API v2. Requires `events_routing_key`. `dedup_key` = idempotent alerting. |
| `resolve_alert(dedup_key)` | Resolve an alert previously fired with the same `dedup_key`. |

### Escape hatch

`get_client()` returns an authenticated `requests.Session` for the REST API.

## Companion components

- **`PagerDutyIncidentUpsertComponent`** — mirror DataFrame rows into PagerDuty incidents (keyed by `incident_key` for server-side dedup).
- **`PagerDutyIncidentSensorComponent`** — poll incidents and fire runs on new triggers.
- **`PagerdutyHeartbeatJobComponent`** — periodic heartbeat via `send_alert`.

## Authentication

Two-part credential model — the REST API needs a token, and incident writes also need a `From:` email header (PagerDuty enforces this so incident-creation attribution is honest):

```bash
export PAGERDUTY_API_TOKEN=<your_pd_api_token>
export PAGERDUTY_FROM_EMAIL=you@company.com
# Optional: only needed for send_alert / resolve_alert
export PAGERDUTY_ROUTING_KEY=1234567890abcdef...
```

Generate a REST API token at *Integrations → API Access Keys → Create New API Key* in the PagerDuty UI (needs admin permissions). Get the `from_email` from the user whose account the token belongs to.

For alerting via Events API v2, get the routing key from a specific service's **Integrations** tab (create an "Events API v2" integration first).
