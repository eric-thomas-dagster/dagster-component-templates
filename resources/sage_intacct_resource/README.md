# Sage Intacct Resource

Register a `SageIntacctResource` wrapping Sage Intacct's **legacy XML Web Services gateway** (`xmlgw.phtml`) for use by other Dagster components. This is not a JSON REST API: every call is a hand-built XML envelope, parsed with stdlib `xml.etree.ElementTree` — no heavy SDK dependency.

## Installation

```bash
pip install requests
```


## Usage in other components

```yaml
attributes:
  resource_name: sage_intacct_resource
```

The resource exposes two methods for consumers:

- `read_by_query(object_name, fields, query=None, pagesize=100)` — runs the legacy `readByQuery` function, returning `{"records": [...], "count": N, "numremaining": M, "resultid": "..."}`.
- `read_more(resultid)` — continues a prior `readByQuery` using the `resultId` it returned; loop until `numremaining == 0`.

## Authentication

Sage Intacct's XML gateway requires **two independent layers of credentials**:

1. **Web Services credentials** — a `senderid` + password pair you register with Sage support, then explicitly whitelist on the target company (*Company > Company Info > Security > Web Services Authorizations*). These go in the outer `<control>` block of every request.
2. **Company/user credentials** — `userid` + `companyid` + password for an API-enabled Intacct user (plus an optional `locationid` for multi-entity companies). These go in `<operation><authentication><login>`.

```bash
export INTACCT_SENDER_PASSWORD="your-webservices-sender-password"
export INTACCT_USER_PASSWORD="your-intacct-user-password"
```

Both credential layers are validated independently by Intacct and surface as separate failure points in the XML response: a `<control><status>failure</status>` means the sender credentials themselves were rejected (request never reached company-level auth); `<operation><authentication><status>failure</status>` means the sender passed but the company/user login failed; `<operation><result><status>failure</status>` means auth succeeded but the function call itself errored (bad object name, malformed query, etc).

## API notes

- Endpoint: `POST https://api.intacct.com/ia/xml/xmlgw.phtml`, body is a raw XML document (`Content-Type: application/xml`), **not** form-encoded or JSON.
- Query semantics use the legacy `readByQuery` function (`object` + comma-separated `fields` + a single SQL-like `query` where-clause string, e.g. `"WHENCREATED >= '01/01/2026'"`) rather than the newer structured `query` function, since its pagination is simpler to drive generically.
- Pagination: the first `readByQuery` response includes a `resultId` plus `numremaining` on the `<data>` element; keep calling `readMore` with that `resultId` until `numremaining` reaches `0`.
- Dates in Intacct query clauses use `MM/DD/YYYY` format, not ISO-8601.
- Sage has designated the XML API "legacy" in favor of a newer REST API, but the XML gateway remains fully supported for existing integrations and is the only option without a REST API contract/beta enrollment.
