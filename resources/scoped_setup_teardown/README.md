# ScopedSetupTeardown

Registers a Dagster resource with real setup/teardown lifecycle hooks — the Airflow setup/teardown task pattern equivalent. Any asset or op that declares `required_resource_keys={resource_key}` gets `setup` run once before it, and `teardown` run once after — **even if that asset/op fails**. `teardown` does **not** run if `setup` itself fails (Dagster's own documented contract).

Confirmed real gap before building: no resource anywhere in this repo overrides `teardown_after_execution`. Verified live (a real `dg.materialize()` run with a deliberately failing asset, before writing this component) that `ConfigurableResource.setup_for_execution`/`.teardown_after_execution` behave exactly as Dagster's own docstring promises — nothing invented here, just wrapped in a reusable component.

## Python callables

```yaml
type: dagster_community_components.ScopedSetupTeardownComponent
attributes:
  resource_key: db_tunnel
  setup_callable_path: myproject.infra:open_tunnel      # returns a value, e.g. a connection handle
  teardown_callable_path: myproject.infra:close_tunnel  # receives that value, if it declares a parameter
```

```python
# myproject/infra.py
def open_tunnel():
    tunnel = start_ssh_tunnel(...)
    return tunnel  # passed to close_tunnel below

def close_tunnel(tunnel):
    tunnel.stop()
```

`setup`'s return value is handed to `teardown` as its one positional argument **if teardown's own signature declares a parameter** — a teardown declared with no parameters is just called with none. This is in-process value passing (both run inside the same Dagster process, during one resource's lifetime), simpler than Airflow's cross-task XCom indirection for the same pattern.

## Shell commands

```yaml
type: dagster_community_components.ScopedSetupTeardownComponent
attributes:
  resource_key: db_tunnel
  setup_command: "./scripts/open_ssh_tunnel.sh"
  teardown_command: "./scripts/close_ssh_tunnel.sh"
  env_vars:
    TUNNEL_HOST: db.internal
```

Shell commands can't receive a Python object, so there's no value passed from `setup_command` to `teardown_command` — each runs independently, via `bash -c`.

Mix and match: `setup_callable_path` with `teardown_command`, or vice versa, both work.

## Using the resource

```python
@dg.asset(required_resource_keys={"db_tunnel"})
def my_asset(context):
    ...  # the tunnel is already open by the time this runs
```

Any number of assets/ops can declare the same `resource_key` — Dagster initializes the resource (running `setup`) once per run, the first time it's needed, and tears it down once at the end.
