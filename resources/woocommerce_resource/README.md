# WooCommerce Resource

Register a `WooCommerceResource` — a self-contained WooCommerce REST API v3 workhorse (raw HTTP + HTTP Basic auth) — for use by other Dagster components.

## Authentication — HTTP Basic auth, not OAuth2

WooCommerce's REST API v3 authenticates with the **consumer key as the HTTP Basic-auth username and the consumer secret as the HTTP Basic-auth password**, sent over HTTPS:

```
Authorization: Basic base64(consumer_key:consumer_secret)
```

This is a static, long-lived credential pair — **not** an OAuth2 client-credentials / refresh-token flow (unlike this repo's `outreach_resource`, for example). There's no token exchange, no expiry, and no refresh step. You generate the key/secret pair once from the WooCommerce admin and use it directly as HTTP Basic auth on every request (this resource passes `auth=(consumer_key, consumer_secret)` to `requests`, rather than building the header manually).

(WooCommerce also documents a query-string fallback, `?consumer_key=X&consumer_secret=Y`, needed only when a server mis-parses the Authorization header over SSL, and a separate OAuth1-over-query-string scheme for plain-HTTP, non-HTTPS stores. Both are out of scope here — this resource implements HTTP Basic auth as the primary/only mode, matching this repo's `woocommerce_ingestion` component.)

## Example

```yaml
type: dagster_component_templates.WooCommerceResourceComponent
attributes:
  resource_key: woocommerce
  store_url: https://mystore.com
  consumer_key_env_var: WOOCOMMERCE_CONSUMER_KEY
  consumer_secret_env_var: WOOCOMMERCE_CONSUMER_SECRET
```

## When to use

- Any component or custom asset code that needs to read or write WooCommerce Products (or other WooCommerce REST resources) via raw HTTP.
- Pairs with `woocommerce_product_upsert` for reverse-ETL product sync, and with `woocommerce_ingestion` for bulk reads.

## Prerequisites

1. **A WooCommerce REST API key** — WooCommerce Admin -> Settings -> Advanced -> REST API -> Add key.
2. Grant **Read/Write** permissions (Read-only is enough if you only ever read).
3. Copy the generated **Consumer key** and **Consumer secret** into environment variables — WooCommerce only shows the secret once at creation time.

## Pairs with

- **`woocommerce_product_upsert`** — reverse-ETL sink (search-by-SKU upsert) built on this resource.
- **`woocommerce_ingestion`** — the READ-side counterpart (dlt-based bulk pull), which authenticates the same way but configures `auth: {type: http_basic, ...}` directly in its dlt REST API source config rather than going through this resource.

## Behavior + gotchas

- **SKU is the natural merge key** — WooCommerce Products have no native upsert endpoint; `upsert_product_by_sku` does a `GET /products?sku=X` search, then `PUT`/`POST`.
- **Retries** — the resource retries on `429` (honoring `Retry-After`) and `5xx` responses, up to `max_retries` (default 3), with exponential backoff on transport errors and 5xx.
- **Soft deletes** — `delete_product` passes `force=True` by default (WooCommerce otherwise moves products to trash instead of permanently deleting).
- **Batch fast-path** — `batch_products(create=..., update=..., delete=...)` wraps `POST /products/batch` (up to 100 items per array, per WooCommerce's documented limit) for callers that need bulk throughput instead of the default per-row search-then-write.
- **HTTPS required** — HTTP Basic auth over plain HTTP is rejected by WooCommerce; `store_url` must be an `https://` URL in production.
