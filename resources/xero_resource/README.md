# Xero Resource

Register a `XeroResource` wrapping the **Xero Accounting API** for use by other Dagster components.

## Auth: OAuth 2.0 refresh-token flow + `Xero-tenant-id` on every request

Xero auth is OAuth2 refresh-token, but the token refresh call — `POST https://identity.xero.com/connect/token` — posts `client_id`/`client_secret`/`refresh_token` as **regular form fields**, not HTTP Basic auth (a difference from QuickBooks, which Basic-auths the same call).

Xero is **multi-tenant per OAuth2 connection**: one access token can be authorized against multiple orgs ("tenants"), and every API call must carry an `Xero-tenant-id` header. The tenant id isn't embedded in the access token — it's discovered via `GET https://api.xero.com/connections`, which lists every tenant the token is authorized for. This resource auto-discovers the first connected tenant (caching it), or you can set `tenant_id` explicitly — recommended if your app is connected to more than one org, since discovery order is otherwise undefined.

### Refresh-token rotation caveat

Like QuickBooks, Xero **rotates the refresh token** on every refresh for public/PKCE OAuth2 apps (~60-day refresh-token lifetime). This resource caches the in-memory **access** token for its ~30min lifetime within a process, but does **not** persist newly-rotated **refresh** tokens anywhere — pair this with an external secret-manager write-back or scheduled re-auth job in production, or access eventually fails with `invalid_grant`.

## Configuration

```yaml
type: dagster_component_templates.XeroResourceComponent
attributes:
  resource_key: xero
  client_id_env_var: XERO_CLIENT_ID
  client_secret_env_var: XERO_CLIENT_SECRET
  refresh_token_env_var: XERO_REFRESH_TOKEN
  # tenant_id: "a1b2c3d4-..."
```

## Authentication setup

```bash
export XERO_CLIENT_ID="..."
export XERO_CLIENT_SECRET="..."
export XERO_REFRESH_TOKEN="..."
```

1. Create an app at [developer.xero.com](https://developer.xero.com/app/manage) and complete the OAuth2 authorization-code flow once (interactively, with the `accounting.contacts` scope) to obtain an initial refresh token.
2. Store the Client ID/Secret and that initial refresh token as env vars / secrets.
3. See the rotation caveat above.

## Usage in other components

```yaml
attributes:
  resource_key: xero
```

Exposes `request(method, path, json_body=None, params=None)`. Higher-level upsert logic (lookup-then-create-or-update) lives in consuming components (e.g. `xero_contact_upsert`), not in this resource, per this repo's no-shared-logic convention.
