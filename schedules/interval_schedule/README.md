# IntervalSchedule

Friendlier than cron when you just want "every 30 minutes". Generates a cron expression under the hood, plus the same job + `ScheduleDefinition` shape as `cron_schedule`.

Two modes — same field surface as [`cron_schedule`](../cron_schedule/README.md):

1. **Un-partitioned** (default): `ScheduleDefinition(job=..., cron_schedule=<derived from every>)`.
2. **Time-partitioned** (opt-in via `partition_type` / `partition_dimensions`): `build_schedule_from_partitioned_job`. Each tick auto-targets the most-recent finished partition. `every` MUST match the partition cadence exactly (`every: 1h` ↔ hourly, `every: 1d` ↔ daily, etc.).

## Supported `every` values

| Value | Meaning | Cron generated (un-partitioned mode) |
|---|---|---|
| `<N>m` | every N minutes (N < 60) | `*/N * * * *` |
| `<N>m` | every N minutes (N ≥ 60) | `0 */(N//60) * * *` |
| `<N>h` | every N hours | `0 */N * * *` |
| `<N>d` | every N days | `0 0 */N * *` |
| `1w` | weekly (Sunday 00:00) | `0 0 * * 0` |
| `1mo` | monthly (1st 00:00) | `0 0 1 * *` |

## Un-partitioned example

```yaml
type: dagster_community_components.IntervalScheduleComponent
attributes:
  schedule_name: poll_inventory
  every: 30m
  asset_keys: [inventory_snapshot, stockout_alerts]
  execution_timezone: America/New_York
  default_status: STOPPED
  tags:
    team: ops
```

## Partitioned-job mode

When a time-based partition field (`partition_type` / `partition_dimensions`) is set, the component switches to `build_schedule_from_partitioned_job`. Each tick fires against the most-recent finished partition — without this switch, a `ScheduleDefinition` against a partitioned asset job errors with "no partition key provided" on every tick.

`every` must match the partition cadence exactly:

| every | partition_type | Fires |
|---|---|---|
| `1h` | `hourly` | Top of every hour |
| `1d` | `daily` | Midnight every day |
| `1w` | `weekly` | Sunday 00:00 |
| `1mo` | `monthly` | 1st of the month 00:00 |

Anything else (`every: 15m` + `hourly`, `every: 2h` + `hourly`, etc.) raises `ValueError` at load time — the schedule would over- or under-fire relative to the partition boundaries, which is a misconfiguration.

```yaml
type: dagster_community_components.IntervalScheduleComponent
attributes:
  schedule_name: hourly_orders_pipeline
  every: 1h
  asset_keys: [python_hourly_orders_for_pipe, orders_to_s3]
  partition_type: hourly
  partition_start: "2026-05-26-00:00"
  default_status: RUNNING
```

`partition_type: static` and `partition_type: dynamic` raise `ValueError` in this path — `build_schedule_from_partitioned_job` needs a time-based partitions_def.

## Constraints in the partitioned path

`build_schedule_from_partitioned_job` REJECTS `cron_schedule` and `execution_timezone` for time-partitioned jobs (Dagster raises at load time). This component handles both:

- **cron shape**: derived from `every` + the partition cadence. In partitioned mode, `every` must match the cadence, so the fire time is always the natural period boundary (`:00`).
- **timezone**: Dagster uses the partitions_def's timezone (defaults UTC). The component's `execution_timezone` field is applied in the un-partitioned path only; in the partitioned path it's silently ignored (baked into the partitions_def instead).

If you need a non-boundary fire time (e.g. hourly partitions firing at `:15`), use [`cron_schedule`](../cron_schedule/README.md) instead — it accepts a full cron expression that gets decomposed into `minute_of_hour` / `hour_of_day` args.
