# Anthropic Batch Status Sensor

Watches the materialization metadata of an `anthropic_batch_submit` asset for a `batch_id`, re-checks that batch's **LIVE** `processing_status` directly against the Anthropic API (never trusting the possibly-stale status snapshot stamped into the watched asset's own metadata), and fires a run against `job_name` once the batch has `processing_status == "ended"`.

Third of three components that make up the Anthropic Message Batches pipeline:

- `anthropic_batch_submit` — submits the batch, writes `batch_id` to its materialization metadata.
- **`anthropic_batch_status_sensor`** (this component) — polls for completion, fires the downstream run.
- `anthropic_batch_results` — fetches and parses the finished batch's results.

```yaml
type: dagster_component_templates.AnthropicBatchStatusSensorComponent
attributes:
  sensor_name: support_ticket_batch_done
  watch_asset_key: support_ticket_batch
  job_name: support_ticket_batch_results_job
  results_asset_key: support_ticket_batch_results
  api_key_env_var: ANTHROPIC_API_KEY
  minimum_interval_seconds: 60
  default_status: running
```

## Wiring `results_asset_key` correctly (read this before deploying)

A naive port of the `qlik_compose_workflow_status_sensor` template (this component's structural template) would emit:

```python
run_config={"ops": {"config": {"batch_id": batch_id}}}
```

This is **wrong** for an `@asset`-backed op: `"config"` is only a valid key under `"ops"` if the target op is literally named `"config"`. For an asset, Dagster names the underlying op after the asset's key, rendered through `AssetKey.to_python_identifier()` — e.g. `ai__anthropic_batch_results` for asset key `ai/anthropic_batch_results`, not the literal string `"config"`. Using the literal-`"config"` shape would silently produce a run where the `anthropic_batch_results` asset's `config.batch_id` is always empty — exactly the bug already found and fixed in this repo's `precisely_job_sensor`.

To avoid resurrecting that bug, this sensor takes a dedicated **`results_asset_key`** field (the `anthropic_batch_results` asset's `asset_name`, used only to derive the correct op name via `AssetKey.to_python_identifier()` — never looked up at sensor-eval time) and builds `run_config` from that derived name instead. Set `results_asset_key` to exactly the `asset_name` configured on the paired `anthropic_batch_results` component.

`job_name` is separate — it's the actual Dagster job name passed to `@sensor(job_name=...)`, wrapping the `anthropic_batch_results` asset (e.g. via `dg.define_asset_job(name=job_name, selection=[asset_key])`).

## Why the sensor re-checks live status instead of trusting metadata

`anthropic_batch_submit` stamps a `processing_status` into its own materialization metadata at the moment it last ran — but that snapshot can go stale the instant it's written (a batch in `in_progress` keeps processing after the submit asset's run finishes). This sensor always calls `client.messages.batches.retrieve(batch_id)` itself and acts on the fresh response, the same principle `qlik_compose_workflow_status_sensor` uses re-polling Compose's live workflow state rather than trusting any cached value.

## Cursor-based dedup

Once a batch is found `ended`, the sensor fires a `RunRequest` keyed on `run_key=f"{batch_id}|ended"` and advances the cursor to that same fingerprint. A later tick that sees the same ended batch (nothing new to process) skips instead of re-firing.
