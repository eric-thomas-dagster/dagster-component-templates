# failed_run_agent_sensor

On a failed run, launches `asset_keys` (a bug-fixer asset + its Slack-reply asset, typically) with the failed run's id on the launched run's tags, posts an announcement to Slack, and puts the run's Slack thread on the launched run's tags so [`slack_reply`](../../assets/sinks/slack_reply) answers in it.

Built on `@dg.run_failure_sensor` (not a plain sensor) -- which only ever accepts a fixed `request_job`, never an asset selection, so this component builds its own `dg.define_asset_job(f"{sensor_name}_job", selection=asset_keys)` internally and passes that as `request_job`.

## Cooldown per (job, error signature)

Same append-only, one-file-per-event rate-limiter [`RunFailureRemediationComponent`](../../assets/ai/run_failure_remediation) already uses, under `<evidence_dir>/_state/ratelimit/`: an error signature is the job name + root error class + the message with ids/numbers normalized + the failed step keys, hashed. `max_triage_per_hour` bounds how many DISTINCT signatures get triaged per rolling hour; `cooldown_minutes` suppresses re-triaging the SAME signature (a flapping job failing the same way repeatedly) for that long after the first one.

This is the one place in the whole engineering-agents component family that genuinely needs a file -- it bounds a rate across many never-repeating run ids, which Dagster's own `RunRequest(run_key=...)` dedup (one run per distinct key) can't express by itself.

## Tags on the launched run

`eng/failed_run_id`, `eng/error_signature`, `slack/channel`, `slack/thread_ts` -- read these in `asset_keys`' own assets to know which run to look into and which thread to reply in.

## Filtering

`code_location_names` / `job_names` / `required_tags` -- any combination, all optional (unset = monitor everything). A run must satisfy all three that are set.

## Pod memory

The run this sensor launches is an LLM agent asset -- a code location's default container memory limit (often 1G) is sized for ordinary pipeline steps, not an LLM call plus tool-use loop. An under-provisioned run gets OOMKilled (exit 137), which Dagster+ reports as "Run has not completed but K8s job has no active pods" rather than anything that looks like a memory error. Give the launched job a few GB via `container_context.k8s.run_k8s_config.container_config.resources.limits.memory` -- see [`github_pull_request_agent_sensor`'s README](../github_pull_request_agent_sensor#deployment-notes-from-a-real-dagster-hybrid-kubernetes-deployment) for the full example.
