# github_pull_request_agent_sensor

On each new pull request, or a new head commit on an existing one, launches `asset_keys` (an agent asset + its Slack-reply asset, typically) with the PR number on the run's tags, and announces the PR in Slack with approve/reject reactions seeded -- the thread stays open for `slack_reply` to answer in, and for [`slack_pr_approval_watcher`](../slack_pr_approval_watcher) to turn a reaction into a recorded GitHub review (and optionally a merge).

A plain sensor, not `@dg.run_failure_sensor` (which only accepts a fixed `request_job`, never an asset selection) -- this one fires `RunRequest(asset_selection=...)` directly, the same way [`linear_issue_sensor`](../linear_issue_sensor)/[`github_event_sensor`](../github_event_sensor) already do in this repo.

## What ships

One sensor. Per tick:

1. Lists the repo's open pull requests (`GET /pulls`).
2. Compares each one's head commit against this sensor's own cursor (a `{pr_number: head_sha}` map) -- new or changed only.
3. For each: posts to Slack with the approve/reject emoji seeded, embedding the PR number (and, if set, `approver_allowlist`) as the message's own hidden metadata -- not a file. Fires `RunRequest(run_key=f"pr-{number}-{sha[:7]}", asset_selection=asset_keys, tags={"eng/pr_number", "slack/channel", "slack/thread_ts"})`.
4. Updates the cursor, pruning entries for PRs that are no longer open.

## Tags on the launched run

`eng/pr_number` (the PR number as a string), `slack/channel`, `slack/thread_ts` -- read these in `asset_keys`' own assets (e.g. via `context.run.tags`) to know which PR to review and which thread to reply in.

## No shared state file with `slack_pr_approval_watcher`

The two sensors need to agree on "which Slack message reviews which PR", but they don't share a document -- the config rides inside the posted message's own hidden metadata (`chat.postMessage`'s `metadata` parameter, read back via `conversations.history(include_all_metadata=true)`), the same mechanism [`slack_approval_gate`](../../assets/ai/slack_approval_gate)'s `message_metadata` correlation mode uses. Two sensors rewriting one shared file is a real race (confirmed against a real sandbox that hit it); this sidesteps the class of bug entirely.

## Slack bot scopes

`chat:write`, `reactions:write`, and `channels:history`/`groups:history` (so `slack_pr_approval_watcher` can discover the posted message's metadata later).

## Deployment notes (from a real Dagster+ hybrid-Kubernetes deployment)

- **Pod memory.** The run this sensor launches is an LLM agent asset, not this sensor itself -- a code location's default container memory limit (commonly 1G) is sized for ordinary pipeline steps, not an LLM call plus tool-use loop. An under-provisioned agent run gets OOMKilled (exit 137), which Dagster+ reports as "Run has not completed but K8s job has no active pods" -- a message that reads like an agent-framework problem but is actually a pod sizing one. Give the launched job a few GB, e.g. in `dagster_cloud.yaml` or the code location's `container_context`:
  ```yaml
  container_context:
    k8s:
      run_k8s_config:
        container_config:
          resources:
            limits:
              memory: "4Gi"
  ```
  4Gi is a reasonable starting point; raise it if an agent run still OOMs.
- **Branch deployments.** `skip_in_branch_deployments` (default `true`) keeps a branch deployment's copy of this sensor from running at all -- without it, a branch deployment announces every PR a second time in the same Slack channel and launches a second review run alongside the full deployment's. `sensors/slack_pr_approval_watcher` has the same option for the same reason.
- **Tick timeouts.** A Dagster+ sensor tick times out at 60 seconds. `announcements_per_tick` (default `5`) bounds how many PRs get announced (one Slack post + one `RunRequest` each) in a single tick -- a large backlog (e.g. the first tick after turning this sensor on, or after a long outage) is spread across several ticks instead of timing the tick out partway through.
