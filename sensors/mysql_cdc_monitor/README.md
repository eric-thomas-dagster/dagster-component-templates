# MySQL CDC Monitor Sensor

Micro-batch change-data-capture source reading MySQL's binary log (binlog): resumes from a stored position, classifies every row change as insert/update/delete, batches a tick's changes into one run, and stops once it has caught up to the server's current position.

## Purpose

This is the ongoing-changes half of a CDC pipeline for MySQL/MariaDB — not a long-running streaming process, a **poll-catch-up-stop sensor** like this registry's `s3_monitor`/`kafka_monitor`. Perfect for:

- Replacing a StreamSets "MySQL Binary Log" origin when migrating a continuous CDC pipeline to Dagster
- Feeding a CDC-apply sink (insert/update/delete-by-key) with exactly the row changes it needs to apply
- Keeping a warehouse staging table in sync with an OLTP MySQL database without full-table re-reads

**Not built for:** an initial load of existing rows. Pair this sensor with a separate one-time snapshot (e.g. this registry's own full-table ingestion components) to seed the target before CDC takes over — `on_first_run: start_now` (the default) deliberately skips all historical binlog and begins from the server's current position.

## How it works

1. **Resolve tracked tables.** `table_patterns` are fnmatch-style globs (`orders`, `order_items_*`) matched against bare table names in `database`, re-resolved against `INFORMATION_SCHEMA.TABLES` on every tick — a new table matching a wildcard is picked up automatically, no restart needed.
2. **Connect to the binlog stream** (via `mysql-replication`'s `BinLogStreamReader`) from the stored position — binlog file+position by default (`position_mode: binlog`), or a GTID set (`position_mode: gtid`, requires `gtid_mode=ON` on the server).
3. **Read until caught up, then stop.** The reader runs with `blocking=False`: once the server has no more binlog data to send, it returns EOF and the sensor's loop ends naturally — it never blocks waiting for new writes. This is the "micro-batch" behavior: one tick processes whatever's available right now, nothing more.
4. **Classify every row change** by event type:
   - `WriteRowsEvent` → `_cdc_op: "insert"`, `after` populated, `before: null`
   - `UpdateRowsEvent` → `_cdc_op: "update"`, both `before` and `after` populated
   - `DeleteRowsEvent` → `_cdc_op: "delete"`, `before` populated, `after: null`
   - `PartialUpdateRowsEvent` (MySQL 8.0.18+'s `binlog_row_value_options=PARTIAL_JSON` optimization for JSON-column updates) → also classified as `_cdc_op: "update"`, same shape as a regular update
5. **Emit one `RunRequest` per tick** (when there are changes) carrying the whole batch, and persist the new position as the sensor's cursor.

## Output shape (`run_config`)

```python
{
  "ops": {
    "config": {  # or op_name, if set
      "database": str,
      "tables": list[str],       # distinct table names seen this tick
      "event_count": int,
      "events": [
        {
          "table": str,
          "_cdc_op": "insert" | "update" | "delete",
          "before": dict | None,  # column name -> value, pre-image (update/delete)
          "after": dict | None,   # column name -> value, post-image (insert/update)
          "log_file": str,
          "log_pos": int,
        },
        # ...
      ],
    }
  }
}
```

`_cdc_op` is this registry's convention for a CDC-apply sink to key its insert/update/delete handling on — align any new CDC-apply sink's column naming to `_cdc_op` with these three string values for direct compatibility.

**Column value coercion:** MySQL column values (`datetime`, `date`, `Decimal`, `bytes`) are coerced to plain strings before they're embedded in `run_config`, since none of those types round-trip through Dagster's run-config JSON serialization. A downstream asset that needs the original type back (e.g. a `Decimal` for a monetary column) must re-parse that specific column itself — this is a real, permanent limitation of passing row data through `run_config`, not a bug to be fixed later.

## Required MySQL privileges

```sql
GRANT REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO 'repl_user'@'%';
GRANT SELECT ON `sales`.* TO 'repl_user'@'%';  -- for the INFORMATION_SCHEMA table-resolution query
```

Binary logging must be enabled on the server (`log_bin = ON`) with row-based format (`binlog_format = ROW` — `STATEMENT` or `MIXED` format do not carry the actual row data this sensor needs).

## Honest limitations

- **Cross-schema table-name collisions.** MySQL's own replication-protocol filters (`only_tables`/`only_schemas`) match bare names independently, not as a joint `(schema, table)` tuple — if two different schemas both have a table named `orders`, a single sensor configured with `only_tables=["orders"]` would match both. This component sidesteps that entirely by tracking exactly **one** `database` per sensor instance; declare one sensor per schema if you track more than one.
- **GTID mode tracks its own advancing position, not the reader's.** `BinLogStreamReader`'s own `auto_position` attribute is write-once (whatever GTID set it was constructed with) and is never updated as transactions are consumed, unlike `log_file`/`log_pos`. This sensor tracks every `GtidEvent` seen during a tick itself and merges it into the stored GTID set via `GtidSet.merge_gtid` (the library's own range-merging logic, not hand-rolled), so the stored position correctly advances tick over tick. On a quiet tick with no new transactions, the stored set is left unchanged.
- **Purged binlog position fails loudly, by design.** If the stored file+position (or GTID range) has already aged out of the server's binlog retention, this sensor raises a clear `skip_reason` telling you to re-snapshot and reset the cursor — it will never silently skip the gap and claim to be caught up.
- **Not validated against a real MySQL server with live binlog replication in this repo's CI** (no such server is available here) — tests mock `mysql-replication`'s `BinLogStreamReader` at the library boundary; the event-classification, table-pattern-resolution, cursor-parsing, and error-handling logic around it are exercised for real. Validate against a real server/pipeline before production use.

## Example

```yaml
type: dagster_community_components.MySQLCDCMonitorSensorComponent
attributes:
  sensor_name: orders_cdc_sensor
  host: db.internal
  port: 3306
  username: repl_user
  password_env_var: MYSQL_REPL_PASSWORD
  server_id: 1001
  database: sales
  table_patterns:
    - orders
    - order_items_*
  job_name: apply_sales_cdc_job
  minimum_interval_seconds: 30
```

`server_id` must be unique among every replication client connected to this MySQL server (including other instances of this same sensor) — picking a colliding id causes MySQL to disconnect one of the two clients.

## Requirements

- Python 3.8+
- Dagster 1.5.0+
- `mysql-replication>=1.0.0` (import name `pymysqlreplication`)
- `PyMySQL>=1.0.0`
- A MySQL/MariaDB server with `log_bin=ON`, `binlog_format=ROW`, and a user granted `REPLICATION SLAVE`/`REPLICATION CLIENT`
