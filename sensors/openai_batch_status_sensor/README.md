# OpenAI Batch Status Sensor

> **🔑 API key required.** Set `OPENAI_API_KEY` (or point `api_key_env_var` at an alternate env var).

Watches an `openai_batch_submit` asset's materialization metadata for a `batch_id`, polls OpenAI's Batch API for its **live** current status, and fires a `RunRequest` once the batch reaches a terminal state (`completed` / `failed` / `expired` / `cancelled`).

## Purpose

Middle component of the `openai_batch_submit` → `openai_batch_status_sensor` → `openai_batch_results` trio. The submit asset's own Dagster materialization metadata can be stale by the time this sensor runs (the batch can take up to 24 hours), so this sensor always re-polls `client.batches.retrieve(batch_id)` for the live status rather than trusting whatever status was stamped at submit time — the same principle `qlik_compose_workflow_status_sensor` (this component's structural template) uses for re-polling Compose's live workflow state.

Structural template: `sensors/qlik_compose_workflow_status_sensor/component.py`.

## Cursor-based dedup

Once a batch is terminal, its `f"{batch_id}|{status}"` fingerprint is compared against the sensor's cursor (exactly like qlik's `fingerprint` pattern) so the same completed batch never fires twice.

## Why `results_asset_key` exists (a deliberate addition beyond the bare qlik shape)

A literal port of qlik's run_config shape would emit `run_config={"ops": {"config": {"batch_id": batch_id}}}` — but `"config"` is only a valid key there if the target op is literally named `"config"`. For an `@asset`-backed op like `openai_batch_results`, the real op name is the asset key rendered through `AssetKey.to_python_identifier()` (e.g. `"ai__openai_batch_results"` for key `ai/openai_batch_results`), not the string `"config"`. Using the literal-`"config"` shape here would silently produce a run where the results asset's `config.batch_id` is always `None` — this is the *exact* bug this repo already found and fixed in `sensors/precisely_job_sensor/component.py` (its comment: *"The old run_config={'ops': {'config': {...}}} treated the literal string 'config' as an op name, so downstream ops' context.op_config was always empty"*).

Rather than reintroduce that bug, this sensor takes `results_asset_key` — the asset key of the target `openai_batch_results` asset — and derives the correct op name from it automatically at `build_defs` time (`AssetKey.from_user_string(results_asset_key).to_python_identifier()`). This was verified empirically against the installed `dagster` package before shipping, not assumed.

```yaml
type: dagster_component_templates.OpenaiBatchStatusSensorComponent
attributes:
  sensor_name: support_reply_batch_done
  watch_asset_key: support_reply_batch
  job_name: fetch_support_reply_results
  results_asset_key: support_reply_results
```
