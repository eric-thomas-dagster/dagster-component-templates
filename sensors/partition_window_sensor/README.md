# PartitionWindowSensor

Waits for a **window** of an upstream asset's partitions, then triggers a downstream job —
Airflow 3.3's `RollupMapper`/`FanOutMapper` + `DayWindow`/`WeekWindow`/`MonthWindow`/
`SegmentWindow` + `WaitForAll`/`MinimumCount`, verified against Airflow's own official
`example_asset_partition` example DAG source (`airflow.sdk`), not guessed.

## Why a sensor, not a Dagster `PartitionMapping`

Dagster's `AutomationCondition.all_deps_match(...)` is documented to be true "if **at
least one** partition of... the target's dependencies" matches — confirmed both live and
via its own docstring — not "ALL mapped partitions of this one dependency." There is no
built-in Dagster primitive for "require ALL (or N of M) partitions within one
partition-mapped dependency before firing," which is exactly what Airflow's
`RollupMapper`/`WaitForAll`/`MinimumCount` model. This sensor checks
`instance.get_materialized_partitions()` directly instead.

## Two modes, mirroring Airflow's two mapper families

- **`mode: rollup`** (`RollupMapper`, N upstream partitions → 1 downstream run): waits
  until a window of upstream keys is materialized (fully, or partially per
  `wait_policy`), then fires ONE `RunRequest` for the rolled-up key. Fires once per
  window (tracked in the sensor's own cursor).
- **`mode: fan_out`** (`FanOutMapper`, 1 upstream partition → N downstream runs): on each
  newly materialized upstream partition, fires one `RunRequest` per downstream key in its
  window.

## `window_type`

- **`segment`** — an explicit, fixed categorical key list (`segment_keys`; Airflow's
  `SegmentWindow`). Not time-based.
- **`day` / `week` / `month`** — a time-based window (Airflow's `Day`/`Week`/`MonthWindow`).
  Upstream keys are parsed via `upstream_key_format` and truncated to a day / week
  (Monday-start) / month anchor; the rolled-up (or, for `fan_out`, the fanned-out)
  key(s) are formatted via `downstream_key_format`.

## Examples, matching the real Airflow DAGs they translate

```yaml
# segment_region_stats_rollup: wait for us, eu, AND apac before rolling up
type: dagster_community_components.PartitionWindowSensorComponent
attributes:
  sensor_name: segment_region_stats_rollup
  upstream_asset_key: regional/region_raw_stats
  job_name: rollup_regional_stats_job
  mode: rollup
  window_type: segment
  segment_keys: [us, eu, apac]
  wait_policy: all
```

```yaml
# segment_region_stats_early_rollup: fire once 2 of 3 regions have arrived
attributes:
  mode: rollup
  window_type: segment
  segment_keys: [us, eu, apac]
  wait_policy: minimum_count
  minimum_count: 2
```

```yaml
# daily_team_a_rollup: hourly upstream -> daily downstream, wait for all 24 hours
attributes:
  mode: rollup
  window_type: day
  upstream_key_format: "%Y-%m-%d-%H:%M"
  downstream_key_format: "%Y-%m-%d"
```

```yaml
# trailing_week_inference: weekly upstream key -> 7 daily runs ENDING at that key
attributes:
  mode: fan_out
  window_type: week
  max_downstream_keys: 7
  direction: backward
  upstream_key_format: "%Y-%m-%d"
  downstream_key_format: "%Y-%m-%d"
```

```yaml
# scatter_live_region_to_segments: 1 region materializes -> 1 same-named downstream run
attributes:
  mode: fan_out
  window_type: segment
  segment_keys: [us, eu, apac]
```

## `mode: fan_out`'s anchor is the raw upstream key, not a truncated one

Unlike `rollup` (which truncates to a day/week/month ANCHOR before checking completeness),
`fan_out` steps directly from the materialized upstream key itself: `direction: forward`
starts AT that key; `direction: backward` ends AT it — matching the real example DAG's own
comment, "fanning out to the seven days ending at the key." If your upstream key itself
needs truncating first (e.g. Airflow's own `StartOfWeekMapper()` ahead of a `FanOutMapper`),
do that truncation before this sensor sees the key (e.g. in whatever materializes the
upstream asset).

## What this does NOT do

- No native Dagster partition-mapping — this bypasses `PartitionMapping` entirely and
  reads `instance.get_materialized_partitions()` on a timer, same category of mechanism
  as this repo's other `*_monitor`/`*_sensor` components.
- `wait_policy: minimum_count` fires once the threshold is met and never looks for the
  rest — matching Airflow's `MinimumCount(n)`, which also doesn't wait for stragglers.
- The downstream `RunRequest` always carries `partition_key=<rolled-up or fanned-out key>`
  — the downstream job's own job/assets must actually be partitioned with a
  `PartitionsDefinition` that includes that key (daily/weekly/monthly/static, matching
  `window_type`), or the run launch will fail with an unknown-partition error.
