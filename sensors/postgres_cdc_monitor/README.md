# Postgres CDC Monitor Sensor

Micro-batch change-data-capture source reading a PostgreSQL logical replication slot (the built-in `pgoutput` protocol, no server-side plugin install required): classifies every row change as insert/update/delete, batches a tick's changes into one run, and stops once the slot has nothing further to decode right now.

## Purpose

This is the ongoing-changes half of a CDC pipeline for PostgreSQL — not a long-running streaming process, a **poll-catch-up-stop sensor** like this registry's `s3_monitor`/`kafka_monitor`/`mysql_cdc_monitor`. Perfect for:

- Replacing a StreamSets PostgreSQL CDC origin when migrating a continuous CDC pipeline to Dagster
- Feeding a CDC-apply sink (insert/update/delete-by-key) with exactly the row changes it needs to apply
- Keeping a warehouse staging table in sync with an OLTP PostgreSQL database without full-table re-reads

**Not built for:** an initial load of existing rows. Pair this sensor with a separate one-time snapshot (e.g. this registry's own full-table ingestion components) to seed the target before CDC takes over. Unlike MySQL's binlog, a logical replication slot has no "replay from an older retained position" mode — it only ever emits changes created after the slot itself was created, so there's no `on_first_run: from_beginning` option here; it wouldn't mean anything at the protocol level.

## Provenance — why this exists now, and why it didn't before

This repo previously investigated Postgres CDC (`docs/postgres-cdc-design.md`) and found no acceptable path: every real option required vendoring someone else's scaffolded source files into this repo, which this registry's house rules forbid. That investigation explicitly said to re-run itself if a real, maintained, pip-installable package ever surfaced for decoding Postgres's `pgoutput` wire protocol.

The [`pgoutput`](https://pypi.org/project/pgoutput/) package (PyPI, MIT, zero required runtime dependencies) was published **2026-11-09** — two days after that investigation's cutoff. It decodes Postgres's own published, versioned wire protocol directly (`https://www.postgresql.org/docs/current/protocol-logicalrep-message-formats.html`), not a vendored copy of someone else's scaffolded source, so this component is built on it.

**Honest caveat:** as of this component's build date, `pgoutput` is roughly two weeks old (v0.1.0) — nowhere near `mysql-replication`'s (the library `mysql_cdc_monitor` depends on) multi-year production track record. It's small, dependency-free, and MIT-licensed, so read its source before depending on this in production.

## How it works

1. **Resolve tracked tables.** `table_patterns` are fnmatch-style globs (`orders`, `order_items_*`) matched against bare table names in `schema` (default `public`), re-resolved against `pg_catalog.pg_tables` on every tick — a new table matching a wildcard is picked up automatically, no restart needed.
2. **Ensure the replication slot and publication exist.** Creates the logical replication slot (output plugin `pgoutput`) on first use if missing, and creates/keeps the publication's table list in sync with the resolved tables every tick (`ALTER PUBLICATION ... ADD/DROP TABLE`). If a slot with the configured name already exists using a different output plugin, this sensor refuses to read it rather than decode garbage.
3. **Peek before consuming.** `pg_logical_slot_peek_binary_changes` reads whatever's currently decodable without consuming it from the slot — the sensor only consumes (`pg_logical_slot_get_binary_changes`, via the exact same LSN range it just peeked) *after* it has successfully built the batch into a `RunRequest`. If the process crashes mid-batch, nothing was consumed; the next tick peeks the same unconsumed range again. No separate stored cursor is needed for position tracking — the slot's own server-side position *is* the position.
4. **Classify every row change** by message type:
   - `Insert` → `_cdc_op: "insert"`, `after` populated, `before: null`
   - `Update` → `_cdc_op: "update"`, both `before` and `after` populated (`before` is `null` if the table's replica identity doesn't carry an old-row image)
   - `Delete` → `_cdc_op: "delete"`, `before` populated, `after: null`
   - `Begin`/`Commit`/`Relation`/`Type` catalog/transaction-boundary messages are consumed but not emitted as events
5. **Emit one `RunRequest` per tick** (when there are row-change events) carrying the whole batch.

## Output shape (`run_config`)

```python
{
  "ops": {
    "config": {  # or op_name, if set
      "database": str,
      "schema": str,
      "tables": list[str],       # distinct "schema.table" qualified names seen this tick
      "event_count": int,
      "events": [
        {
          "table": str,           # "schema.table"
          "_cdc_op": "insert" | "update" | "delete",
          "before": dict | None,  # column name -> value, pre-image (update/delete)
          "after": dict | None,   # column name -> value, post-image (insert/update)
          "lsn": int,
        },
        # ...
      ],
    }
  }
}
```

`_cdc_op` is this registry's convention for a CDC-apply sink to key its insert/update/delete handling on — the exact same contract `mysql_cdc_monitor` uses, so a downstream CDC-apply sink can consume either source identically.

**Column value coercion:** Postgres column values (`datetime`, `date`, `Decimal`, `bytes`) are coerced to plain strings before they're embedded in `run_config`, since none of those types round-trip through Dagster's run-config JSON serialization. A downstream asset that needs the original type back must re-parse that specific column itself.

## Required PostgreSQL setup

```sql
ALTER SYSTEM SET wal_level = logical;  -- requires a server restart to take effect
ALTER ROLE repl_user WITH REPLICATION;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO repl_user;
```

Tracked tables need a **PRIMARY KEY** or `ALTER TABLE ... REPLICA IDENTITY FULL` for update/delete payloads to carry a full old-row image — without either, `before` on an update/delete carries only key columns (or `null` entirely on a table with `REPLICA IDENTITY NOTHING`).

Creating the publication requires table ownership or superuser on the connecting role (this sensor creates/alters it automatically given that privilege — it does not need to be pre-created by hand, unlike some other CDC tooling's documented prerequisites).

## Honest limitations

- **`pgoutput`'s youth.** See "Provenance" above — this is a ~2-week-old package at build time, not a multi-year-maintained one. Dependency-free and MIT-licensed, so low blast radius if abandoned, but genuinely unproven at scale.
- **One schema per sensor instance**, same reasoning as `mysql_cdc_monitor`'s one-database-per-sensor limitation — a publication and slot track one schema's resolved tables cleanly; mixing schemas in one sensor instance isn't supported.
- **Not validated against a real PostgreSQL server with live logical replication in this repo's CI** (no such server is available here) — tests mock the `psycopg2`/`pgoutput` library boundary; the event-classification, table/slot/publication-management, and error-handling logic around it is exercised for real. Validate against a real server/pipeline before production use.

## Example

```yaml
type: dagster_community_components.PostgresCDCMonitorSensorComponent
attributes:
  sensor_name: orders_cdc_sensor
  host: db.internal
  port: 5432
  username: repl_user
  password_env_var: POSTGRES_REPL_PASSWORD
  database: sales
  schema: public
  slot_name: dagster_orders_slot
  publication_name: dagster_orders_pub
  table_patterns:
    - orders
    - order_items_*
  job_name: apply_sales_cdc_job
  minimum_interval_seconds: 30
```
