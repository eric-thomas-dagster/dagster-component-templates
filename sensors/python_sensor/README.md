# Python Sensor

Wraps an arbitrary Python callable in a Dagster sensor — mirrors Airflow's `PythonSensor`
(`mode: trigger`) and serves as the generic "discover items via a function" dynamic-task-mapping
source (`mode: discover_partitions`) for anything [`s3_monitor`](../s3_monitor/README.md) /
[`gcs_monitor`](../gcs_monitor/README.md) / [`adls_monitor`](../adls_monitor/README.md) /
[`filesystem_monitor`](../filesystem_monitor/README.md) / [`sql_monitor`](../sql_monitor/README.md)
don't already cover — those are prefix/table-specific; this is for an API call, a config file, a
custom registry, or anything else a function can list.

One component, not two, since both modes are the same underlying shape (poll a callable, decide
what to run) differing only in cardinality.

## `mode: trigger` — Airflow's PythonSensor

The callable returns:
- a bool — fire (if truthy) with no payload,
- a non-empty dict — fire, used as the job's run_config,
- a `(bool, dict)` 2-tuple — fire if the bool is truthy, with that run_config.

`fire_mode` controls how repeated truthy results are handled:

| `fire_mode` | Behavior |
|---|---|
| `every_true_tick` (default) | Fires a new run every tick the callable returns truthy. |
| `edge_rising` | Fires only on the false→true transition, tracked in the sensor's own cursor. |
| `once` | Fires exactly one time ever (cursor-gated), then never again — closest to Airflow's `PythonSensor`, whose task instance is terminal once it succeeds. |

```yaml
type: dagster_community_components.PythonSensorComponent
attributes:
  sensor_name: upstream_file_ready_sensor
  callable_path: my_project.sensors:check_upstream_ready
  job_name: downstream_job
  fire_mode: edge_rising
  minimum_interval_seconds: 30
```

## `mode: discover_partitions` — function-driven dynamic task mapping

The callable returns the **current full set** of item keys (not just new ones) — each bare
`str`, or a `(key, payload_dict)` 2-tuple. Every key not already seen becomes a dynamic partition
+ one `RunRequest(partition_key=key)`, exactly the mechanism `s3_monitor`/`sql_monitor` already
use for their own discovery sources. Already-seen keys are silently skipped (tracked via
`dynamic_partition_state_path`, which doubles as the pruning state when `dynamic_partition_keep_days`
is set).

```yaml
attributes:
  sensor_name: pending_exports_sensor
  callable_path: my_project.sensors:list_pending_exports
  job_name: export_job
  mode: discover_partitions
  dynamic_partitions_name: export_ids
  dynamic_partition_keep_days: 14
```

## Requirements

No extra pip dependency — the callable itself may need its own.
