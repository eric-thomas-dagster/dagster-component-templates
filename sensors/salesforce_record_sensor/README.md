# SalesforceRecordSensor

Polls a Salesforce object (SOQL) for records created or updated since the cursor and triggers a RunRequest per match. Of the SaaS-record sensors in this repo (Stripe, Zendesk, Jira, Linear, Notion, ServiceNow, PagerDuty, GitHub), Salesforce was the one gap -- despite `salesforce_ingestion` and `salesforce_record_upsert` both already existing.

## Example YAML
```yaml
type: dagster_community_components.SalesforceRecordSensorComponent
attributes:
  sensor_name: salesforce_closed_won_sensor
  asset_keys: [opportunity_features]
  sobject: Opportunity
  fields: [Id, Name, StageName, Amount, LastModifiedDate]
  soql_filter: "StageName = 'Closed Won'"
  resource_key: salesforce
  minimum_interval_seconds: 300
```

### Two ways to authenticate

Like `salesforce_ingestion`, this sensor can share one credential with the
rest of your Salesforce footprint via `resource_key` (a
`SalesforceResourceComponent` configured with `auth_mode='password'`), or
authenticate standalone with its own `consumer_key`/`consumer_secret`/
`username`/`password`/`security_token`/`domain` fields (OAuth 2.0 password
grant). Exactly one of the two must be fully configured -- validated at
component-build time, not left to fail obscurely at the first poll.

```yaml
type: dagster_community_components.SalesforceRecordSensorComponent
attributes:
  sensor_name: salesforce_new_lead_sensor
  asset_keys: [lead_features]
  sobject: Lead
  consumer_key: "{{ env('SALESFORCE_CONSUMER_KEY') }}"
  consumer_secret: "{{ env('SALESFORCE_CONSUMER_SECRET') }}"
  username: "{{ env('SALESFORCE_USERNAME') }}"
  password: "{{ env('SALESFORCE_PASSWORD') }}"
  security_token: "{{ env('SALESFORCE_TOKEN') }}"
```
