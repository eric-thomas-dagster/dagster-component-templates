# slack_pr_approval_watcher

The reaction half of what [`slack_approval_gate`](../../assets/ai/slack_approval_gate) does for an upstream asset, but for pull requests -- watches the Slack threads [`github_pull_request_agent_sensor`](../github_pull_request_agent_sensor) posts, and when an allowlisted person reacts:

1. **Records a GitHub review through a SECOND identity** -- GitHub blocks a PR's own author approving it, so recording a human's approve/reject always needs a genuinely different token (`reviewer_token_env_var`) from whatever opened the PR.
2. **Refuses to approve while CI checks are failing** -- a 👍 reaction does not override a red build.
3. **Optionally merges**, once the reviewer identity has approved and checks pass, and **only for branches under `branch_prefix`** (default `agent/`) -- a human's own branch is never touched.

## What ships

One sensor. Per tick: scans the Slack channel for still-open PR-review threads (the same hidden-metadata mechanism `github_pull_request_agent_sensor` posts with -- no shared file between the two sensors), and for each:

- If the PR is no longer open (merged or closed elsewhere), marks the thread resolved and moves on.
- If the reviewer identity hasn't approved yet, reads the thread's reactions (first allowlisted vote wins) and calls the GitHub reviews API under the reviewer identity -- refusing while checks are failing, posting the result back into the thread.
- If approved and `auto_merge` is set, squash-merges once checks pass, deletes the branch, and marks the thread resolved.

Already-resolved threads and already-shown warnings are tracked in this sensor's own Dagster-native sensor cursor -- not a shared document two sensors could race on rewriting (a real race the reference sandbox this was built from hit: "two sensors rewriting one state file re-announced PRs").

## Verifying the fix actually worked (`verify_after_merge`)

Merging a PR doesn't prove the fix works -- it proves CI passed, which may not even cover the failure the PR claims to fix. With `verify_after_merge: true`, once `auto_merge` merges a PR, this sensor looks for `Fixes failed run <uuid>` or `Run ID: <uuid>` in the PR body (the convention a fixer asset's PR description should use) and re-executes that exact failed run (Dagster's own `launchRunReexecution`, `ALL_STEPS` strategy) against the just-merged code:

```yaml
auto_merge: true
verify_after_merge: true
dagster_url: "https://my-org.dagster.cloud/prod"
dagster_cloud_api_token_env_var: DAGSTER_CLOUD_API_TOKEN
post_merge_command: "./deploy.sh"   # optional -- run before the re-run, e.g. a redeploy step
```

The thread stays open (not marked resolved) until the re-run finishes -- a later tick polls it and posts `:white_check_mark: Verified...` / `:x: Still failing...` / `:hourglass: ... did not finish in N minutes` into the SAME thread. Tracked in the cursor (`verifying`), same no-shared-state-file discipline as everything else here -- a pod restart doesn't lose track of an in-flight verification. If the PR body never names a failed run, or `dagster_url` isn't set, the thread is simply marked resolved with a note instead of silently hanging forever.

## `reviewer_token_env_var` / `reviewer_login`

Set up a second GitHub account or bot with write access to the repo, and export its token under a different env var than the one that opens PRs. `reviewer_login` is that identity's username -- checked before merging, to confirm the SPECIFIC reviewer identity approved (not just anyone). Leave `reviewer_token_env_var` unset and every approve attempt fails loudly with an explanatory message instead of silently only commenting.

## `auto_merge`

Off by default. When on, a merge still requires ALL of: the reviewer identity's approval, passing checks, and the PR's branch starting with `branch_prefix`. Turning this on is a real decision about how much autonomy to grant -- review the branch-prefix convention your `propose_fix`-opened PRs actually use before enabling it.

## Slack bot scopes

`reactions:read`, `chat:write` (to post the approved/changes-requested/merged confirmation into the thread), and `channels:history`/`groups:history` (to discover pending threads).
