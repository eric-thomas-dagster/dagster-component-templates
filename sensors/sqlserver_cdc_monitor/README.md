# SQL Server CDC Monitor Sensor

Micro-batch change-data-capture source using SQL Server's full **Change Data Capture** feature (`cdc.<capture_instance>_CT` + `cdc.fn_cdc_get_all_changes_<capture_instance>`): resumes from a stored LSN, classifies every row change as insert/update/delete with real before/after values, batches a tick's changes into one run, and stops once it has caught up to the server's current LSN.

## Purpose

This is the ongoing-changes half of a CDC pipeline for SQL Server — not a long-running streaming process, a **poll-catch-up-stop sensor** like this registry's `mysql_cdc_monitor`/`s3_monitor`/`kafka_monitor`. Perfect for:

- Replacing a StreamSets JDBC CDC origin (SQL Server) when migrating a continuous CDC pipeline to Dagster
- Feeding a CDC-apply sink (insert/update/delete-by-key) with exactly the row changes it needs to apply
- Keeping a warehouse staging table in sync with an OLTP SQL Server database without full-table re-reads

**Not built for:** an initial load of existing rows. Pair this sensor with a separate one-time snapshot to seed the target before CDC takes over — `on_first_run: start_now` (the default) deliberately skips all historical CDC data and begins from the server's current max LSN.

**Different from `sql_server_change_tracking_asset`:** that component uses SQL Server's lighter-weight **Change Tracking** feature (`CHANGETABLE`), which only exposes an I/U/D flag plus each row's *current* values — it cannot give you an update's before-image at all. This component uses full **Change Data Capture** instead, which reads the transaction log itself, so both before- and after- row images are available. Pick Change Tracking for a simple single-table "what changed" asset with no before-values need; pick this component when you need the real `_cdc_op`/`before`/`after` contract (e.g. feeding a delete-aware CDC-apply sink).

## How it works

1. **Discover capture instances.** `table_patterns` are fnmatch-style globs matched against `schema.table` (e.g. `dbo.orders`, `dbo.order_items_*`), re-resolved every tick against `cdc.change_tables` joined to `sys.schemas`/`sys.tables` — a newly CDC-enabled table matching a wildcard is picked up automatically, no restart needed. A table can resolve to more than one capture instance (e.g. mid-migration); all matching instances are queried.
2. **Determine the LSN range.** `sys.fn_cdc_get_max_lsn()` gives the server's current max LSN (database-wide) — the "catch up to" boundary. The stored cursor (or, on first run, the server's current max/min LSN depending on `on_first_run`) gives the starting point.
3. **Check retention before reading.** Each matched capture instance's own `sys.fn_cdc_get_min_lsn('<capture_instance>')` floor is checked against the stored position — if the stored LSN has aged out of that instance's retention, this sensor fails the tick loudly rather than silently skipping the gap.
4. **Read every matched instance's `cdc.fn_cdc_get_all_changes_<capture_instance>(from_lsn, to_lsn, 'all update old')`.** The `'all update old'` row-filter option is what makes update before-images available at all — without it, SQL Server only gives you the after-image.
5. **Classify every row by `__$operation`:**
   - `1` → `_cdc_op: "delete"`, `before` populated, `after: null`
   - `2` → `_cdc_op: "insert"`, `after` populated, `before: null`
   - `3` then `4` (a matched pair) → `_cdc_op: "update"`, both `before` and `after` populated
6. **Emit one `RunRequest` per tick** (when there are changes) carrying the whole batch, and persist the new position (via `sys.fn_cdc_increment_lsn`, so the next tick never reprocesses the boundary row) as the sensor's cursor.

## Output shape (`run_config`)

```python
{
  "ops": {
    "config": {  # or op_name, if set
      "database": str,
      "tables": list[str],       # "schema.table" labels seen this tick
      "event_count": int,
      "events": [
        {
          "table": str,          # "schema.table"
          "_cdc_op": "insert" | "update" | "delete",
          "before": dict | None,  # column name -> value, pre-image (update/delete)
          "after": dict | None,   # column name -> value, post-image (insert/update)
        },
        # ...
      ],
    }
  }
}
```

`_cdc_op` is this registry's convention for a CDC-apply sink to key its insert/update/delete handling on — the same contract `mysql_cdc_monitor` uses, so a downstream CDC-apply sink can consume either source identically.

**Column value coercion:** SQL Server column values (`datetime`, `Decimal`, `bytes`/`memoryview`) are coerced to plain strings/hex before they're embedded in `run_config`, since none of those types round-trip through Dagster's run-config JSON serialization — the same convention `mysql_cdc_monitor` uses. A downstream asset that needs the original type back must re-parse that specific column itself.

## Required SQL Server setup

```sql
-- Database-level (once per database)
EXEC sys.sp_cdc_enable_db;

-- Per tracked table
EXEC sys.sp_cdc_enable_table
  @source_schema = N'dbo',
  @source_name   = N'orders',
  @role_name     = NULL,
  @supports_net_changes = 0;

-- The login this sensor connects as needs SELECT on the tracked tables and
-- membership in db_owner (or the capture instance's gating role, if one was set).
```

## Honest limitations

- **LSNs are database-wide, not per-table.** `sys.fn_cdc_get_max_lsn()` takes no arguments — the "catch up to" boundary each tick is a single position shared across every tracked table in the database, matching how this sensor stores a single cursor (same design as `mysql_cdc_monitor`'s single binlog position). Each capture instance's own *retention floor* (`sys.fn_cdc_get_min_lsn`) is still checked independently, since one table's history can be cleaned up while another's isn't.
- **`max_events_per_tick` correctly resumes from where it actually stopped**, not from the originally-fetched max LSN — an update's before/after pair is never split across that boundary (the cap is only checked once a complete event has been appended).
- **Purged CDC history fails loudly, by design.** If the stored LSN has already aged out of a tracked capture instance's retention (`@retention` on `sys.sp_cdc_change_job`, or the default 3-day cleanup job), this sensor raises a clear `skip_reason` naming which table(s) are affected and telling you to re-snapshot and reset the cursor — it will never silently skip the gap and claim to be caught up.
- **Not validated against a real SQL Server instance with live CDC enabled in this repo's CI** (no such server is available here) — tests mock the `pymssql`/`pyodbc` connection boundary; the LSN arithmetic, operation-classification (including the before/after pairing), table-pattern resolution, and retention-check logic around it are exercised for real. Validate against a real server/pipeline before production use.
- **`'all update old'` doubles the row count for every update** (SQL Server returns before AND after as two separate rows, `__$operation` 3 then 4) — this is the real, documented mechanism for getting an update's before-image at all; there is no way to get both values from a single returned row.

## Example

```yaml
type: dagster_community_components.SQLServerCDCMonitorSensorComponent
attributes:
  sensor_name: orders_cdc_sensor
  host: db.internal
  username: cdc_reader
  password_env_var: MSSQL_CDC_PASSWORD
  database: sales
  table_patterns:
    - dbo.orders
    - dbo.order_items_*
  job_name: apply_sales_cdc_job
  minimum_interval_seconds: 30
```

## Requirements

- Python 3.8+
- Dagster 1.5.0+
- `pymssql>=2.2.0` (default driver, pure Python) or `pyodbc` + ODBC Driver 18 for SQL Server
- A SQL Server instance with CDC enabled on the database and each tracked table (`sys.sp_cdc_enable_db` / `sys.sp_cdc_enable_table`)
