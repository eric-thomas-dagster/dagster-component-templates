# Webhook Inbox Sensor

Poll a local JSONL "inbox" file for new inbound webhook callbacks and trigger jobs automatically.

## Why this is two components, not one

Dagster sensors are **poll loops** -- a `SensorEvaluationContext` is evaluated on an interval
by the Dagster daemon. There is no Dagster mechanism for a sensor to bind a port and receive a
pushed HTTP request synchronously; it can only react to something that already exists
somewhere durable (a queue, a bucket, a file) by checking it periodically. That's true of
every "react to an external event" sensor in this repo -- `sqs_monitor` polls SQS, `s3_monitor`
polls S3, `http_poll_sensor` polls an HTTP GET endpoint. None of them *receive* a push.

An inbound webhook, by definition, is something being *pushed at you* -- a vendor (e.g. a
document OCR/extraction API) finishes a job asynchronously and POSTs a callback to a URL you
gave it, whenever it feels like it. Something has to be listening on that port, synchronously,
at the moment the POST arrives. A Dagster sensor cannot be that listener. So this capability is
necessarily two separate pieces, running as two separate processes:

1. **`resources/webhook_inbox_receiver`** -- a small standalone HTTP server (stdlib
   `http.server.ThreadingHTTPServer`, no Dagster involved at all) that you run as its own
   always-on process. It accepts the vendor's POST, verifies an HMAC signature if configured,
   and appends one JSONL line per accepted webhook to a local inbox file. It responds 200
   immediately and does no further processing -- vendors retry aggressively on anything but a
   fast 2xx.
2. **`webhook_inbox_sensor`** (this component) -- an ordinary Dagster sensor, exactly like
   `sqs_monitor` or `s3_monitor`, except it polls that same local inbox file instead of an AWS
   service. Each new line becomes a `RunRequest`.

If your constraint is "I don't want to run an extra always-on process," this pattern isn't for
you -- see **Alternative: already on AWS** below.

## Worked end-to-end example

1. Start the receiver as its own process (behind a reverse proxy that terminates TLS -- TLS
   termination is out of scope for the receiver itself; it only ever speaks plain HTTP):

   ```bash
   python -m dagster_community_components.resources.webhook_inbox_receiver \
     --port 8080 \
     --inbox-path /var/lib/webhooks/inbox.jsonl \
     --signature-header-name X-Signature-256 \
     --signature-secret-env-var OCR_VENDOR_WEBHOOK_SECRET \
     --signature-prefix "sha256="
   ```

2. Give the vendor your reverse proxy's public URL (e.g.
   `https://ingest.yourcompany.com/webhook`) as its callback URL, configured with the same
   shared secret as `OCR_VENDOR_WEBHOOK_SECRET`.

3. The vendor's OCR job finishes and POSTs a JSON body to that URL. The receiver verifies the
   signature, appends `{"received_at": ..., "remote_addr": ..., "path": "/webhook", "body":
   {...vendor's JSON...}}` to `/var/lib/webhooks/inbox.jsonl`, and responds 200.

4. This sensor, deployed in your Dagster code location with `inbox_path:
   /var/lib/webhooks/inbox.jsonl` (same path, readable by the Dagster daemon), notices the new
   line on its next evaluation and fires a `RunRequest` for `job_name`, carrying the parsed
   webhook body in `run_config` under `op_name`.

5. Your job's op reads `config.body` and does the real processing (e.g. loading the OCR result
   into your pipeline).

> **Note on `op_name`'s default:** the literal string `"config"` can never actually be a real
> op's name in Dagster (it's a reserved node name), so the bare default only works at all if
> you also happen to name your op `"config"` -- which you can't. In practice, always set
> `op_name` explicitly to match the real op in your `job_name` job that should receive the
> payload. This mirrors `s3_monitor`'s own `op_name` field/default for consistency across this
> repo's sensors; it is called out explicitly here rather than silently relied upon.

## Cursor behavior

The cursor is a line count into `inbox_path`. On each tick:

- Lines before the cursor are never re-read.
- A line is only counted as "processed" (cursor advances past it) once it both ends with a
  newline AND parses as JSON.
- A line that ends with a newline but fails to parse (corrupted data) is logged and skipped,
  but the cursor still advances past it -- a permanently malformed line must not wedge the
  sensor forever.
- A line that does NOT yet end with a newline (the receiver's write is still in flight) is left
  alone entirely; the sensor stops reading there and retries that same line on the next tick.

## `event_id_field` and partition mode

Webhooks have no universal "id" convention the way an S3 object has a key+etag or an SQS
message has a MessageId. `event_id_field` is a best-effort dotted-path lookup (e.g. `job.id`)
into each payload's `body`. When that field is present, its value is used as the `RunRequest`
run_key (or, in `dynamic_partition` mode, the partition key). When it's absent from a given
payload, a stable SHA-256 hash of the entire payload is used instead -- this is NOT a
vendor-assigned id, just a way to still dedupe/partition that specific payload consistently.
Document this for your own team if you rely on it.

## Alternative: already on AWS

If you're already running on AWS and don't want to stand up and babysit an extra always-on
receiver process, `sensors/sqs_monitor`'s own README documents a zero-new-code pattern:
vendor webhook -> API Gateway -> Lambda (or an SQS-integrated API Gateway) -> SQS ->
`sqs_monitor`. That pattern needs no new component at all. `webhook_inbox_receiver` +
`webhook_inbox_sensor` is for the opposite situation: a simpler, self-hosted deployment that
doesn't want API Gateway/Lambda/SQS in the loop, at the cost of running and operating one more
process yourself.
