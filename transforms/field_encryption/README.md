# FieldEncryptionComponent

Field-level encrypt/decrypt using the real AWS Encryption SDK — raw-key or
KMS-backed, type-preserving, per-field encryption-context binding.

## Two modes: `native` (default) and `streamsets`

- **`compatibility: native`** (default) — this component's own type-preserving
  scheme (see "Type preservation" below). Base64-encoded ciphertext, an
  auto-added `field: <column>` encryption-context entry so ciphertext can't be
  silently swapped between columns. **Not StreamSets-compatible** — see below.
- **`compatibility: streamsets`** — matches StreamSets' "Encrypt and Decrypt
  Fields" processor's real AWS Encryption SDK layout byte-for-byte: plaintext
  is the value's UTF-8 text (not a JSON wrapper), the type goes in the
  encryption context as `SDC_FIELD_TYPE` instead, output is raw bytes not
  base64, and no `field` context entry is auto-added (StreamSets doesn't add
  one either — adding it would break real interop). Verified against a real
  Data Collector 6.4.1 and 3.18.1, both directions, by the
  `migrating-streamsets-to-dagster` skill's own test suite
  (`tests/test_sdc_crypto_parity.py`) and reference implementation
  (`streamsets_to_dagster.runtime.encrypt_value`/`decrypt_value`) — this
  component's own tests include a real cross-implementation check against
  that reference implementation (`tests/test_sdc_compatibility.py`), proving
  the two agree on the wire format. The AWS KMS path uses the same
  plaintext/context shape but was not independently exercised against a real
  AWS account by the skill either — treat KMS mode as corroborated, not
  engine-verified.

Use `compatibility: streamsets` to read ciphertext StreamSets wrote, or write
ciphertext StreamSets can read. Don't mix ciphertext between the two modes —
they are genuinely different wire-adjacent layouts (same AWS ESDK envelope,
different plaintext/context contents) and neither mode's output is readable
by the other.

## Type preservation

AWS ESDK's `encrypt()`/`decrypt()` operate on raw bytes. To make a decrypted
value round-trip to its original Python type, this component wraps each
value before encrypting it as `{"t": <type tag>, "v": <value>}` JSON (type
tags: `bool`, `int`, `float`, `iso_datetime`, `str`), encodes the resulting
ciphertext as base64 (so it's safe to store in any text column), and
reverses both steps on decrypt. Null/NaN values are passed through
untouched — they are never encrypted and never counted as a decrypt
failure.

## Encryption context binding

Every field gets its own AAD binding automatically: whatever you set in
`encryption_context` has a `field: <column name>` entry merged in before
encrypting. This means ciphertext from one column cannot be silently
swapped into another column and decrypted successfully — a value encrypted
as `ssn` will fail to decrypt if read back as `date_of_birth`, even with the
right key.

## Key sources

- **`raw_key`** (default) — a symmetric key you manage yourself, supplied
  base64-encoded via an environment variable. Uses AWS ESDK's
  `RawMasterKeyProvider`. Simple, no AWS account required.
- **`kms`** — one or more AWS KMS CMKs, via AWS ESDK's
  `StrictAwsKmsMasterKeyProvider`. For `mode='encrypt'` any valid KMS key
  identifier works; for `mode='decrypt'` AWS requires the **full key ARN**
  — key ids and alias names/ARNs are not accepted for decryption. Requires
  real AWS credentials and KMS permissions at run time.

## SQL source

Instead of `upstream_asset_key`, set `source` to pull rows directly via SQL
-- no intermediate asset required:

```yaml
source:
  kind: warehouse_query
  resource_key: snowflake_resource   # or database_url_env_var: DATABASE_URL
  sql: "SELECT * FROM my_table"
```

Mutually exclusive with `upstream_asset_key` -- set exactly one. Works with
any resource exposing `.get_engine()` (SQLAlchemy), `.get_connection()`
(DBAPI -- Postgres/Snowflake/DuckDB/MySQL/Databricks SQL), or `.get_client()`
(BigQuery, Redshift).
